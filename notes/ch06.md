It shows why DRAM is slow and delivers data in bursts, how the hardware merges ("coalesces") the loads of one warp when they hit consecutive addresses, how banks and channels let many requests overlap their latency, and why high occupancy and wider per-thread loads are needed to actually use the memory bandwidth. ## Concepts

### Chapter opening (pp. 123–124)
- Execution speed of a parallel program depends on how its resource demands interact with the hardware's resource constraints; managing that interaction is a practical skill that needs architectural understanding and hands-on practice (p. 123).
- Where the chapter sits: Ch. 4 covered compute architecture (control divergence, occupancy); Ch. 5 covered on-chip memory (shared-memory tiling, register tiling). Ch. 6 covers the off-chip memory (DRAM) architecture: coalescing, latency hiding, vector loads/stores; plus shared-memory bank conflicts, thread granularity coarsening, loop unrolling, double-buffering; then a checklist that guides Parts 2 and 3 (p. 123).
- **Bottleneck:** the architectural constraint that dominates and limits performance for a given application. Tuning usually trades use of one resource for another. That works only if the relieved constraint was the dominant one and the resource you now use more of does not hurt parallel execution. Without that understanding, tuning is guesswork (p. 124).

### §6.1 Global memory access coalescing (pp. 124–132)
- Global memory bandwidth is limited and is often the bottleneck because data-parallel kernels pull a lot of data from it quickly. Tiling (Ch. 5) reduces how much data is fetched; coalescing makes the fetching itself efficient. The two are normally used together (p. 124).
- **Why DRAM is slow** (pp. 124–125, main text plus sidebar "Why are DRAMs so slow?"):
  - A DRAM bit is a tiny capacitor; charge present or absent encodes 1 or 0. To read it, the capacitor must drive a highly capacitive line to a sensor (sense amplifier) which decides whether enough charge is there (p. 124).
  - This takes **tens of nanoseconds** in modern DRAM chips, against **sub-nanosecond** clock cycles in modern computing devices (p. 124).
  - Sidebar detail: a decoder drives a horizontal line connected to the gates of thousands of cells, and charging/discharging that line takes time. Harder still, the selected cell must shift the potential of a long vertical bit line (large capacitance) enough for the sense amplifier to detect, by charge sharing. The sidebar figure annotates "About 1000 cells connected to each vertical line" (p. 125).
  - Sidebar analogy: someone holds a small cup of coffee at one end of a long hallway and another person down the hall must identify the flavour by smell (p. 125).
  - Bigger capacitors would be faster, but DRAM has gone the other way: cells keep shrinking so more bits fit per chip. Hence DRAM access latency has not improved over time (p. 125).
- Because one access is slow, DRAM uses parallelism to raise **memory access throughput** (p. 124).
- **DRAM burst:** each access to a location also senses a range of consecutive locations that includes it; many sensors work in parallel, one per bit. Once sensed, all of that data can be sent to the processor at high speed. The consecutive locations accessed and delivered together are a burst. A program that uses the data within bursts gets far more throughput than one touching random locations spread over many bursts (p. 125).
- **Caches:** modern GPUs have SRAM-based L1 and L2 on-chip caches that cut latency and raise throughput for global memory accesses. They are not prominent in the CUDA programming model so the book has not covered them, but they affect observed performance. Data moves L2→L1 in units of a **cache block / cache line**. Focused, consecutive access still pays off after data is in cache because fewer lines have to move (pp. 125–126).
- **Coalescing rule** (p. 126): all threads of a warp execute the same instruction at the same time. When they execute a load, the hardware checks whether they access consecutive global memory locations. Best case: all threads of the warp access consecutive locations within the same DRAM burst and/or cache line; the hardware then **coalesces** them into one consolidated access. Example: thread 0 reads location X, thread 1 reads X+1, thread 2 reads X+2, and so on.
- **Alignment** (p. 126): a second consideration. If the first address of the run is aligned to the start of a burst or cache line, the coalesced access needs the minimum number of memory transactions. If not aligned, the same amount of data spans more bursts/lines and creates extra traffic.
- **Row-major recap** (pp. 126–127, Fig. 6.1 = Fig. 3.3): C/CUDA multi-dimensional arrays are linearized row by row. Elements adjacent in a row are adjacent in memory. `M[0][0]` and `M[1][0]` look adjacent in 2D but are four positions apart in a 4-wide matrix.
- **Coalesced case** (pp. 127–128, Fig. 6.2): in the basic matmul kernel the second input is read as `N[k*Width + col]`. `k` and `Width` are identical across the warp; `col = blockIdx.x*blockDim.x + threadIdx.x`, so consecutive threads have consecutive `col` and read consecutive elements. Each loop iteration `k` reads one row segment of N: adjacent in memory, coalesced. The book states that every kernel shown so far in the book had naturally coalesced accesses (p. 128).
- **Uncoalesced case** (pp. 128–129, Fig. 6.3): suppose the second matrix is stored column-major.
  - Why that happens: you often need a matrix and its transpose, and storing both is wasteful. Common practice is to store one form and read the transpose by swapping the roles of the row and column indices, which is the same as treating the transposed matrix as column-major (p. 128).
  - The read becomes `N[col*Width + k]`. Now `col` is multiplied by `Width`, so adjacent threads read elements `Width` apart. For realistic matrices that is hundreds or thousands of elements; the hardware sees the addresses are far apart and cannot coalesce (pp. 128–129).
- **Three strategies when access is not naturally coalesced** (p. 129): (1) rearrange how threads map to data; (2) rearrange the data layout; (3) move data between global and shared memory in a coalesced way and do the unfavourable pattern in shared memory, which is less sensitive to layout and has lower latency. (1) and (2) are discussed in §6.8.
- **Corner turning** (pp. 129–130, Fig. 6.4): strategy (3) applied to tiled matmul with M row-major, N column-major, P row-major, all in global memory.
  - M tile: loaded as in Ch. 5. A thread loads the input element with the same tile-local row/column as its output element; a row of threads reads a row of M: coalesced.
  - N tile, Ch. 5 arrangement (Fig. 6.4a): the threads on the tile's top edge logically read a row of N, but with column-major storage those elements are far apart: uncoalesced.
  - Fix (Fig. 6.4b): consecutive threads load consecutive elements along the tile's **left edge** (same column). In effect the roles of `threadIdx.x` and `threadIdx.y` are swapped when computing the linearized index for the N load. Same-column elements are adjacent in column-major storage, so the load coalesces.
  - The tile can be stored in shared memory in either row-major or column-major layout; afterwards every thread reads its inputs with little penalty because shared memory is SRAM and "does not require coalescing" (p. 130).
  - The figure uses 4 threads and 4×4 tiles as a toy. The book says that in reality the corner-turning tile size is the warp size, 32, so the first 32 threads of the block read 32 consecutive elements on the tile's left edge (p. 130).
- **Stores** (p. 130): coalescing matters for stores too, and uncoalesced stores can hurt more than uncoalesced loads. Reason given: they produce partial store operations that do read-modify-write, which can need more memory bandwidth on GPUs with error correcting code (ECC) enabled.
- **Main benefit** (pp. 130–131): less global memory traffic, by merging several accesses into one. Merging requires same time and adjacent locations.
- **Carpool analogy** (pp. 131–132, Figs. 6.5–6.6): congestion happens when too many cars use a road built for fewer; the fix is fewer cars for the same number of commuters, i.e. carpooling, which governments encourage (odd/even plate days, carpool lanes for cars with more than two or three people, expensive fuel). Carpooling needs people with compatible schedules. Mapping: data = commuters, DRAM requests = vehicles. When the request rate exceeds the DRAM system's provisioned throughput, congestion rises and arithmetic units idle. Threads of one warp are ideal carpoolers because SIMD execution makes them issue the load at the same moment (p. 132).
- **CPUs too** (p. 132): CPU cache design also reflects DRAM bursts; a CPU cache line typically maps to a fraction of, one, or several bursts. Programs that use all bytes of each cache line they touch run much faster than those that access randomly. The chapter's techniques transfer to CPU code.

### §6.2 Hiding memory latency (pp. 132–137)
- Bursting alone does not deliver the bandwidth processors need. DRAM systems add two more levels of parallel organization: **banks** and **channels** (p. 132).
- **Channel:** a memory controller plus a bus that connects a set of DRAM banks to the processor. A processor has one or more channels. Fig. 6.7 draws four channels with four banks each; real processors typically have one to eight channels, each connected to a large number of banks (pp. 132–133).
- **Bus bandwidth = width × clock frequency** (× 2 for double data rate, DDR, which transfers on both the rising and falling clock edge) (p. 133).
  - Worked example: 64-bit DDR5-6400 bus at 3.2 GHz → 8 B × 2 × 3.2 GHz = 51.2 GB/s `[device: DDR5-6400]` (p. 133).
  - Demand: a modern CPU might need at least 200 GB/s; a GPU might need more than 1000 GB/s. The book converts that to four buses for the CPU and 20 for the GPU (p. 133).
  - That many buses draw too much power when driving wires on traditional circuit boards. This motivated **High Bandwidth Memory (HBM)**, which co-packages processor and DRAM to shrink the connections and raise both clock frequency and bus count (p. 133).
  - HBM3E example as printed: bus clock "4.9 GHz/s" and 16 64-bit buses, "resulting in 1 TB/s memory bandwidth" `[device: HBM3E]` (p. 133). See "Unclear in the PDF": the arithmetic gives about 1.25 TB/s.
- **Bank:** contains an array of DRAM cells, the sense amplifiers for them, and the interface that delivers bursts to the bus. The number of banks per channel is set by how many are needed to keep the bus busy (p. 133).
- **Single bank timeline** (Fig. 6.8a, pp. 133–134): each access is a long cell-array latency followed by a short burst transfer on the bus. In reality latency is much longer than transfer time.
  - Worked numbers: if latency : transfer = 20 : 1, bus utilization is at most 1/21 = 4.8 %. A 16 GB/s channel would deliver at most 0.76 GB/s (p. 134).
- **Multiple banks** (Fig. 6.8b, p. 134): start an access in bank 1 while bank 0 is still in its latency period. Latencies overlap; bursts go out back to back. Two banks can roughly double utilization.
  - General rule: if latency/transfer ratio is R, at least **R + 1 banks** are needed to fully use the bus. R = 20 → at least 21 banks per channel (p. 134).
  - In practice more than that, for two reasons (pp. 134–135): (1) more banks lowers the chance that simultaneous accesses hit the same bank, a **bank conflict**; one bank serves one access at a time, so conflicting accesses cannot overlap their latency. (2) Each cell array is sized for reasonable latency and manufacturability, which caps cells per bank; many banks may be needed just for capacity.
- **Interleaved data distribution** (Fig. 6.9, p. 135): hardware addressing spreads consecutive bursts across channels first, then banks. Toy setup: burst = 2 elements (8 bytes), 4 channels × 2 banks.
  - M[0..1] → Channel 0 Bank 0; M[2..3] → Ch 1 Bank 0; M[4..5] → Ch 2 Bank 0; M[6..7] → Ch 3 Bank 0; M[8..9] → Ch 0 Bank 1; M[10..11] → Ch 1 Bank 1; M[12..13] → Ch 2 Bank 1; M[14..15] → Ch 3 Bank 1; then wraps: M[16..17] → Ch 0 Bank 0, M[18..19] → Ch 1 Bank 0, etc.
  - Equivalent rule (our restatement of the book's listing): burst index b = ⌊i/2⌋; channel = b mod 4; bank = ⌊b/4⌋ mod 2.
  - Point: even small arrays are spread out. In the toy, any array of at least 16 elements touches every channel and bank.
- **Thread parallelism ↔ DRAM parallelism** (pp. 135–136): to reach the device's specified memory bandwidth, enough threads must be issuing memory accesses at the same time. So maximizing occupancy has a second benefit beyond Ch. 4's pipeline-latency hiding: it generates enough memory requests to hide DRAM latency. For best utilization the accesses must also be spread evenly over channels and banks, and each access to a bank must itself be coalesced.
- **Toy trace** (Figs. 6.10–6.11, pp. 136–137): 4×4 matmul, 2×2 thread blocks, 2×2 tiles, all four blocks running in parallel.
  - Phase 0: each block makes two coalesced accesses to M (two row segments of 2 elements). Blocks (0,0) and (0,1) both load M[0],M[1],M[4],M[5]; blocks (1,0) and (1,1) both load M[8],M[9],M[12],M[13]. Under the Fig. 6.9 mapping these go to the banks of Channel 0 and Channel 2, in parallel.
  - Phase 1: M[2],M[3],M[6],M[7] and M[10],M[11],M[14],M[15] → banks of Channel 1 and Channel 3.
  - Blocks that load the same elements: most modern devices have caches that merge such accesses into one if the blocks' timings are close enough. The book says GPU cache memories are mainly designed to combine such accesses and reduce DRAM accesses (pp. 136–137).
- **Symbiosis** (p. 137): using DRAM bandwidth well needs many threads accessing simultaneously; device throughput in turn needs those accesses spread over banks and channels. If all simultaneously running threads access data in the same channel, memory throughput and overall speed drop sharply.
- Left to the reader (p. 137): check that 8×8 matrices with the same 2×2 blocks use all four channels of Fig. 6.9; and note that a larger burst size would need even larger matrices to use all channels fully.

### §6.3 Vector loads and stores (pp. 138–139)
- Besides more threads, each thread can access more contiguous data per instruction. Such instructions are **vector loads** and **vector stores** (p. 138).
- Starting point: vecadd from Fig. 2.10. Each thread loads two 4 B floats and stores one. Accesses are coalesced, and since the kernel over-uses no resource it runs at maximum occupancy. Even so it executes one load/store instruction per 4 B (p. 138).
- Fig. 6.12 rewrites it so each thread handles 16 B per instruction: launch a quarter as many threads; index `i` now names a chunk of four floats; cast the `float*` to `float4*` before indexing. `float4` packs four floats into one 16 B object with fields `.x .y .z .w`. Dereferencing a `float4` pointer makes the compiler emit a vector load or store of the whole 16 B (p. 138).
- Boundary conditions (pp. 138–139): if the element count is not divisible by four, the boundary thread must fall back to scalar loads/stores to avoid reading out of bounds, and out-of-range threads in the last block must be inactive. Left as an exercise (Exercise 4).
- Benefit (p. 139): less instruction-execution overhead per byte moved. Two vector loads replace eight scalar loads: 75 % less load-instruction overhead for the same data.
- Second benefit (p. 139): when a kernel cannot run at full occupancy, vector loads/stores still let it issue enough concurrent memory traffic to tolerate memory latency and use the bandwidth. An example comes in Ch. 15.

### §6.4 Shared memory bank conflicts (pp. 139–141)
- Shared memory is SRAM with much shorter latency than DRAM, so it does not need bursting and its banks can be narrow. "Typical" structure given: latency of a few clock cycles, **32 banks, each 32 bits (4 bytes) wide** `[device: unspecified "typical" GPU shared memory]`. One thread reading a 32-bit int or float uses a whole bank's output (p. 139).
- Layout: consecutive 4 B chunks go to consecutive banks, interleaved; after bank 31 it wraps to bank 0. So bank = (4-byte word index) mod 32. If the 32 threads of a warp access 32 consecutive 4 B values, each is served by a different bank in parallel (p. 139).
- **Shared memory bank conflict:** threads of the same warp hit the same bank at the same time. A bank cannot serve several threads at once; the hardware detects the conflict and splits the access into several conflict-free accesses served one after another (p. 139).
- Example from corner turning (Fig. 6.4b), pp. 139–140: the global load is coalesced but the shared-memory store is strided.
  - `__shared__ float a[TILE_DIM][TILE_DIM]; // TILE_DIM = 32` and `a[threadIdx.x][threadIdx.y] = ...;`
  - With a 32×32 block, a warp has one `threadIdx.y` and consecutive `threadIdx.x`. Thread 0 writes `a[0][0]`, thread 1 `a[1][0]`, thread 2 `a[2][0]`: a column. Row-major linear index of `a[i][j]` is i×32 + j → 0, 32, 64, …: 32 positions (128 B) apart.
  - Index 0 is in bank 0; indices 1–31 in banks 1–31; index 32 back in bank 0; 64 mod 32 = 0. Every thread of the warp writes bank 0: a **32-way bank conflict**. Hardware performs 32 successive accesses to one bank while 31 banks sit unused (p. 140).
- **Padding** (p. 140): add one unused column so the row stride is no longer a multiple of 32.
  - `__shared__ float a[TILE_DIM][TILE_DIM + 1]; // TILE_DIM = 32` (the access line is unchanged).
  - Linear index becomes i×33 + j. Thread 0 → 0 → bank 0; thread 1 → 33 → bank 1; thread 2 → 66 → bank 2. All 32 threads hit different banks; no serialization.
- Costs of padding (pp. 140–141): (1) extra shared memory; (2) index arithmetic can get more expensive when a dimension stops being a power of two. With 32 columns the multiply reduces to one shift; with 33 it becomes a shift plus an add. The extra work grows with the number of padding columns. (The book prints the shift as `i >> 5`; see "Unclear in the PDF".)
- Benefit depends on access pattern and original dimensions (p. 141): had the array been 16 columns wide, the warp's conflicts would fall on two banks with a 16-way conflict each, so padding would gain less. A smaller stride means the warp's accesses are closer together.

### §6.5 Thread coarsening (pp. 141–143)
- All kernels so far parallelize at the finest granularity: one thread per output element (vecadd, Ch. 2), per output pixel (grayscale, blur, Ch. 3), per output matrix element (matmul, Ch. 3 and Ch. 5) (p. 141).
- Advantage of finest granularity: **transparent scalability** (Ch. 4). With enough hardware everything runs in parallel; otherwise the hardware serializes by running thread blocks in several waves (p. 141).
- Disadvantage: parallelizing can carry overhead: redundant data loading by different thread blocks, redundant work, synchronization overhead, instruction execution overhead, and others. Worth paying if threads truly run in parallel; wasted if the hardware serializes them anyway. Then the programmer should partially serialize the work: assign each thread several units of work. This is **thread coarsening** (p. 141).
- Terms (p. 142): **coarsening factor** = units of work per thread; **coarsening loop** = the per-thread loop over its units.
- Toy code (pp. 141–142): before, `i = blockIdx.x*blockDim.x + threadIdx.x; foo(i);`. After, with factor 4, `iStart = 4*(global index)` and a loop `c = 0..3` calling `foo(iStart + c)`. Thread 0 handles 0–3, thread 1 handles 4–7.
- Already seen (p. 142): Fig. 6.12 is thread coarsening. The overhead there is the instruction execution overhead of loads/stores; serializing four additions in one thread lets the accesses merge into vector loads/stores.
- Also beneficial (p. 142): tiled matmul from Ch. 5. Many thread blocks reload the same input tiles; fewer blocks each producing a larger output tile load each input tile fewer times. Treated in depth in Ch. 15.
- **Pitfall 1: unnecessary coarsening** (pp. 142–143). It helps only when parallelization has an overhead. If threads are fully independent with no coordination or shared data, expect no substantial difference.
- **Pitfall 2: too much coarsening** (p. 143). Coarsening reduces the parallelism exposed to the hardware. Worked numbers on a GPU that can run 264 blocks simultaneously `[device: hypothetical GPU, 264 concurrent blocks]`:
  - 1056 blocks → 4 full waves. Coarsen by 8 → 132 blocks = 0.5 wave: half the GPU idle.
  - 1584 blocks → 6 full waves. Coarsen by 4 → 396 blocks = 1.5 waves: after the first full wave a partial wave under-uses the GPU (the **tail effect** from Ch. 4). Pick a factor that avoids partial waves.
  - The best factor is usually device-specific and dataset-specific and must be retuned. Scalability becomes less transparent: the kernel may need recompiling with a different factor for another GPU generation.
- **Pitfall 3: occupancy loss** (p. 143). Coarsening may need more registers per thread or more shared memory per block. If that cuts occupancy, the penalty must not exceed the coarsening benefit.

### §6.6 Loop unrolling (pp. 144–146)
- Context (p. 144): GPUs are throughput-oriented, not latency-oriented (Ch. 1): many concurrent threads, long latency per thread. Ch. 4's answer was occupancy: when a warp stalls on a long-latency instruction, another ready warp probably exists. Loop unrolling is a second latency-tolerance tool.
- Definition (p. 144): replicate the loop body by some factor and cut the iteration count by the same factor. Example: a 16-iteration loop with body `A(i); B(i)` unrolled by 4 becomes a 4-iteration loop (`i += 4`) with body `A(i) B(i) A(i+1) B(i+1) A(i+2) B(i+2) A(i+3) B(i+3)`.
- **Advantage 1: fewer branches** (p. 144). CPUs have sophisticated branch prediction; GPUs do not. A GPU thread that reaches a branch stalls until the outcome is resolved. Fewer iterations → fewer branch instructions → fewer stalls.
- **Advantage 2: more independent instructions to reorder** (pp. 144–145). If `B(i)` depends on `A(i)`, the thread stalls between them. If `A(i+1)` is independent of `A(i)` and `B(i)`, the unrolled body can be reordered to `A(i) A(i+1) A(i+2) A(i+3) B(i) B(i+1) B(i+2) B(i+3)`, giving the thread work to do while `A(i)` completes. This reordering is part of **instruction scheduling**.
- Who does it (p. 145): the compiler applies unrolling and instruction scheduling automatically and aggressively, at its discretion; the programmer need not worry. For a small body with a small constant bound it will most likely unroll fully, removing all branches.
- Manual control (p. 145): `#pragma unroll N` placed before the loop unrolls by factor N; `N = 1` means do not unroll. The book annotates loops with it only where it wants to stress that unrolling is expected.
- **Advantage 3: register promotion, essential for coarsening** (pp. 145–146). A scalar `int x` lives in a register. After coarsening by 4 it becomes `int x[4]` used as `foo(x[c])` in a loop. The book says (citing Ch. 5) that local arrays like `x[4]` are placed in global memory by default, because a variable index requires the array to be in memory; that memory access overhead can outweigh the coarsening benefit. A coarsening loop has a small constant bound, so it can be fully unrolled into `foo(x[0]); foo(x[1]); foo(x[2]); foo(x[3]);`. With only constant indices the compiler can promote `x` to registers.
- Summary of benefits (p. 146): fewer branches, more schedulable instructions, constant propagation, and memory→register promotion.

### §6.7 Double buffering (pp. 146–147)
- Setup (p. 146): threads of one block pass data through a shared buffer inside a loop. Each iteration: read `buffer[anotherThreadID]`, `__syncthreads()`, write `buffer[myThreadID]`, `__syncthreads()`.
- The barrier after the write (second in the loop body) makes sure all writes finish before anyone reads them next iteration: a **read-after-write** dependence, called a **true dependence** because it is unavoidable (pp. 146–147).
- The barrier after the read (first in the loop body) makes sure all reads finish before anyone overwrites the values: a **write-after-read** dependence, called a **false dependence**. It exists only because the value read and the value written share a memory location. Put them in different locations and that barrier is unnecessary (p. 147).
- Options (p. 147): a fresh buffer per iteration removes the false dependence but wastes memory. Better: two buffers that alternate each iteration. That is **double-buffering** (the book writes it both as "double buffering" and "double-buffering").
- Resulting loop (p. 147): read `inBuffer[anotherThreadID]`; write `outBuffer[myThreadID]`; `__syncthreads()`; `swap(inBuffer, outBuffer)`. The barrier between read and write is gone. After the write the newest data is in `outBuffer`, so the swap at the end of the body makes the next iteration read the right buffer.
- Net effect: one barrier per iteration instead of two. The book calls this a toy; real uses come later (Ch. 11 and Ch. 15 per §6.8).

### §6.8 A checklist of optimizations (pp. 147–153)
- Fig. 6.13 consolidates Part 1's optimizations. Not exhaustive; it holds the "universal" ones to consider first. Parts 2 and 3 apply them to patterns and applications (p. 148).
- Three main categories by the performance aspect they target, plus one general row (p. 149):
  - **Compute utilization:** reduce idleness of GPU cores; make sure cores have useful work.
  - **Memory utilization:** make the memory subsystem's use more efficient.
  - **Synchronization latency:** reduce time threads spend waiting at barrier synchronizations.
  - Some optimizations fit several categories; each is filed under its primary intent. Thread coarsening is labelled **General** because its category depends on context.

Help it by using loops with constant bounds where possible |

**Per-optimization commentary in the text (pp. 149–153):**
- *Occupancy tuning* (p. 149). Introduced in Ch. 4: many more threads than cores, so there is work to hide long-latency pipeline operations. Tune so that max blocks per SM or registers per SM do not cap the thread count; Ch. 5 added shared memory as a third limiting resource; §6.2 added that it also hides memory latency. The book will assume the programmer keeps occupancy healthy when later optimizations add shared memory or registers. Ch. 15 shows a case where using more resources is worth lower occupancy, with other optimizations compensating.
- *Loop unrolling* (p. 149). Recap of §6.6. The book assumes the compiler unrolls adequately. Ch. 11 (prefix sum) and Ch. 15 stress unrolling as essential for register tiling after coarsening; Ch. 15 also says unrolling is critical to compensate for low occupancy.
- *Reducing control divergence* (pp. 149–150). From Ch. 4. Part 1 kernels only diverged at boundary conditions. Strategies: (a) redistribute work/data across threads so the threads of one warp are all used before threads of other warps (Ch. 10, reduction); (b) same redistribution to give threads in a warp similar workloads (Ch. 18, graph traversal: vertex-centric vs edge-centric); (c) rearrange the data layout so adjacent data, processed by one warp, has similar workload (Ch. 17, sparse matrices, the JDS format).
- *Coalesced global memory accesses* (pp. 150–151). Threads of a warp access adjacent locations in the same cache line and/or burst. Strategies for irregular patterns:
  - Coalesced transfer to shared memory, irregular access there: corner turning (§6.1); **packing** in Ch. 12 (filter) and Ch. 14 (sorting), where threads that would scatter writes into an array collaborate to do the scattered accesses in shared memory and then write shared → global with more coalescing for elements with nearby destinations; Ch. 13 (merge), where a block's threads all binary-search the same array, so they load it into shared memory coalesced and search there.
  - Rearranging the thread-to-data mapping: Ch. 10 (reduction) and Ch. 15.
  - Rearranging the data layout: Ch. 17 (ELL and JDS formats); also transposing a matrix, or converting an array of structures to a structure of arrays.
- *Shared memory tiling* (p. 151). Data reused within a block is placed in shared memory and read repeatedly so it crosses global ↔ SM once. Introduced in Ch. 5 with matmul. Reappears in most patterns. Input and output tiles of different dimensions complicate it in Ch. 7 (convolution) and Ch. 8 (stencil). More sophisticated uses in Ch. 15 (matmul) and Ch. 16 (sequence alignment by dynamic programming).
- *Register tiling* (p. 151). Data reused within a warp or thread kept in registers so it crosses global-or-shared ↔ registers once. Already used in Ch. 3 and Ch. 5: each thread accumulated its result in a local variable before one global write; the registers of all threads together form a tile of the output. Reappears in Ch. 8 (a shared-memory input tile moved temporarily to registers and back, for efficient access and to preserve shared memory capacity), Ch. 11 and Ch. 15 (each thread owns several outputs and reuses several inputs).
- *Vector loads and stores* (p. 151). Applicable to most computations in the book; because it is simple, the book will not apply it throughout and will only mention it where especially relevant.
- *Avoiding shared memory bank conflicts* (pp. 151–152). Strategies: remap threads to data, or change the layout, often with padding. Reappears in Ch. 11 and Ch. 15, where threads make strided shared-memory accesses when loading their portions of the input.
- *Privatization* (p. 152). Not yet introduced; listed for completeness. When several threads or blocks update a common (public) output, give each a private copy to update partially, then commit private → public at the end. Examples: Ch. 9 (histogram counters); Ch. 12 (filter) and Ch. 18 (graph traversal), where many threads insert into the same output list.
- *Warp-level primitives* (p. 152). Briefly mentioned in Ch. 4: threads in a warp synchronize and share data without the costlier block-wide barrier and without going through shared memory. Strategy: decompose a block-wide computation by warp; do the barrier-needing steps at warp level; then consolidate at block level. Examples: Ch. 10, 11, 12 (reduction, prefix sum, filter); Ch. 15, where they assist register tiling.
- *Double buffering* (p. 152). Recap of §6.7. Real uses: Ch. 11 and Ch. 15.
- *Thread coarsening* (pp. 152–153). The overhead removed differs by context:
  - Ch. 8 (stencil) and Ch. 15 (matmul): larger output tile, so loaded input data is reused for more outputs; the overhead of fine granularity was redundant input loading by more blocks.
  - Ch. 9 (histogram): fewer private copies to commit to the public copy (with privatization).
  - Ch. 10 (reduction) and Ch. 11 (prefix sum): less synchronization and control-divergence overhead.
  - Ch. 11 also: less redundant work of the parallel algorithm relative to the sequential one.
  - Ch. 12 (filter) and Ch. 14 (sorting): better memory coalescing.
- Other optimizations appear only in specific chapters, e.g. constant memory in Ch. 7 (p. 153).

### §6.9 Optimization strategy (pp. 153–154)
- Pick optimizations by first identifying the resource limiting the kernel: the **performance bottleneck** (p. 153).
- Optimizations typically spend more of one resource to relieve another. If the one relieved is not the bottleneck, expect no benefit. If the one spent is the bottleneck, expect a slowdown (p. 153).
- Example (p. 153): shared memory tiling spends shared memory to relieve global memory bandwidth. Good when global bandwidth is the bottleneck. Harmful when the kernel is limited by occupancy and occupancy is already constrained by shared memory use.
- Process (pp. 153–154): iterative. Find the bottleneck → apply an optimization for it → find the new bottleneck → repeat. Profiling tools find bottlenecks; the book points to CUDA documentation, reference [1] (NVIDIA Nsight Compute).
- Bottlenecks can be hardware-specific: one kernel may hit different bottlenecks on different devices, so the process needs knowledge of architectural differences across GPUs (p. 154).
- **When to stop** (p. 154): use the roofline model (Ch. 5). Estimate computations performed and data accessed → computational intensity → compute-bound or memory-bound. Compare the profiler's measured utilization against the hardware limit. Near the limit: little room left. Below it: more optimization is likely possible.

### §6.10 Summary (p. 154)
- Recaps: DRAM architecture, coalescing, hiding memory latency through memory parallelism; then coarsening, unrolling, double-buffering; then the checklist. Claim: with this and earlier chapters, the reader should be able to reason about the performance of any kernel code. (The summary's list omits vector loads/stores and shared-memory bank conflicts, although the chapter covers them.)

## Code listings

### Fig. 6.2 (code panel) — matmul inner product with row-major N (p. 127)
- Purpose: body of the basic one-thread-per-output-element matmul, used to show a coalesced read of N. No function signature is shown; assumes a 2D grid of 2D blocks and square `Width`×`Width` matrices.
- Walkthrough: lines 1–2 compute `row` from the y built-ins and `col` from the x built-ins. Line 3 is the bounds guard `if (row < Width && col < Width)`. Inside: `float Pvalue = 0.0f;`, a loop over `k` from 0 to `Width`, and a final store `P[row*Width + col] = Pvalue;`.
- Line that matters: `Pvalue += M[row*Width + k]*N[k*Width + col];`. Within a warp, `row`, `k`, `Width` are the same and `col` is consecutive, so `N[...]` addresses are consecutive (coalesced).
- Built-ins: `blockIdx`, `blockDim`, `threadIdx` (`.x`, `.y`).

### Fig. 6.3 (code panel) — same with column-major N (p. 128)
- Identical to Fig. 6.2 except the loop line: `Pvalue += M[row*Width + k]*N[col*Width + k];`.
- Now consecutive threads' N addresses differ by `Width`: uncoalesced.
- Care: the M read `M[row*Width + k]` is the same in both figures. The book does not analyse it in this section (within a warp all threads share `row` and `k`, so they read the same M element).

### Fig. 6.12 — `vecadd_kernel` with vector loads (p. 138)
- Purpose: vector addition where each thread adds four element pairs using 16 B loads and one 16 B store.
- Signature as printed: `__global__ void vecadd_kernel(float* x, float* y, float* z, int N)`.
- Launch configuration assumed: 1D grid; the number of threads is one quarter of the number of elements. `N` is not used in the body as printed, and there is no bounds check; the text says boundary handling is left as an exercise.
- Walkthrough:
  - Line 02: `int i = blockDim.x*blockIdx.x + threadIdx.x;` — global thread index; here it names a chunk of four floats.
  - Lines 03–04: `float4 x4 = ((float4*)x)[i];` and `float4 y4 = ((float4*)y)[i];` — two vector loads of 16 B each.
  - Line 05: `float4 z4;`.
  - Lines 06–09: componentwise adds `z4.x = x4.x + y4.x;` … `z4.w = x4.w + y4.w;`.
  - Line 10: `((float4*)z)[i] = z4;` — one vector store; the cast is what makes it a vector store.
- Lines that need care: the cast-then-index form means element `4*i … 4*i+3` of the float array; nothing guards the tail when the length is not a multiple of 4, nor idle threads in the last block.
- APIs / types: `__global__`, `float4` with fields `.x .y .z .w`, `blockDim`, `blockIdx`, `threadIdx`.

### §6.4 snippets — corner-turning shared tile, unpadded and padded (p. 140)
- Unpadded: `__shared__ float a[TILE_DIM][TILE_DIM]; // TILE_DIM = 32` then `a[threadIdx.x][threadIdx.y] = ...;`
- Padded: `__shared__ float a[TILE_DIM][TILE_DIM + 1]; // TILE_DIM = 32` with the same access line.
- Assumes a 32×32 block. First index is `threadIdx.x`, so a warp writes down a column: linear indices i×32 (all bank 0) vs i×33 (banks 0, 1, 2, …).
- Qualifier: `__shared__`.

### §6.5 snippets — thread coarsening toy (pp. 141–142)
- Before: `unsigned int i = blockIdx.x*blockDim.x + threadIdx.x; foo(i);`
- After (factor 4): `unsigned int iStart = 4*(blockIdx.x*blockDim.x + threadIdx.x);` then `for(unsigned int c = 0; c < 4; ++c) { unsigned int i = iStart + c; foo(i); }`
- Care: the multiply by the coarsening factor is applied to the whole global index; the grid must be launched with a quarter as many threads.

### §6.6 snippets — loop unrolling (pp. 144–146)
- Original: `for(unsigned int i = 0; i < 16; ++i) { A(i) B(i) }`.
- Unrolled by 4: `for(unsigned int i = 0; i < 16; i += 4)` with body A(i) B(i) A(i+1) B(i+1) A(i+2) B(i+2) A(i+3) B(i+3).
- Reordered: same loop header, body A(i) A(i+1) A(i+2) A(i+3) B(i) B(i+1) B(i+2) B(i+3). Valid if A(i+1) is independent of A(i) and B(i).
- Directive: `#pragma unroll 4` on the line before the original loop. `#pragma unroll 1` disables unrolling.
- Register promotion sequence: `int x; foo(x);` → coarsened `int x[4]; for(unsigned int c = 0; c < 4; ++c) { foo(x[c]); }` → unrolled `int x[4]; foo(x[0]); foo(x[1]); foo(x[2]); foo(x[3]);`. Only the last form has constant indices and can be promoted to registers.

### §6.7 snippets — double buffering (pp. 146–147)
- Single buffer: `for(unsigned int i = 0; i < N; ++i) { ... = buffer[anotherThreadID]; __syncthreads(); buffer[myThreadID] = ...; __syncthreads(); }`
- Double buffer: `for(unsigned int i = 0; i < N; ++i) { ... = inBuffer[anotherThreadID]; outBuffer[myThreadID] = ...; __syncthreads(); swap(inBuffer, outBuffer); }`
- Sync points: the remaining barrier sits after the write and before the swap; it protects the true (read-after-write) dependence into the next iteration.
- `inBuffer`/`outBuffer` are pointers to two allocated buffers; `swap` exchanges the pointers. The book does not show declarations or say where the buffers live.

### Exercise 1 kernel — `foo_kernel` (pp. 154–155)
- `__global__ void foo_kernel(float* a, float* b, float* c, float* d, float* e)`; 12 numbered lines.
- 02: `unsigned int i = blockIdx.x*blockDim.x + threadIdx.x;`
- 03–04: `__shared__ float a_s[256];` and `__shared__ float bc_s[4*256];`
- 05: `a_s[threadIdx.x] = a[i];`
- 06–08: `for(unsigned int j = 0; j < 4; ++j) { bc_s[j*256 + threadIdx.x] = b[j*blockDim.x*gridDim.x + i] + c[i*4 + j]; }`
- 09: `__syncthreads();`
- 10: `d[i + 8] = a_s[threadIdx.x];`
- 11: `e[i*8] = bc_s[threadIdx.x*4];`
- Built-ins: `gridDim` appears here in addition to the usual three.

## Relevance to LLM-inference kernels

The book's Ch. 6 examples are matmul and vecadd; the mapping to LLM kernels below is ours unless a page is cited.

- **GEMM / linear layers.** The transposed-operand case on p. 128 is the everyday case in inference: weights are stored one way and consumed the other (`x @ W.T`), and attention scores are `Q @ K.T`. Reading a transposed operand through swapped indices is exactly the `N[col*Width + k]` pattern of Fig. 6.3. Options straight from the checklist: store the transposed copy once at load time (layout change), or corner-turn the tile load (Fig. 6.4) and pad the shared tile (§6.4).
- **Tiled GEMM tuning.** Tile width = warp size for coalesced tile loads (p. 130); padded shared tiles when any access walks a column; coarsening to larger output tiles to cut redundant tile loads (p. 142, expanded in Ch. 15); unrolling so per-thread accumulators stay in registers (pp. 145–146). This is the path from the Ch. 5 kernel towards something BLAS-like.
- **Memory-bound decode steps.** Batch-1 token generation is dominated by reading weights once per token (matrix × vector), so by the chapter's logic (§6.2, §6.3, §6.9) the levers are coalescing, enough concurrent requests (occupancy), and wider loads per instruction, not more arithmetic tricks. The roofline check on p. 154 is the stopping rule.
- **Quantized ops.** Vector loads are shown only for `float4` (16 B). The same idea of moving more bytes per load instruction is attractive for packed int8/4-bit weights, where one 16 B load carries 16 or 32 weights, but the book does not show non-float vector types here `[unverified]`. Dequantize-in-registers is a form of register tiling (checklist row 6).
- **Attention.** Besides `Q @ K.T`, per-head layouts are an array-of-structures vs structure-of-arrays choice (checklist, coalescing row): which dimension is innermost decides whether a warp's reads are adjacent. KV-cache reads are long sequential streams, well suited to coalescing and vector loads.
- **Sampling.** Softmax and argmax are reductions (Ch. 10), where the checklist points to divergence reduction, warp-level primitives and coarsening. Top-p needs a cumulative sum (prefix sum, Ch. 11), the book's first real use of double buffering and of unrolling for register tiling. Top-k involves sorting/filtering (Ch. 12, Ch. 14), where packing, privatization and coarsening for coalescing appear. Gathers (embedding lookup, logit selection by index) are the "irregular access" case: coalesce what you can into shared memory first.
- **Bank conflicts in practice.** Any shared-memory buffer indexed with a power-of-two stride (e.g. 32 or 64 wide per-head or per-row scratch) is a candidate for the 32-way conflict of p. 140; the gcd rule in Exercise 5 predicts it.

## Unclear in the PDF

Suspected errata (recorded as printed, not corrected in the notes above except where flagged):
1. **Shift direction, pp. 140–141.** The text says multiplying by 32 = 2^5 "can be simplified into a shift operation i >> 5", and for 33 columns "i × (32 + 1) = i >> 5 + i". Multiplication by 32 is a left shift (`i << 5`); `>>` divides. The second expression also needs parentheses as C code. Almost certainly a typo for `(i << 5) + i`.
2. **Which barrier is removed, p. 147.** The analysis says the *first* barrier (after the read) enforces the false dependence and "would not be needed". The next paragraph then says "we can eliminate the **second** barrier synchronization by using different memory buffers". The final code and the sentence after it ("the call to `__syncthreads()` that separates these two memory accesses can be eliminated") match "first". "Second" looks like a slip.
3. **HBM3E arithmetic, p. 133.** Printed: clock "4.9 GHz/s" (unit should be GHz) and 16 64-bit buses "resulting in 1 TB/s". Using the page's own formula: 8 B × 2 × 4.9 GHz × 16 = 1254.4 GB/s ≈ 1.25 TB/s. Either "1 TB/s" is a loose rounding or one input is off.
4. **Local arrays "in global memory", p. 146.** Ch. 6 says local arrays "are placed in global memory by default" and cites Ch. 5. The Ch. 5 text (book p. 103, checked in the text extraction only, not the page image) says automatic arrays are stored in "the thread's local memory". Wording differs between chapters.
5. **Naming drift.** Fig. 6.4 labels the shared tiles `A_s` and `B_s` although the matrices are M and N. §6.4 uses `a` and `TILE_DIM`. Exercise 3 asks about `BLOCK_SIZE` "for tiled matrix multiplication in Chapter 5", but the Ch. 5 text extraction uses `TILE_WIDTH` (and `Mds`/`Nds`) and contains no `BLOCK_SIZE`. Treat `BLOCK_SIZE` as the tile/block width.
6. **Minor typos.** p. 124: main text cites the sidebar as "Why is DRAM so slow?" while its title is "Why are DRAMs so slow?". p. 126: "the accesses data wall span" (probably "accessed data will span"). p. 135: "Bank 0 or Channel 1" (should be "of"). p. 139: "4 B integer of floating point values" (should be "or"). p. 133: "connected a large number of banks" (missing "to").

Ambiguities and things to be careful with:
7. **Fig. 6.8 labels vs text.** The legend calls the light segments "Idle time"; the text calls them access latency. The book does not say whether it means "across the run" or "at once", and it may also be counting N loads. Derived by us, not stated in the book.
