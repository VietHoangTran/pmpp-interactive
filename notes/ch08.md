# Chapter 8 — Stencil computation

- **Book pages:** 183–200 (p. 200 is blank)  **PDF pages:** 210–227 (pdf = book + 27)
- **In one paragraph:** (Chapter subtitle: "And thread coarsening".) Stencils are the workhorse of finite-difference PDE solvers: every output grid point is a weighted combination of the input point and a sparse set of neighbours along the axes. The chapter introduces grids, finite differences and stencil order, then develops a 3D 7-point "stencil sweep" through four kernels: basic, shared-memory tiled, thread-coarsened in z (a 2D block marches through z keeping only three planes in shared memory), and coarsened plus register-tiled (previous/next planes live in per-thread registers). Each step is evaluated by arithmetic intensity against an ideal of 13/8 = 1.625 FLOP/B. Afterwards a reader can explain why 3D tiling runs into the 1024-thread and shared-memory limits, apply thread coarsening to enlarge tiles, and decide which data belongs in registers versus shared memory.

## Concepts

### Chapter opening (p. 183)
- Stencils underpin numerical PDE solving in fluid dynamics, heat conductance, combustion, weather forecast, climate simulation, electromagnetics. Data are discretised physical quantities (mass, velocity, force, acceleration, temperature, electrical field, energy) (p. 183).
- A common use: approximate derivative values of a function from function values in a neighbourhood (p. 183).
- **Similarity to convolution:** new value of an element computed from the same-position element and its neighbours in another multidimensional array; so stencils also face halo cells and ghost cells (p. 183).
- **Differences from convolution** (p. 183):
  - Used to iteratively solve for continuous, differentiable functions over a domain.
  - Data and weights are dictated by the differential equation.
  - Some stencil patterns allow optimisations that convolution does not.
  - In solvers that propagate initial conditions through the domain, output calculations can have dependences and ordering constraints.
  - Numerical accuracy needs push toward high-precision floating-point data, which consumes more on-chip memory under tiling.

### §8.1 Background (pp. 184–187)
- **Discretisation** (p. 184, Fig. 8.1): first step is converting functions/models into a discrete representation. Example: `y = sin(x)` on `0 <= x <= π` sampled on a 1D regular grid of seven points spaced `π/6` apart, stored as array `F = [0.00, 0.50, 0.87, 1.00, 0.87, 0.50, 0.00]`. The `x` value is implicit: `x = i · π/6`. `F[2] = 0.87 = sin(2·π/6)`.
- **Structured grids** cover n-dimensional Euclidean space with identical parallelotopes (segments in 1D, rectangles in 2D, bricks in 3D); derivatives become finite differences, so they are mainly used in **finite-difference methods**. **Unstructured grids** are more complex and used in finite-element and finite-volume methods. The chapter uses only regular grids (p. 184).
- Values between grid points need interpolation (linear, splines). Fidelity improves with smaller spacing, at the cost of more storage and more compute when solving a PDE (p. 184).
- **Precision** (pp. 184–185): mainstream CPUs and GPUs support double (64-bit), single (32-bit), half (16-bit) and other formats (Appendix A). Double gives the best fidelity, but single and half have "much higher arithmetic computation throughput" on modern CPUs/GPUs, and double consumes more memory bandwidth and capacity. That hurts tiling, which needs many grid values held in on-chip memory and registers to reach high arithmetic intensity (ties back to Chapter 7).
- **Stencil (definition)** (p. 185): "a geometric pattern of weights applied at each point of a structured grid". It specifies how the value at a point of interest is derived from neighbouring values by a numerical approximation routine.
- **Finite-difference first derivative** (p. 185): `f'(x) = (f(x+h) - f(x-h)) / (2h) + O(h²)`. `h` is the grid spacing; error is proportional to `h²`. In the sine example `h = π/6 ≈ 0.52`: not negligible error but "a reasonably close approximation".
- In array form (p. 185): `FD[i] = (F[i+1] - F[i-1]) / (2h)`, rewritten as `FD[i] = (-1/(2h))·F[i-1] + (1/(2h))·F[i+1]`.
- So the derivative at point `i` uses points `[i-1, i, i+1]` with coefficients `[-1/(2h), 0, 1/(2h)]`: a **1D 3-point stencil** (p. 186, Fig. 8.2(a)).
- Higher derivatives need higher-order finite differences. Up to second derivative → points `[i-2 .. i+2]`, a 1D 5-point stencil (Fig. 8.2(b)). In general, up to the n-th derivative → n grid points on each side of the centre. 1D 7-point shown in Fig. 8.2(c) (p. 186).
- **Order of a stencil** = number of grid points on each side of the centre point; the book ties it to the order of the derivative being approximated (p. 186).
- **2D/3D stencils** (pp. 186–187, Fig. 8.3): a PDE in two variables needs a 2D grid and 2D stencil. If it involves only partial derivatives with respect to a single variable at a time (∂f/∂x, ∂f/∂y, but not the mixed ∂f/∂x∂y), the stencil's points all lie along the x and y axes. First derivatives in x and y → 2D 5-point stencil (Fig. 8.3(a)); up to second-order derivatives in x or y → 2D 9-point stencil (Fig. 8.3(b)). 3D analogues: 7-point (order 1) and 13-point (order 2) (Fig. 8.3(c), (d)).
- **Stencil sweep** (p. 187, Fig. 8.4): the computation pattern in which the stencil is applied to all relevant input grid points to produce output values at all grid points. Grid values are stored in multidimensional arrays; Fig. 8.4 shows a 2D grid stored as a 2D array with a 5-point stencil.

### §8.2 Parallel stencil – a basic kernel (pp. 187–189)
- **Simplifying assumptions** (pp. 187–188, Fig. 8.5):
  1. No dependence between output grid points within a sweep.
  2. Boundary grid points hold boundary conditions and do not change from input to output; only interior points are computed. Called reasonable because stencils mainly solve differential equations with boundary conditions.
- Kernel design (p. 188, Fig. 8.6): each block computes a tile of output values, each thread one output point. Fig. 8.5 illustrates 2D tiling with 4×4 output tiles, but the kernel is for a 3D grid with a 3D 7-point stencil because "most real-world applications solve 3D differential equations".
- Thread-to-point mapping uses the usual linear expressions in the x, y, z fields of `blockIdx`, `blockDim`, `threadIdx` (p. 188).
- Each output is the input at the point and its six axis neighbours, multiplied by coefficients `c0..c6` and summed. Coefficients may be hard-coded or put in constant memory depending on the flexibility wanted; their values come from the PDE being solved (pp. 188–189).

### §8.3 Memory bandwidth considerations (p. 189)
- Grid `n × n × n`. Interior points computed: `(n-2)³`. Per point: 13 FLOP (7 multiplies + 6 adds). Total `13·(n-2)³` FLOP.
- Data touched: all input points except those on edges and corners of the cube, `n³ - 12·n + 16` values (the 12 edges hold `12(n-2) + 8 = 12n - 16` points; the breakdown in parentheses is ours); all interior output points, `(n-2)³`. Each value 4 B single precision. Bytes: `4·(n³ - 12n + 16 + (n-2)³)`.
- **Ideal AI** (each input loaded once) = `13·(n-2)³ / (4·(n³ - 12n + 16 + (n-2)³))` → for large `n` approaches **13/8 = 1.625 FLOP/B**. "Very small", so the 3D 7-point stencil is memory bound "on modern GPUs".
- **Basic kernel AI:** per thread 13 FLOP, seven 4 B loads, one 4 B store → `13 / ((7+1)·4) = 0.41` FLOP/B (exactly 0.40625). Measured values may be somewhat higher thanks to L1/L2 hits; tiling is the more reliable route.

### §8.4 Shared-memory tiling for stencil sweep (pp. 189–193)
- Tiling design is "almost identical" to convolution with "a few subtle but important differences" (pp. 189–190).
- **Difference 1: no corners** (p. 190, Fig. 8.7). The input tile of a 2D 5-point stencil does not include the corner grid points (compare Fig. 7.11). This matters later for register tiling.
- **Difference 2: lower reuse / lower ideal AI** (p. 190). Fewer inputs per output than a dense filter of the same extent:

  | Case | Stencil ideal AI | Convolution counterpart |
  |---|---|---|
  | 2D order 1 (5-point) | 1.125 FLOP/B | 3×3: 2.25 FLOP/B |
  | 2D order 2 (9-point) | 2.125 FLOP/B | 5×5: 6.25 FLOP/B |
  | 2D order 3 (13-point) | 3.125 FLOP/B | 7×7: 12.25 FLOP/B |
  | 3D order 3 (19-point) | 4.625 FLOP/B | 7×7×7: 85.75 FLOP/B |

  (The stencil numbers equal `(2p - 1)/8` for a p-point stencil: p multiplies, p − 1 adds, 8 B per output for one load and one store. That closed form is ours; the book gives only the values.)
- So loading a value into shared memory pays off much less for stencils, especially in 3D, "the prominent use case". This motivates thread coarsening and register tiling in the third dimension (p. 190).
- **Tiled kernel** (pp. 191–192, Fig. 8.8): modelled on Fig. 7.12. Blocks are the size of the input tile; some threads are turned off for the compute phase. See Code listings.
  - The `- 1` in the coordinate expressions is the stencil order; in general subtract the order (p. 191).
  - Load guards: `i,j,k >= 0` protect against ghost cells below the grid; `i,j,k < N` protect at the upper end (p. 191).
  - Compute guards: boundary layer of the grid excluded (line 10); extra loader threads at the block's surface excluded (lines 11–12) (pp. 191–192).
- **AI of the tiled kernel** (p. 192). Input tile is a cube of side `t`, output tile side `t - 2`. Per block: `(t-2)³` active threads × 13 FLOP; `t³` loads and `(t-2)³` stores of 4 B:
  - AI = `13·(t-2)³ / (4·t³ + 4·(t-2)³)` = `(13/8) · 1 / ( ½·t³/(t-2)³ + ½ )` FLOP/B.
  - Increases with `t`; asymptote 13/8 = 1.625 FLOP/B.
- **Hardware limits on `t`** (p. 192): the 1024-thread block limit "on current hardware" makes large `t` hard; "the practical limit on t is 8 because an 8×8×8 thread block has a total of 512 threads". Shared memory use grows as `t³`.
- **Disadvantage 1 of small `t`: low AI** (pp. 192–193). `t = 8` → 0.96 FLOP/B vs 1.625 ideal. Cause: halo overhead; halo elements are reused less than interior elements and their share grows as `t` shrinks.
  - 2D comparison: radius-1 convolution with 32×32 input tile → 1024 inputs, 30×30 = 900 outputs, 124 halo elements ≈ 12%.
  - 3D order-1 stencil with 8×8×8 input tile → 512 inputs, 6×6×6 = 216 outputs, 296 halo elements ≈ 58%.
- **Disadvantage 2 of small `t`: poor coalescing** (p. 193). In an 8×8×8 tile each 32-thread warp loads 4 different rows of 8 values, so one load instruction touches at least 4 distant global-memory locations; not coalesced, DRAM bandwidth underused. Fix: non-cubic blocks with x-dimension 32 so a warp reads 32 contiguous elements, e.g. block dims 32, 8, 4 in x, y, z. Better performance than 8×8×8, but the output tile is still small and AI stays low. This motivates §8.5.

### §8.5 Thread coarsening (pp. 193–195)
- Idea (p. 193, Fig. 8.9): coarsen each thread's work from one grid point to a **column of grid points** in z, to escape the block-size limit. Recalls Chapter 6: thread coarsening partially serialises parallel work units into each thread to reduce the overhead of parallelisation. Here that overhead is having to load low-reuse halo elements into more thread blocks.
- Illustration parameters (p. 193): input tile `t³ = 6³ = 216` points; output tile `(t-2)³ = 4³ = 64`; each input x-y plane 36 points, each output x-y plane 16 points. The block has as many threads as one input x-y plane (6×6); only the inner 4×4 active threads are drawn.
- **Kernel behaviour** (pp. 194–195, Fig. 8.10):
  - The block iterates in z (into the figure), computing one x-y output plane per iteration. Threads are assigned to an (x, y) position; `i` is the z index, identical for all threads in an iteration.
  - Before the loop: all threads load the first input plane into `inPrev_s` and the second into `inCurr_s`.
  - Each iteration: all threads load the third plane into `inNext_s`; barrier; active threads compute their output using four x-y neighbours from `inCurr_s`, the z neighbours from `inPrev_s` and `inNext_s`; barrier; then every thread copies `inCurr_s → inPrev_s` and `inNext_s → inCurr_s` because the planes' roles shift as the block advances one plane in z.
  - So at the end of each iteration two of the three planes needed next are already in place; the next iteration loads only one new plane. Fig. 8.11 shows the mapping after the first iteration.
- **Advantages** (p. 195):
  - Tile size grows without more threads; not all input-tile planes need to be in shared memory at once.
  - Block size is `t²` rather than `t³`, so `t = 32` is possible (1024 threads).
  - With `t = 32` the book states AI = **1.52 FLOP/B**, versus 0.96 FLOP/B for the 8×8×8 tiled kernel and 1.625 ideal. (See Unclear: the cube formula gives 1.47 for t = 32.)
  - Shared memory holds `3·t²` elements instead of `t³`. For `t = 32`: `3·32²·4 B = 12 KB` per block, "a reasonable level".

### §8.6 Register tiling (pp. 196–198)
- Applies to stencil patterns whose neighbours lie only along the x, y, z directions through the centre; all stencils in Fig. 8.3 qualify (p. 196).
- Observation on Fig. 8.10 (p. 196): each `inPrev_s` and `inNext_s` element is used by exactly one thread (the one with the same x-y indices). Only `inCurr_s` is read by multiple threads and "truly" needs shared memory. So the z neighbours can stay in the registers of their single user.
- **Register tiling** (term, p. 196): keeping data in registers to reduce shared or global memory accesses (as discussed in Chapters 5 and 6).
- **Kernel changes** (pp. 196–197, Fig. 8.12): registers `inPrev`, `inCurr`, `inNext` per thread; `inPrev`/`inNext` replace the shared arrays; `inCurr_s` is kept so x-y neighbours can be shared; a copy of the current plane is always maintained in shared memory. Shared memory drops to one third of the coarsening-only kernel (the text says "that by the kernel in Fig. 8.12"; evidently Fig. 8.10 is meant, see Unclear).
- Both Fig. 8.10 and Fig. 8.12 keep only the **"active part"** of the input tile on chip. The number of planes in the active part depends on the stencil order; it is 3 for the 3D 7-point stencil (p. 197).
- **Two advantages over Fig. 8.10** (p. 197):
  1. Many shared-memory reads/writes become register accesses; registers have "significantly lower latency and higher bandwidth than the shared memory", so the code is expected to run faster.
  2. Each block uses one third of the shared memory.
- **Cost** (p. 197): three more registers per thread, i.e. 3072 more registers per block for 32×32 blocks. Higher-order stencils need even more. If register usage becomes a problem, move some planes back to shared memory. "A common trade-off ... between shared memory and register usage."
- **No change in global-memory traffic** (p. 198): data reuse is now split across registers and shared memory, the number of global accesses is unchanged, so register tiling on top of coarsening does not affect global memory bandwidth consumption (hence the same AI as the coarsening kernel).

### §8.7 Summary (p. 198)
- Stencil sweep "seems to be just convolution with special filter patterns", but two characteristics motivate different optimisations:
  1. Sweeps are typically on 3D grids (convolution typically on 2D images or a few time slices of 2D images) → tiling considerations differ → thread coarsening for larger input tiles and higher AI.
  2. Stencil patterns can sometimes enable register tiling of input data → better data access throughput and less shared-memory pressure.

## Code listings

### Fig. 8.6 — basic `stencil_kernel` (p. 188)
- **Purpose:** one thread computes one interior output point of a 3D 7-point stencil sweep directly from global memory.
- **Signature:** `__global__ void stencil_kernel(float* in, float* out, unsigned int N)`; grid is `N × N × N`, linearised as `i*N*N + j*N + k`.
- **Launch configuration assumed:** 3D grid of 3D blocks whose threads cover all `N³` points including boundaries (host code not shown).
- **Walkthrough:**
  - Lines 02–04: `i = blockIdx.z*blockDim.z + threadIdx.z` (z), `j` from `.y`, `k` from `.x`; all `unsigned int`.
  - Line 05: `if(i >= 1 && i < N - 1 && j >= 1 && j < N - 1 && k >= 1 && k < N - 1)` restricts work to interior points.
  - Lines 06–12: `out[i*N*N + j*N + k] = c0*in[centre] + c1*in[k-1] + c2*in[k+1] + c3*in[j-1] + c4*in[j+1] + c5*in[i-1] + c6*in[i+1]` (each neighbour written out with the full linearised index).
- **Lines that need care:** neighbour indices differ by 1 (x), `N` (y) and `N*N` (z); the interior guard also guarantees every neighbour index is in range. `c0..c6` are not declared in the listing (hard-coded or constant memory per the text).
- **APIs / built-ins:** `__global__`, `blockIdx`, `blockDim`, `threadIdx` with `.x/.y/.z`.
- **AI:** 13 FLOP / 32 B = 0.41 FLOP/B (p. 189).

### Fig. 8.8 — `stencil_kernel` with shared-memory tiling (p. 191)
- **Purpose:** each block loads a cubic input tile into shared memory, then its inner threads compute the output tile from shared memory.
- **Signature:** same as Fig. 8.6. Uses `IN_TILE_DIM` and `OUT_TILE_DIM` (not defined in the listing; the text takes output side = input side − 2).
- **Launch configuration assumed:** block = `IN_TILE_DIM³` threads (practically 8×8×8 = 512); blocks per dimension sized by `OUT_TILE_DIM` (inferred).
- **Walkthrough:**
  - Lines 02–04: `int i = blockIdx.z*OUT_TILE_DIM + threadIdx.z - 1;` and likewise `j` (y), `k` (x). Signed, offset by the stencil order.
  - Line 05: `__shared__ float in_s[IN_TILE_DIM][IN_TILE_DIM][IN_TILE_DIM];`.
  - Lines 06–08: if `0 <= i,j,k < N`, `in_s[threadIdx.z][threadIdx.y][threadIdx.x] = in[i*N*N + j*N + k];`. No `else`.
  - Line 09: `__syncthreads();`.
  - Line 10: interior-of-grid guard (`>= 1`, `< N-1` on all three).
  - Lines 11–12: interior-of-block guard: `threadIdx.{z,y,x} >= 1` and `< IN_TILE_DIM-1`.
  - Lines 13–19: seven-term sum reading `in_s` at `[z][y][x]`, `[z][y][x-1]`, `[z][y][x+1]`, `[z][y-1][x]`, `[z][y+1][x]`, `[z-1][y][x]`, `[z+1][y][x]` with `c0..c6` in that order.
- **Lines that need care:**
  - Unlike Fig. 7.12 there is no zero-fill for out-of-range loads. That is safe because outputs are computed only for grid-interior points, whose neighbours are always in the grid (our reasoning; the book just calls the conditions out-of-bound guards).
  - Two independent guards (grid boundary vs loader-only threads) both apply.
- **APIs:** `__shared__`, `__syncthreads()`.
- **AI:** `13·(t-2)³ / (4·t³ + 4·(t-2)³)`; 0.96 FLOP/B at `t = 8` (p. 192).

### Fig. 8.10 — `stencil_kernel` with thread coarsening in z (p. 194)
- **Purpose:** a 2D block (one x-y plane of the input tile) iterates over `OUT_TILE_DIM` output planes in z, keeping three input planes in shared memory.
- **Signature:** same as before.
- **Launch configuration assumed:** block = `IN_TILE_DIM × IN_TILE_DIM` (e.g. 32×32); 3D grid of blocks, with `blockIdx.z` selecting a z-slab of `OUT_TILE_DIM` planes (inferred from line 02).
- **Walkthrough:**

## Relevance to LLM-inference kernels

- **Little direct relevance of the stencil pattern itself**: transformer inference has no PDE-style neighbour sweeps. The value of the chapter for this reader is in two general optimisations it demonstrates on a real kernel.
- **Thread coarsening to beat block-size and shared-memory limits** (§8.5). The same move, giving each thread a column of work and streaming through the third dimension with a small rolling on-chip window, is what the book itself points to for matrix multiplication: Ch. 6 p. 153 and Ch. 15 p. 352 link the Chapter 8 coarsening to the advanced matmul optimisations. For GEMM/attention kernels this is the template for "few threads, bigger tiles, more reuse per load".
- **Register tiling decision rule** (§8.6): data read by exactly one thread belongs in that thread's registers; only data read by several threads needs shared memory. Directly applicable to accumulators in dot products, per-thread partial sums in softmax or top-k scans, and per-thread slices of an operand tile in GEMM. The stated cost model (registers per thread vs shared memory per block, p. 197) is the trade-off to tune.
- **Rolling-window buffering** (`prev/curr/next` planes, Figs. 8.10–8.12) is a clean small example of streaming a large operand through limited on-chip memory with two barriers per step; the barrier placement reasoning transfers to any block-cooperative kernel that reuses a shared buffer across loop iterations.
- **Halo fraction and coalescing analysis** (p. 193): the 12% vs 58% calculation and the "x-dimension of the block should be 32 so a warp reads a contiguous chunk" argument are reusable when choosing block shapes for 2D/3D tensor layouts.
- **Precision vs bandwidth vs on-chip capacity** (pp. 184–185): the same three-way trade-off drives fp16 and quantised inference (smaller elements raise FLOP/B and fit more per tile). The book makes the point for double vs single/half; the quantisation link is ours.
- **AI bookkeeping**: the per-thread count "13 FLOP, 7 loads, 1 store" (p. 189) is a compact worked example of analysing a kernel whose loads and stores are comparable in number, as in elementwise/quantise/dequantise ops.
- **Connection to Exercise 3d of Chapter 7**: the `[-1/2, 0, 1/2]` filter is the 1D 3-point derivative stencil with `h = 1`, a useful bridge between the two chapters.
