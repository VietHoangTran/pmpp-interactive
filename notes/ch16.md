# Chapter 16 — Dynamic programming and wavefront parallelism

- **Book pages:** 373–400  **PDF pages:** 399–426 (pdf = book + 26)
- **Chapter credit:** "With special contributions from Juan Gómez-Luna" (p. 373). New in the 5th edition.
- **In one paragraph:** The chapter is about parallelising computations whose cells depend on previously computed cells, so that only some of the work can run at once. It uses dynamic programming (DP) as the vehicle. A *wavefront* is the set of table cells whose inputs are all ready, so they can be computed together. Two case studies are worked through in CUDA: Floyd-Warshall all-pairs shortest paths (every cell is in every wavefront; one kernel launch per step) and Smith-Waterman sequence alignment (anti-diagonal wavefronts that grow and shrink). For Smith-Waterman the chapter builds up from one kernel launch per anti-diagonal, to square tiles held in shared memory (one thread block per tile), to sheared "hypertiles" that keep every thread busy in every iteration, and finally sketches flag-based inter-block synchronisation and DPX instructions. Afterwards a reader can identify the wavefronts of a recurrence, choose where to synchronise (kernel relaunch, `__syncthreads()`, or flags), and write the index arithmetic for tiled and sheared-tile kernels.

Legend used below: **[read]** = taken directly from the page; **[derived]** = our own calculation or inference from what the page shows, not stated by the book.

## Concepts

### Opening and §16.1 Dynamic programming (pp. 373–374)

- **Wavefront parallelism** is described as an algorithmic technique for exploiting data parallelism in applications that have data dependencies along space and/or time dimensions (p. 373).
- **Dynamic programming**: divide a problem recursively into smaller sub-problems, save each sub-problem's solution, and assemble saved solutions into the final answer. Saved solutions are typically used several times, which is where the saving comes from (pp. 373–374).
- Problems suited to DP have **optimal substructure** with **overlapping sub-problems** (the book's italicised terms). Contrast with divide-and-conquer, where sub-problems are disjoint; merge sort (Chapter 14) is the example of disjoint sub-problems (p. 374).
- Fibonacci, Eq. (16.1): `F_i = F_{i-1} + F_{i-2}`. Plain recursion solves the same sub-problem repeatedly (computing both `F_i` and `F_{i-1}` each pays for `F_{i-2}`). The fix is to store solutions in a table; the book names this **memoization** or **tabulation** depending on the implementation approach (p. 374).
- **Wavefronts** (first definition): groups of intermediate solutions that can be calculated in parallel because there are no dependencies between them. Parallel execution within a wavefront is the natural way to parallelise DP (p. 374).
- DP problem families listed (p. 374): shortest path (Dijkstra, Bellman-Ford, Floyd-Warshall), chain matrix multiplication, time series (dynamic time warping), Hidden Markov models (Viterbi), and bioinformatics: sequence alignment (Smith-Waterman, Needleman-Wunsch), protein folding, RNA structure prediction, protein-DNA binding (citing ref. [1]).

### §16.2 Implementation approaches (pp. 374–376)

- Two approaches: **top-down** and **bottom-up**, both shown for Fibonacci in Fig. 16.1 (p. 374).
- **Top-down** = recursive; each call may meet the same sub-problem several times, so results are **memoized** in an associative array (`hash_table`). Each call first checks the table (line 4), otherwise recurses (line 7) or returns the base case `n` for `n` = 0 or 1 (line 10), and stores the result (line 11) (pp. 374–375).
- Worked trace (pp. 375–376): `F_3` calls `F_2` then `F_1`; `F_2` calls `F_1` and `F_0`; those hit the base case and are stored; when `F_3` makes its second call for `F_1`, the value is found in the hash table and returned at line 4.
- **Why top-down is inefficient on GPUs** (p. 376), two reasons:
  1. CUDA-enabled GPUs do not efficiently support deep nesting of function calls in kernel code. Device functions are normally inlined; recursive calls cannot be inlined indefinitely, so they stay as real calls and are slow.
  2. Accesses to the associative array tend to be uncoalesced across the threads of a warp.
- **Bottom-up** = iterative; solve the smallest sub-problems first and **tabulate** them, then progressively larger ones. Because the loop goes from small to large, every iteration finds its inputs already in the table (p. 376).
- **Wavefront** (second, operational definition): the set of sub-problems solved (table cells filled) in one iteration. For Fibonacci, wavefront `i` is the single cell `table[i]`, so execution is sequential. Many DP problems have multi-cell wavefronts (often with multi-dimensional tables); cells of one wavefront are independent and can run in parallel (p. 376).
- Wavefront parallelism suits GPUs but needs careful pre-planning based on (a) the dynamic behaviour (the wavefront may grow or shrink) and (b) the dependencies between different wavefronts. The rest of the chapter uses bottom-up only (p. 376).

### §16.3 Wavefront patterns (pp. 376–377)

- In each iteration the wavefront consists of sub-problems that are mutually independent and whose smaller sub-problems are already solved. Consecutive iterations (the book also calls them **waves**) are serialised by enforcing the data dependencies through synchronisation of the parallel compute units, e.g. barriers (p. 376).
- Fig. 16.2 shows four patterns: (a) Checkerboard, (b) Financial, (c) Smith-Waterman, (d) H.264. The number in each cell is its wavefront index. Wavefront size is constant in (a) and (b), and changes in (c) and (d) (pp. 376–377).
- Floyd-Warshall is a constant-size wavefront like (a)/(b), except each iteration computes a whole 2D plane of a 3D sub-problem space rather than one row of a 2D space. Smith-Waterman is pattern (c): grows then shrinks (p. 377).
- **Retention of the table** (p. 377): some algorithms need only a few recent wavefronts. Fibonacci only needs the two most recent values (the Fig. 16.1 code keeps them all, but need not). Floyd-Warshall keeps a single 2D plane of the 3D space. Smith-Waterman must keep every wavefront because the full matrix is used to trace back the alignment.

### §16.4 Floyd-Warshall algorithm (pp. 377–381)

- Purpose: shortest paths between **all pairs** of vertices in a directed weighted graph (footnote 1 points to Chapter 18 for graphs) (p. 377).
- Define `d(i, j, k)` = shortest distance from `i` to `j` using only vertices `0..k` as intermediates. Recurrence (unnumbered, p. 378):
  `d(i, j, k) = min(d(i, j, k−1), d(i, k, k−1) + d(k, j, k−1))`
  i.e. either avoid `k`, or go `i→k` then `k→j`. Three smaller sub-problems feed each cell.
- Bottom-up: `d(i, j, −1)` is the edge weight or infinity if there is no edge. Solve for `k = 0, 1, …, N−1`; `d(i, j, N−1)` is the final answer (p. 378).
- **Storage**: once plane `k` is done, plane `k−1` is not needed. Sub-problem space is O(N³) but only O(N²) must be stored at once (p. 378).
- Pseudo-code (Fig. 16.3): three nested loops `k`, `i`, `j`. The order in which `k` values are visited does not matter as long as all are visited. At the start of iteration `k` the `dist` table holds plane `k−1`; at the end it holds plane `k`. All cells in an iteration can be computed in parallel (p. 378).
- **GPU mapping** (pp. 378–379): one `(i, j)` pair per thread; one kernel launch per `k`. Threads synchronise between iterations by kernel termination and grid relaunch; this **global synchronisation** guarantees that every distance that could change because of vertex `k` is stored before the next `k` begins.
- Launch configuration (p. 379): 1D blocks of `threads` threads; 2D grid. Grid x = `(n_vertices + threads − 1) / threads` so the blocks cover a full row of the table; grid y = `n_vertices`, one block-row per table row. Each block covers a section of one row.
- **Why one table is safe (no double buffering)** (pp. 379–380): in iteration `k` a thread reads its own cell, `dist[k][j]` (row `k`) and `dist[i][k]` (column `k`). For graphs with non-negative distances and `dist[k][k] = 0`, the threads that own row `k` or column `k` compute `min(dist[i][k], dist[i][k] + dist[k][k])` and `min(dist[k][j], dist[k][k] + dist[k][j])`, which reduce to the existing values. So row `k` and column `k` are unchanged during iteration `k`, and no thread reads a value that another thread is changing. In problems where threads do update values read by others, the double-buffering approach of Chapter 6 would be needed.
- Kernel behaviour (p. 381): all threads of a block share the same row, so they all need the same `dist[row][k]`. Thread 0 reads it from global memory into a shared scalar `dist_k_col`. If it is infinity, `k` cannot be on a shortest path from this row and the whole block retires. Otherwise each thread reads `dist[k][col]` (these reads are coalesced across the block), retires if that is infinity, and otherwise writes the sum if it is smaller than the current value.
- Example from Fig. 16.5 (p. 381): with `k` = vertex c, every thread in a block needs the cell in its row and column c; thread 4 reads column e of row c.
- **Why Floyd-Warshall is easy** (p. 381): (1) every vertex pair is considered every iteration, so wavefront size is constant; (2) dependencies are simple: every cell depends only on row `k` and column `k` of the previous iteration.
- [derived] Using the Fig. 16.5 table as printed, iteration `k = c` changes exactly two cells: b→e becomes 9 + 10 = 19 and h→e becomes 3 + 10 = 13 (column c holds b:9, e:8, h:3; row c holds e:10; e→e stays 0 because 18 > 0).

### §16.5 Genome sequence alignment and Smith-Waterman algorithm (pp. 382–384)

- Domain background (p. 382): DNA is a string over A, C, G, T; the human genome has 3.2 billion base pairs (bp); sequencers produce fragments ("reads") that must be mapped to a reference genome; short reads are 50–300 bp, long reads 10 K–100 K bp. Sequence alignment is a key step and has traditionally used quadratic-time DP (Smith-Waterman, Needleman-Wunsch).
- Data structure: the **homology score matrix** (also **scoring matrix**) `H`, of size `(L_A + 1) × (L_B + 1)` for sequences of length `L_A` and `L_B`. Base pairs are numbered from 1. Row 0 and column 0 hold the boundary value 0. `H_{i,j}` is the homology score between a prefix of one sequence and a prefix of the other; higher means more similar (p. 382).
- Per-pair **similarity score** `S_{i,j}`: positive on a match (e.g. +3), negative on a mismatch (e.g. −3). A **gap penalty** (e.g. 2) is applied for a deletion or an insertion (`deletion_penalty`, `insertion_penalty`) (p. 382).
- Recurrence, Eq. (16.2) as printed (p. 382): `H_{i,j} = max( H_{i−1,j−1} + S_{i,j},  H_{i−1,j} − deletion_penalty,  H_{i,j−1} − insertion_penalty,  0 )`. (The surrounding text and Fig. 16.6 attach the two penalty names the other way round; see "Unclear in the PDF".)
- Three scenarios explained on p. 383, using `B_i` for the row sequence and `A_j` for the column sequence: (1) `B_{i−1}` aligned with `A_{j−1}`: add `S_{i,j}`; (2) coming from `H_{i−1,j}`: an insertion in B, subtract the insertion penalty; (3) coming from `H_{i,j−1}`: a base pair missing from B, subtract the deletion penalty. If all three are negative the cell is set to 0, so the matrix stays non-negative.
- **Dependence structure**: each cell depends on three neighbours (north, west, north-west) which lie in the previous two anti-diagonals. Cells on the same anti-diagonal are independent, so each **anti-diagonal is a wavefront** (pp. 383–384).
- Worked wavefronts (p. 384): wavefront 1 is `H_{1,1}` alone (uses boundary cells `H_{0,1}`, `H_{0,0}`, `H_{1,0}`); wavefront 2 is `H_{2,1}` and `H_{1,2}`; wavefront 3 is `H_{3,1}`, `H_{2,2}`, `H_{1,3}`. The wavefront grows then shrinks.
- **Traceback** (p. 384): after all wavefronts, start from the highest-scoring cell and follow predecessors (top, top-left, left) until a 0 is reached in the first row or column. It is sequential and needs the entire matrix, so the chapter only parallelises the wavefront computation.

### §16.6 Wavefront parallelization: block-level tiling (pp. 384–389)

- **Baseline** (p. 384, Fig. 16.7(a)): one kernel launch per anti-diagonal, one thread per cell. Correct, but (i) no data locality across adjacent anti-diagonals, (ii) wasted reuse opportunities, (iii) a kernel launch per anti-diagonal. Its implementation is left as an exercise.
- **Block-level tiling** (p. 384, Fig. 16.7(b)): split the matrix into tiles and give each tile to one thread block. Inside a tile, threads compute anti-diagonal entries and synchronise with `__syncthreads()` between anti-diagonals. Global synchronisation (kernel termination) is then needed only between **anti-diagonals of tiles**. Extra benefit: the tile lives in shared memory and is written back to global memory in a coalesced way at the end.
- Simplifying assumption: both sequences have the same length `L_seq`, so the matrix is `L × L` with `L = L_seq + 1` (p. 384).
- Sizing (p. 385): blocks are 1D with `threads` threads; tiles are `threads × threads` cells; `numTiles_x = (L_seq + threads − 1) / threads`. With equal-length sequences the same number applies to the vertical direction and to the maximum number of tiles on a tile anti-diagonal.
- **Tile anti-diagonals** (p. 386): numbered `d = 0 … 2*numTiles_x − 2`, giving `2*numTiles_x − 1` kernel calls. In Fig. 16.7(b) `numTiles_x = 3`, so 5 calls with `d` = 0..4. For simplicity every call launches the maximum `numTiles_x` blocks; some are inactive. Setting `numBlocks` to the exact count per call is left as an exercise.
- **Block → tile mapping** (pp. 386–387): `tile_row = blockIdx.x`, `tile_col = d − blockIdx.x`. A block is active only if `0 ≤ tile_col < numTiles_x`. Examples: at `d = 1` blocks 0 and 1 get tiles (0, 1) and (1, 0), block 2 gets column −1 and is inactive; at `d = 3` block 0 gets column 3 (= `numTiles_x`, out of range), blocks 1 and 2 are active.
- **Thread → cell mapping inside a tile** (pp. 387–388, Fig. 16.7(c)): same idea one level down. `r_tile = threadIdx.x` (a thread owns one tile row for the whole kernel) and `q_tile = d_tile − threadIdx.x`. The intra-tile loop runs `2*tile_width − 1` iterations. A thread is active in an iteration only if `0 ≤ q_tile < tile_width` and the global indices are inside the matrix (`r < L && q < L`). Global indices add 1 because row 0 and column 0 are boundary zeros that are never computed; that is also why no `r >= 0 && q >= 0` test is needed.
- **Loading the three inputs** (p. 388): `load_n`, `load_w`, `load_nw` read from the shared-memory tile unless the cell is on the tile's top edge (`r_tile == 0`) or left edge (`q_tile == 0`); edge inputs come from global memory because they were produced by an earlier kernel call.
- `max4()` returns the maximum of four integers (Fig. 16.11). `__syncthreads()` at the end of each intra-tile iteration guarantees the whole anti-diagonal is in shared memory before the next starts (pp. 388–389).
- **Storing the tile** (p. 389): `store_tile` writes the tile to global memory row by row, all threads together, so the writes are coalesced. The book calls this an example of turning uncoalesced accesses into coalesced ones via shared memory, similar to corner turning (Chapter 6) and packing (Chapter 12).
- [derived] In the compute loop a thread index means "tile row"; in `store_tile` the same thread index means "tile column". This role switch is what makes the store coalesced.
- [derived] Active blocks per `d` for the Fig. 16.7(b) example: 1, 2, 3, 2, 1. Active threads per intra-tile iteration for a 3×3 tile: 1, 2, 3, 2, 1.

### §16.7 Hyperplane transformation (pp. 389–397)

- Square tiling improves on the baseline by cutting kernel-call overhead and using shared memory, but square (or rectangular) tiles have **two drawbacks** (pp. 389–390, Fig. 16.13):
  1. **Non-uniform anti-diagonal lengths inside a tile.** The number of active threads differs per iteration and is usually below the maximum, so threads idle and warps are under-used. An `n × n` tile takes `2n − 1` iterations.
  2. **Lost locality between neighbouring tiles on different tile anti-diagonals.** Only a tile's *last* anti-diagonals are likely still in cache (the book says e.g. L2 in a GPU). The neighbour's *first* anti-diagonals need the tile's top-right cells, which were computed early and may have been evicted; the cells that are still cached are needed by the neighbour only later, by which time they too are likely evicted.
- **Hypertiles** (p. 390, refs [2–4]): transform rectangular tiles with an affine transformation called **hyperplane partitioning**, which turns rectangles into quadrilaterals. The book restricts itself to parallelograms obtained by shifting tile rows horizontally, a **shear transformation**, so that what was a tile *column* now lies along a matrix *anti-diagonal*. Example: a 3×3 tile becomes a parallelogram by shifting the middle row left by 1 and the bottom row left by 2 (Fig. 16.14).
- **Three advantages** (pp. 390–391):
  1. Every intra-tile wavefront has the same length, so every thread is active in every iteration: less warp divergence and under-utilisation.
  2. Fewer iterations per tile because each does more work: 5 for a 3×3 square tile versus 3 for a 3×3 hypertile.
  3. The last anti-diagonal of one tile feeds directly into the first anti-diagonal of the next tile, improving locality across blocks and possibly cache hits.
- **Coordinate mapping** (p. 391): if tile coordinates `(r_tile, q_tile)` map to matrix coordinates `(r, q)` under rectangular tiling, they map to `(r, q + m × r_tile)` after shearing; `m` is the **shear factor**. The example uses `m = −1`, i.e. `(r, q − r_tile)`.
- **Disadvantage** (p. 391): the "wavefront of tiles" changes. The tilted first tile leaves cells (1, 2), (2, 1), (2, 2) of the top-left square uncovered; tile (1, 0) needs them, so it must wait for tile (0, 1) (second iteration) and runs in the third. Incomplete tiles appear at the left and right edges of the matrix. The number of `d` iterations rises (5 → 8 in Fig. 16.14) and the number of tiles per iteration falls.
- **Counting host iterations** (p. 392): square tiles: `numTiles_x` wavefronts to reach the top-right corner, then `numTiles_x − 1` more; each block is one tile column ahead of the next block, total `2*numTiles_x − 1`. Hypertiles: each block must be **two** tile columns ahead of the next; the first tile row needs `numTiles_x + 1` iterations (one extra for the last incomplete tile) and each of the remaining `numTiles_x − 1` rows adds two, total `3*numTiles_x − 1`. In Fig. 16.14 the right-most matrix column is touched by 3 tiles under square tiling (5 wavefronts) and by 6 tiles under hypertiling (8 iterations).
- **Kernel differences** (pp. 392–394): `tile_col = d − 2*blockIdx.x` (the first row of a tile is the reference for its column index); the active test allows `tile_col <= numTiles_x`; the intra-tile loop bound is `tile_width` rather than `2*tile_width − 1`; `q_tile = d_tile` for every thread; the global column applies the shear; the bounds test only checks global `r` and `q`.
- **Shared-memory layout**: for simple indexing the hypertile is stored as a *square* in shared memory. Each thread stores its value for intra-tile wavefront `d_tile` in column `q_tile = d_tile` of that square (p. 394). Consequence: neighbour offsets inside the tile shift. The north neighbour is in row `r_tile − 1` but, because of the shear, in column `q_tile − 1` of the stored square. The book asks the reader to reason out `load_w` and `load_nw` the same way.
- **Zero-initialising the tile** (p. 395, Fig. 16.19): needed only in the hypertile kernel. All threads stay active, but the bounds check stops some from writing their shared-memory cell (their cell is outside the real matrix). Those unwritten cells may later be read through `load_n/w/nw`; initialising to 0 stops garbage being used.
- **Bank conflicts and padding** (pp. 395–396, Fig. 16.20): with the row-major square layout, bank conflicts occur if the hypertile width is a multiple or a divisor of the number of shared-memory banks. Fix: **padding**, one empty location after each tile row, so consecutive threads' addresses shift. Suggested macro: `pad(x)` = `(x + (x >> LOG_NUM_BANKS))`, where `LOG_NUM_BANKS` is log2 of the number of banks. Shared-memory allocation in the host launch must grow to `(threads * threads + ((threads * threads) >> LOG_NUM_BANKS)) * sizeof(int)`.
- **Work analysis** (p. 396): square tile, Eq. (16.3): `Σ_{i=1..n} i + Σ_{i=n+1..2n−1} (2n − i) = n²` over `2n − 1` iterations, about `n/2` cells per iteration. Hypertile, Eq. (16.4): `Σ_{i=1..n} n = n²` over `n` iterations, `n` cells per iteration. Same total work; the book concludes the hypertile is twice as efficient per iteration.
- Cost on the host side: up to 1.5× the number of wavefronts. If the matrix is large enough occupancy can still be good; the remaining penalty is kernel-call overhead, which §16.8's synchronisation technique can remove (p. 396).
- **Sidebar: Hyperplane Partitioning for Stencil Computation** (p. 397): the same idea applies to stencils (Chapter 8). In a Jacobi-style stencil with an outer time loop, there are wavefronts in both space and time. Toy 1D example: `A[i] = 0.5 * (A[i] + A[i+1])` inside `for t` / `for i` loops. With straightforward partitioning only cells with the same `t` run in parallel, with a global synchronisation after each `t`. Hypertiles in the time–space plane define intra-tile and inter-tile wavefronts, exposing more parallelism with fewer global synchronisations.

### §16.8 More optimizations (pp. 397–399)

- **Synchronisation across anti-diagonals of tiles** (pp. 397–398):
  - Relaunching the kernel makes each block wait for *all* blocks of the previous two anti-diagonals although it depends on only three of them. This can cause load imbalance and wasted compute slots on the streaming multiprocessors.
  - **Cooperative groups** (described as recently provided by CUDA; detailed in Chapter 18) can synchronise all threads in a warp, a block, several blocks, or the whole grid. Grid-level sync lets all blocks synchronise without relaunching, but requires **persistent thread blocks**, and the grid size must be at most the number of blocks that can run concurrently on the SMs. It still makes each block wait for all blocks of the previous two anti-diagonals.
  - **Array of flags**: one flag per tile, set when the tile is done. A block checks only two flags (tile above, tile to the left) and starts as soon as both are set. With persistent blocks assigned one per row of tiles, each block needs to check only one flag. The book likens this to the unidirectional synchronisation of Chapter 11 (Scan). Fig. 16.21 illustrates it.
  - The flag mechanism also applies to hypertiles; there the hypertile width sets both the number of synchronisation operations and the waiting time, so width is a tuning knob.
- **Small DP problems** (p. 398): the chapter assumed several blocks per scoring matrix, suited to long sequences (thousands of bp). For short sequences (hundreds of bp) one block or even one warp per alignment may be enough; such versions benefit from keeping tiles in registers and exchanging intermediate results with shuffle instructions (introduced in Chapter 10).
- **DPX instructions** (p. 398): since the NVIDIA Hopper architecture, CUDA has a class of SIMD instructions called DPX aimed at DP. Example: replace `max4()` with `__vimax3_s32_relu()`, which uses special hardware to compute the maximum of three inputs and 0. `[device: NVIDIA Hopper architecture and later]`

### §16.9 Summary (p. 399)

- DP divides problems into sub-problems recursively; bottom-up versions keep intermediate results in tables; dependencies between cells define wavefronts. Block-level tiling and hypertiles improve resource utilisation; inter-block synchronisation and DPX are further options.

### Fig. 16.1 — Fibonacci top-down and bottom-up (p. 375)
- Purpose: contrast memoized recursion with iterative tabulation. Plain C++ (host), no GPU code.
- Top-down, `int fibonacci_topdown(int n, std::unordered_map<int, int>& hash_table)`: line 4 returns the cached value if present; lines 6–8 recurse on `n-1` and `n-2` when `n` is neither 0 nor 1; line 10 base case `result = n`; line 11 stores; line 12 returns.
- Bottom-up, `int fibonacci_bottomup(int n)`: for `n` not 0 or 1, allocate `std::vector<int> table(n + 1, 0)`, set `table[0] = 0`, `table[1] = 1`, loop `i = 2..n` with `table[i] = table[i-1] + table[i-2]` (lines 8–10), return `table[n]`; otherwise return `n`.
- Lines that need care: none; the point is structural. The bottom-up code keeps the whole table although only the last two values are needed (p. 377).
- APIs: `std::unordered_map`, `std::vector`.

### Fig. 16.3 — Floyd-Warshall pseudo-code (p. 379)
- Purpose: show the loop structure and where the synchronisation sits.
- Walkthrough: line 2 `initialize(dist)` (direct neighbours get the edge weight, everything else infinity); line 4 sequential `for k in range(V)`; lines 6 and 8 `Parallel for_each i` / `j`; line 10 `dist[i][j] = min (dist[i][j], dist[i][k] + dist[k][j])`; line 13 `Synchronize` once per `k`.
- Care: the two inner loops are fully parallel; only `k` is sequential, and `k` may be visited in any order as long as each value is visited (comment on line 3 and p. 378).

### Fig. 16.4 — `FW_bottomup` kernel and host loop (p. 380)
- Signature: `__global__ void FW_bottomup(int k, int *dist, int n_vertices)`.
- Launch configuration (host snippet): `dim3 dimBlock(threads);` `dim3 dimGrid((n_vertices + threads - 1) / threads, n_vertices);` then `for(int k = 0; k < n_vertices; k++) { FW_bottomup<<<dimGrid, dimBlock>>>(k, dist, n_vertices); cudaDeviceSynchronize(); }`.
- Walkthrough:
  - Lines 4–6: `col = blockIdx.x * blockDim.x + threadIdx.x`; return if `col >= n_vertices`; `row = blockIdx.y`.
  - Line 9: `distIndex = n_vertices * row + col` (row-major).
  - Lines 11–15: `__shared__ int dist_k_col;` thread 0 loads `dist[n_vertices * row + k]` into it; `__syncthreads()`.
  - Lines 16–18: if `dist_k_col == INFINITY` every thread returns.
  - Lines 21–24: each thread reads `dist_k_row = dist[k * n_vertices + col]`; return if infinity.
  - Lines 27–29: `new_distance = dist_k_col + dist_k_row`; write if `new_distance < dist[distIndex]`.
- Lines that need care:
  - A single shared scalar is written by one thread and read by all after the barrier: one global read is reused by the whole block.
  - The two `INFINITY` early exits are described by the book as "vertex k is not on the shortest path". [derived] They also avoid adding to `INFINITY`.
  - In-place update is race-free only under the stated assumptions (non-negative distances, `dist[k][k] = 0`) (p. 380).
  - Line 5 returns before the `__syncthreads()` on line 15 for out-of-range threads in the last block of a row; the book does not comment on this. [derived] Thread 0 of a launched block always has `col < n_vertices`, so the shared value is always written.
  - `INFINITY` is used but not defined in the listing.
- APIs / qualifiers: `__global__`, `__shared__`, `__syncthreads()`, `blockIdx`, `blockDim`, `threadIdx`, `dim3`, `<<<…>>>`, `cudaDeviceSynchronize()`.

### Fig. 16.8 — host code, square tiling (p. 385)
- Verbatim core: `int L = L_seq + 1;` `int numTiles_x = (L_seq + threads - 1) / threads;` `int numBlocks = numTiles_x;` `for(unsigned int d = 0; d < 2 * numTiles_x - 1; d++){ sw_kernel_square<<<numBlocks, threads, threads * threads * sizeof(int)>>>(sw, rea, ref, L, d); }`
- The third launch parameter sizes the dynamically allocated shared-memory tile (`threads × threads` ints).
- Care: the maximum number of blocks is launched for every `d`; unused blocks exit at the kernel's `tile_col` test. No explicit host-side synchronisation call appears between launches in this listing (unlike Fig. 16.4).

### Fig. 16.9 — `sw_kernel_square` (p. 387)
- Signature: `__global__ void sw_kernel_square(int* sw, T* rea, T* ref, unsigned int L, unsigned int d)`. `sw` = scoring matrix (row-major, `L × L`), `rea`/`ref` = the two sequences, `d` = tile anti-diagonal.
- Assumes: 1D grid of `numTiles_x` blocks, 1D blocks of `tile_width` threads, dynamic shared memory of `tile_width² × sizeof(int)`.
- Walkthrough:
  - Line 2: `extern __shared__ int swTile[];`
  - Lines 3–4: `tile_width = blockDim.x`; `numTiles_x = (L-1+tile_width-1)/tile_width` (only the `(L−1) × (L−1)` interior is tiled).
  - Lines 6–8: `tile_row = blockIdx.x`; `tile_col = d - blockIdx.x`; proceed only if `tile_col >= 0 && tile_col < numTiles_x`.
  - Line 10: `for(int d_tile=0; d_tile<2*tile_width-1; d_tile++)`.
  - Lines 12–16: `r_tile = threadIdx.x`; `r = tile_width * tile_row + r_tile + 1`; `q_tile = d_tile - threadIdx.x`; `q = tile_width * tile_col + q_tile + 1`.
  - Line 18: `if(q_tile>=0 && q_tile<tile_width && r<L && q<L)`.
  - Lines 20–22: load `n`, `w`, `nw`.
  - Line 24: `int subs_val = (rea[r-1] == ref[q-1]) ? MATCH : MISMATCH;`
  - Line 26: `swTile[r_tile * tile_width + q_tile] = max4(0, nw + subs_val, w + DELETION, n + INSERTION);`
  - Line 28: `__syncthreads();` inside the `for`, outside the `if`.
  - Line 31: `store_tile(sw, swTile, L, tile_width, tile_row, tile_col);`
- Lines that need care:
  - The `+ 1` in `r` and `q` skips the boundary row/column; `rea[r-1]`, `ref[q-1]` convert back to 0-based sequence positions.
  - `__syncthreads()` is executed by every thread every iteration, active or not (it is outside the bounds `if`).
  - The penalties are *added* (`w + DELETION`, `n + INSERTION`), so the constants must be negative for this to match Eq. (16.2); `MATCH`, `MISMATCH`, `DELETION`, `INSERTION` and the type `T` are not defined in the listing.
  - [derived] `d` and `blockIdx.x` are unsigned; `tile_col` is declared `const int`, and the code relies on the difference becoming negative after conversion.
- APIs: `__global__`, `extern __shared__`, `__syncthreads()`, `blockDim`, `blockIdx`, `threadIdx`.

### Fig. 16.10 — `load_n`, `load_w`, `load_nw` (square tiles) (p. 388)
- Common signature: `__device__ inline int load_X(int* sw, int r, int q, unsigned int L, int* swTile, int r_tile, int q_tile, int tile_width)`.
- `load_n`: `return (r_tile == 0) ? sw[(r - 1) * L + q] : swTile[(r_tile - 1) * tile_width + q_tile];`
- `load_w`: `return (q_tile == 0) ? sw[r * L + (q - 1)] : swTile[r_tile * tile_width + (q_tile - 1)];`
- `load_nw`: `return (r_tile == 0 || q_tile == 0) ? sw[(r - 1) * L + (q - 1)] : swTile[(r_tile - 1) * tile_width + (q_tile - 1)];`
- Care: tile-edge cells read global memory (values written by an earlier kernel call, or boundary zeros); interior cells read shared memory.

### Fig. 16.11 — `max4` (p. 389)
- `__device__ inline int max4(int a, int b, int c, int d)`: `m = a; if(m < b) m = b; if(m < c) m = c; if(m < d) m = d; return m;`
- This is the function §16.8 proposes replacing with the DPX instruction `__vimax3_s32_relu()`.

### Fig. 16.12 — `store_tile` (square tiles) (p. 389)
- `__device__ inline void store_tile(int* sw, int* swTile, unsigned int L, int tile_width, int tile_row, int tile_col)`.
- Loop `for(int row = 0; row < tile_width; row++)`: `r = tile_width * tile_row + row + 1`; `q = tile_width * tile_col + threadIdx.x + 1`; `if(r < L && q < L) sw[r * L + q] = swTile[row*tile_width+threadIdx.x];`
- Care: here `threadIdx.x` selects the *column*; in each loop iteration the block writes one contiguous row segment, which is what makes the global writes coalesced (p. 389).

### Fig. 16.15 — host code, hypertiles (p. 392)

### Fig. 16.16 — `sw_kernel_hyper` (p. 393)

### Fig. 16.17 — `load_n`, `load_w`, `load_nw` (hypertiles) (p. 394)
- `load_n`: `return (r_tile == 0 || q_tile == 0) ? sw[(r - 1) * L + q] : swTile[(r_tile - 1) * tile_width + q_tile - 1];`
- `load_w`: `return (q_tile == 0) ? sw[r * L + (q - 1)] : swTile[r_tile * tile_width + (q_tile - 1)];`
- `load_nw`: `return (r_tile == 0 || q_tile == 0 || q_tile == 1) ? sw[(r - 1) * L + (q - 1)] : swTile[(r_tile - 1) * tile_width + (q_tile - 2)];`
- Why (book explains `load_n` only, p. 394; the rest is [derived]): a stored cell `(r_tile, q_tile)` sits at matrix column `base + q_tile − r_tile`. The north cell is one row up at the same matrix column, hence stored column `q_tile − 1`; west is same row, stored column `q_tile − 1`; north-west is one row up and one matrix column left, hence stored column `q_tile − 2`. When the stored column would be negative the value belongs to another tile and is read from global memory.

### Fig. 16.18 — `store_tile` (hypertiles) (p. 395)
- Same as Fig. 16.12 except the loop variable is `unsigned int row` and line 4: `int q=tile_width*tile_col+_shear(threadIdx.x, row)+1;`
- Bounds test is still `if(r < L && q < L)`. [derived] There is no `q >= 1` test here although `q` can be ≤ 0 for left-edge tiles; because `L` is `unsigned int`, a negative `int q` compares as a huge unsigned value and fails `q < L`, and `q == 0` would write a never-written (zero-initialised) tile cell onto a boundary zero. The book does not discuss this.

### Fig. 16.19 — `initialize_tile` (p. 395)
- `__device__ inline void initialize_tile(int* swTile, int tile_width)`: `for(unsigned int row = 0; row < tile_width; row++){ swTile[row * tile_width + threadIdx.x] = 0; }` then `__syncthreads();`
- Each thread clears one column; the barrier makes the cleared tile visible before the compute loop.
- [derived] Zero is also the Smith-Waterman boundary value, so out-of-matrix neighbours read as boundary cells.

## Relevance to LLM-inference kernels

Candid summary: the two case-study algorithms are not LLM-inference operations. What transfers is the reasoning about dependencies and three specific kernel-engineering techniques. A course can keep roughly a third of this chapter and compress the rest.

**Transferable techniques (keep)**

- **Dependency-driven scheduling.** Separate what must be ordered from what can run together, then pick the cheapest synchronisation that enforces exactly those dependencies: kernel relaunch (global), `__syncthreads()` (block), or flags between specific blocks (pp. 384, 397–398). The 2-SM schedule in Fig. 16.21 is a clear picture of why a global barrier wastes slots. Direct uses in decoding: anything with a recurrence along sequence or time. The book itself lists Viterbi and dynamic time warping as DP (p. 374); [derived] beam-search scoring, CTC/forced-alignment and edit-distance style post-processing have the same anti-diagonal or row wavefront shape.
- **Tile in shared memory, then store coalesced** (pp. 384, 389): compute a tile with an awkward access order in shared memory, then write it out row by row. Same structure as tiled GEMM; the role switch of `threadIdx.x` between compute and store (Figs. 16.9, 16.12) is worth showing.
- **Tilting tiles (shear) to equalise work per step** (pp. 390–396): a general idea for keeping every thread of a warp busy when the natural iteration space is triangular. [derived] The closest LLM analogue is causal (lower-triangular) attention masks and other triangular iteration spaces, where a re-indexing can give uniform-width steps. This is our analogy, not the book's.
- **Shared-memory bank-conflict padding** (pp. 395–396, Fig. 16.20): applies to any kernel that strides through a shared-memory tile.
- **In-place update safety argument** (p. 380): proving that the cells read by other threads do not change during a step, so double buffering is unnecessary. Useful habit for in-place ops.
- **Why recursion and hash tables are poor GPU patterns** (p. 376): two-sentence takeaway.
- **Work-per-iteration analysis** (Eqs. 16.3–16.4): a small, reusable way to compare two schedules with equal total work.
- [derived] Floyd-Warshall's inner update is a min-plus rank-1 update (column `k` combined with row `k`), structurally the same broadcast pattern as an outer product; the Fig. 16.4 trick of loading the shared operand once per block carries over to GEMM-like kernels. The integer max-with-zero in `max4` / `__vimax3_s32_relu` is a ReLU-style integer max, loosely relevant to quantised ops.

**Domain material (compress or skip)**

- Genomics background, the meaning of homology scores, insertion/deletion semantics, traceback (pp. 382–384).
- The four named patterns in Fig. 16.2 beyond "constant versus changing wavefront size".
- Graph-theory framing of Floyd-Warshall beyond the recurrence.
- Fibonacci code details.

**By target operation**

- matmul/GEMM: indirect (shared-memory tiling + coalesced store, bank padding, shared-operand broadcast).
- attention: little direct relevance; triangular-domain scheduling analogy only.
- quantized ops: little direct relevance; integer max/ReLU via DPX is the only touch point.
- sampling (softmax, top-k/top-p, argmax): little direct relevance. Sequence-level decoding algorithms (Viterbi, beam search) are where wavefront thinking applies.

## Portability notes

The chapter states nothing about HIP or Metal. Every HIP/Metal remark below is `[unverified]`.

- `__global__`, `__device__ inline`, `<<<grid, block, sharedBytes>>>` launch, `dim3`, `blockIdx`/`blockDim`/`threadIdx` (Figs. 16.4, 16.8, 16.9). HIP: expected to accept the same kernel syntax `[unverified]`. Metal: needs a compute-kernel entry point with thread-position built-ins and an explicit threadgroup size `[unverified]`.
- `__shared__` scalar (Fig. 16.4) and `extern __shared__ int swTile[]` sized by the third launch argument (Figs. 16.9, 16.16). A port needs per-block (threadgroup) scratch memory whose size can be chosen at launch; whether Metal allows a run-time size is `[unverified]`.
- `__syncthreads()` used once per intra-tile wavefront. A port needs a block-level barrier that is legal inside a loop `[unverified]`. Note the book's code calls it after some threads have returned (Fig. 16.4) and from inside a device function (Fig. 16.19); check both patterns on the target `[unverified]`.
- `cudaDeviceSynchronize()` after each launch (Fig. 16.4) and reliance on ordered kernel launches for global synchronisation (Fig. 16.8). A port needs an equivalent "wait for completion" or guaranteed in-order execution of submitted kernels `[unverified]`.
- Shared-memory banks and the `pad()` trick (p. 395): bank structure is a property of NVIDIA SMs as described by the book; whether other GPUs have the same conflict behaviour is `[unverified]`.
- Cooperative groups, grid-level sync, persistent thread blocks (p. 398): CUDA feature; availability elsewhere `[unverified]`. The flag-array scheme needs only global memory plus a visibility guarantee between blocks; the memory-ordering primitives required are not specified in this chapter.
- DPX `__vimax3_s32_relu()` (p. 398): tied by the book to NVIDIA Hopper. A port keeps `max4()` `[unverified that no equivalent exists]`.
- Warp shuffle instructions for register-held tiles (p. 398): CUDA-specific as presented; equivalents `[unverified]`.
