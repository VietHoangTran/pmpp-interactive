# Chapter 10 — Reduction (And mitigating control divergence)

- **Book pages:** 221–250  **PDF pages:** 248–277 (pdf = book + 27)
- **In one paragraph:** A reduction collapses a list into one value with a binary operator (sum, max, min, product). The chapter builds a parallel sum reduction from scratch and uses it to expose, one at a time, the bottlenecks that any cooperating-threads kernel hits: control divergence, uncoalesced memory access, global-memory traffic, barrier-synchronisation overhead, the one-block limit, and hardware underutilisation. It moves from a reduction-tree model (work, span, associativity, commutativity) through seven kernels: a simple in-place tree, a "convergent" tree with shrinking stride, a shared-memory version, a version whose last iterations use the warp shuffle primitive `__shfl_down_sync`, a two-stage warp-wide reduction, a multi-block version that commits with an atomic add, and a thread-coarsened version. After the chapter a reader can draw the access pattern of each kernel, compute its resource-utilisation efficiency and memory-request counts, write a warp-level reduce, and choose a coarsening factor argument for a given input size.

Legend used in these notes: **[book]** = stated in the PDF; **[inferred]** = our deduction, not printed in the book.

## Concepts

### Chapter opening (p. 221)
- A reduction derives one value from a list: sum, maximum, minimum, etc. Element type can be integer, single/double/half-precision float, characters; the computation structure is the same for all (p. 221).
- Like histogram, reduction summarises large data. In parallel form the threads must coordinate, and careless coordination creates bottlenecks, which is why the chapter uses it as a teaching vehicle (p. 221).

### §10.1 Background (pp. 221–223)
- Definition: a reduction turns a set of items into one item using a **binary operator** (p. 221). Example: sum of {7.0, 2.1, 5.3, 9.0, 11.2} = 34.6 (p. 222).
- Sequential sum (Fig. 10.1): start `sum` at the operator's **identity value** (0.0 for addition) and accumulate each element. Trace given: 7.0 after the first iteration, 9.1 after the second, 34.6 at the end (p. 222).
- Identity value (footnote 1, p. 222): the value that, used as one input, makes the operator return the other input unchanged. Using it is a convenience; if an operator has no identity, initialise with element 0 and start the loop at `i=1`.
- Other reductions: product (identity 1.0), min (identity +infinity for real numbers), max (identity -infinity) (p. 222).
- General form (Fig. 10.2): `acc = IDENTITY;` then `acc = Operator(acc, input[i])` for each element; `Operator` is a two-input function (e.g. returns the larger input for max). N elements take N iterations (pp. 222–223).
- Libraries: C++ `std::accumulate` and `std::reduce` (different variants of reduction); CUDA libraries Thrust [refs 1, 2] and CUB [ref 3] have highly optimised GPU reductions. The chapter implements it by hand because it demonstrates many optimisation techniques (p. 223).

### §10.2 Reduction trees (pp. 223–227)
- **Reduction tree** (Fig. 10.3): time flows downward; operations in the same row run in parallel. For 8 inputs: 4 operations in the first step, 2 in the second, 1 in the third (pp. 223–224).
- Parallel reduction changes the **order of operations**. Sequential max on 3, 1, 7, 0, ... compares acc(-inf) with 3, then 3 with 1, then 3 with 7. The tree instead compares 7 with 0 before combining with max(3, 1) (p. 224).
- Requirement 1, **associativity**: (a Θ b) Θ c = a Θ (b Θ c). Then parentheses can be placed anywhere without changing the result (p. 224).
  - Integer addition is associative: (1+2)+3 = 1+(2+3). Footnote 2 (p. 224): not exactly so in C++, because the order may change whether overflow/underflow occurs, which is undefined behaviour; fine if the programmer knows overflow cannot occur.
  - Integer subtraction is not: (1-2)-3 != 1-(2-3). It can be rewritten as addition of negated operands: (1+(-2))+(-3) = 1+((-2)+(-3)) (p. 224).
  - Floating-point addition is associative mathematically but **not strictly in floating point**, because rounding depends on the parenthesisation. Applications that accept results within a tolerance let developers and compilers treat it as associative. Appendix A has the details (p. 224).
- The two orders as parenthesisations (p. 225):
  - Sequential (Fig. 10.2): `((((((3 max 1) max 7) max 0) max 4) max 1) max 6) max 3`
  - Tree (Fig. 10.3(a)): `((3 max 1) max (7 max 0)) max ((4 max 1) max (6 max 3))`
- Requirement 2 (needed from §10.4 on), **commutativity**: a Θ b = b Θ a, so operands may be reordered, not just re-parenthesised. Max, min, addition and multiplication are commutative; subtraction is not (1-2 != 2-1) (p. 225). Footnote 3 (p. 225): floating-point max/min are not exactly commutative when an operand is NaN (see the IEEE floating-point standard); fine if inputs contain no NaN.
- "Reduction tree" is not a tree data structure: the edges are conceptual information flow from one time step to the next (p. 225).
- **Work** = number of operations performed. **Span** = time needed assuming infinite resources, measured in **steps**; a step is a period in which all or some threads each execute one operation in parallel (p. 225).
  - Vector addition kernel (Ch. 2): O(N) work, O(1) span; sequential vector addition: O(N) span. For sequential algorithms work and span coincide (pp. 225–226).
  - Reduction tree: N/2 + N/4 + N/8 + ... + 1 = **N - 1** operations, so O(N) work, the same as sequential. Chapter 11 will show parallel algorithms that do more work than the sequential one, which leads to the notion of **work efficiency** (p. 226).
  - Span is log2 N steps, O(log N). N = 1024: 10 steps; needs 512 execution resources in step 1 and 1 in the last (p. 226).
  - **Average parallelism** = (N - 1) / log2 N = 102.3 for N = 1024, against a **peak** of 512. This variation in parallelism and resource use is what makes reduction trees awkward for parallel hardware (p. 226).
- Sidebar "Parallel Reduction in Sports and Competitions" (pp. 226–227, Fig. 10.4): a knockout tournament is a max reduction tree where "max" returns the team that wins. 8 teams: 4 winners after the quarter-finals, 2 after the semi-finals, 1 after the final. 1024 teams need 10 rounds (512, 256, 128, ... games per round); about sixty thousand teams need 16 rounds. Trees are fast but resource-hungry (stadiums, staff). The four 2010 quarter-finals used three cities; the two Johannesburg games were on different days, i.e. sharing a resource between two operations lengthens the reduction. The same trade-off returns in §10.10.
- Fig. 10.3(b), the sum tree for 8 values: log2 8 = 3 steps and at most four adders. This is the example the kernels implement (p. 227).

### §10.3 A simple reduction kernel (pp. 227–230)
- A tree needs collaboration among all threads, which is not possible across a whole grid, so start with **one block**. For N elements launch one block of N/2 threads; with at most 1024 threads per block this handles at most **2048 elements** (lifted later) (pp. 227–228).
- Step 1: all N/2 threads each add two elements. Each later step: half the threads drop out. Last step: one thread produces the total (p. 228).
- Simple kernel (Fig. 10.5, Fig. 10.6): input is in global memory and is overwritten in place. Thread `t` **owns** location `2*t` (even locations) and is the only writer of it: an owner-computes design (p. 228).
- `stride` starts at 1 and doubles (1, 2, 4, 8, ...). An active thread adds `input[i + stride]` into its own `input[i]`. Thread 0: adds input[1] (first iteration), then input[2] (which by then holds original 2+3), and so on; at the end input[0] holds the total and thread 0 writes it to `*output` (pp. 228–229).
- Which threads are active: in the iteration with stride 2^n, those whose `threadIdx.x` is a multiple of 2^n; the test is `threadIdx.x % stride == 0`. All threads run the same code; inactive ones skip the add (pp. 229–230).
- `__syncthreads()` inside the loop guarantees all partial sums of an iteration are written before any thread starts the next iteration (p. 230).
- **Memory fence** remark (p. 230): data written to global memory by one thread should not be read by other threads without executing a memory fence operation. Because writers and readers here are in the same block, `__syncthreads()` at the end of each iteration "also serves as a memory fence operation for threads within the same block". The rules for data exchange through memory are the **memory consistency model**; see the CUDA programming guide.

### §10.4 Reducing control divergence (pp. 230–234)
- Problem: the active threads of the simple kernel are spread evenly through every warp. In the second iteration half of each warp's 32 threads are active, in the third a quarter, and by the sixth iteration one of 32, wasting 31/32 of the warp's execution resources. The book defines **execution resource utilization efficiency** as the share of consumed resources that produce useful results (p. 230).
- 256-element example (128 threads = 4 warps), simple kernel (pp. 230–231):
  - Iterations 1–6: all 4 warps active with the same divergence pattern.
  - Iteration 7: warps 1 and 3 fully inactive (no divergence); warps 0 and 2 have one active thread each.
  - Iteration 8: only warp 0 active, with one thread.
- Resources consumed (every active warp costs all 32 thread slots however few threads are active), general form (p. 231): `(N/64*6 + N/64*1/2 + N/64*1/4 + ... + 1) * 32`. N/64 is the number of warps (N/2 threads, 32 per warp); all warps are active for 6 iterations, then the count halves each iteration. For N = 256: (4*6 + 2 + 1) * 32 = **864**.
- Results committed = total active threads over all iterations (p. 231): `N/64*(32+16+8+4+2+1) + N/64*1/2*1 + N/64*1/4*1 + ... + 1`. For N = 256: 4*63 + 2 + 1 = **255** (as expected: reducing 256 values takes 255 operations).
- Efficiency of the simple kernel for N = 256: 255/864 = **0.30** (p. 231).
- Per-iteration table for N = 256 [inferred from the kernels; totals match the book]:

  | Iteration | Simple kernel stride | Active threads | Active warps | Convergent kernel stride | Active threads | Active warps |
  |---|---|---|---|---|---|---|
  | 1 | 1 | 128 | 4 | 128 | 128 | 4 |
  | 2 | 2 | 64 | 4 | 64 | 64 | 2 |
  | 3 | 4 | 32 | 4 | 32 | 32 | 1 |
  | 4 | 8 | 16 | 4 | 16 | 16 | 1 |
  | 5 | 16 | 8 | 4 | 8 | 8 | 1 |
  | 6 | 32 | 4 | 4 | 4 | 4 | 1 |
  | 7 | 64 | 2 | 2 | 2 | 2 | 1 |
  | 8 | 128 | 1 | 1 | 1 | 1 | 1 |
  | Total | | 255 | 27 (x32 = 864) | | 255 | 12 (x32 = 384) |

- Diagnosis: partial sums, and hence the active threads that own them, drift further apart over time (p. 231–232).
- Fix (Fig. 10.7, Fig. 10.8): make stride **decrease**. Threads own the **first half** of the array (`i = threadIdx.x`). First iteration: each thread reaches half-way across (thread 0 adds input[8] to input[0], thread 1 adds input[9] to input[1] for 16 elements). Each later iteration: the active half shrinks to the lowest-indexed threads, and each adds the element "number of active threads" away (p. 232).
- This reorders the **operands**, not just the parentheses: effective order is {input[0], input[8], input[1], input[9], ..., input[7], input[15]}. So the operator must be **commutative as well as associative** (pp. 232–233).
- Three code changes relative to Fig. 10.5 (p. 233): `i = threadIdx.x` instead of `2*threadIdx.x`; stride starts at `blockDim.x` and halves down to 1; active test is `threadIdx.x < stride`.
- Why this helps although the number of active threads per iteration is unchanged: what matters is **where** the active threads are. For 256 elements, in the second iteration threads 0–63 are active and 64–127 inactive, i.e. warps 0–1 entirely active and warps 2–3 entirely inactive. Every warp is uniform, so no divergence (pp. 233–234).
- Divergence is not eliminated: once fewer than 32 threads are active (the last five iterations: 16, 8, 4, 2, 1 active threads) the single remaining warp diverges (p. 234).
- Resources consumed by the convergent kernel (p. 234): `(N/64*1 + N/64*1/2 + ... + 1 + 5*1) * 32`. For N = 256: (4 + 2 + 1 + 5) * 32 = **384**; efficiency 255/384 = **66%**. Because warps take turns on an SM with limited resources, total execution time also improves (p. 234).
- Moral: a tiny code change with a large effect; making it confidently requires understanding how threads execute on SIMD hardware (p. 234).

### §10.5 Reducing memory access divergence (pp. 234–235)
- Second problem of the simple kernel: accesses are not coalesced. Each active thread per iteration does two global reads (its own location; the location one stride away) and one global write (its own location). Owned locations of adjacent threads are not adjacent (pp. 234–235).
- First iteration: a warp's locations are 2 elements apart, so twice as many global memory transactions as a coalesced access, and half the returned data is unused. Second iteration: 4 apart, four times the transactions, one quarter used. It gets worse as stride grows, until a warp has a single active thread and makes one request (p. 235).
- Book's count of global memory requests for the simple kernel (p. 235): `(N/64*5*2 + N/64*1 + N/64*1/2 + N/64*1/4 + ... + 1) * 3`. First term: five iterations in which every warp has two or more active threads and its divergent accesses trigger two requests; then one request per warp with one active thread, halving each iteration; x3 for two reads and one write. For N = 256: (4*5*2 + 4 + 2 + 1) * 3 = **141**.
- Convergent kernel: adjacent threads always touch adjacent locations, so every access is coalesced; inactive warps make no requests. The only under-use is when the data requested is smaller than one memory transaction. DRAM bandwidth is limited, so this kernel is "likely to be significantly better" (p. 235).
- Conclusion (p. 235): the convergent kernel wins on both execution resources and DRAM bandwidth, from reduced divergence and improved coalescing.

### §10.6 Reducing global memory accesses (pp. 236–237)
- Remaining waste: every iteration writes partial sums to global memory and rereads them. Some of that may hit the last-level cache, but there are "still significant latency and bandwidth limitations" there. Shared memory has much lower latency and higher bandwidth than both the last-level cache and global memory (p. 236).
- Shared-memory kernel (Fig. 10.9, Fig. 10.10): each thread loads its two original elements from global memory, adds them, and stores the result in a `__shared__` array. That is the first tree level, so the loop starts at `blockDim.x/2`. `__syncthreads()` moves to the **top** of the loop body so the initial shared-memory writes are synchronised before the first iteration. Thread 0 writes the result to `output` (p. 236).
- Counts (pp. 236–237): global accesses drop to N reads + 1 write = **N + 1**. Both reads are coalesced, so only **(N/32) + 1** global memory requests. For 256 elements: from **36** (convergent kernel) to 8 + 1 = **9**, a 4x improvement.
- Side benefit: the input array is no longer modified (p. 237).

### §10.7 Reducing synchronization overhead with warp-level primitives (pp. 237–241)
- Observation: in the shared-memory kernel, from stride 32 onward only one warp is active. CUDA offers **warp-level primitives** that let threads of the same warp share data and synchronise in ways unavailable across warps, avoiding shared memory and `__syncthreads()` (p. 237).
- `__syncwarp()`: like `__syncthreads()` at warp level. All threads in the warp reach the call before any proceeds; in particular it makes diverged threads of the warp reconverge (p. 237).
- **Warp shuffle functions**: let threads of a warp exchange ("shuffle") data directly between their **registers**, with no shared memory and no `__syncthreads()` (pp. 237–238).
- `__shfl_down_sync` (Fig. 10.11, p. 238): `T __shfl_down_sync(unsigned mask, T var, unsigned int delta);`
  - `mask`: which threads of the warp are to be active when executing the shuffle.
  - `var`: the value the sending thread passes.
  - `delta`: how much higher the sending thread's index is than the receiving thread's.
  - Return value for thread `i`: the value of `var` in thread `i + delta`, assuming both threads have their bits set in `mask`.
- Helper device functions (pp. 238–239): `warpIdx()` returns `threadIdx.x/WARP_SIZE` (threads 0–31 give 0, 32–63 give 1, ...); `laneIdx()` returns `threadIdx.x%WARP_SIZE`, the **lane index**, i.e. the index of the thread within its warp (thread 32 has lane 0, thread 33 lane 1).
- `warp_reduce` (Fig. 10.13, pp. 239–240): called by all threads of a warp, each passing its value. Stride goes 16, 8, 4, 2, 1; in each iteration every thread adds the partial sum of the thread `stride` lanes above it. After the loop the full sum is in **lane 0's** `partialSum`; the function returns each thread's `partialSum`, with the understanding that only the first thread's return value is the true result (p. 240).
- Hybrid kernel (Fig. 10.12, Fig. 10.14, pp. 240–241): shared-memory tree with `__syncthreads()` while more than one warp is active (loop runs while `stride >= WARP_SIZE`); then warp 0 loads its 32 values from shared memory into registers and finishes with `warp_reduce`. Shared-memory accesses and barriers are eliminated "from the iterations with stride 16 onwards" (p. 241).
- Fig. 10.12 is drawn with a toy block of 4 warps of 4 threads; a real 1024-thread block has 32 warps of 32 threads (p. 238).
- **Width parameter** (p. 241): `__shfl_down_sync` and other warp-level primitives take an additional optional parameter giving the width of the cooperating group. Default 32 (whole warp). A width of 8 treats the warp as four independent groups of eight threads.
- Other shuffle functions: `__shfl_sync`, `__shfl_up_sync`, `__shfl_xor_sync` (see the CUDA C++ Programming Guide) (p. 241).
- Other families of warp-level primitives (p. 241): **warp voting functions** (which threads in a warp meet a condition; an example comes in Chapter 12), **warp match functions** (which threads hold the same value of some parameter), and **warp reduce functions** (warp-wide reductions "for integer values"). No function names are given for these.

### §10.8 Further reducing synchronization overhead with two-stage warp-wide reduction (pp. 241–244)
- The hybrid kernel still pays shared-memory and barrier overhead in the early iterations. Idea: use warp-wide reduction at the start as well (p. 241).
- Two stages (Fig. 10.15, Fig. 10.16, pp. 241–243):
  1. Each thread loads and adds its two elements into a register; each warp runs `warp_reduce` independently (all warps active throughout).
  2. Lane 0 of each warp writes the warp's sum to a shared array indexed by warp; one `__syncthreads()`.
  3. Warp 0 loads those per-warp sums (one per thread) and runs `warp_reduce` again; thread 0 writes the result.
- Why one warp suffices for stage 2 (footnote 5, p. 243): at most 1024 threads per block and 32 per warp means at most 32 warps, hence at most 32 partial sums.
- Footnote 4 (p. 242): still assumes one block reducing up to 2048 elements, which is why all warps can exchange data through shared memory.
- Trade-off the book states (p. 243): shared memory and barrier are needed only once, at the stage boundary. But where the hybrid kernel deactivated whole warps each iteration without divergence, here all warps stay active through stage 1 and within each warp "not all threads perform useful work in every shuffle operation", which the book describes as suffering "from more control divergence". So it trades more control divergence for fewer shared-memory accesses and barriers.
- Why it is worth it (pp. 243–244): once the data is loaded, the rest of the kernel is **latency bound**. Removing shared-memory accesses and barriers removes long-latency instructions. Removing divergent warps does not help a latency-bound kernel much, because the saved execution cycles "will likely be replaced by stall cycles".

### §10.9 Reduction for arbitrary length inputs (pp. 244–246)
- All kernels so far need one block because `__syncthreads()` only works within a block, capping parallelism at 1024 threads "on current hardware". There is no good barrier across blocks, so blocks must run independently (p. 244).
- Multi-block scheme (Fig. 10.17, Fig. 10.18): split the input into segments of `2*blockDim.x` elements (2048 for 1024-thread blocks; block 0 starts at 0, block 1 at 2048, block 2 at 4096). Each block reduces its segment with any of the single-block methods, and its leader thread (thread 0) **atomically adds** the block's sum into `*output` (pp. 244–245).
- Atomics give mutual exclusion but **not ordering**, so blocks contribute in arbitrary order. The operator must therefore be both commutative and associative (p. 245).
- Alternatives without atomics (pp. 245–246): leaders write to a partial-sum array indexed by block; then (a) launch a second, single-block kernel to reduce that array, or (b) copy it to the host and finish on the CPU. These make sense "in systems where atomic operations are not available or are too expensive" and give the programmer more control over accumulation order.

### §10.10 Thread coarsening to reduce overhead (pp. 246–248)
- So far: N/2 threads for N elements, i.e. N/2048 blocks of 1024 threads. On hardware that can only run some of those blocks at once, the surplus blocks are serialised by the hardware (p. 246).
- Parallelising has a price: in each successive tree stage more threads are idle, and this underutilised phase is paid **for every block launched**. Unavoidable if blocks truly run in parallel; but if the hardware would serialise them anyway, it is better to serialise the work ourselves more efficiently. **Thread (granularity) coarsening** (from Ch. 6) serialises some work into fewer threads to cut parallelisation overhead (p. 246).
- Fig. 10.19: versus Fig. 10.9 (16 elements per block, 2 per thread), coarsening by a factor of two gives 32 elements per block, 4 per thread. Each thread adds its four elements independently as it loads them (three add steps), with all threads active and no synchronisation, and only then does the tree start (p. 246).
- Code (Fig. 10.20): segment start gains a factor `COARSE_FACTOR`; a coarsening loop adds `COARSE_FACTOR*2` elements per thread, strided by the block size; no `__syncthreads()` in that loop (p. 247).
- Step accounting, Fig. 10.21 (pp. 247–248):
  - (a) two original blocks run one after the other: each block has 1 fully-utilised step (the initial pairwise add) + 3 tree steps where half the threads drop out each time and which need barrier + shared memory. Total **8 steps: 2 fully utilised, 6 underutilised**.
  - (b) one block coarsened by two doing the same work: 3 fully-utilised independent add steps + 3 tree steps. Total **6 steps: 3 fully utilised, 3 underutilised**.
- Limits (p. 248): coarsening reduces the data parallelism exploited. If so few blocks are launched that the hardware is not full, performance is lost. The best factor leaves just enough blocks to fully utilise the hardware; it depends on the input size and the specific device.

### §10.11 Summary (p. 249)
- Techniques listed: thread index assignment for reduced divergence; shared memory for fewer global accesses; warp-level primitives for fewer barriers and shared-memory accesses; multi-block reduction with atomics; thread coarsening.
- Reduction is the foundation for the prefix-sum pattern (next chapter).
- In practice use Thrust or CUB rather than hand-writing a reduction.

## Code listings

### Fig. 10.1 — sequential sum reduction (p. 222)
- Fragment, no function header: `sum = 0.0f;` then `for(i = 0; i < N; ++i) { sum += input[i]; }`.

### Fig. 10.2 — general sequential reduction (p. 222)
- Fragment: `acc = IDENTITY;` then `for(i = 0; i < N; ++i) { acc = Operator(acc, input[i]); }`.

### Fig. 10.5 — `SimpleSumReductionKernel` (p. 228)
- Purpose: in-place tree reduction within one block. Signature: `__global__ void SimpleSumReductionKernel(float* input, float* output)`.
- Launch configuration: one block of N/2 threads for N elements; N at most 2048 (p. 228).
- Walkthrough: line 02 `unsigned int i = 2*threadIdx.x;` (owned location). Line 03 `for (unsigned int stride = 1; stride <= blockDim.x; stride *= 2)`. Line 04 `if (threadIdx.x % stride == 0)`. Line 05 `input[i] += input[i + stride];`. Line 07 `__syncthreads();` (inside the loop, after the `if`). Lines 09–11: `if(threadIdx.x == 0) { *output = input[0]; }`.
- Care: destroys the input array. The barrier is executed by all threads, active or not. Divergent and uncoalesced by construction.
- APIs: `threadIdx`, `blockDim`, `__syncthreads()`.

### Fig. 10.8 — `ConvergentSumReductionKernel` (p. 233)
- Purpose: same result with contiguous active threads and coalesced accesses. Same signature and launch as Fig. 10.5.
- Differences from Fig. 10.5 (verbatim lines):
  - Line 02: `unsigned int i = threadIdx.x;`
  - Line 03: `for (unsigned int stride = blockDim.x; stride >= 1; stride /= 2) {`
  - Line 04: `if (threadIdx.x < stride) {`
  - Line 05 unchanged: `input[i] += input[i + stride];`
- Care: requires a commutative operator. The tree halves cleanly only when the block size is a power of two [inferred; not stated]. Still overwrites the first half of the input.

### Fig. 10.10 — `SharedMemorySumReductionKernel` (p. 237)
- Purpose: do the first level while loading from global memory, keep the rest in shared memory.
- Signature as printed: `__global__ void SharedMemorySumReductionKernel(float* input)` (the body nevertheless writes `*output`; see "Unclear").
- Walkthrough: line 02 `__shared__ float input_s[BLOCK_DIM];`. Line 03 `unsigned int t = threadIdx.x;`. Line 04 `input_s[t] = input[t] + input[t + BLOCK_DIM];`. Line 05 `for (unsigned int stride = blockDim.x/2; stride >= 1; stride /= 2) {`. Line 06 `__syncthreads();`. Lines 07–09 `if (threadIdx.x < stride) { input_s[t] += input_s[t + stride]; }`. Lines 11–13 `if (threadIdx.x == 0) { *output = input_s[0]; }`.
- Care: the barrier is at the **top** of the loop body, so it also separates the initial shared-memory writes from the first iteration. After the final iteration (stride 1) only thread 0 wrote, and thread 0 is the one that reads `input_s[0]`, so no barrier is needed after the loop [inferred]. `BLOCK_DIM` is a compile-time constant that must equal the launched `blockDim.x` [inferred].
- APIs: `__shared__`, `__syncthreads()`.

### Fig. 10.13 — `warp_reduce` (p. 240)
- Purpose: warp-wide sum using register shuffles only. Signature: `__device__ __inline__ float warp_reduce(float val)`.
- Body (verbatim core):
  - `float partialSum = val;`
  - `for(unsigned int stride = WARP_SIZE/2; stride > 0; stride /= 2) {`
  - `partialSum += __shfl_down_sync(0xffffffff, partialSum, stride);`
  - `}` then `return partialSum;`
- Walkthrough: with 32 lanes, stride 16 makes lanes 0–15 absorb lanes 16–31; stride 8 makes lanes 0–7 absorb 8–15; and so on to stride 1. Lane 0 ends with the sum of all 32 inputs. Mask `0xffffffff` = all 32 lanes participate.
- Care: there is no `if`; every lane executes every shuffle and add. Only lane 0's return value is meaningful. The book does not say what a lane receives when `i + stride` is past the end of the warp.
- APIs: `__device__`, `__inline__`, `__shfl_down_sync`, `WARP_SIZE` (constant, 32).

### Fig. 10.14 — `WarpLevelSumReductionKernel` (p. 240)
- Purpose: shared-memory tree until one warp remains, then `warp_reduce`. Signature: `__global__ void WarpLevelSumReductionKernel(float* input, float* output)`.
- Walkthrough: lines 02–04 as Fig. 10.10. Line 05 `for (unsigned int stride = blockDim.x/2; stride >= WARP_SIZE; stride /= 2) {` with barrier and conditional add as before (lines 06–09). Line 11 `__syncthreads();` after the loop. Line 12 `if(warpIdx() == 0) {`. Line 13 `float partialSum = input_s[t];`. Line 14 `partialSum = warp_reduce(partialSum);`. Lines 15–17 `if (threadIdx.x == 0) { *output = partialSum; }`.
- Care: the loop's last iteration is stride 32, leaving 32 values in `input_s[0..31]`; the extra barrier on line 11 makes those writes visible before warp 0 reads them. Uses the helpers `warpIdx()` / `laneIdx()` defined on pp. 238–239:
  - `__device__ unsigned int warpIdx() { return threadIdx.x/WARP_SIZE; }`
  - `__device__ unsigned int laneIdx() { return threadIdx.x%WARP_SIZE; }`

### Fig. 10.16 — `TwoStageWarpLevelSumReductionKernel` (p. 243)
- Purpose: per-warp register reduction, one shared-memory hand-off, final warp reduction. Signature: `__global__ void TwoStageWarpLevelSumReductionKernel(float* input, float* output)`.
- Walkthrough:
  - Line 03 `unsigned int t = threadIdx.x;`. Line 04 `float partialSum = input[t] + input[t + BLOCK_DIM];`. Line 05 `partialSum = warp_reduce(partialSum);` (all warps).
  - Line 07 `__shared__ float partialSums_s[BLOCK_DIM/WARP_SIZE];`. Lines 08–10 `if(laneIdx() == 0) { partialSums_s[warpIdx()] = partialSum; }`. Line 11 `__syncthreads();`.
  - Line 13 `if(warpIdx() == 0) {`. Line 14 `float partialSum = partialSums_s[t];`. Line 15 `partialSum = warp_reduce(partialSum);`. Lines 16–18 `if (threadIdx.x == 0) { *output = partialSum; }`.
- Care: exactly one barrier. In stage 2 every one of warp 0's 32 threads reads `partialSums_s[t]`, so the array must hold 32 valid entries, i.e. `BLOCK_DIM/WARP_SIZE == 32`, a 1024-thread block [inferred; see "Unclear"].

### Fig. 10.18 — `reduce_kernel`, multi-block with atomic commit (p. 245)
- Purpose: arbitrary-length sum; each block reduces a `2*blockDim.x` segment. Signature: `__global__ void reduce_kernel(float* input, float* output, unsigned int N)`.
- Launch: N/(2*blockDim.x) blocks (p. 246 gives N/2048 for 1024-thread blocks). `*output` must hold the identity (0) before launch [inferred].
- Walkthrough:
  - Line 03 `unsigned int segment = 2*blockDim.x*blockIdx.x;`. Line 04 `unsigned int i = segment + threadIdx.x;`. Line 05 `float partialSum = input[i] + input[i + BLOCK_DIM];`. Line 06 `partialSum = warp_reduce(partialSum);`.
  - Line 08 `__shared__ float partialSums_s[BLOCK_DIM/WARP_SIZE];`. Lines 09–11 `if(threadIdx.x%WARP_SIZE == 0) { partialSums_s[threadIdx.x/WARP_SIZE] = partialSum; }`. Line 12 `__syncthreads();`.
  - Line 14 `if(threadIdx.x < WARP_SIZE) {`. Line 15 `float partialSum = partialSums_s[threadIdx.x];`. Line 16 `partialSum = warp_reduce(partialSum);`. Line 17 `if(threadIdx.x == 0) {`.
  - Lines 18–20 (verbatim): `cuda::atomic_ref<float, cuda::thread_scope_device>` / `output_ref(*output);` / `output_ref.fetch_add(partialSum, cuda::memory_order_relaxed);`
- Care: same structure as Fig. 10.16 with the lane/warp helpers written out inline. Parameter `N` is declared but never used in the printed body; there is no bounds check, so the input length is assumed to be a multiple of `2*blockDim.x` (exercise 5 addresses this for Fig. 10.20). Commit order across blocks is arbitrary.
- APIs: `cuda::atomic_ref<float, ...>`, `cuda::thread_scope_device`, `fetch_add`, `cuda::memory_order_relaxed` (all introduced in Ch. 9), `blockIdx`.

### Fig. 10.20 — `CoarsenedSumReductionKernel` (partial listing, p. 247)
- Purpose: multi-block kernel where each thread first adds `2*COARSE_FACTOR` elements serially. Header as printed: `__global__ CoarsenedSumReductionKernel(float* input, float* output) {` (no return type printed).
- Printed lines:
  - Line 03 `unsigned int segment = COARSE_FACTOR*2*blockDim.x*blockIdx.x;`
  - Line 04 `unsigned int i = segment + threadIdx.x;`
  - Line 05 `float partialSum = input[i];`
  - Line 06 `for(unsigned int c = 1; c < COARSE_FACTOR*2; ++c) {`
  - Line 07 `partialSum += input[i + c*BLOCK_DIM];`
  - Line 09 is a literal `...`: the rest is the reduction and commit from Fig. 10.18.
- Care: the per-thread elements are `BLOCK_DIM` apart, so in each loop iteration the block reads a contiguous run: coalesced (the interleaved partitioning of Ch. 9). No barrier inside the loop. With `COARSE_FACTOR` = 2 each thread adds 4 elements in 3 additions, matching Fig. 10.19.

## Relevance to LLM-inference kernels

The book does not mention LLMs in this chapter; the mapping below is ours [inferred], built on facts the chapter does state.
- **Softmax normalisation (sampling and attention).** A numerically stable softmax over a row needs a **max reduction** (identity -infinity) followed by a **sum reduction** of exp(x - max). For the output logits the row length is the vocabulary size (tens of thousands or more), far above the 2048-element single-block limit (p. 228), so the choices are exactly §10.9 and §10.10: several blocks with an atomic commit, or few blocks with a large coarsening factor, or a partial-result array finished by a second single-block kernel.
- **Attention softmax** is many independent short reductions, one per (batch, head, query) row over the sequence length. Rows up to a few thousand elements fit the one-block kernels; short rows can be given to a single warp, where `warp_reduce` (Fig. 10.13) needs no shared memory and no barrier at all. The optional width parameter (p. 241) allows several even shorter rows per warp.
- **Argmax (greedy decoding) and max-logit.** A max reduction whose element is a (value, index) pair. Because the convergent tree reorders operands (p. 232) and the atomic commit has no defined order (p. 245), the combine function must be commutative and associative as a pair operator, which requires a deterministic tie-break such as "lower index wins". NaN logits break commutativity of max (footnote 3, p. 225). A pair does not fit a single float atomic, which makes the book's non-atomic alternatives (partial array + second kernel, or finish on the host, pp. 245–246) attractive.
- **Reproducibility.** Floating-point addition is not associative (p. 224), so different tree shapes, coarsening factors or block counts give softmax denominators that differ in the last bits; the atomic commit order varies between runs (p. 245). The partial-array alternatives give "more control over the order" (p. 246).
- **Normalisation layers** (LayerNorm, RMSNorm): per-row sum and sum-of-squares reductions over the hidden dimension, same structure, typically one row per block or warp group.
- **Quantized ops:** min/max or abs-max reductions to pick dynamic quantization scales; integer accumulations must respect the overflow caveat of footnote 2 (p. 224).
- **Top-k / top-p:** the normalising sum and running maxima are reductions; cumulative probability is a prefix sum (Ch. 11, which the summary names as building on reduction) and ordering is a sort (later chapters).
- **GEMM / matmul:** each output element is a dot product, i.e. a map followed by a sum reduction, but it is normally computed serially inside one thread (the fully coarsened extreme), so the tree machinery matters little there. The lessons that do transfer are contiguity of active threads, coalescing, and keeping intermediates in registers or shared memory.
- **Latency-bound reasoning** (pp. 243–244): after the load, a reduction is dominated by long-latency steps, so removing barriers and shared-memory round trips beats removing idle lanes. Useful rule for the small per-token reductions in a decode loop.

## Portability notes

The book states only one portability-relevant fact here: "In systems where atomic operations are not available or are too expensive, using a single-block grid or the host to complete the reduction would make sense" (p. 246). It says nothing about HIP or Metal. Everything else below is `[unverified]` and is a list of things to check, not claims.
- `__syncthreads()` (all kernels): needs a block/threadgroup barrier; also relied on as a memory fence within a block (p. 230). HIP and Metal equivalents and their fence semantics `[unverified]`.
- `__shared__` arrays: need per-block (threadgroup) memory. Names, size limits and declaration rules in HIP/Metal `[unverified]`.
- Warp size 32 and the `0xffffffff` mask (Fig. 10.13): hard-coded to a 32-lane warp. The SIMD group width on AMD and Apple GPUs, and whether it is fixed or queryable, is `[unverified]`; code assuming 32 lanes and exactly 32 warps per block must be parameterised.
- `__shfl_down_sync`, `__shfl_sync`, `__shfl_up_sync`, `__shfl_xor_sync`, `__syncwarp()`, warp vote/match/reduce functions (pp. 237–241): CUDA intrinsics. Whether HIP provides same-named intrinsics, and whether Metal Shading Language offers SIMD-group shuffle/reduce functions (and on which OS/GPU versions), is `[unverified]`. Fallback that needs no warp primitives: the shared-memory kernel of Fig. 10.10.
- `cuda::atomic_ref<float, cuda::thread_scope_device>` with `fetch_add` on a **float** (Fig. 10.18): availability of floating-point atomic add outside CUDA is `[unverified]`. Book-stated fallbacks: partial-sum array reduced by a second single-block kernel, or on the host (pp. 245–246).
- `__device__`, `__inline__`, `__global__` qualifiers, `threadIdx`, `blockIdx`, `blockDim`: CUDA spellings; HIP/Metal counterparts `[unverified]`.
- Limits assumed: at most 1024 threads per block (pp. 228, 244). Other platforms' limits `[unverified]`.
- Thrust and CUB (pp. 223, 249) are CUDA libraries; equivalents elsewhere `[unverified]`.
