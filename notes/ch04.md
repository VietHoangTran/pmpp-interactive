# Chapter 4 — Compute architecture and scheduling

- **Book pages:** 67–92  **PDF pages:** 95–120 (pdf = book + 28)
- **In one paragraph:** This chapter explains what happens to the grid after a kernel is launched, so that a programmer can reason about performance. A GPU is an array of Streaming Multiprocessors (SMs), each a group of streaming processors sharing control logic and on-chip memory. Blocks are assigned whole to SMs, in any order, which is what lets the same code scale across GPUs ("transparent scalability") and what limits barrier synchronisation (`__syncthreads()`) to a block. Inside an SM each block is cut into 32-thread warps that execute in SIMD fashion on a processing block; when threads of one warp take different control paths the hardware makes extra passes ("control divergence"). SMs hold far more warps than they can execute at once so they can switch to a ready warp whenever another waits on a slow operation ("latency tolerance", "zero-overhead scheduling"); how full an SM is relative to its maximum is its "occupancy", limited by block slots, thread slots, registers and shared memory. The chapter ends with the host API for querying device properties. Afterwards a reader can count warps and divergent warps for a launch, compute occupancy and spot performance cliffs, use `__syncthreads()` correctly, and query a device before choosing a launch configuration. Hopper-era additions (GPU Processing Clusters, thread block clusters) are introduced by name.

Conventions used in these notes: `[device: …]` tags a number that belongs to a specific GPU model. `[inferred]` marks something we derived (arithmetic checks, answer sketches, observations) rather than read directly. Everything untagged was read from the page.

## Concepts

### Chapter opening (p. 67)
- Recap from Ch. 1: CPUs are designed to minimise instruction-execution latency, GPUs to maximise instruction throughput.
- Ch. 2–3 covered creating and calling kernels. Ch. 4–6 cover the architecture (compute, then memory) and the optimisation techniques that follow from it.
- This chapter's stated order: simplified compute architecture → flexible resource assignment, block scheduling, occupancy → thread scheduling, latency tolerance, control divergence, synchronisation → API for querying resources and tools for estimating occupancy.
- Ch. 5 = on-chip memory architecture; Ch. 6 = off-chip memory briefly, then performance considerations of the whole architecture.

### §4.1 Architecture of a modern GPU (p. 68)
- Programmer's view (Fig. 4.1): the GPU is an array of highly threaded **Streaming Multiprocessors (SMs)**. Each SM contains several processing units called **streaming processors** that share control logic and memory resources.
- Footnote 1: streaming processors are sometimes called "CUDA cores"; the book avoids that term to prevent confusion with CPU cores.
- `[device: Hopper H100]` 132 SMs × 128 streaming processors each = 16,896 streaming processors.
- Starting with the Hopper architecture, SMs are grouped into **GPU Processing Clusters (GPCs)**. `[device: Hopper H100]` its 132 SMs are arranged into 8 GPCs.
- SM memory resources are several on-chip structures collectively labelled "Memory" in Fig. 4.1 (topic of Ch. 5).
- GPUs also have gigabytes of off-chip device memory, "Global Memory" in Fig. 4.1, reached through multiple memory controllers / memory channels that together give high data-access bandwidth.
- Memory technology: older GPUs used GDDR (Graphics Double Data Rate) SDRAM; GPUs starting with NVIDIA's Pascal architecture may use HBM (High-Bandwidth Memory), HBM2, HBM2E or HBM3 — DRAM modules tightly integrated with the GPU in the same package. The book calls all of these "DRAM" from here on; accessing GPU DRAM is covered in Ch. 6.

### §4.2 Thread block scheduling (pp. 69–70)
- A kernel call makes the CUDA run-time system launch a grid; the grid can need far more execution resources than the GPU has, so a scheduling mechanism assigns threads to resources as they free up (p. 69).
- Assignment is **block by block**: all threads of a block are assigned to the same SM simultaneously (p. 69).
- Several blocks can sit on one SM at once, as SM resources permit (three per SM in Fig. 4.2). Each block reserves hardware resources, so the number per SM is limited; the text says the factors are discussed in "Section 4.6" (the discussion is actually in §4.7; see Unclear in the PDF) (p. 69).
- Limited SMs × limited blocks per SM ⇒ a cap on blocks executing simultaneously on a device. Grids usually have many more; the run-time keeps a list of blocks still to execute and assigns new ones as earlier ones finish (p. 69).
- Guarantee from block-wise assignment: threads of the same block execute on the same SM at the same time. That makes two kinds of same-block interaction possible that are not available across blocks (p. 69):
  - block-wide **barrier synchronisation** (§4.3);
  - data exchange through **shared memory**, a low-latency SRAM that resides in the SM (Ch. 5).
- **Thread block cluster** (pp. 69–70): with the Hopper architecture CUDA introduces an *optional* hierarchy level, a group of thread blocks.
  - Analogy the book draws: threads of a block → same SM; blocks of a cluster → co-scheduled on the same GPC.
  - Threads in the same cluster can synchronise through a dedicated API (§4.3).
  - They can access **distributed shared memory**, defined as the shared memory of all blocks participating in the cluster (more in Ch. 5).
  - No launch syntax or code for clusters is given in this chapter.

### §4.3 Synchronization and transparent scalability (pp. 70–74)
- `__syncthreads()` is the block-wide barrier. The two leading underscore characters are the CUDA convention for intrinsic functions (p. 70).
- Semantics: a thread calling it is held at that program location until every thread of the same block reaches it. Vocabulary: a thread **arrives at** the barrier; once all have arrived they are **released from** the barrier. A barrier guarantees all threads of the block finish one phase before any starts the next (p. 70).
- Sidebar "Intrinsic Functions" (p. 70): special processor instructions exposed as functions; they look like library calls but the compiler turns each into the corresponding instruction, usually with no function call in the generated code. gcc, the Intel C compiler and Clang/LLVM support intrinsics.
- Cluster level: a cluster-wide barrier is available through the **Cooperative Groups API** [1]; it ensures that all threads of the cluster have arrived *and* that all their distributed-shared-memory operations have completed before release (p. 70).
- **Scope** of a barrier = the collection of threads involved in it (p. 70).
- Grid level: a grid-wide barrier also exists via Cooperative Groups, but it is more heavyweight than the block- and cluster-wide ones and has several restrictions that must be obeyed so that all grid threads really are executing simultaneously and can reach the barrier. An example appears in Ch. 18. The rest of §4.3 is about block-wide barriers (pp. 70–71).
- Everyday analogy: four friends drive to a mall, shop separately in parallel, and must all be back at the car before leaving; early finishers wait; without the barrier someone is left behind (p. 71).
- Fig. 4.3: threads reach the barrier at different times; early arrivals wait for the latest; then all continue. "No one is left behind" (pp. 71–72).
- Usage rules (p. 72):
  - If a `__syncthreads()` statement is present it must be executed by **all** threads of the block.
  - Inside an `if`: either all threads of the block take the path containing it, or none do.
  - In an if-then-else where each branch has its own `__syncthreads()`, the two calls are **different** barriers; all threads must take the same branch.
  - Fig. 4.4 violates this (branch chosen by `threadIdx.x % 2`): even threads wait at one barrier, odd threads at another; the book calls the result undefined execution behaviour.
  - Misuse can give wrong results or a **deadlock** (threads waiting for each other forever). Avoiding it is the programmer's responsibility.
- System-side requirement (pp. 72–73): threads in a barrier's scope should run close together in time, and all must have the resources to eventually reach the barrier. CUDA ensures this by assigning resources to a block as a unit: a block starts only when the run-time has secured everything all its threads need to complete. That bounds waiting time and rules out indefinite waits.
- Consequence (p. 73): because barriers are confined to a block, blocks have no ordering constraints among themselves and the run-time may execute them in any order. Fig. 4.5: the same 8-block grid runs two blocks at a time on a small device and four at a time on a larger one. "A high-end GPU today can execute hundreds or even thousands of blocks simultaneously."
- **Wave** (p. 73): a group of blocks executing simultaneously. **Number of waves** = (total blocks in the grid) / (blocks that can execute simultaneously). Fig. 4.5 left = four waves, right = two waves.
  - Many waves are desirable when the load across blocks is imbalanced (gives the hardware chances to balance load across SMs).
  - Few waves are acceptable, sometimes desirable, when load is balanced (Ch. 6, thread coarsening).
- **Tail effect** (pp. 73–74): with few waves, an incomplete last wave under-uses the hardware. Example: 660 blocks on a GPU that runs 264 simultaneously = 2.5 waves: 264, 264, then a partial wave of 132. Remedy: make the block count a multiple of the number that can run simultaneously (which depends on the GPU's resources). `[inferred]` 264 = 132 SMs × 2 blocks per SM would match an H100 with 1024-thread blocks, but the book does not name the device here.
- **Transparent scalability** (p. 74): the ability to run the same application code unchanged on hardware with different amounts of execution resources. It lets vendors build GPUs for different cost/power/performance segments (the book's example: a mobile processor runs the application slowly at very low power, a desktop processor faster at higher power) and reduces the burden on developers.

### §4.4 Warps and SIMD hardware (pp. 74–79)
- Within a block, assume threads may execute in **any order** relative to one another. Algorithms with phases must use barriers; correctness must never rely on threads happening to run in step without a barrier (p. 74).
- Thread scheduling is a hardware-implementation matter. "In most implementations to date", a block assigned to an SM is divided into 32-thread units called **warps**. Warp size is implementation specific and may change in future GPUs; knowing about warps helps understand and tune performance on particular device generations (p. 74).
- A warp is **the unit of thread scheduling in SMs** (p. 74).
- Counting warps (pp. 74–75): 256-thread block = 256/32 = 8 warps; three such blocks on an SM = 24 warps (Fig. 4.6).
- Partitioning rule, 1D block (p. 75): by `threadIdx.x`, consecutive and increasing. Warp n holds threads 32·n through 32·(n+1) − 1 (warp 0: 0–31, warp 1: 32–63, …).
- Padding (p. 75): if the block size is not a multiple of 32 the last warp is filled with inactive threads. A 48-thread block → 2 warps, the second padded with 16 inactive threads.
- Multidimensional blocks (pp. 75–76): thread indices are first projected to a linear **row-major** order, then cut into warps. All threads with `threadIdx.y` = 0 come first (in increasing `threadIdx.x`), then y = 1, and so on; for 3D, all of z = 0 first (laid out as a 2D block), then z = 1, etc.
  - 4×4 block (Fig. 4.7): 16 threads = half a warp, padded with 16 more positions.
  - 8×8 block: two warps, T_{0,0}…T_{3,7} and T_{4,0}…T_{7,7} (T_{y,x} notation).
  - 3D "2 × 8 × 4" block (x = 4, y = 8, z = 2; 64 threads): warp 0 = T_{0,0,0}…T_{0,7,3}, warp 1 = T_{1,0,0}…T_{1,7,3} (T_{z,y,x}).
- SIMD execution (p. 76): an SM executes all threads of a warp under the Single-Instruction, Multiple-Data model — at any instant one instruction is fetched and executed for all threads of the warp.
- **Processing blocks** (p. 76): an SM is organised into several processing blocks; the SM's warps are distributed across them. Fig. 4.8 toy: two processing blocks of eight streaming processors each, each with a shared instruction fetch/dispatch unit. `[device: Hopper H100]` an SM's 128 streaming processors form four processing blocks of 32.
- Threads of one warp go to the same processing block, which fetches each instruction once and executes it for all of them on their own data (pp. 76–77).
- **SIMT** (p. 77): because the scheduler maps warps onto processing blocks and so effectively restricts all threads of a warp to the same instruction at any time, warp execution is often called Single Instruction, Multiple Thread. Advantage stressed by the book: the programmer writes scalar per-thread code; grouping into warps and use of the SIMD hardware is transparent. Contrast: on CPUs the programmer/compiler must use API functions to exploit SIMD within each thread. Footnote 2: SIMT is easier, but control divergence should still be avoided (§4.5).
- Why SIMD at all (p. 77): the cost of control hardware (e.g. instruction fetch/dispatch) is shared by many execution units, so a smaller fraction of the chip goes to control and more to arithmetic throughput. The book expects warp partitioning to remain popular; "up to this point in time, all CUDA devices have used similar warp configurations where each warp consists of 32 threads."
- **Warp-level primitives** (pp. 77–78): API functions exposing efficient data exchange and synchronisation among the threads of a warp; they support a "warp-centric" style that treats the warp as an extra software level between block and thread and can bring significant performance benefits. Introduced in Ch. 10, 11 and 12.
- Sidebar "Warps and SIMD Hardware" (pp. 78–79):
  - Von Neumann model (1945 report, based on the EDVAC design): I/O, Memory, a Processing Unit (ALU + register file) and a Control Unit holding the Program Counter (PC, address of the next instruction) and Instruction Register (IR). Each instruction cycle fetches the instruction at PC into IR; its bits determine what every component does. "Stored program" model: behaviour changes by storing a different program.
  - GPU adaptation: one processor in the modified diagram corresponds to a processing block; it has a single control unit, whose control signals fan out to multiple processing units, each corresponding to a streaming processor running one thread of the warp.
  - Since one IR drives all processing units, they differ only in the operand values in their register files. Example: all execute `add r1, r2, r3` but r2 and r3 hold different contents in each unit.
  - Flynn's taxonomy [2]: SISD, SIMD, MISD, MIMD.
  - Control units are complex (instruction fetch logic, access ports to the instruction cache); sharing one among many processing units cuts manufacturing cost and power.

### §4.5 Control divergence (pp. 79–82)
- SIMD works well when all threads of a warp follow the same control-flow path. When they do not, the hardware makes **multiple passes**, one per path; in each pass the threads on the other path "are not allowed to take effect" (pp. 79–80).
- **Control divergence** = threads of the same warp following different control-flow paths (p. 80).
- The multi-pass scheme is what lets SIMD hardware implement full per-thread semantics: every thread appears to follow its own path. Costs named by the book: the extra passes, and the execution resources consumed by inactive threads in each pass (p. 80).
- If-else example (Fig. 4.9; p. 80): warp of threads 0–31 hits `if(threadIdx.x < 24)`. One pass: threads 0–23 execute A, 24–31 inactive. Another pass: threads 24–31 execute B, 0–23 inactive. The threads "may then reconverge" and execute C.
- Architecture difference (p. 80): in Pascal and earlier the passes run **sequentially** (one to completion, then the other). From Volta onwards the passes **may be interleaved** — a feature called **independent thread scheduling** (details in the Volta V100 whitepaper [3]).
- Implication (p. 81): you cannot assume the threads of a warp reconverge after the divergent paths. If all threads of a warp must finish a phase before any moves on, use a warp-level barrier primitive such as `__syncwarp()`.
- Loop example (Fig. 4.10; p. 81): each thread's trip count comes from data (`N = a[threadIdx.x]`), varying between four and eight. All threads are active for the first four iterations; from the fifth, threads that have finished are inactive while the others continue.
- Spotting divergence (p. 81): look at the decision condition. If it depends on `threadIdx` values, the statement can cause divergence. `if(threadIdx.x > 2) {...}` splits the first warp of a block: threads 0, 1, 2 versus 3, 4, 5, …. A loop whose condition depends on thread index values can diverge likewise. (`[inferred]` Fig. 4.10 shows the same holds for data-dependent conditions that differ per thread.)
- The prevalent cause in practice: **boundary checks** when mapping threads to data, because the thread count is a multiple of the block size while the data size is arbitrary (p. 81).
  - Vector length 1003, block size 64 → 16 blocks = 1024 threads; the last 21 threads of block 15 must be disabled. The 16 blocks form 32 warps; only the last warp (second warp of the last block) diverges (pp. 81–82).
- The cost shrinks with data size (p. 82):
  - length 100: one of four warps diverges — potentially significant;
  - length 1000: one of 32 warps, about 3% of execution; even if that warp takes twice as long the total impact is about 3%;
  - length 10,000 or more: one of 313 warps, well under 1%.
- 2D case, the 62×76 grayscale example with 16×16 blocks (Ch. 3, Figs. 3.2 and 3.5) (p. 82):
  - Each 16×16 block = 8 warps, each warp = two rows of the block; 20 blocks = 160 warps.
  - Region 1 (12 blocks, 96 warps): no divergence.
  - Region 2 (3 blocks, 24 warps): all diverge (each row has 12 valid and 4 invalid columns).
  - Region 3: the bottom warp of each block maps entirely outside the image, so none of its threads pass the test and it does not diverge. The book notes it *would* diverge if the picture's height were odd.
  - Region 4: the first seven warps diverge, the last does not.
  - Total: 31 of 160 warps diverge.
- Larger example: a "200 × 150" picture with 16×16 blocks → 130 = 13 × 10 blocks = 1040 warps; warps in regions 1–4 are 864 (12×9×8), 72 (9×8), 96 (12×8), 8 (1×8); the book says only 80 warps diverge, so the impact is under 8%. For realistic pictures with more than 1000 pixels horizontally the impact is under 2% (p. 82). (See Unclear in the PDF for the dimension order and the count of 80.)
- Stated trend: the impact decreases as the number of pixels in the horizontal dimension increases (p. 82).

### §4.6 Warp scheduling and latency tolerance (pp. 82–85)
- An SM usually has more threads assigned than it has streaming processors, so it can execute only a subset at any time. Earlier designs: one instruction for a single warp at a given instant. More recent designs: instructions for a small number of warps at once (multiple processing blocks, Fig. 4.8) (pp. 82–83).
- Why hold so many warps? To tolerate long-latency operations such as **global memory accesses** (p. 83).
- Mechanism (p. 83): a warp whose next instruction is waiting on a previously started long-latency operation is not selected. Warps not waiting on earlier results are **ready**; if several are ready a **priority logic** selects one. Picking a different ready warp at each instant is called **fine-grained multithreading**; the effect — high utilisation of execution units despite long instruction latencies — is **latency tolerance** or **latency hiding**.
- Sidebar "Latency Tolerance" (p. 83): post-office analogy. A customer who still has to fill in a form steps aside so the clerk serves ready customers, and is served as soon as the form is done rather than rejoining the queue. Customers = warps, clerk = hardware execution unit, form-filling = a long-latency operation.
- Warp scheduling also hides other latencies: pipelined floating-point arithmetic and conditional branches (pp. 83–84).
- **Zero-overhead thread scheduling** (p. 84): selecting a ready warp inserts no idle or wasted time in the execution timeline.
- Design consequence (p. 84): this latency tolerance is the main reason GPUs devote far less chip area than CPUs to cache memories and branch prediction, and can spend it on floating-point execution units and memory access channels.
- Sidebar "Threads, Context-switching, and Zero-overhead Scheduling" (p. 84): a thread = a program plus the state of executing it (the code, the instruction being executed, and the values of its variables and data structures). In von Neumann terms: code in memory, PC tracks the instruction address, IR holds the current instruction, registers and memory hold the data. CPU context switching saves/restores PC and registers to and from memory, which costs time. GPU SMs keep the execution state of **all** assigned warps in hardware registers, so switching warps needs no save/restore — hence zero overhead.
- For latency tolerance to work the SM should hold many more threads than it can execute at once (pp. 84–85). `[device: Hopper H100]` an SM has 128 streaming processors but can hold up to 2048 threads, i.e. up to 16× more threads than it can execute in a given clock cycle. This oversubscription is called essential for latency tolerance.

### §4.7 Resource partitioning and occupancy (pp. 85–87)
- **Occupancy** (p. 85): ratio of the number of warps assigned to an SM to the maximum number the SM supports. (The summary on p. 90 states it with threads instead of warps.)
- SM execution resources besides streaming processors: **registers**, **shared memory** (Ch. 5), **thread block slots**, **thread slots**. They are **dynamically partitioned** among threads (p. 85).
- `[device: Hopper H100]` limits (p. 85): at most 32 blocks per SM, 64 warps (2048 threads) per SM, 1024 threads per block.
- Thread-slot partitioning on H100 (p. 85):

  | Threads per block | Blocks per SM | Threads on SM | Occupancy |
  |---|---|---|---|
  | 1024 | 2 | 2048 | 100% |
  | 512 | 4 | 2048 | 100% |
  | 256 | 8 | 2048 | 100% |
  | 128 | 16 | 2048 | 100% |
  | 64 | 32 | 2048 | 100% |
  | 32 | 32 (needs 64, only 32 block slots) | 1024 | 50% |
  | 768 | 2 (a third does not fit) | 1536 | 75% |

  All seven rows are cases worked in the text (pp. 85–86).
- Dynamic vs fixed partitioning (p. 85): dynamic lets an SM run many small blocks or a few large ones. A fixed partition would waste thread slots when blocks are small and could not support blocks larger than the partition.
- Interaction 1, block slots vs thread slots (pp. 85–86): with 32-thread blocks the block-slot limit binds first; occupancy 1024/2048 = 50%. On H100 you need at least 64 threads per block to reach full occupancy.
- Interaction 2, divisibility (p. 86): block size 768 does not divide 2048; only 2 blocks (1536 threads) fit, 512 slots idle, occupancy 75%; neither the thread limit nor the block limit is reached.
- Registers (p. 86): automatic variables declared in a kernel are placed in registers (Ch. 5), so register demand per thread varies by kernel. Registers are partitioned dynamically too: more blocks fit if each thread needs few registers.
  - `[device: Hopper H100]` 65,536 registers per SM. Full occupancy needs ≤ 65,536/2048 = 32 registers per thread.
  - A kernel using 64 registers per thread can have at most 1024 threads on an SM → occupancy at most 50% whatever the block size.
  - The compiler may perform **register spilling** to lower the per-thread requirement and raise occupancy, typically at the cost of extra execution time to access spilled values in memory; total grid time may increase.
  - A similar analysis for shared memory is in Ch. 5.
- **Performance cliff** example (p. 86): kernel with 31 registers/thread and 512 threads/block → 4 blocks per SM, 2048 × 31 = 63,488 registers (< 65,536). Declaring two more automatic variables raises it to 33 registers/thread → 2048 × 33 = 67,584 (> limit). The run-time may then place only 3 blocks per SM (1536 threads, 50,688 registers): occupancy falls from 100% to 75%. A slight increase in resource use causing a large drop in parallelism and performance is called a "performance cliff" [4].
- Tools (p. 87): because the constraints interact in complex ways, use the **Occupancy Calculator** [5] (part of the NVIDIA Nsight Compute profiler [6]), which computes the actual number of threads running on each SM for a given device and kernel resource usage; or call CUDA Occupancy API functions from host code, e.g. `cudaOccupancyMaxActiveBlocksPerMultiprocessor()`, to determine a kernel's occupancy for a grid configuration on the GPU in use.

### §4.8 Querying device properties (pp. 87–89)
- Motivation (p. 87): applications run on many hardware systems and need to query available resources and capabilities to exploit capable systems and compensate on weaker ones. Sidebar "Resource and Capability Queries" (p. 87): hotel-amenities analogy (check what the room provides before packing).
- **Compute capability** (p. 88): the amount of resources in each SM is specified as part of the device's compute capability; higher levels generally mean more resources per SM, and it tends to rise from generation to generation. `[device: A100]` compute capability 8.0. `[device: H100]` compute capability 9.0.
- Device count (p. 88): `int devCount; cudaGetDeviceCount(&devCount);` returns the number of CUDA-capable devices. The API is attributed to the CUDA run-time system (device driver).
- The book's claim (p. 88): a modern PC often has two or more CUDA-capable devices because many PCs come with one or more "integrated" GPUs that are the default graphics units with only rudimentary resources; most CUDA applications perform poorly on them. Hence host code should iterate over devices, query them and pick those with enough resources.
- Devices are numbered 0 … `devCount-1`. `cudaGetDeviceProperties(&devProp, i)` fills a `cudaDeviceProp` (a C struct) for device `i`; the full field list is in the CUDA C++ Programming Guide (p. 88).
- Fields discussed (p. 89):

  | Field / call | Meaning given in the book |
  |---|---|
  | `devProp.maxThreadsPerBlock` | Maximum threads per block on that device. Some devices allow 1024, others may allow fewer, future ones perhaps more — so query it. |
  | `cudaOccupancyMaxPotentialClusterSize()` | API call (not a field) recommended for programs using thread block clusters, to get the maximum cluster size. |
  | `devProp.multiProcessorCount` | Total number of SMs in the device. |
  | `devProp.clockRate` | Clock frequency. Clock rate together with SM count indicates the device's maximal hardware execution throughput. |
  | `devProp.maxThreadsDim[0..2]` | Maximum threads along x, y, z of a block. Example use: an auto-tuner bounding the block shapes it tries. |
  | `devProp.maxGridSize[0..2]` | Maximum blocks along x, y, z of a grid. Typical use: decide whether one grid can cover the data set or an iterative approach is needed. |
  | `devProp.regsPerBlock` | Number of registers available in each SM; useful for judging whether register use will limit occupancy. The name is "a little misleading": for most compute capability levels a block's register maximum equals the SM total, but for some levels it is less than the SM total. |
  | `devProp.warpSize` | Size of a warp on that hardware. |

- Many more `cudaDeviceProp` fields exist; the book introduces them as the corresponding concepts appear (p. 89).

### §4.9 Summary (pp. 89–90)
- SMs consist of multiple processing blocks of streaming processors sharing control logic and memory resources.
- Blocks are assigned to SMs in arbitrary order ⇒ transparent scalability, with the constraint that threads in different blocks should not synchronise with each other.
- Since Hopper: SMs grouped into GPCs; blocks optionally grouped into thread block clusters; blocks of one cluster run on the same GPC, can synchronise with each other and can access each other's distributed shared memory.
- Threads are assigned block by block, then partitioned into warps executed in SIMD fashion; divergent paths are executed in passes, each thread active only in the pass for its own path.
- An SM holds many more threads than it can execute at once and executes a subset of its resident warps at any time, so others can wait on long-latency operations without hurting throughput. Occupancy (here: threads assigned / maximum threads supported) measures this; higher occupancy hides latency better.
- Each device has its own limits on blocks, threads, registers and other resources per SM; any of them can be the limiting factor for a given kernel. CUDA provides occupancy calculators and API functions to choose kernels and launch configurations per GPU, and run-time queries of device resources.

## Relevance to LLM-inference kernels
- **matmul/GEMM:** every thread of the naive kernel runs the same trip count, so the only divergence is the boundary guard, and by the book's argument (pp. 81–82) that is negligible for large matrices and noticeable for small ones (short sequences, small heads). Block shape decides warp membership: with 16×16 blocks a warp is two rows of the block (p. 82), with 32×32 `[inferred]` one row, with 8×8 four rows (p. 76). Optimised GEMM kernels use many automatic variables; the register arithmetic on p. 86 (32 registers/thread for full occupancy on H100, and the 31 → 33 register cliff) is the check to run after each optimisation. Exercise 9 is a matmul launch-validity check.
- **Decode-time matrix–vector and embedding lookups** are dominated by global-memory reads; §4.6 is the explanation of why throughput holds up: other resident warps run while one waits. This is the reason occupancy matters for those kernels.
- **Attention:** per-thread loops whose bounds depend on position or sequence length (causal masking, variable-length sequences in a batch) are exactly the Fig. 4.10 pattern (per-thread trip counts); padding/mask tests keyed on index are the Fig. 4.9 pattern. Launch geometry (one block per head or per query row) also sets the number of waves and the tail effect (pp. 73–74) when grids are small.
- **Quantized ops:** `[inferred]` clamping and per-group scale selection can be written with or without per-thread branches; §4.5 gives the criterion (does the condition differ among threads of one warp?) for when a branch costs extra passes.
- **Sampling (softmax, top-k/top-p, argmax):** these are reductions and selections with data-dependent control flow, hence divergence candidates; they also need the barrier rules of §4.3 (all threads of the block must reach the same `__syncthreads()`) and the warning that warp-synchronous assumptions are unsafe without `__syncwarp()` (p. 81). The book points to warp-level primitives in Ch. 10–12 for the efficient versions. A single vocabulary-sized vector is a small workload: few blocks, possibly a partial wave.
- **Portability of launch configuration:** §4.8's queries (`maxThreadsPerBlock`, `warpSize`, `multiProcessorCount`, `regsPerBlock`) and the occupancy API are the tools for making one kernel choose sensible block sizes across devices.

## Portability notes
The chapter is about NVIDIA CUDA hardware and APIs and states nothing about HIP or Metal. The only cross-vendor statement in the text is generic: the same application code can run on hardware with different amounts of execution resources, e.g. a mobile versus a desktop processor (p. 74). Every HIP/Metal remark below is therefore `[unverified]`.

- **SM / streaming processor / GPC / processing block** (pp. 68, 76): NVIDIA architecture terms. Corresponding units on AMD or Apple GPUs and their counts `[unverified]`.

3. **Fig. 4.10 labels vs text (p. 81):** the thread labels printed above the columns are 0, 1, 2, 4, 5, 6, 7, …, 31 (no "3"), with N values 8, 6, 7, 4, 5, 6, 8, 7. The text says thread 4 drops out at the fifth iteration (consistent with the column labelled 4, N = 4) but that in the eighth iteration "only threads 1 and 7" execute A; by the printed labels the two N = 8 columns are labelled 0 and 7. `[inferred]` The text would match if the first three labels were meant to be 1, 2, 3. Not resolved here. The text also has "eight iteration" for "eighth".
4. **200 × 150 example (p. 82):** by the book's own convention (vertical × horizontal, footnote 1 of Ch. 3) this is 200 rows × 150 columns, which gives region 2 (right edge) = 12 blocks = 96 warps and region 3 (bottom edge) = 9 blocks = 72 warps — the reverse of the printed "72 (9 × 8), 96 (12 × 8)". The printed counts match a 200-wide × 150-high reading. Under that reading `[inferred]` a careful count gives 72 divergent warps in region 2, none in region 3 (150 = 9·16 + 6, so each bottom block has three fully valid and five fully invalid warps) and 3 in region 4, i.e. 75, not the printed 80 (which equals 72 + all 8 warps of region 4); both 75 and 80 of 1040 are under 8%. Under the rows × columns reading `[inferred]` the count would instead be 96 + 0 + 4 = 100 of 1040 (about 9.6%), which would not support the printed "<8%". The course should restate this example with explicit width and height.
5. **Occupancy defined two ways:** warps assigned / maximum warps (p. 85) versus threads assigned / maximum threads (p. 90). Equivalent when warps are full; worth one consistent definition in the course.
6. **"SIMD efficiency" and "active" warps** appear only in exercise 1 (p. 91) and are not defined in the chapter.
7. **132 SMs in 8 GPCs (p. 68):** 132 is not divisible by 8; the book does not say how the SMs are distributed among GPCs. `[inferred observation; no outside source consulted]`
8. **`regsPerBlock` (p. 89):** described as "the number of registers available in each SM" while its name says per block; the book acknowledges the name is misleading and that on some compute capability levels the per-block maximum is lower than the SM total, without saying which levels.
9. **Reconvergence wording (pp. 80–81):** p. 80 says the threads "may then reconverge and execute C"; p. 81 says reconvergence cannot be assumed from Volta on. Consistent, but Fig. 4.9 draws C as a single fully active pass, which should not be read as a guarantee.
10. **Sidebar cross-reference (pp. 78–79):** the sidebar speaks of "arrows that go from the Control Unit to the Processing Units in Fig. 4.8"; Fig. 4.8 has no arrows — the arrows are in the unnumbered sidebar diagram on p. 79.
11. **Missing word (p. 86):** "A similar occupancy analysis is done for the shared memory resource in 5." (presumably Chapter 5).
12. **Kernel name drift:** Ch. 4 calls the vector addition kernel `addVecKernel` (p. 81); Ch. 3 calls it `vecAddKernel`.
13. **Integrated-GPU statement (p. 88):** the text says PCs often have two or more *CUDA-capable* devices because of integrated GPUs; whether integrated graphics units are CUDA-capable is not qualified. Recorded as printed.
14. **Thread block clusters:** only described in prose (pp. 69–70, 89, 90); no launch syntax, size limits or code in this chapter. Details must come from Ch. 5 notes.
15. **Figs. 4.2 and 4.6 thread labels:** tiny text reads "t0 t1 t2 … tm" (Fig. 4.2) and "t0 t1 t2 … t31" (Fig. 4.6); legible at high zoom.
