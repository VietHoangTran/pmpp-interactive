# Chapter 2 — Heterogeneous data-parallel computing

- **Book pages:** 21–44  **PDF pages:** 49–72 (pdf = book + 28). Book p. 43 is References; p. 44 is blank.
- **In one paragraph:** The first programming chapter. It defines data parallelism using colour-to-grayscale conversion, then builds a complete CUDA C++ program for vector addition step by step: the host/device split, allocating device global memory, copying data to and from the device, writing a kernel that every thread executes, computing each thread's global index from built-in variables, guarding against out-of-range threads, launching a grid with the `<<< >>>` configuration, and how the compiler splits and builds host and device code. Afterwards a reader can write, launch and reason about a one-dimensional elementwise kernel, compute grid sizes with ceiling division, and say exactly how many threads run and how many do useful work.

## Concepts

### Chapter opening (p. 21)
- **Data parallelism**: computations on different parts of a dataset can be done independently of each other, and so in parallel (p. 21).
- Applications rich in data parallelism are amenable to scalable execution, where speed improves in proportion to execution resources (p. 21).

### §2.1 Data parallelism (pp. 21–23)
- Slow modern applications are usually slow because of the amount of data: images and video with millions to trillions of pixels, fluid dynamics with billions of grid points, molecular dynamics with thousands to billions of atoms, airline scheduling with thousands of flights, crews and gates (p. 21).
- Three graded examples of independence (p. 21):
  - colour pixel to grayscale: needs only that pixel;
  - blur: needs a small neighbourhood of pixels;
  - average brightness of an image: looks global but can be broken into smaller computations executed independently.
- Writing data-parallel code means (re)organizing the computation around the data so that the independent computations can run in parallel (p. 21).
- **Grayscale example (pp. 21–23)**: each pixel holds fractional r, g, b values from 0 (black) to 1 (full intensity). Luminance per pixel is a weighted sum (Eq. 2.1, p. 22):
  `L = r*0.299 + g*0.587 + b*0.114`
- With input array `I` of RGB values and output array `O` of luminance values, `O[k]` depends only on `I[k]`. No per-pixel computation depends on another (Fig. 2.2, p. 23).
- The book calls the skill of finding and exploiting data parallelism in more complex applications "parallel thinking" (p. 23).
- **Sidebar, RGB Color Image Representation (p. 22)**: each pixel is an (r, g, b) tuple; a row is stored as (r g b)(r g b)…(r g b). Each value is the intensity (0 dark, 1 full) of the red, green and blue light sources.
- **Sidebar, Data Parallelism vs. Task Parallelism (p. 23)**:
  - *Task parallelism* comes from task decomposition. Example: an application that needs a vector addition and a matrix-vector multiplication has two tasks; task parallelism exists if they can run independently. I/O and data transfers are also common tasks.
  - Larger applications have more independent tasks. Molecular dynamics example: vibrational forces, rotational forces, neighbour identification for non-bonding forces, non-bonding forces, velocity and position.
  - Data parallelism is the main source of performance improvement and of **scalability** (performance growing with each hardware generation that has more execution resources). Task parallelism can still matter.

### §2.2 CUDA C++ program structure (pp. 24–25)
- CUDA C++ extends C++ with minimal new syntax plus library functions for systems containing both CPUs and GPUs. The book states concepts learned with it extend easily to other languages and platforms (p. 24).
- Footnote 1 (p. 24): the book's examples use C-style code for simplicity and bring in C++ features where needed, while noting that CUDA programming has moved toward C++ for generic and object-oriented practice.
- A program reflects a **host** (CPU) and one or more **devices** (GPUs). A source file can mix *host code* and *device code*. Any ordinary C++ program is a CUDA C++ program with only host code. Device code is marked with CUDA keywords and contains functions, or **kernels**, executed in a data-parallel manner (p. 24).
- Execution model (Fig. 2.3, p. 24):
  - starts as host code, a single thread;
  - calling a kernel launches a large number of threads on the device; all threads launched by one kernel call are a **grid**;
  - each grid consists of multiple **blocks** of threads;
  - when all threads of a grid finish, the grid terminates and execution continues on the host until the next grid is launched;
  - the book adds that applications can manage overlapped CPU and GPU execution.
- **Sidebar, Threads (pp. 24–25)**:
  - A thread is a simplified view of how a processor executes a sequential program: the program's code, the point in the code being executed, and the values of its variables and data structures.
  - Execution of a thread is sequential from the user's view, which is what a source-level debugger exposes. Each CUDA device thread is sequential too.
  - A CUDA program starts parallel execution by calling a kernel, which makes the runtime launch a grid of device threads that process different parts of the data.
  - For grayscale, one thread per output pixel means millions of threads for large images. In practice a thread may compute several outputs for efficiency (treated later in the book).
  - Cost claim: CUDA threads take very few clock cycles to generate and schedule because of hardware support, in contrast to traditional CPU threads, which typically take thousands of clock cycles.
  - Ch. 3 implements grayscale and blur kernels; this chapter uses vector addition.

### §2.3 A vector addition example (pp. 26–28)
- Vector addition is presented as the "Hello World" of data-parallel programming (p. 26).
- **Naming convention**: host-used variables get the suffix `_h`, device-used variables `_d` (p. 26).
- Sequential version (Fig. 2.4): `main` allocates and fills arrays A, B, C and calls `vecAdd(A, B, C, N)`; `vecAdd` loops `i` from 0 to `n − 1` writing `C_h[i] = A_h[i] + B_h[i]` (pp. 26–27).
- **Sidebar, Pointers in the C++ Language (pp. 26–27)**: `float *P;` declares a pointer; `P = &V` makes P point to V; `*P` is then a synonym for V; an array name is a pointer to its 0th element, so passing `A` makes parameter `A_h` point to `A[0]` and `A_h[i]` accesses `A[i]`.
- **Moving the work to the device (Fig. 2.5, p. 27)**: the revised `vecAdd` has three parts:
  1. allocate device memory for A, B, C and copy A and B from host to device;
  2. call the kernel, launching a grid of threads that does the addition;
  3. copy C from device to host and free the three device arrays.
- This host function acts as an outsourcing agent: `main` does not need to know the addition now happens on a device (p. 28).
- **Pitfall the book flags (p. 28)**: this "transparent" outsourcing can be very inefficient because of all the copying back and forth. Real code often keeps large, important data structures on the device and just invokes device functions on them from the host. The transparent model is used here only for teaching.

### §2.4 Device global memory and data transfer (pp. 28–32)
- Devices are often hardware cards with their own DRAM, called **device global memory** or just **global memory**. Example: the NVIDIA Hopper H100 comes with 80 GB or 94 GB of global memory `[device: NVIDIA Hopper H100]` (p. 28).
- "Global" distinguishes it from other device memory types programmers can use (the memory model is in Ch. 5) (p. 28).
- Shorthand adopted from here on: "transfer from host to device" means copy from host memory to device global memory, and likewise in reverse (p. 28).
- The CUDA runtime system, typically running on the host, provides the API functions (p. 28).
- **`cudaMalloc` (Fig. 2.6, pp. 28–29)**:
  - called from host code; two parameters: (1) the *address of a pointer* variable that will be set to the allocated object, cast to `(void**)` because the function is generic over object types; (2) the size in **bytes**.
  - differs from C `malloc`, which takes one size parameter and returns the pointer. `cudaMalloc` writes the pointer through its first parameter so the return value is free to report errors, like other CUDA API functions.
  - The resemblance to `malloc` is deliberate: the book's line is that CUDA C++ is C++ with minimal extensions.
  - Footnote 2 (p. 29): the generic object returned by `cudaMalloc` makes dynamically allocated multidimensional arrays more complex; addressed in Ch. 3.
- **`cudaFree` (Fig. 2.6, p. 29)**: one parameter, the pointer value (not its address), because it only needs the value to return the memory to the pool (pp. 29–30).
- Size arithmetic (p. 30): for `n` single-precision floats, size is `n * sizeof(float)`; the text states a single-precision float is 4 bytes "in computers today", so size is `n*4`.
- **Pitfall: do not dereference device pointers on the host (p. 30).** Addresses in `A_d`, `B_d`, `C_d` refer to device global memory. In host code they should only be passed to API functions and kernels. Dereferencing them in host code can cause exceptions or other run-time errors.
- More advanced allocation functions exist that copy faster or remove the explicit copy by copying on demand; covered in Ch. 23 and Appendix C (p. 29).
- **`cudaMemcpy` (Fig. 2.7, p. 30)**: four parameters in this order: destination pointer, source pointer, number of bytes, and a constant giving the kind of copy. The kinds are host to host, host to device, device to host, and device to device (p. 30).
- The two constants used: `cudaMemcpyHostToDevice` and `cudaMemcpyDeviceToHost`, predefined by the CUDA environment. The same function serves both directions by ordering the pointers and choosing the constant (p. 31).
- Host code of this kind (allocate, transfer, call kernel) is called a **stub** for calling a kernel (p. 31).
- **Sidebar, Error Checking and Handling in CUDA C++ Programs (p. 32)**:
  - CUDA API functions return flags indicating whether an error occurred; most errors come from inappropriate argument values.
  - The book omits checks in its examples for brevity, but shows the pattern: capture the result as `cudaError_t`, compare with `cudaSuccess`, print `cudaGetErrorString(...)` with `__FILE__` and `__LINE__`, and `exit(EXIT_FAILURE)`.
  - Example failure it would catch: the system is out of device memory.
  - Suggests wrapping this in a C++ macro.

### §2.5 Kernel functions and threading (pp. 32–37)
- A kernel function specifies the code executed by GPU threads during a parallel phase. Because all threads run the same code, CUDA C++ is an instance of **Single-Program Multiple-Data (SPMD)** (pp. 32–33).
- **Two-level hierarchy (p. 33)**: a grid is an array of **thread blocks** ("blocks"). All blocks in a grid have the same size. A block can hold up to 1024 threads "on current systems".
- The host code sets the number of blocks and the threads per block at each kernel call; the same kernel may be launched with different values in different places (p. 33).
- **`blockDim` (p. 33)**: built-in variable giving the number of threads in a block. A struct with three unsigned integer fields `x`, `y`, `z`, allowing 1D, 2D or 3D organization. For 1D only `x` is used; for 2D `x` and `y`; for 3D all three. The dimensionality is normally chosen to match the data.
- **Sidebar, Built-in Variables (p. 33)**: special-meaning variables pre-initialized by the runtime, typically read-only; programmers should not redefine them.
- Recommendation: the total number of threads in a block should be a multiple of 32 "for hardware efficiency reasons"; revisited later (p. 34).
- **`threadIdx` (p. 34)**: unique coordinate of a thread within its block. In the 1D example `threadIdx.x` is 0, 1, 2, … within each block.
- **`blockIdx` (p. 34)**: block coordinate shared by all threads in a block: 0 for the first block, 1 for the second, and so on.
- **Global index (pp. 33–34, Fig. 2.9)**: `i = blockIdx.x * blockDim.x + threadIdx.x`. With `blockDim.x` = 256: block 0 covers i = 0–255, block 1 covers 256–511, block 2 covers 512–767. Three blocks cover the first 768 loop iterations; launching n or more threads covers a vector of length n.
- **Sidebar, Hierarchical Organizations (pp. 34–35)**: telephone analogy. Area code corresponds to `blockIdx`, the seven-digit local number to `threadIdx`. Example given: area code 217 for much of central Illinois; seven digits allow about ten million numbers per area. The hierarchy gives "locality": inside an area you dial only the local number. CUDA's thread hierarchy also provides a form of locality, to be studied later.
- **The kernel (Fig. 2.10, p. 35)**: no `_h`/`_d` suffixes in kernel code since there is no ambiguity; kernels in the book's examples do not touch host memory.
  - Footnote 3 (p. 35): kernel code can in general access host memory through *Unified Virtual Address* (UVA), at lower bandwidth than device global memory; see Appendix C.
- **Function qualifier keywords (Fig. 2.11, pp. 35–36)**:
  - `__global__` (two underscores each side): a kernel. Runs on the device; callable from the host; on systems supporting dynamic parallelism (starting with the Kepler architecture) also callable from the device. Calling it launches a new grid of device threads.
  - `__device__`: a device function. Runs on the device, callable only from a kernel or another device function, executed by the calling device thread; no new threads are launched.
  - `__host__`: a host function, an ordinary C++ function callable only from host functions. This is the default when no qualifier is given, which spares porting effort for existing CPU code.
  - `__host__` and `__device__` together: the compiler generates two versions of the object code, one for host callers and one for device/kernel callers. The book expects many user library functions to fall in this category.
- Built-in variables are how threads read hardware registers that hold their identifying coordinates; different threads see different values (pp. 36–37).
- Notation: the book sometimes writes a thread as thread with subscript (blockIdx.x, threadIdx.x) (p. 37).
- **Automatic variables are private per thread (p. 37)**: `i` in the kernel is an automatic (local) variable; each thread gets its own copy. A grid of 10,000 threads has 10,000 versions of `i`, none visible to other threads. More in Ch. 5.
  - Footnote 4 (p. 37): on `int` versus `unsigned int` for indices, sizes and loop bounds. `unsigned int` states intent and can trigger helpful warnings; `int` avoids bugs with subtraction and mixed arithmetic, and because signed overflow is undefined the compiler can exploit it when optimizing. The book uses both; readers may use either.
- **Where did the loop go? (p. 37)**: the kernel has no loop. The grid replaces it: each thread corresponds to one iteration of the original loop. This is called **loop parallelism**.
- **Boundary guard (p. 37)**: `if (i < n)` is needed because vector lengths are not always multiples of the block size. Worked case: n = 100, block size 32 (the text calls 32 the smallest efficient block dimension) needs four blocks = 128 threads; the last 28 threads, in block 3, must do nothing. All threads test `i` against n; the first 100 add, the last 28 do not. This lets the kernel handle any length.

### §2.6 Calling kernel functions (pp. 37–39)
- A kernel call sets grid and block dimensions through **execution configuration parameters**, placed between `<<<` and `>>>` before the ordinary argument list. First parameter: number of blocks in the grid. Second: number of threads per block (pp. 37–38).
- Number of blocks = ceiling of (threads wanted) / (block size). One way: `ceil(n/256.0)`; the floating-point literal `256.0` forces a floating division so the ceiling rounds up correctly (p. 38).
- Worked numbers (pp. 38–39):
  - n = 1000: `ceil(1000/256.0)` = 4 blocks, 4*256 = 1024 threads, 1000 work and 24 do not.
  - n = 750: 3 blocks. n = 4000: 16 blocks. n = 2,000,000: 7813 blocks.
- The example hard-wires 256 threads per block; only the block count depends on n (p. 39).
- **No ordering guarantee (p. 39)**: blocks work on different parts of the vectors and may execute in any order. Programmers must not assume an execution order.
- **Scalability (p. 39)**: a small GPU may run only one or two blocks at a time; a larger one may run 128 or 256 blocks in parallel. The same code runs slower on small GPUs and faster on large ones. Revisited in Ch. 4.

### §2.7 Compilation (pp. 39–40)
- Code using CUDA extensions is not accepted by a traditional C++ compiler. It needs a compiler that understands them, such as **NVCC** (NVIDIA CUDA Compiler) (p. 39).
- NVCC uses the CUDA keywords to separate host code from device code (p. 39).
  - Host code is plain C++, compiled by the standard C/C++ compiler and run as a normal CPU process.
  - Device code (kernels plus associated device functions and data structures) is compiled by NVCC into "virtual binary files" called **PTX** files.
  - PTX files are further compiled by a run-time component of NVCC into real object files and executed on a CUDA-capable GPU (pp. 39–40).

### §2.8 Summary (p. 40)
- Four groups of extensions introduced: function declarations (`__global__`, `__device__`, `__host__`); kernel call and grid launch (`<<< >>>`); built-in read-only variables (`threadIdx`, `blockDim`, `blockIdx`); runtime API (`cudaMalloc`, `cudaFree`, `cudaMemcpy`).
- The chapter is explicitly not comprehensive; other execution configuration parameters and API functions exist and readers are sent to the CUDA C++ Programming Guide (p. 40).

### Unnumbered snippet — error checking (p. 32)
- Purpose: pattern for checking a CUDA API return value.
- As printed: `cudaError_t err = cudaMalloc((void **) &A_d, size);` then `if (error != cudaSuccess) {` then a `printf("%s in %s at line %d \n", cudaGetErrorString(err), __FILE__, __LINE__);` then `exit(EXIT_FAILURE);`.
- Care: the declaration names the variable `err` but the condition tests `error`; as printed this does not compile. Intended form is clearly `err != cudaSuccess`. See "Unclear in the PDF".
- APIs: `cudaError_t`, `cudaSuccess`, `cudaGetErrorString`.

### Fig. 2.10 — `vecAddKernel` (p. 35)
- Purpose: the vector addition kernel; each thread does one pair-wise addition. Signature: `__global__ void vecAddKernel(float* A, float* B, float* C, int n)` (the qualifier is printed on its own line 03, the rest on line 04). Assumes a 1D grid of 1D blocks with at least n threads in total.
- Walkthrough: lines 01–02 comments; line 05 computes the global index into a private `int i`; line 06 guard; line 07 the addition; lines 08–09 close.
- Lines that need care:
  - `int i = threadIdx.x + blockDim.x * blockIdx.x;` (same value as the form in the text and Fig. 2.9, operands in a different order).
  - `if (i < n) {` then `C[i] = A[i] + B[i];`. Without the guard, threads past the end of the vectors would read and write out of bounds.
- APIs/qualifiers/built-ins: `__global__`, `threadIdx.x`, `blockDim.x`, `blockIdx.x`.

### Fig. 2.12 — host code with the kernel call statement (p. 38)
- Purpose: isolate the launch statement. Signature as printed: `int vectAdd(float* A, float* B, float* C, int n)`.
- Walkthrough: line 02 comment that `A_d`, `B_d`, `C_d` allocations and copies are omitted; line 03 ellipsis; line 04 comment "Launch ceil(n/256) blocks of 256 threads each"; line 05 the call.
- Line that needs care: `vecAddKernel<<<ceil(n/256.0), 256>>>(A_d, B_d, C_d, n);`. The `256.0` literal matters: with integer `256` the division would truncate before `ceil` sees it.
- Care: the function name is spelled `vectAdd` and the return type is `int` with no return statement shown; elsewhere it is `void vecAdd`. See "Unclear in the PDF".
- APIs: `<<< >>>` execution configuration, C++ `ceil`.

### Fig. 2.13 — complete host `vecAdd` (p. 38)
- Purpose: final host code, completing the skeleton of Fig. 2.5. Signature: `void vecAdd(float* A, float* B, float* C, int n)`. Launch: `ceil(n/256.0)` blocks of 256 threads.
- Walkthrough: line 02 `float *A_d, *B_d, *C_d;`; line 03 `int size = n * sizeof(float);`; lines 05–07 `cudaMalloc` for each; lines 09–10 `cudaMemcpy(A_d, A, size, cudaMemcpyHostToDevice);` and the same for B; line 12 the kernel launch (same statement as Fig. 2.12); line 14 `cudaMemcpy(C, C_d, size, cudaMemcpyDeviceToHost);`; lines 16–18 `cudaFree` for each.
- Care: host parameters are `A`, `B`, `C` here (no `_h`), unlike Fig. 2.8. Device pointers are passed to the kernel by value. No error checking, as the sidebar on p. 32 warns.
- APIs: all of the chapter's API functions plus the launch syntax.

### Fig. 2.15 — code for Exercise 9 (p. 42)
- Purpose: exercise on counting blocks and threads. Kernel: `__global__ void foo_kernel(float* a, float* b, unsigned int N)`. Host: `void foo(float* a_d, float* b_d)`.
- Walkthrough: line 02 `unsigned int i = blockIdx.x*blockDim.x + threadIdx.x;`; line 03 `if(i < N) {`; line 04 `b[i] = 2.7f*a[i] - 4.3f;`; line 08 `unsigned int N = 200000;`; line 09 `foo_kernel <<< (N + 128 - 1)/128, 128 >>>(a_d, b_d, N);`.
- Lines that need care: `(N + 128 - 1)/128` is integer ceiling division, an alternative to `ceil(n/256.0)` that the chapter text does not otherwise show. With N = 200000 it evaluates to 1563.

## Relevance to LLM-inference kernels
- **Template for every elementwise op.** `vecAddKernel` (Fig. 2.10) is the shape of residual additions, bias adds, activations, scaling, and per-element quantize/dequantize: compute a global index, guard it, do one element. Exercise 9's kernel (`b[i] = 2.7f*a[i] - 4.3f`) is literally an affine map of the kind used for scale-and-offset. The mapping to LLM ops is ours; the book uses only vector addition here.
- **Index arithmetic and the guard.** Sequence lengths, vocabulary sizes and hidden sizes are rarely multiples of the block size, so the `if (i < n)` pattern and ceiling-division grid sizing (p. 38; integer form in Fig. 2.15) recur in every kernel.
- **Data transfer cost.** The warning that transparent outsourcing is inefficient and that large data structures should stay on the device (p. 28) is the principle behind keeping weights, activations and caches resident on the GPU and crossing the host/device boundary as little as possible. The H100's 80/94 GB of global memory (p. 28) is the budget such data competes for.
- **Data vs task parallelism (p. 23).** The sidebar's own example pairs a vector addition with a matrix-vector multiplication as independent tasks; in inference the bulk of the gain is data parallelism within each op.
- **Exercises 2 and 3** (one thread computing two elements, in adjacent or sectioned layouts) are an early look at thread coarsening and at choosing which elements a thread owns, which the Preface says is central to the optimized matrix multiplication of Ch. 15.
- **`__host__ __device__` functions (p. 36)**: lets small math helpers be shared between a CPU reference implementation and the kernel, which is useful for testing kernels against a scalar baseline (the testing use is our suggestion).
- **Error checking (p. 32)**: out-of-device-memory is the example the book itself gives; allocation failures are a routine condition when loading large models.
- GEMM, attention, top-k/top-p and softmax are not covered in this chapter; it supplies only the launch and indexing mechanics they are built on.

## Ideas for interactives and labs
- **Loop-to-grid stepper (Figs. 2.4 → 2.10)**: show the sequential loop and animate each iteration turning into a thread; the loop header disappears and `i` becomes the index formula. Ends with the question the book poses: "where did the loop go?" (p. 37).
- **Thread index explorer (Fig. 2.9)**: sliders for n, `blockDim.x` and (derived) block count. A strip of array cells coloured by owning block; hovering a thread shows `blockIdx.x`, `threadIdx.x` and `i`; threads with i ≥ n are greyed out with a live count of idle threads. Preset buttons for the book's cases: n = 100 with block size 32 (28 idle), n = 1000 with 256 (24 idle), n = 750, 4000, 2,000,000 (3, 16, 7813 blocks).
- **Predict-then-reveal: Exercise 9**: ask for the five counts before revealing 128 / 200,064 / 1563 / 200,064 / 200,000.
- **Ceiling division bug hunt**: present `ceil(n/256)` with integer n beside `ceil(n/256.0)` and `(n + 255)/256`; the learner finds which launches too few blocks for n = 1000 (the first gives 3 blocks, 768 threads). The broken variant is ours, built from the book's remark about why `256.0` is used (p. 38).
- **Remove-the-guard bug hunt (p. 37)**: delete `if (i < n)` and have the learner say which indices are touched out of bounds for n = 100, block size 32 (100–127).
- **Argument-order drills (Figs. 2.6, 2.7)**: drag-and-drop for `cudaMalloc` (address-of pointer with cast, bytes) and `cudaMemcpy` (destination, source, bytes, direction); reuse Exercises 5–7 as checks.
- **Spot the print errors**: show the Fig. 2.5 declaration line and the p. 32 error-check snippet and ask what would not compile (`*d_A *d_B` missing comma; `err` vs `error`). Doubles as practice reading compiler errors.
- **Qualifier legality quiz (Fig. 2.11)**: matrix of caller (host function, kernel, device function) against callee qualifier; learner marks legal calls and who executes them; include the `__host__ __device__` case from Exercise 10.
- **Lab 1, vector add end to end (measurable)**: implement Fig. 2.13 + Fig. 2.10 with error checking added. - **Lab 2, coarsened vector add**: implement Exercises 2 and 3 (two elements per thread, adjacent versus sectioned) and verify correctness against Lab 1 for lengths that are not multiples of 2 × block size. This forces the learner to redesign the guard.
- **Lab 3, shared helper**: write the Exercise 9 affine map as a `__host__ __device__` function and use it from both a CPU reference and the kernel, comparing outputs element by element.
- **Compilation pipeline click-through (Fig. 2.14)**: colour each function of the vecAdd program by where it ends up (host compiler versus device path).
