# Chapter 3 — Multidimensional grids and data

- **Book pages:** 45–66 (p. 66 is blank)  **PDF pages:** 73–94 (pdf = book + 28)
- **In one paragraph:** Chapter 2 launched a 1D grid over 1D arrays. This chapter generalises: grids and blocks are each up to three-dimensional, every thread learns who it is from `blockIdx`/`threadIdx` (and the launch shape from `gridDim`/`blockDim`), and the programmer turns those coordinates into a row/column (and plane) index, then into a flat offset because dynamically allocated arrays must be linearised in row-major order. Three kernels of rising complexity carry the ideas: colour-to-grayscale (one thread per pixel, pure mapping), image blur (one thread per output pixel, each thread loops over a neighbourhood with boundary checks), and square matrix multiplication (one thread per output element, each thread runs a dot-product loop). Afterwards a reader can choose a `dim3` launch configuration for 2D/3D data, write the row/col/plane index arithmetic, guard out-of-range threads, and hand-trace the naive matmul kernel that later chapters optimise.

Conventions used in these notes: `[inferred]` marks something we derived (arithmetic checks, answer sketches, observations) rather than read directly. Everything untagged was read from the page.

## Concepts

### Chapter opening (p. 45)
- Ch. 2 taught a kernel call that launches a 1D grid of threads over 1D arrays; a kernel is the statement sequence each individual thread executes (p. 45).
- This chapter looks at thread organisation in general and at using threads and blocks for multidimensional arrays, with three running examples: colour→grayscale, blur, matrix multiplication (p. 45).
- Stated purpose of the examples: practice reasoning about data parallelism before the chapters on GPU architecture, memory organisation and performance optimisation (p. 45).

### §3.1 Multidimensional grid organization (pp. 45–48)
- All threads of a grid run the same kernel function; the only thing that distinguishes them is their coordinates (thread indices), which they use to pick their part of the data (p. 45).
- Two-level hierarchy: a grid has one or more blocks; a block has one or more threads. Threads of one block share a block index (`blockIdx`, built-in); each thread also has its own `threadIdx` (built-in). The launch dimensions are visible inside the kernel as `gridDim` and `blockDim` (built-ins) (p. 45).
- General shape: a grid is a 3D array of blocks, each block a 3D array of threads (p. 46).
- Execution configuration parameters sit between `<<<` and `>>>` in the kernel call. First parameter = grid dimensions in number of blocks; second = block dimensions in number of threads. Each has type `dim3`, an integer vector with fields `x`, `y`, `z`. Unused dimensions are set to 1 (p. 46).
- Example: 1D grid of 32 blocks × 128 threads = 4096 threads (p. 46):
  `dim3 dimGrid(32, 1, 1); dim3 dimBlock(128, 1, 1); vecAddKernel<<<dimGrid, dimBlock>>>(...);`
- `dimGrid`/`dimBlock` are ordinary host variables; any legal C++ names work (the book demonstrates with `dog` and `cat`) as long as the type is `dim3` (p. 46).
- Dimensions may be computed: `dim3 dimGrid(ceil(n/256.0), 1, 1); dim3 dimBlock(256, 1, 1);`. With block size fixed at 256, n = 1000 gives 4 blocks, n = 4000 gives 16 blocks. Once launched, grid and block dimensions stay fixed until the whole grid finishes (p. 46).
- 1D shorthand: plain arithmetic expressions may be used instead of `dim3` variables, e.g. `vecAddKernel<<<ceil(n/256.0), 256>>>(...)`. Reason given: the `dim3` constructor's parameters default to 1, so a single value fills `x` and leaves `y` = `z` = 1 (pp. 46–47).
- Inside the kernel, `gridDim` and `blockDim` are pre-initialised from the execution configuration. For n = 4000 in `vecAddKernel`, `gridDim.x` = 16 and `blockDim.x` = 256. Unlike the host-side `dim3` variables, the names `gridDim`/`blockDim` are part of the CUDA C++ specification and cannot be renamed (p. 47).
- Allowed ranges: `gridDim.x` from 1 to 2^31 − 1; `gridDim.y` and `gridDim.z` from 1 to 2^16 − 1 (65,535) (p. 47).
- `blockIdx.x` ranges 0 … `gridDim.x`−1, `blockIdx.y` 0 … `gridDim.y`−1, `blockIdx.z` 0 … `gridDim.z`−1; all threads of a block see the same `blockIdx` values (p. 47).
- Blocks: 2D block by setting `blockDim.z` = 1; 1D block by setting `blockDim.y` = `blockDim.z` = 1. All blocks of a grid have identical dimensions (p. 47).
- Block size limit: "current CUDA systems" allow at most 1024 threads per block in total, distributed across the three dimensions any way you like. Allowed: (512, 1, 1), (8, 16, 4), (32, 16, 2). Not allowed: (32, 32, 2) because the product exceeds 1024 (p. 47).
- Grid and block need not have the same dimensionality (either may be higher). Toy example for Fig. 3.1: `dim3 dimGrid(2, 2, 1); dim3 dimBlock(4, 2, 2); KernelFunction<<<dimGrid, dimBlock>>>(...);` (p. 47).
- Labelling convention (important, used for the rest of the book): blocks are labelled (`blockIdx.y`, `blockIdx.x`), threads (`threadIdx.z`, `threadIdx.y`, `threadIdx.x`), i.e. highest dimension first. This is the reverse of the order in the `dim3` constructor (lowest dimension first). The book says the reversed labelling works better when mapping thread coordinates to data indices. Example: Block (1,0) has `blockIdx.y` = 1, `blockIdx.x` = 0; Thread (1,0,2) has z = 1, y = 0, x = 2 (p. 48).
- Fig. 3.1 totals: 4 blocks × 16 threads = 64 threads. Real grids typically hold thousands to millions of threads (p. 48).

### §3.2 Mapping threads to MultiDimensional data (pp. 48–55)
- Choose 1D/2D/3D thread organisation from the shape of the data; pictures are 2D pixel arrays, so a 2D grid of 2D blocks is convenient (p. 48).
- Running example: a 62×76 picture `Pin` (62 pixels vertically / y, 76 horizontally / x), 16×16 blocks. Needs 4 blocks in y and 5 in x → 20 blocks (p. 49).
- Footnote 1 (p. 49), a book-wide convention: data dimensions are written in descending order z, y, x. A picture with n pixels vertically and m horizontally is "n × m"; `P[y][x]` is written P_{y,x}. This matches C++ multidimensional indexing but is the opposite of the `gridDim`/`blockDim` field order, which the book itself calls a source of confusion.
- The mapping every later kernel reuses (p. 49):
  - vertical (row) coordinate = `blockIdx.y*blockDim.y + threadIdx.y`
  - horizontal (column) coordinate = `blockIdx.x*blockDim.x + threadIdx.x`
- Worked example: Thread (0,0) of Block (1,0) handles Pin_{1·16+0, 0·16+0} = Pin_{16,0} (pp. 49–50).
- Over-provisioning: the grid has 64×80 threads for 62×76 pixels (2 extra thread rows in y, 4 extra thread columns in x). Same situation as a 1000-element vector with four 256-thread blocks (24 surplus threads) in Ch. 2, so the kernel needs an `if` testing both indices (p. 50).
- Host-side launch assumed by the book (p. 50): `n` = pixels in y, `m` = pixels in x, `Pin_d`/`Pout_d` are device-memory pointers.
  `dim3 dimGrid(ceil(m/16.0), ceil(n/16.0), 1); dim3 dimBlock(16, 16, 1); colorToGrayscaleConversion<<<dimGrid,dimBlock>>>(Pin_d, Pout_d, m, n);`
  Note the grid's x extent comes from the width `m` and its y extent from the height `n`.
- Scale example: a 1500×2000 (3-million-pixel) picture needs 94 blocks in y × 125 in x = 11,750 blocks; in the kernel `gridDim.x` = 125, `gridDim.y` = 94, `blockDim.x` = `blockDim.y` = 16 (p. 50).
- Why flatten: we would like `Pin_d[j][i]`, but the C++ standard that CUDA C++ builds on needs the number of columns at compile time to index a 2D array, and that is unknown (by design) for dynamically allocated arrays. So the programmer must linearise ("flatten") a dynamically allocated 2D array into a 1D one "in the current CUDA C++" (p. 50).
- All multidimensional C/C++ arrays are really linearised, because memory is flat; for statically allocated arrays the compiler does the index translation, for dynamically allocated ones the programmer does (pp. 50–51).
- Sidebar "Memory Space" (p. 51): a memory space is a simplified view of how a processor accesses memory; usually one per running application; holds both data and instructions; each location holds a byte and has an address; multi-byte values (`float` 4 bytes, `double` 8 bytes) occupy consecutive bytes and are accessed by start address + byte count; most modern computers have at least 4G byte locations where G = 1,073,741,824 (2^30); one address per location ⇒ "flat" organisation ⇒ multidimensional arrays are ultimately flattened; the compiler turns multidimensional syntax into base pointer + 1D offset.
- Row-major layout (p. 51): all elements of a row are consecutive; rows are placed one after another. M_{j,i} denotes row j, column i (= `M[j][i]`). For a 4×4 matrix the flat index is `j*4 + i`; the `j*4` term skips the rows before row j. Example: M_{2,1} → 2·4+1 = 9. This is how C/C++ compilers linearise 2D arrays.
- Column-major layout (pp. 51–52): all elements of a column consecutive; used by FORTRAN compilers; equals the row-major layout of the transpose. CUDA C++ uses row-major. Many C libraries meant for FORTRAN callers use column-major, so their manual pages typically tell C/C++ users to transpose inputs.
- Grayscale formula stated in the text (p. 52): L = 0.299·r + 0.587·g + 0.114·b. (The listing uses different constants; see Unclear in the PDF.)
- Coverage argument (pp. 52–53): there are `blockDim.x*gridDim.x` threads horizontally; `col = blockIdx.x*blockDim.x + threadIdx.x` takes every integer from 0 to `blockDim.x*gridDim.x − 1`; since that product is ≥ the image width (and likewise vertically), every pixel is covered provided only threads with `(col<width) && (row<height)` do work.
- Offsets (p. 53): `grayOffset = row*width + col` indexes `Pout` directly (one `unsigned char` per grey pixel). The RGB input stores three bytes per pixel, so `rgbOffset = grayOffset*CHANNELS` (footnote 2, p. 53: `CHANNELS` is assumed to be a constant 3 defined outside the kernel); r, g, b are at `rgbOffset`, `+1`, `+2`.
- Worked numbers for Thread (0,0) of Block (1,0) in the 62×76 example: `Pout[16*76+0] = Pout[1216]` (p. 53); `Pin[16*76*3+0] = Pin[3648]`, i.e. the three bytes starting at offset 3648 (p. 54).
- Four execution cases for the 20 blocks (Fig. 3.5; pp. 54–55):
  1. Area 1 — 12 blocks; all 256 threads in each pass the test.
  2. Area 2 — 3 blocks on the right edge (upper part); rows always valid, but the last 4 columns of threads have `col` ≥ 76 (80 is the smallest multiple of 16 covering 76). 12×16 = 192 of 256 threads work.
  3. Area 3 — 4 blocks on the bottom edge (left part); columns always valid, the last 2 thread rows have `row` ≥ 62 (64 is the smallest multiple of 16 covering 62). 16×14 = 224 of 256 threads work.
  4. Area 4 — the bottom-right block; both effects: 14×12 = 168 of 256 threads work.
  - Check `[inferred]`: 12·256 + 3·192 + 4·224 + 168 = 4712 = 62·76.
- 3D extension (p. 55): place each "plane" after the previous one. With `m` = number of columns and `n` = number of rows: `int plane = blockIdx.z*blockDim.z + threadIdx.z;` and the access is `P[plane*m*n + row*m + col]`. The kernel must range-check all three of `plane`, `row`, `col`. 3D arrays return with the stencil pattern in Ch. 8.

### §3.3 Image blur – a more complex kernel (pp. 55–59)
- Motivation: `vecAddKernel` and the grayscale kernel do a few arithmetic operations on one element, independently. Real CUDA threads often do complex work and must cooperate; the next chapters build up to that, starting with blur (p. 55).
- What blurring is for (p. 56): smooths abrupt pixel-value variation; reduces noise and granular rendering effects by correcting bad pixels with clean neighbours; in computer vision lets edge detection/object recognition focus on thematic objects; in displays highlights a region by blurring the rest.
- Mathematically an output pixel is a weighted sum of a patch around the corresponding input pixel; such weighted sums are the convolution pattern (Ch. 7). Here the book simplifies to an unweighted average of an N×N patch including the centre pixel. Distance-based weights (e.g. Gaussian blur) are common in practice but not used here (p. 56).
- 3×3 example: output (row, col) uses rows row−1..row+1 and columns col−1..col+1. For output pixel (25, 50): (24,49), (24,50), (24,51), (25,49), (25,50), (25,51), (26,49), (26,50), (26,51) (p. 56).
- Thread-to-output mapping is unchanged from grayscale: one thread per output pixel, same `col`/`row` computation and same outer range check (pp. 56, 58).
- `BLUR_SIZE` is a defined constant equal to the patch radius (pixels on each side of the centre); patch width is `2*BLUR_SIZE+1`. 3×3 → `BLUR_SIZE` = 1; 7×7 → `BLUR_SIZE` = 3 (p. 58).
- Loop trace for output pixel (25, 50) with `BLUR_SIZE` = 1: outer iteration 1 has `curRow` = 24 and the inner loop visits columns 49..51; iteration 2 visits row 25; iteration 3 row 26 (p. 58).
- Accumulate-and-count: `pixVal` is a running sum, `pixels` counts how many values were added; the output is `pixVal/pixels` (p. 58).
- Boundary handling: the inner `if` skips patch positions outside the image. Corner case 1 (output pixel (0,0)): the nine (`curRow`, `curCol`) pairs are (−1,−1), (−1,0), (−1,1), (0,−1), (0,0), (0,1), (1,−1), (1,0), (1,1); five have a negative index and are skipped, so four values are summed and `pixels` = 4 (p. 58).
- Counts by position: interior threads sum 9 pixels, the four corner pixels 4, other edge pixels 6. That variation is the reason for the `pixels` counter (p. 59).

### §3.4 Matrix multiplication (pp. 59–64)
- Why it matters: matrix–matrix multiplication is a key part of the BLAS standard, the basis of many linear-algebra solvers (e.g. LU decomposition), and an important computation for deep learning; the book points to Ch. 19 (convolutional neural networks) and Ch. 20 (large language models) (p. 59).
- Sidebar "Linear Algebra Functions" (pp. 59–60): BLAS is a de facto standard for libraries of basic linear-algebra operations, in three levels of increasing operation count.
  - Level 1: vector operations y = αx + y (x, y vectors, α scalar). Ch. 2's vector addition is the special case α = 1.
  - Level 2: matrix–vector y = αAx + βy. A form of level 2 appears in Ch. 17 (sparse linear algebra).
  - Level 3: matrix–matrix C = αAB + βC. This chapter's matmul is the special case α = 1, β = 0.
  - BLAS functions are building blocks for higher-level routines (linear system solvers, eigenvalue analysis); the performance of different BLAS implementations can differ by orders of magnitude on both sequential and parallel machines.
- Definition (p. 60): an i×j matrix M times a j×k matrix N gives an i×k matrix P. Each P element is the inner (dot) product of a row of M and a column of N:
  P_{row,col} = Σ M_{row,k} · N_{k,col} for k = 0, 1, …, Width − 1.
  Example with row = 1, col = 5: P_{1,5} = M_{1,0}·N_{0,5} + M_{1,1}·N_{1,5} + M_{1,2}·N_{2,5} + … + M_{1,Width−1}·N_{Width−1,5}.
- Convention continues: P_{row,col} is at position `row` vertically and `col` horizontally (p. 60).
- Thread mapping (p. 60): identical to grayscale — each thread computes exactly one P element, with
  `row = blockIdx.y*blockDim.y + threadIdx.y` and `col = blockIdx.x*blockDim.x + threadIdx.x`.
  Because the mapping is one-to-one, a thread's (row, col) is both its output position and the selector of its inputs: row `row` of M and column `col` of N (pp. 60, 63).
- Simplifying assumption: the kernel handles square matrices only, so a single `Width` replaces both `width` and `height` (p. 61).
- Tiling view: this mapping divides P into tiles; each block computes one tile (the light square in Fig. 3.10, side `BLOCK_WIDTH`) (p. 61).
- Per-thread work (pp. 61–62): initialise a local `Pvalue` to 0; loop k from 0 to Width−1; each iteration multiplies one element of M's row by one element of N's column and accumulates into `Pvalue`; after the loop write `P[row*Width+col]`.
- Index reasoning (p. 62), both matrices stored row-major as flat arrays:
  - M: row `row` starts at `M[row*Width]` (all earlier rows are skipped); its k-th element is `M[row*Width+k]` — consecutive memory locations as k advances.
  - N: column `col` starts at `N[col]` (element `col` of row 0); the next element of the same column is one whole row further on, so its k-th element is `N[k*Width+col]` — a stride of `Width` per step.
  - P: `P[row*Width+col]`, the same pattern as the grayscale output.
- Small execution example (p. 62; Fig. 3.12): 4×4 P with `BLOCK_WIDTH` = 2, so four 2×2 blocks, one per tile. Thread (0,0) of Block (0,0) computes P_{0,0}; Thread (0,0) of Block (1,0) computes P_{2,0}. The book stresses these sizes are unrealistically small and chosen to fit a picture.
- Block (0,0) produces four dot products (Fig. 3.13). Thread (1,0) of Block (0,0) has row = 1, col = 0, so it computes P_{1,0} = row 1 of M · column 0 of N (p. 63).
- Hand trace of the loop for Thread (0,0) of Block (0,0), Width = 4 (p. 63):

  | k | `row*Width+k` | `k*Width+col` | M element | N element |
  |---|---|---|---|---|
  | 0 | 0·4+0 = 0 | 0·4+0 = 0 | `M[0]` = M_{0,0} | `N[0]` = N_{0,0} |
  | 1 | 0·4+1 = 1 | 1·4+0 = 4 | `M[1]` = M_{0,1} | `N[4]` = N_{1,0} |
  | 2 | 0·4+2 = 2 | 2·4+0 = 8 | `M[2]` = M_{0,2} | `N[8]` = N_{2,0} |
  | 3 | 0·4+3 = 3 | 3·4+0 = 12 | `M[3]` = M_{0,3} | `N[12]` = N_{3,0} |

  Then the thread writes `P[row*Width+col]` = `P[0]` = P_{0,0}. The book leaves the other threads/blocks as a hand-execution exercise.
- Size limit (p. 64): a grid is bounded by the maximum number of blocks per grid and threads per block, so this kernel's largest output matrix is bounded too. Two ways out are named: (a) split the output into sub-matrices that a grid can cover and launch a separate grid per sub-matrix from host code, or (b) change the kernel so each thread computes several P elements.
- Forward pointers: matmul is optimised further in Ch. 5 and treated in depth in Ch. 15 (p. 64).
- Not in this section (so do not attribute to it): no host/launch code for the matmul kernel is printed, and nothing is said yet about memory-access efficiency, shared memory or tiling of the *inputs*. `[inferred]` A launch consistent with Fig. 3.12 would be a 2D grid of `ceil(Width/BLOCK_WIDTH)` blocks per dimension with `BLOCK_WIDTH`×`BLOCK_WIDTH` blocks.
- `[inferred]` Cost shape of the naive kernel: Width² threads, each doing Width multiply-adds and 2·Width global-memory reads (M at stride 1, N at stride Width) plus one write; every M row is re-read by Width threads and every N column by Width threads. This is our observation to set up Ch. 5/15, not a statement in §3.4.

### §3.5 Summary (p. 64)
- Grids and blocks are multidimensional (up to three dimensions), which helps organise threads over multidimensional data; execution configuration parameters set the dimensions.
- `blockIdx` and `threadIdx` give each thread unique coordinates; it is the programmer's job to use them so each thread finds its portion of the data.
- Multidimensional accesses usually need manual linearisation to a 1D offset, because dynamically allocated multidimensional arrays in C++ are typically stored as 1D arrays in row-major order.
- These mechanics are called foundational for the parallel patterns and optimisation techniques in the rest of the book.

## Code listings

### Fig. 3.4 — colour-to-grayscale kernel (p. 53)
- **Purpose:** one thread converts one RGB pixel (3 consecutive `unsigned char`s) to one grey `unsigned char`.
- **Signature as printed:** `__global__ void colortoGrayscaleConvertion(unsigned char * Pout, unsigned char * Pin, int width, int height)` (spelling as printed; the text and caption call it `colorToGrayscaleConversion`).
- **Launch configuration assumed (p. 50):** 2D grid `dim3 dimGrid(ceil(m/16.0), ceil(n/16.0), 1)`, 2D blocks `dim3 dimBlock(16, 16, 1)`, with `m` = width, `n` = height.
- **Walkthrough:**
  - 01–02: comments — input is `unsigned char` in [0, 255], three consecutive chars per pixel (RGB).
  - 06–07: `col` from the x coordinates, `row` from the y coordinates.
  - 08: range guard `if (col < width && row < height)`.
  - 10: `grayOffset = row*width + col` (flat offset into the grey image).
  - 13: `rgbOffset = grayOffset*CHANNELS` (comment on 11–12: think of the RGB image as having CHANNEL(S) times more columns).
  - 14–16: read r, g, b at `rgbOffset`, `rgbOffset + 1`, `rgbOffset + 2`.
  - 19: weighted sum stored into `Pout[grayOffset]`.
- **Lines that need care:**
  - Line 19 verbatim: `Pout[grayOffset] = (unsigned char) 0.21f*r+0.71f*g+0.07f*b;` The constants differ from the text's 0.299/0.587/0.114 (p. 52), and the cast as written binds only to `0.21f` (see Unclear in the PDF).
  - The in-text line references are one off for the guard: the text says "(line 07)" for the range test, which is line 08 in the figure (p. 53).
  - `CHANNELS` must be defined elsewhere as 3 (footnote 2, p. 53).
  - Host call on p. 50 passes `(Pin_d, Pout_d, m, n)` while the kernel's first parameter is `Pout` (see Unclear in the PDF).
- **APIs / qualifiers / built-ins:** `__global__`, `blockIdx.x/.y`, `blockDim.x/.y`, `threadIdx.x/.y`.

### Fig. 3.8 — image blur kernel (p. 57)
- **Purpose:** one thread computes one output pixel as the integer average of the valid pixels in a (2·`BLUR_SIZE`+1)² neighbourhood of a single-channel `unsigned char` image.
- **Signature:** `__global__ void blurKernel(unsigned char *in, unsigned char *out, int w, int h)`.
- **Launch configuration assumed:** not printed; the text says the thread-to-output mapping is the same as the grayscale kernel (2D grid of 2D blocks covering w×h) (p. 56).
- **Walkthrough:**
  - 03–04: `col`, `row` as before.
  - 05: outer guard `if(col < w && row < h)`.
  - 06–07: `int pixVal = 0; int pixels = 0;`.
  - 10–11: nested loops `blurRow` and `blurCol` from `-BLUR_SIZE` to `BLUR_SIZE` inclusive (written `< BLUR_SIZE+1`).
  - 12–13: `curRow = row + blurRow; curCol = col + blurCol;`.
  - 15: inner guard `if(curRow>=0 && curRow<h && curCol>=0 && curCol<w)`.
  - 16–17: `pixVal += in[curRow*w + curCol]; ++pixels;`.
  - 22: `out[row*w + col] = (unsigned char)((float)pixVal/pixels);`.
- **Lines that need care:**
  - Two different guards: line 05 disables surplus threads; line 15 trims the patch at the image border. Dropping either is a bug (out-of-bounds write vs out-of-bounds read).
  - The divisor is `pixels`, not the patch area, so borders are averaged over 4 or 6 values (pp. 58–59).
  - The comment on line 09 says "BLUR_SIZE x BLUR_SIZE box" although the box is (2·BLUR_SIZE+1) on a side (p. 58 text is the accurate description).
  - Printed line numbers jump from 07 to 09 (no line 08); text references (lines 10–11, 15, 16, 17, 22) match the printed numbers.
  - `BLUR_SIZE` is an externally defined constant (p. 58).
- **APIs / qualifiers / built-ins:** `__global__`, `blockIdx`, `blockDim`, `threadIdx` (x and y).

### Fig. 3.11 — matrix multiplication kernel, one thread per P element (p. 61)
- **Purpose:** compute P = M·N for square `Width`×`Width` single-precision matrices stored as flat row-major arrays; each thread produces one P element by a dot product.
- **Signature as printed:** `__global__ void MatrixMulKernel(float* M, float* N, float* P, int Width)` (the text and Fig. 3.12 caption write `matrixMulKernel`).
- **Launch configuration assumed:** not printed in the chapter. The mapping implies a 2D grid of 2D blocks covering Width×Width; Fig. 3.12 uses `BLOCK_WIDTH`×`BLOCK_WIDTH` blocks (2×2 for a 4×4 P) (p. 62).
- **Full listing (12 lines; short enough that exactness matters):**
  ```
  01 __global__ void MatrixMulKernel(float* M, float* N,
  02                                 float* P, int Width) {
  03     int row = blockIdx.y*blockDim.y+threadIdx.y;
  04     int col = blockIdx.x*blockDim.x+threadIdx.x;
  05     if ((row < Width) && (col < Width)) {
  06         float Pvalue = 0;
  07         for (int k = 0; k < Width; ++k) {
  08             Pvalue += M[row*Width+k]*N[k*Width+col];
  09         }
  10         P[row*Width+col] = Pvalue;
  11     }
  12 }
  ```
- **Walkthrough:**
  - 03–04: global row/column of this thread = the P element it owns (p. 60).
  - 05: guard for surplus threads when Width is not a multiple of the block dimension (p. 60).
  - 06: per-thread accumulator, a local (automatic) variable (p. 62).
  - 07–09: dot product of M's row `row` and N's column `col` (pp. 61–62).
  - 10: single write of the result (p. 62).
- **Lines that need care:**
  - Line 08: `M[row*Width+k]` walks a row (stride 1); `N[k*Width+col]` walks a column (stride `Width`). Swapping the roles of `k` computes a different product.
  - Lines 03/04: `row` comes from the **y** fields, `col` from the **x** fields; the grid's x extent must cover columns and its y extent rows.
  - Square-only: one `Width` stands for rows of M, columns of M/rows of N, and columns of N (p. 61).
  - No synchronisation is needed: threads only read M and N and each writes a distinct P element `[inferred from the one-to-one mapping on p. 60]`.
- **APIs / qualifiers / built-ins:** `__global__`, `blockIdx`, `blockDim`, `threadIdx` (x and y).

## Relevance to LLM-inference kernels
- **matmul/GEMM:** Fig. 3.11 is the reference GEMM every later optimisation is measured against, and the book itself ties matmul to deep learning and to the LLM chapter (p. 59). The row/col mapping, the range guard and the `M[row*Width+k]` / `N[k*Width+col]` index pair are the pieces a reader must be able to write from memory before tiling, shared memory or mixed precision make sense. The BLAS sidebar (pp. 59–60) gives the vocabulary: decode-time `W·x` is a level-2 operation (exercise 2 is exactly that kernel), batched/prompt-phase projections are level-3.
- **Rectangular reality:** the listing is square-only (p. 61); LLM weights are rectangular (e.g. hidden×vocab), so a course lab should generalise it to separate row/column/inner dimensions — a direct extension of the i×j · j×k definition on p. 60.
- **Layout:** row-major flattening (pp. 51–52) and the 3D form `P[plane*m*n + row*m + col]` (p. 55) are how [batch, seq, hidden] or [head, query, key] tensors are addressed inside a kernel. The column-major warning (p. 52) matters when calling BLAS-style libraries.
- **Attention:** the "one thread per output element, loop over inputs" shape of matmul is also the shape of a naive QKᵀ score kernel; the blur kernel's inner boundary test (line 15, p. 57) is the same construct as a causal or padding mask applied inside the per-thread loop.
- **Quantized ops:** the grayscale and blur kernels read `unsigned char`, compute in float/int, and cast back to `unsigned char` (pp. 53, 57) — the same read-narrow / compute-wide / write-narrow structure as int8 dequantise-compute-requantise. The cast pitfall on line 19 of Fig. 3.4 is a useful cautionary example.
- **Sampling (softmax, top-k/top-p, argmax):** little direct relevance; only the thread-to-data mapping and guards carry over. Reductions come in later chapters.
- **Launch sizing:** the `ceil(dim/blockDim)` grid sizing and surplus-thread guard (pp. 46, 50) apply to every per-element kernel (activation functions, bias add, logit scaling).

## Portability notes
The chapter is written entirely for CUDA C++ and states nothing about HIP or Metal. Every HIP/Metal remark below is therefore `[unverified]` and must be checked against current vendor documentation before it appears in the course.

- `__global__` kernel qualifier and `kernel<<<grid, block>>>(args)` launch syntax (pp. 46, 53, 57, 61). HIP: believed to accept the same qualifier and launch syntax `[unverified]`. Metal: kernels are compute functions in Metal Shading Language launched via a compute command encoder with threadgroup counts/sizes `[unverified]`.
- `dim3` with x/y/z fields and default-1 constructor (pp. 46–47). HIP: same type name expected `[unverified]`. Metal: a 3-component size struct on the host side `[unverified]`.
- Built-ins `blockIdx`, `threadIdx`, `blockDim`, `gridDim` (pp. 45–47). HIP: same names expected `[unverified]`. Metal: per-thread position supplied through attributed kernel parameters (global position, position within threadgroup, threadgroup position) rather than global built-ins `[unverified]`; if a global position is supplied directly, the `blockIdx*blockDim + threadIdx` arithmetic may be unnecessary `[unverified]`.
- Limits: 1024 threads per block; `gridDim` ranges (p. 47). Device/API specific; a port must query its own limits `[unverified for HIP and Metal]`.
- Manual row-major flattening of dynamically allocated arrays (pp. 50–52) is plain C/C++ reasoning and should carry over to any C-like kernel language `[unverified for Metal Shading Language specifics]`.
- Out-of-range guard for surplus threads (pp. 50, 53) is needed wherever the launch is rounded up to whole blocks/threadgroups `[unverified whether Metal offers a non-uniform dispatch that avoids it]`.
