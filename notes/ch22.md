# Chapter 22 — Algorithm selection, problem decomposition, and problem formulation

- **Book pages:** 529–540  **PDF pages:** 553–564 (pdf = book + 24)
- **In one paragraph:** A reflective, code-free chapter that steps back from individual kernels and names the decisions a parallel programmer makes before writing any code: which algorithm to pick (trading complexity, exposed parallelism, generality and accuracy), how to cut the problem into per-thread work units (output-centric "gather" versus input-centric "scatter"), how much of the whole application is actually accelerated (Amdahl's law), whether the problem itself should be re-posed (problem formulation), and whether to optimise for one instance's latency or for the throughput of many instances (batching). It revisits nearly every pattern in the book and classifies its decomposition. After it, a reader can look at a new computation and argue, with named criteria, for a decomposition and for a latency-or-throughput goal. The chapter has no code listings, no exercises and no device-specific numbers.

Note: the running page header shortens the title to "Algorithm selection and problem decomposition" (pp. 530–540).

## Concepts

### Chapter introduction (p. 529)
- The book so far covered practical knowledge: CUDA features, GPU architecture, performance optimisation techniques, parallel patterns and application case studies. This chapter moves to more abstract concepts (p. 529).
- Parallel programming is framed as a thinking process: design or select parallel algorithms, then decompose a domain problem into well-defined, coordinated parallel work units that the chosen algorithms can each perform efficiently (p. 529).
- Good algorithm selection plus good decomposition yields an appropriate compromise among three things: parallelism, work efficiency, and resource consumption (p. 529).
- Domain knowledge combined with parallel thinking is usually needed for hard problems. A programmer with strong parallel thinking need not merely implement problems handed down by domain scientists; they can work with those scientists to analyse and transform the problem's structure: which parts are inherently serial, which parts suit high-performance parallel execution, and what domain-specific trade-offs are involved in moving parts from the first category to the second (p. 529).

### §22.1 Algorithm selection (pp. 530–531)
- **Definition of an algorithm:** a step-by-step procedure in which every step is precisely stated and can be carried out by a computer. Three essential properties (p. 530):
  - **Definiteness** — each step is stated precisely, with no ambiguity about what to do.
  - **Effective computability** — each step can actually be carried out by a computer.
  - **Finiteness** — the algorithm is guaranteed to terminate.
- For one problem there are usually several algorithms, and they differ along at least four axes: number of computation steps (algorithmic complexity), degree of parallel execution exposed, generality of applicability, and accuracy / numerical stability. Usually no single algorithm wins on all axes, so the programmer picks the best compromise for the given hardware (p. 530).
- **Trade-off 1: complexity vs exposed parallelism (prefix sum, Ch. 11).** Brent-Kung has lower algorithmic complexity (fewer operations, more work-efficient). Kogge-Stone exposes more parallelism and finishes in fewer iterations. The book calls this a classic trade-off. The best choice depends on the target hardware and on how far the higher complexity can be softened by hybrid approaches: combining two parallel algorithms, or combining a parallel algorithm with a lower-complexity sequential algorithm through thread coarsening (p. 530).
- **Trade-off 2: generality vs parallel execution efficiency (sorting, Ch. 14).** Odd-even sort has the highest complexity but is the most trivial to parallelise. Radix sort can beat merge sort on complexity because it is a non-comparison sort, and it parallelises very well, but it only works for certain key types. Merge sort is comparison-based, so it works for any key type with a well-defined comparison operator (p. 530).
- **Trade-off 3: complexity vs accuracy (electrostatic potential map, Ch. 21).** Direct Coulomb Summation (DCS) and cutoff summation both expose ample parallelism. Cutoff summation gives up a small amount of accuracy for a large gain in execution efficiency (pp. 530–531).
  - Why it is needed: for fully accurate methods like DCS the amount of computation grows with the square of the volume, which becomes excessive for large systems even on massively parallel devices (p. 531).
  - Why it is legitimate: many grid calculations rest on physical laws under which contributions from particles far from a grid point are tiny and can be treated collectively with an implicit method at much lower complexity (p. 531).
  - This trade-off also exists in sequential code, but it brings extra difficulties for parallel programmers (p. 531).
- **The extra parallel difficulty, illustrated with cutoff summation (p. 531):**
  - Sequentially, a simple cutoff algorithm handles one atom at a time: for each atom it walks the grid points within a radius of the atom. This is easy because the grid points are in an array indexable by coordinate.
  - That atom-centric procedure does not carry over to parallel execution because of its scatter memory-access behaviour.
  - So a **cutoff binning algorithm** based on the **grid-centric** decomposition is used: each thread computes the energy at one grid point.
  - Key idea: first sort the input atoms into bins by coordinate. Each bin is a box in grid space holding every atom whose coordinates fall inside the box.
  - A grid point's **neighbourhood** is the set of bins containing all atoms that can contribute to that grid point under the cutoff distance threshold. Ch. 21 describes an efficient way to manage neighbourhood bins.
  - In that algorithm all blocks iterate through their own neighbourhood bins; all threads in a block scan the atoms of their combined neighbourhood bins together, but each thread decides individually whether a given atom is within its own cutoff radius.
- **Subtle issue: uneven bins and the overflow list (p. 531).**
  - Bins end up with different atom counts; some may be empty, some crowded.
  - Sizing every bin for the largest possible count is prohibitively expensive.
  - Well-known solution: fix the bin capacity at a reasonable level, typically far below the worst case, and keep an **overflow list**. During binning, an atom whose home bin is full goes on the overflow list instead.
  - After the device finishes the cutoff-summation kernel, the atoms on the overflow list still have to be processed to add their missing contributions. (The book does not say here where that processing runs.)

### §22.2 Problem decomposition (pp. 532–536)
- After choosing an algorithm, the problem must be formulated so that it decomposes into sub-problems that can safely be solved at the same time; the programmer then writes code and organises data to solve them concurrently (p. 532).
- Finding parallelism in large problems is often conceptually simple but hard in practice. The key is identifying the unit of work each thread (or collection of threads) performs so that the problem's inherent parallelism is well used (p. 532).
- **Output-centric decomposition:** each sub-problem produces the result for one or more output elements. A thread (or group of threads) is assigned to produce one or more output elements. A sub-problem may need all input elements (grid-centric DCS, Ch. 21) or a subset (matrix multiplication, Ch. 5; grid-centric cutoff summation with binning, Ch. 21) (p. 532).
- **Input-centric decomposition:** each sub-problem derives the contribution of one or more input elements to the final output. A thread (or group) is assigned to process one or more input elements and apply their contributions to output elements. A sub-problem may update one output element (histogram, Ch. 9), a subset of output elements (hypothetically, atom-centric cutoff summation, Ch. 21), or all output elements (atom-centric DCS, Ch. 21) (p. 532).
- Sometimes the two views coincide. In odd-even sort (Ch. 14) each thread reads a pair of inputs and produces the corresponding pair of outputs; inputs and outputs relate so directly that the label does not matter (p. 533).
- Both strategies give the same results but can perform very differently on given hardware (p. 533).
- **Gather (usual behaviour of output-centric):** each thread collects the effect of input values into one output value. Usually preferred on CUDA devices because (p. 533):
  - threads accumulate their results in private registers;
  - several threads can share input values, and can use the GPU caches or shared memory effectively to conserve global memory bandwidth.
- **Scatter (usual behaviour of input-centric):** each thread distributes the effect of one input value into output values. Usually undesirable on CUDA devices because (p. 533):
  - several threads may update the same output value at the same time;
  - the outputs must live in memory writable by all the threads involved;
  - atomic operations are required to avoid races and lost updates, and atomics are significantly slower than the register accesses used in the output-centric version.
- **Gather vs scatter is not the only criterion.** Others the book lists (p. 533):
  1. the amount of parallelism the decomposition exposes;
  2. how easy it is to identify which input data contributes to which output data;
  3. the load balance the decomposition induces;
  4. others that depend on the application.
- Ch. 21 is where both strategies were implemented and compared explicitly (atom-centric = input-centric; grid-centric = output-centric). Elsewhere in the book the decomposition was an implicit design decision; the rest of the section makes it explicit (p. 533).

### §22.3 Application level considerations – Amdahl's law (pp. 537–538)
- A real application is made of several cooperating modules. Example (Fig. 22.2): a molecular dynamics application in which, for every atom, several kinds of force are computed (vibrational, rotational, non-bonded), each by a different method (p. 537).
- The work per module varies dramatically. Non-bonded force calculation involves interactions among many atoms and costs far more than vibrational and rotational forces. So these modules tend to be written as separate passes over the force data structure (p. 537).
- The programmer decides, pass by pass, whether it is worth a CUDA implementation. A plausible outcome: launch a kernel for non-bonded forces while vibrational and rotational forces stay on the host. The update module may also run on the host: it combines the host-computed vibrational/rotational forces with the device-computed non-bonded forces, then computes the new positions and velocities (p. 537).
- **Worked Amdahl example (pp. 537–538):**
  - Assume non-bonded force calculation is 95 % of the original sequential time and is accelerated 100× on the GPU; the remaining 5 % stays on the host with no speedup.
  - Application speedup = 1 / (5 % + 95 %/100) = 1 / (5 % + 0.95 %) = 1 / 5.95 % = 17× (as printed; the exact value is about 16.8×).
  - If host and device execution can be overlapped, the parallel section's time is completely hidden inside the host's time, and the speedup is 1 / 5 % = 20×.
  - Lesson: this is Amdahl's law from Ch. 1. The application speedup is bounded by the sequential portion. Even a small 5 % sequential portion caps the application at 20×, although the accelerated part got 100× and was entirely hidden behind the host's work.
  - Wider point: the accumulated time of many small activities that are not individually worth moving to the GPU can become the limiting factor for the speedup end users see.
- **Amdahl's law motivates task-level parallelisation (p. 538):**
  - Small activities that do not justify fine-grained massively parallel execution may still be worth running in parallel with each other when the data set is large enough.
  - Option A: use a multi-core host to run those tasks in parallel.
  - Option B: run several small kernels simultaneously on the GPU, one per task. Each alone may make poor use of the GPU and show little speedup over the CPU, but overlapping them can give good overall speedup.
  - CUDA supports this kind of task parallelism with **streams**, covered in Ch. 23.

### §22.4 Problem formulation (p. 538)
- The book calls problem formulation arguably the most consequential aspect of parallel application development (citing Wing's "Computational thinking") (p. 538).
- The best approach is *not* to take generic numerical methods, map the domain problem to computing steps, and implement them with this book's skills. That route often gives high computational complexity and/or limited parallelism (p. 538).
- Instead one often has to rethink the numerical method and relax some constraints on the implementation (p. 538).
- Example: cutoff binning (Ch. 21). It needs domain expertise to trade accuracy for dramatically lower algorithmic complexity, plus decomposition and optimisation skill to use grid-centric decomposition with binning techniques designed by computer scientists (p. 538).
- This is where the largest performance advantage and genuinely new capabilities come from, e.g. high-fidelity simulation of a biochemical system of a size considered out of reach for traditional methods. It is interdisciplinary and needs both CS and domain insight; the book says the payoff is worth the effort (p. 538).

### §22.5 Batching: latency vs. throughput (pp. 539–540)
Taken in full detail because it is the section most directly about LLM inference.

- **Starting observation.** Every optimisation discussed so far aims to make a parallel program run faster on the same problem. The book's examples from Ch. 11: double buffering, "warp-level shuffling register tiling" (wording as printed, see Unclear), and look-back. These make the code run faster on the same input, i.e. with shorter latency (p. 539).
- **Term: latency optimisation** — making parallel code run faster for the same input data (p. 539).
- Running faster on one input is desirable but is not the only reason to optimise. The book names at least two motivations (p. 539).

**Motivation 1 (the intuitive one): solve a given problem, i.e. process a given input data set, in less time.** This has been the book's focus (p. 539).
- Example: an investment firm must run a financial portfolio risk analysis on all its portfolios during after-trading hours. With the current parallel program the analysis takes 10 hours. The portfolio management team asks for it to finish in four hours so decisions are more timely. When the program misses the new latency requirement, optimisation techniques raise the speed until it fits the time window (p. 539).
- LLM example given: in Ch. 20, the flash attention technique reduces transformer latency for a given input by eliminating redundant accesses to global memory (p. 539).

**Motivation 2 (less intuitive): improve the total latency for solving many problems** (p. 539).
- Same firm: it may want to run multiple instances of the analysis with different parameters for statistical reasons, and the current program may not fit all instances into the time window (p. 539).
- Optimising for the total latency of many instances brings an extra trade-off: **latency for each individual problem vs latency for all problem instances** (p. 539).

**The LLM inference instance of motivation 2 (p. 539):**
- Processing one user's query (Ch. 20) is one instance of the inference problem. Many users means many instances.
- **Batching** queries from different users lets the transformer layers process them together, which the book says increases the arithmetic intensity of the attention heads.
- Concretely, batching turns the QKV projection's vector-matrix multiplications into matrix multiplications.
- Cost comparison as the book states it: one matrix multiplication takes longer than one vector-matrix multiplication, but much less time than the sum of all the vector-matrix multiplications in the batch.
- Reason given: the matrix multiplication reuses the original matrix elements, which eliminates redundant global memory accesses across the separate vector-matrix multiplications and greatly improves arithmetic intensity.
- Consequence: each individual query experiences a longer QKV projection latency, but the whole group of queries finishes with a shorter total latency.

**Throughput, as the book defines it for the QKV projection (p. 539):**
- with batching: throughput = (total number of queries) / (latency for matrix multiplication)
- without batching: throughput = (total number of queries) / (total latency for all matrix-vector multiplications)
- The first is higher than the second. (The book's inline formula says "matrix-vector" while the surrounding prose says "vector-matrix"; same operation.)

**General statement (pp. 539–540):** the trade-off between latency for individual problem instances and throughput for a batch of instances is an important aspect of optimising parallel programs.

**Link back to Ch. 1 (p. 540):** it is the same trade-off as CPU vs GPU design. The CPU design has shorter latency for processing each individual data element; the GPU design has higher throughput for processing a large number of data elements.

**Closing remarks of the section (p. 540):**
- The literature on algorithms, decompositions, formulation and optimisation strategies is very large and the book does not try to cover it all; it covers a substantial, broadly applicable set in each of the four steps.
- Although shown with CUDA, the techniques build a foundation for parallel thinking in general.
- The authors' stated belief: people learn best bottom-up, first learning concepts in the context of one particular programming model for solid footing, then generalising. Deep CUDA experience builds maturity that helps with parallel concepts that may not even pertain to GPUs.

### §22.6 Summary (p. 540)
- The main steps of parallel programming and thinking are named as: problem formulation, algorithm selection, problem decomposition, and optimisation (p. 540).
- Algorithms for the same problem may offer different trade-offs at equal numerical accuracy, or may give up some accuracy for much more scalable running times (p. 540).
- For a chosen algorithm, the decomposition determines the level of interference between threads, the exposed parallelism, load imbalance, and other performance considerations (p. 540).
- Batching trades increased individual latency for increased throughput for groups of problem instances (p. 540).

## Relevance to LLM-inference kernels

- **§22.5 is directly about LLM serving.** It gives the vocabulary the course needs: latency optimisation (make one request faster, e.g. flash attention removing redundant global-memory traffic) versus throughput optimisation (batch requests so a vector-matrix product becomes a matrix-matrix product that reuses the weight matrix). For a single-GPU inference engine this is the core design axis: time-to-first-token and per-token latency for one stream versus tokens per second across all streams (p. 539). The terms "time-to-first-token" and "tokens per second" are ours, not the book's.
- **GEMM / matmul:** classified as output-centric gather (pp. 533–534). One thread (or tile of threads) owns an output element, accumulates in a register, and shares inputs through shared memory. This is the justification for the tiled matmul structure and it carries to the QKV projection and MLP layers. Batch size 1 degenerates GEMM to a vector-matrix product with low arithmetic intensity (p. 539, and Ch. 20 p. 505).
- **Attention:** the chapter's only attention statement is that batching raises the arithmetic intensity "of the attention heads" via the QKV projection (p. 539). Ch. 20 (p. 505) is more careful: the QKV projection benefits from batching, but the attention layers themselves do not, because each user has a separate KV cache. Teach the Ch. 20 version and flag the looser wording here.
- **Quantised ops:** no direct treatment. The decomposition criteria still apply (a per-output dequantise-and-accumulate loop is gather; nothing in the chapter is specific to integer formats). Little direct relevance.
- **Sampling (softmax, top-k/top-p, argmax):** not mentioned. By the chapter's own classification, softmax normalisation and argmax are reductions (output-centric per iteration, p. 534), top-k selection resembles filter/partition (input-centric, pp. 534–535), and top-p needs a sort plus scan (pp. 534–535). That mapping is our inference from the table, not a statement in the book.
- **Amdahl's law (§22.3):** highly relevant to an inference engine. If the matmul/attention kernels are 95 % of the time and become 100× faster, the remaining host-side work (tokenisation, sampling done on the CPU, kernel launch overhead, host-device copies) caps the end-to-end speedup at 17–20×. This argues for moving sampling onto the GPU and for overlapping host work with device work. The mapping to inference stages is ours; the arithmetic is the book's (pp. 537–538).
- **Problem formulation (§22.4):** the book's example is cutoff binning, not ML. The analogous moves in inference (KV caching, speculative decoding, quantisation as an accuracy-for-cost trade) are discussed in Ch. 20, not here.

## Portability notes

- Claims phrased for "CUDA devices": gather preferred because of private registers, GPU caches and shared memory; scatter penalised because of atomics on shared global memory (p. 533). The book says nothing about whether the same holds on HIP or Metal. Expect the reasoning to transfer because it depends on per-thread registers and contended global writes, but this is `[unverified]`.
- "CUDA devices support task parallelism with streams" (p. 538). The HIP equivalent of streams and the Metal equivalent (command queues / command buffers) are not discussed in the book: `[unverified]`.
- The book makes a general portability claim of its own: techniques shown with CUDA build a foundation for parallel thinking in general, and may apply to concepts not pertinent to GPUs at all (p. 540).

## Ideas for interactives and labs

Merge and BFS are the instructive traps: atomics are not the deciding factor for either.
