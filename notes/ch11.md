# Chapter 11 — Scan

- **Book pages:** 251–287  **PDF pages:** 278–314 (pdf = book + 27)
- **In one paragraph:** (Chapter subtitle: "And work efficiency in parallel algorithms".) Scan (prefix sum) turns a computation that looks inherently sequential, a running total where every output depends on the previous one, into something many threads can do at once. The chapter starts from a 6-line sequential loop, builds a Kogge-Stone block-level kernel, then removes its costs one at a time: the second barrier (double-buffering), per-iteration barriers and shared-memory traffic (warp shuffles plus a scan-scan-add decomposition), wasted work (thread coarsening), shared-memory latency (register tiling) and redundant global-memory traffic (a single-kernel, single-pass global scan with unidirectional synchronization between blocks). It closes with the Brent-Kung alternative and explains why its better work efficiency does not pay off on a GPU. Afterwards a reader can reason about work vs span, count operations and steps for a scan design, compute the memory-bandwidth ceiling of a scan, and read or write each of the kernels below. Chapter credits "special contributions from Li-Wen Chang, Juan Gómez-Luna, and John Owens" (p. 251).

## Concepts

### Chapter opening (pp. 251–252)
- Rule of thumb the book gives: if a computation is naturally a mathematical recursion in which each item is defined in terms of the previous item, it can probably be parallelized as a scan (p. 251).
- Motivation: any sequential section can cap the whole application's performance; scan converts many such sections to parallel form (p. 251).
- Scan is a primitive inside parallel filtering, radix sort, quick sort, string comparison, polynomial evaluation, solving recurrences and tree operations. Filter is Chapter 12; radix sort is Chapter 14 (p. 251).
- Different scan algorithms trade work complexity against span. A parallel scan can do more total work than the sequential one, and with constrained hardware can end up slower, so the chapter is also a study in mitigating extra work (pp. 251–252).
- Techniques flagged as new here: double-buffering and unidirectional synchronization. Techniques reused: warp-level primitives, thread coarsening, register tiling (p. 252). (Note: p. 259 says "Recall from Chapter 6" for double-buffering, so "new" here means first applied to a full kernel pattern.)

### §11.1 Background (pp. 252–254)
- **Inclusive scan**: given a binary operator ⊕ and input `[x0, x1, …, xN−1]`, output is `[x0, (x0⊕x1), …, (x0⊕x1⊕…⊕xN−1)]`. Each output includes the matching input element (p. 252).
- Worked example with addition: input `[3, 1, 7, 0, 4, 1, 6, 3]` gives `[3, 4, 11, 11, 15, 16, 22, 25]`. With addition the operation is also called **prefix sum** (p. 252).
- **Sausage picture** (p. 252): a 40-inch sausage, 8 people ordering 3, 1, 7, 0, 4, 1, 6, 3 inches. Sequential cutting: cut 3 (37 left), cut 1 (36 left), … until 25 inches are served and 15 remain. With an inclusive scan of the orders the outputs are the *cut locations* (3, 4, 11, 11, 15, 16, 22, 25), so all eight cuts can be made simultaneously or in any order. Generalization: scan takes requests from a group and produces all cut points so everything can be served at once (sausage, bread, campground space, a contiguous chunk of memory) (pp. 252–253).
- **Exclusive scan**: output is `[ID⊕, x0, (x0⊕x1), …, (x0⊕…⊕xN−2)]`. Each output excludes the matching input. First element is the operator's identity; last element reflects inputs only up to xN−2 (p. 253).
- **Identity value**: a value that, used as one operand, makes the operator return the other operand unchanged. For addition it is 0 (p. 253).
- Same example, exclusive: `[0, 3, 4, 11, 11, 15, 16, 22]`. These are the *beginning points* of each cut section (person 0 starts at 0, person 7 at 22). Beginning points are what memory allocation needs, since allocated memory is handed back as a pointer to its start (p. 253).
- Converting: inclusive → exclusive: shift everything right by one, put the identity in slot 0. Exclusive → inclusive: shift left by one, fill the last slot with (previous last element ⊕ last input element). Because conversion is easy, the chapter only implements inclusive scan (p. 253).
- Sequential inclusive scan (Fig. 11.1) is O(N): N−1 additions (pp. 253–254).
- Libraries: C++ standard library `std::inclusive_scan` and `std::exclusive_scan`; CUDA libraries Thrust and CUB have GPU-optimized scans. The book says programmers will use these in practice and treats scan as a vehicle for teaching optimization (p. 254).

### §11.2 Parallel scan with the Kogge-Stone algorithm (pp. 254–258)
- **Naive parallel scan**: one thread per output element, each doing a sequential reduction of its prefix. The last thread needs N steps, so the span is O(N), no better than sequential. Total work is Σ_{i=0}^{N−1} i = N·(N−1)/2, i.e. O(N²). More resources, no speedup: a bad idea (p. 254).
- Better: compute each output with a reduction *tree* (Chapter 10). This requires the operator to be associative, "and even commutative depending on the optimizations used" (p. 255). Without sharing, a tree for element i still has i additions, so work stays O(N²) unless partial sums are shared between trees (p. 255).
- **Kogge-Stone**: a sharing scheme originally invented for fast adder circuits in the 1970s and still used in high-speed arithmetic hardware (p. 255).
- It is **in-place**: the array starts as inputs and evolves into outputs. Invariant: after k iterations, position i holds the sum of up to 2^k input elements ending at i. After one iteration position i holds x(i−1)+x(i); after two, x(i−3)+…+x(i) (p. 255).
- Walkthrough on 16 elements (Fig. 11.2, pp. 255–256): y0 = x0 so position 0 is final from the start. Iteration 1: every position except 0 adds its left neighbour; position 1 is then final. Iteration 2: every position except 0 and 1 adds the element two to its left; positions 2 and 3 are then final. And so on with strides 4 and 8.
- Kernel design (Fig. 11.3, pp. 256–257): one block scans one segment of `SEG_SIZE` elements, launched with block size = `SEG_SIZE`, one thread per element. Global consolidation is deferred to §11.9.
- **Two barriers per iteration** (p. 257):
  - barrier 1 (line 10): all writes of the previous iteration are complete before anyone reads (same role as in the Chapter 10 reduction kernel);
  - barrier 2 (line 14): all reads of this iteration are complete before anyone overwrites.
- **Control divergence is modest** (p. 257): while stride < warp size, only threads in the first warp drop out, so only the first warp diverges. Once stride ≥ warp size, whole warps drop out of the first half of the block and there is no divergence.
- **Why the scan needs barrier 2 but reduction did not** (pp. 257–258): each active thread reads its own position and the position `stride` to its left; that left position is being *written* by another active thread in the same iteration. In the Chapter 10 reduction kernels (Figs. 10.6, 10.7) the stride-distance positions read by active threads are never updated by an active thread in the same iteration.
- **Worked race** (pp. 257–258): in the stride-2 iteration, thread 6 must compute old `buffer_s[4]` (x3+x4) + old `buffer_s[6]` (x5+x6) = x3+x4+x5+x6. If thread 4 stores its new value (x1+x2+x3+x4) into `buffer_s[4]` first, thread 6 reads that and stores x1+…+x6. In the next iteration x1+x2 gets added again, giving a wrong answer with x1 and x2 counted twice. If thread 6 happens to read first, the result is correct. So the outcome depends on timing and can vary run to run, which is what makes such bugs hard to find.
- Fix in Fig. 11.3: each thread adds into a private `temp` (line 13), barrier (line 14), then stores (line 16) (p. 258).
- The underlying reason the write target may be read by another thread is that Kogge-Stone runs many reduction trees concurrently and reuses partial sums between them (p. 258).

### §11.3 Double-buffering to reduce synchronization (pp. 258–261)
- The barrier overhead is one of the main bottlenecks of Fig. 11.3 (p. 258).
- The two barriers enforce different kinds of dependence (pp. 258–259):
  - barrier 1: **true dependence** (a read must see a value written earlier);
  - barrier 2: **false dependence** (a write must wait for readers of the old value; a write-after-read).
- From Chapter 6: barriers that enforce only false dependences can be removed by **double-buffering**. General idea: read the iteration's inputs from one buffer and write outputs to another. Allocating a fresh buffer per iteration would waste shared memory; since an iteration's inputs are dead once its outputs exist, two buffers that swap roles each iteration are enough (p. 259).
- With two buffers (Fig. 11.4): load inputs into `buffer1`; iteration 0 reads `buffer1`, writes `buffer2`; iteration 1 reads `buffer2`, writes `buffer1`; and so on. Example from the text: thread 1 writes Σx1..x2 to `buffer2` while thread 2 reads x1 from `buffer1`, so no ordering between them is needed (p. 259).
- **Consequence that is easy to miss** (pp. 259–260): finished values are no longer retained automatically. A thread that would have gone idle (e.g. thread 0 in iteration 0) must now copy its value from the input buffer to the output buffer.
- Result (Fig. 11.5): one `__syncthreads()` per iteration (the true dependence), none for write-after-read because all reads hit `inBuffer_s` and all writes hit `outBuffer_s` (p. 261).

### §11.4 Warp-level primitives to reduce synchronization (pp. 261–265)
- Even after double-buffering, every iteration of Fig. 11.5 pays one barrier and three shared-memory accesses for a single floating-point addition; the loop is dominated by synchronization and shared-memory access (p. 261).
- From Chapter 10: warp-level primitives let threads in a warp synchronize and exchange data far more cheaply than block-wide mechanisms. So decompose the block scan into per-warp scans and combine (p. 261).
- **Scan-scan-add decomposition** (three stages, pp. 261–262):
  1. scan each small segment independently;
  2. collect each segment's last element (= segment total) and scan those totals;
  3. add scanned total k−1 to every element of segment k.
- Worked numbers (Fig. 11.6, pp. 261–262): 16 inputs in four segments of four. Segment 2 inputs 0,4,1,2 → local scan 0,4,5,7; needs +7 (the total of segment 1: 2+1+3+1). Segment 3 inputs 0,3,1,2 → 0,3,4,6; needs +14 (2+1+3+1+0+4+1+2). Segment totals 7,7,6,11 → scanned 7,14,20,31. Scanned totals at indices 0..3 equal the final scan results at positions 3, 7, 11, 15. Final segments: [7,11,12,14], [14,17,18,20], and the last scanned total 31 is also the final element.
- Applied to a block (Fig. 11.7, pp. 262–263): every warp scans its contiguous subsegment with shuffles; the last thread of each warp holds the warp total and writes it to a shared array of warp sums; one warp scans the warp sums; every warp except the first adds the scanned sum of its predecessor to all its elements.
- Warp-level scan (Fig. 11.8) is Kogge-Stone again, but the "element `stride` to my left" comes from a shuffle-up instruction, so there is no shared memory and no barrier. The participation test must use the lane index (`laneIdx()`), not `threadIdx.x`, because the scan is local to the warp (pp. 263–264).
- `laneIdx()` and `warpIdx()` are helper device functions defined in Chapter 10 (p. 264). For reference, Chapter 10 defines them as `threadIdx.x%WARP_SIZE` (p. 239) and `threadIdx.x/WARP_SIZE` (p. 238).
- Block-level scan (Fig. 11.9) performs barriers and shared-memory accesses on only two occasions: between the first warp-scan stage and the warp-sum scan, and between the warp-sum scan and the final add. Compare with Fig. 11.5, which does both every loop iteration (p. 265; note the erratum listed under "Unclear in the PDF").
- The kernel that wraps it (Fig. 11.10) is three statements: load, `blockScan`, store (p. 265).

### §11.5 Work efficiency considerations (pp. 265–267)
- **Work efficiency**: how close the work done by an algorithm is to the minimum work needed for the computation. Footnote: "minimum" is defined empirically as the least work among all known algorithms (p. 265).
- Minimum for scan: N−1 additions, O(N) (what the sequential code does). The naive parallel scan's N·(N−1)/2 is not work efficient (p. 265).
- **Kogge-Stone work** (p. 266): log2N steps; at each step `stride` threads are inactive and N−stride are active, one addition each. Total = Σ over stride = 1, 2, 4, …, N/2 of (N − stride) = N·log2N − (N−1). So O(N·log2N).
- On real hardware it is worse than the formula: inactive threads still consume execution resources until their whole warp finishes, so resource consumption is closer to N·log2N (p. 266).
- Worked number: for 512 elements Kogge-Stone does between 8 and 9 times the work of sequential code (p. 266). (Check: 512·9 − 511 = 4097 vs 511.)
- **Span**: sequential loop runs N iterations; the kernel's loop runs up to log2N iterations, span O(log N). With unlimited resources the step reduction is about N/log2N; for N = 512 that is 512/9 = 56.9× (p. 266).
- **Steps with P execution units** (p. 266): sequential ≈ N steps. Kogge-Stone ≈ (N·log2N)/P steps. If P = N that is log2N. Example: 1024 threads, 32 execution units, 1024 elements → (1024·10)/32 = 320 steps, a 1024/320 = 3.2× reduction (pp. 266–267).
- Two problems with the extra work (p. 267): (1) hardware is used inefficiently, and if P is small the parallel version needs more steps than sequential and is slower; (2) even when faster it uses more energy, which matters in power-constrained settings such as mobile.

### §11.6 Coarsening to improve work-efficiency (pp. 267–270)
- With enough execution resources the lost work efficiency buys a shorter span. When the hardware would serialize threads anyway, the overhead is paid for nothing; better to serialize part of the work ourselves with **thread coarsening** (p. 267).
- Design (Fig. 11.11, pp. 267–268): the block's segment has more elements than threads by the **coarsening factor**. Partition it into one contiguous subsegment per thread. Each thread does a work-efficient *sequential* scan of its subsegment, contributes its last value (subsegment total) to a block-level scan, then adds the scanned total of the previous thread to all of its values. This is scan-scan-add once more.
- Constants: `COARSE_FACTOR` (elements per thread), `BLOCK_DIM` (threads per block); block segment size = `COARSE_FACTOR*BLOCK_DIM` (p. 268).
- **Coalescing pitfall** (p. 269): each thread owns a contiguous run of `COARSE_FACTOR` elements, but if each thread loaded its own run directly from global memory, threads in a warp would touch elements 0, 4, 8, … (for factor 4) in the same instruction: uncoalesced. Instead split the block segment into `COARSE_FACTOR` contiguous chunks of `BLOCK_DIM` elements and load a chunk at a time, so that in each loop iteration thread t loads element t of that chunk. Same on the way out.
- **Work with coarsening**, N elements and P threads (pp. 269–270):
  - sequential subsegment scans: P·(N/P − 1) = N − P
  - parallel scan of P thread sums: P·log2P
  - adds by all threads but the first: (P − 1)·N/P = N − N/P
  - total: 2N + P·log2P − P − N/P
  - P close to N → O(N·log2N), like no coarsening; P ≪ N → close to N, O(N), like sequential.
- **Steps with coarsening** (p. 270): N/P − 1 (sequential scan) + log2P (scan of sums) + N/P (add) = 2N/P + log2P − 1. Without coarsening ≈ (N·log2N)/P. When P is close to N both are O(log2N); when P ≪ N it is roughly 2N/P versus (N·log2N)/P, a substantial improvement.
- Other benefits (p. 270): work moves from the block-level parallel scan (barriers, modest divergence) into the sequential thread-level scan (neither), as with coarsened reduction in Chapter 10.
- **Fewer blocks** (p. 270): coarsening can be done by keeping the block segment size and cutting threads per block by the factor, or by keeping threads per block and enlarging the block segment by the factor. The second option cuts the number of thread blocks by the factor, which helps the inter-block consolidation of §11.9.

### §11.7 Register tiling to avoid shared memory access latency (pp. 270–272)
- In Fig. 11.12 each thread's subsegment lives in shared memory although it is private to that thread; repeated loads and stores to shared memory are wasted latency (pp. 270–271).
- **Register tiling**: copy the subsegment into a per-thread local array (`buffer_r`) on first use and work on it there (Fig. 11.13).
- Loops over `buffer_r` carry `#pragma unroll`. From Chapter 6: unrolling makes every index into the local array a constant, which lets the compiler promote the array to registers. The compiler would probably unroll anyway; the pragma documents intent (pp. 271–272).
- **Why shared memory is still there** (p. 272): global memory ↔ register tile directly would be uncoalesced (the strided pattern from §11.6). Shared memory is kept purely as an intermediary that makes the global accesses coalesced; its data is not reused, so it is not acting as a tile. The book likens this to **corner turning** from Chapter 6.
- Remaining optimizations left as an exercise (p. 272): (1) vector loads and stores for the multi-element global ↔ shared transfers (lines 05–08 and 33–36); (2) the strided accesses to shared memory (lines 13 and 29) can cause **bank conflicts**, removable by padding the shared array as described in Chapter 6.

### §11.8 Memory bandwidth considerations (pp. 272–273)
- Scanning N floats: load 4·N bytes, do N−1 float additions, store 4·N bytes. **Arithmetic intensity** = (N−1)/(4·N + 4·N) ≈ 1/8 OP/B (p. 272).
- `[device: NVIDIA H100]` peak floating-point throughput 66.9 TFLOPS, peak global memory bandwidth 3.35 TB/s, so the compute-bound threshold is 66.9/3.35 = 20.0 FLOP/B (recalled from Chapter 5). Scan at 1/8 is far below: highly memory-bound (p. 272).
- For memory-bound work, peak bandwidth sets peak performance. Scan must touch at least 8 B of global memory per element, so `[device: NVIDIA H100]` ceiling = 3.35×10¹² / 8 = 419×10⁹ elements/s (p. 272).
- Reaching the ceiling would mean touching every global location exactly once and hiding all compute, synchronization and shared-memory latency behind the global accesses. Not achievable in practice: even a plain copy kernel does not hit 100%. Rule of thumb stated: a memory-bound kernel that reaches more than 80% of global memory bandwidth with no redundant global accesses is considered well optimized (pp. 272–273).
- The Fig. 11.13 kernel has no redundant global accesses and can plausibly exceed 80%, but it only does per-block scans. Stitching blocks together needs more global accesses and more synchronization (p. 273).

### §11.9 Consolidating block segments for a global scan (pp. 273–282)
- Some applications only need a block-wide scan; others scan millions or billions of elements and need a grid-wide scan (p. 273).
- **Scan-scan-add across blocks** (Fig. 11.14, p. 273): each block scans its segment; each block's last value goes into an inter-block scan; each block adds the scanned sum of all previous blocks to its values.
- **Three-kernel version** (p. 273): kernel 1 = local scans, kernel 2 = scan of block sums in a single block, kernel 3 = add.
- **Cost in global-memory traffic** (p. 274), S = elements per block segment:
  - kernel 1: load N, store N; kernel 2: load N/S, store N/S; kernel 3: load N, store N
  - total (4 + 2/S)·N elements = (16 + 8/S)·N bytes; for large S ≈ 16 B per element
  - `[device: NVIDIA H100]` 3.35×10¹²/16 = 209×10⁹ elements/s, half the ideal 419×10⁹, because all N intermediate values are stored at the end of kernel 1 and reloaded in kernel 3.
- **Reduce-scan-scan decomposition** (Fig. 11.15, pp. 274–275): (1) each block *reduces* its segment to a single sum (a Chapter 10 kernel); (2) inter-block scan of the block sums; (3) each block adds the sum of all previous blocks to the *first element* of its segment and then scans the segment, which yields final values directly.
- Three-kernel reduce-scan-scan traffic (p. 275): kernel 1 loads N, stores N/S; kernel 2 loads N/S, stores N/S; kernel 3 loads N, stores N. Total (3 + 3/S)·N elements = (12 + 12/S)·N bytes ≈ 12 B per element. `[device: NVIDIA H100]` 3.35×10¹²/12 = 279×10⁹ elements/s, two-thirds of ideal (pp. 275–276). It avoids storing N elements after kernel 1 but still reloads N in kernel 3.
- **Commutativity warning** (p. 276): everything so far assumed only associativity. Some Chapter 10 reduction optimizations also assume commutativity, so for a non-commutative scan operator the choice of reduction implementation inside reduce-scan-scan matters.
- **Why not reduce-scan-scan inside a block?** (p. 276) Both decompositions have two scans; one has an add, the other a reduce. Reduce writes fewer outputs; add needs no multi-step tree with intermediate synchronization. Across blocks the scarce resource is global-memory access, so reduce wins. Across warps or threads the elements are already in registers, where extra accesses are far cheaper than the synchronization a reduce would need, so scan-scan-add wins.
- To approach the ideal, the input must be loaded once and the output stored once, which a multi-kernel design cannot do; the inter-block scan must happen without ending the kernel (refs. [5–7]) (p. 276).
- **Three single-kernel inter-block scan methods** (Fig. 11.16, pp. 276–280):
  - **(a) Grid-wide barrier**: all blocks hand their sums to one block (e.g. block 0), which scans and redistributes. Needs a grid-wide barrier before and after. Possible with cooperative groups (Chapter 18), but all blocks must be running simultaneously, which caps the number of blocks; since each block's segment is capped by shared memory and register capacity in an SM, the total array size is capped too. And grid-wide barriers are very expensive, needed twice (pp. 276–277).
  - **(b) Single lookback**: each block waits for the previous block's scanned sum, adds its own sum, passes the result on. Uses **unidirectional synchronization**: a block waits only for preceding blocks. Unlike a barrier it does not require all blocks to be active at once; it requires only that earlier blocks are *scheduled* before later ones, achieved by assigning block indices dynamically after a block starts running instead of trusting `blockIdx.x` (p. 277).
  - Weakness of single lookback: a dependence chain through all N/S blocks, a long-latency critical path. Method (a) needs two grid-wide barriers; method (b) needs N/S unidirectional synchronizations; cheap individually, too many when there are many blocks (p. 279).
  - **Multiple lookback**: if block b sees that block b−1 has its own sum ready but not yet its scanned sum, it looks at block b−2; if b−2's scanned sum is ready, b adds b−1's sum to b−2's scanned sum itself and proceeds. Redundant work (both b and b−1 do that addition) in exchange for less waiting. Can look back a fixed or a variable number of blocks (pp. 279–280).
  - **Decoupled lookback**: keep looking back until a ready scanned sum is found, then add the plain sums of all the blocks in between (p. 280).
  - **(c)** shows decoupled lookback at its extreme: every block reduces all preceding block sums itself. Fewest steps and synchronizations, most computation. The book compares it to the naive scan of §11.2: worst work efficiency but lowest synchronization overhead, which is the right trade when synchronization costs far more than compute and the number of block sums is far smaller than N (p. 280).
- **Atomics and memory ordering in single lookback** (Fig. 11.17, pp. 278–279):
  - The last thread of the block holds the block sum and acts as **leader** for the block.
  - A `flags` array has one entry per block; a block sets its flag to 1 when its scanned sum is in `partialSums`. Waiting = spinning on the previous block's flag while it reads zero.
  - Flag reads and writes must be atomic (another block's thread writes it) and device-scope (`cuda::thread_scope_device`) so the update is visible across blocks.
  - The read is done as `fetch_add(0, …)`: adding zero leaves the flag unchanged and returns its current value.
  - **Acquire semantics**: the waiting read uses `cuda::memory_order_acquire`, not relaxed, because the following load of `partialSums[bid − 1]` must not be reordered to before the flag check.
  - **Release semantics**: the flag set uses `cuda::memory_order_release` so the preceding store to `partialSums[bid]` is not reordered to after the flag update.
  - This contrasts with Chapter 9's histogram, where relaxed ordering was enough because nothing else depended on the order.
  - A final `__syncthreads()` makes the leader's result (written to a shared variable) visible to the rest of the block.
- **Single-kernel global scan** (Fig. 11.18, pp. 280–282): scan-scan-add is used, because inside one kernel nothing needs to be written to global memory between the first scan and the add, so the reason for preferring reduce-scan-scan is gone (p. 280).
- **Dynamic block index** (p. 280): thread 0 of each block atomically increments a global block counter and publishes the old value in shared memory; the block uses that as its index. Because the counter is incremented as blocks actually start, lower indices always belong to blocks that started earlier, so a block never waits on one that has not been scheduled. The counter is allocated in memory, zero-initialized, and passed to the kernel. The summary phrases the purpose as preventing deadlocks (p. 285).

### §11.10 Parallel scan with the Brent-Kung algorithm (pp. 282–285)
- Included "for completeness"; the book notes that coarsening already made Kogge-Stone's work inefficiency a minor concern (p. 282).
- Idea: a reduction tree computes the total of N values in log2N time units and, on the way, produces sub-sums useful for some scan outputs. Brent-Kung (another adder design, ref. [8]) shares more aggressively than Kogge-Stone at the cost of more steps (p. 282).
- **Phase 1, reduction tree** (top half of Fig. 11.19, p. 282): 16 elements, 4 steps. Step 1 updates positions of the form 2n−1; step 2 positions 4n−1; step 3 positions 8n−1; step 4 position 15 (16n−1). Operations 8+4+2+1 = 15; in general N/2 + N/4 + … + 1 = N−1.
- After phase 1 every position holds a contiguous range x(i)..x(j); positions 0, 1, 3, 7, 15 are already final (p. 283).
- **Phase 2, reverse tree** (bottom half of Fig. 11.19, pp. 282–284): distribute partial sums to the positions that need them. A position never needs more than log2N − 1 partial sums from other positions, and those source positions are powers of two apart (1, 2, 4, …). Example: position 14 holds only x14 and needs positions 7 (x0..x7), 11 (x8..x11) and 13 (x12..x13); the gaps are 1 (14↔13), 2 (13↔11), 4 (11↔7).
- Reverse tree levels for N = 16 (p. 284): level 1 adds position 7 into 11 (distance 4); level 2 completes 5, 9, 13 from 3, 7, 11 (distance 2); level 3 completes 2, 4, 6, 8, 10, 12, 14 from their immediate left neighbours.
- Operation count (p. 284): reverse tree = (16/8 − 1) + (16/4 − 1) + (16/2 − 1) for N = 16; in general (2−1)+(4−1)+…+(N/4−1)+(N/2−1) = N − 1 − log2N. Total = (N−1) + (N−1−log2N) = 2N − 2 − log2N, which is O(N) versus Kogge-Stone's O(N·log2N).
- **Trade-off** (pp. 284–285): Brent-Kung does less work but takes more steps. After coarsening, most of the kernel's work is the sequential per-thread scans; the work-inefficient parallel scan remains only at warp level and is a small part of the run time. At warp level Kogge-Stone performs better in practice: the work Brent-Kung avoids just becomes inactive warp lanes that still occupy execution resources (SIMD execution), so it is better to use those lanes and finish in fewer steps.
- Implementation of Brent-Kung is left as an exercise (p. 285).

### §11.11 Summary (pp. 285–286)
- Kogge-Stone: fast, simple, not work-efficient; the number of execution units needed to break even with sequential grows with data size, so it suits modest-sized blocks on processors with abundant execution resources (p. 285).
- Final advice: scan kernels on GPUs are complex; use Thrust or CUB rather than writing your own, and treat the chapter as a case study in optimization trade-offs (p. 286).

## Code listings

### Fig. 11.1 — `sequential_scan` (p. 254)
- Purpose: reference CPU implementation of inclusive scan with addition. Signature `void sequential_scan(float *input, float *output, unsigned int N)`.
- Walkthrough: line 02 seeds `output[0] = input[0]`; lines 03–05 loop i = 1..N−1 computing `output[i] = output[i - 1] + input[i]`.
- Care: N−1 additions; assumes N ≥ 1.
- APIs: none.

### Fig. 11.3 — Kogge-Stone per-block scan kernel (p. 256)
- Purpose: each thread block does an inclusive scan of its own `SEG_SIZE`-element segment. Signature `__global__ void scan_kernel(float *input, float *output, unsigned int N)`. Launch: block size = `SEG_SIZE` (compile-time constant), one thread per element (pp. 256–257).
- Walkthrough:
  - line 02: `__shared__ float buffer_s[SEG_SIZE];`
  - line 03: global index `i = blockIdx.x*blockDim.x + threadIdx.x`
  - lines 04–08: load `input[i]` into `buffer_s[threadIdx.x]`, or `0.0f` (the identity) if `i >= N`
  - line 09: `for(unsigned int stride = 1; stride < blockDim.x; stride *= 2)`
  - line 10: barrier 1 (previous writes done)
  - lines 11–13: if `threadIdx.x >= stride`, `temp = buffer_s[threadIdx.x] + buffer_s[threadIdx.x-stride];`
  - line 14: barrier 2 (all reads done)
  - lines 15–16: if `threadIdx.x >= stride`, `buffer_s[threadIdx.x] = temp;`
  - lines 18–20: if `i < N`, write `output[i]`.
- Care: both barriers are outside the `if`, so every thread reaches them. Dropping line 14 creates the race described on pp. 257–258. Padding with 0.0f is correct only because 0 is the identity for addition.
- APIs: `__global__`, `__shared__`, `__syncthreads()`, `blockIdx`, `blockDim`, `threadIdx`.

### Fig. 11.5 — Kogge-Stone with double-buffering (p. 260)
- Purpose: same per-block scan with one barrier per iteration. Same signature and launch assumptions as Fig. 11.3.
- Walkthrough:
  - line 02: global index; lines 03–04: `buffer1_s`, `buffer2_s`, both `SEG_SIZE` floats in shared memory
  - lines 05–06: `float* inBuffer_s = buffer1_s; float* outBuffer_s = buffer2_s;`
  - line 07: `inBuffer_s[threadIdx.x] = (i < N)?input[i]:0.0f;`
  - line 08: same loop header as Fig. 11.3; line 09: the single `__syncthreads()`
  - lines 10–12: active threads write `outBuffer_s[threadIdx.x] = inBuffer_s[threadIdx.x] + inBuffer_s[threadIdx.x - stride];`
  - lines 13–15: inactive threads copy `outBuffer_s[threadIdx.x] = inBuffer_s[threadIdx.x];`
  - lines 16–18: swap the two pointers through a local `temp`
  - lines 20–22: `output[i] = inBuffer_s[threadIdx.x];`
- Care: after the swap the freshest data is in `inBuffer_s`, which is why the final read uses it. The copy branch (line 14) is mandatory. The pointers are per-thread locals; all threads swap identically. No barrier is needed before the final store because each thread reads the slot it wrote itself (our observation).
- APIs: as Fig. 11.3.

### Fig. 11.8 — `warpScan` (p. 264)
- Purpose: Kogge-Stone inclusive scan of the 32 values held by the lanes of one warp, entirely in registers. Signature `__device__ inline float warpScan(float val)`; `val` is this thread's element; returns its scanned value.
- Walkthrough: line 02 loops `stride = 1; stride < WARP_SIZE; stride *= 2`; line 03 `float leftVal = __shfl_up_sync(0xffffffff, val, stride);` fetches the value owned by the lane `stride` to the left; lines 04–06 `if(laneIdx() >= stride) val += leftVal;`.
- Care: the mask `0xffffffff` assumes all 32 lanes take part. The test uses `laneIdx()`, not `threadIdx.x`. Lanes below `stride` ignore `leftVal`.
- APIs: `__device__`, `__shfl_up_sync`, helper `laneIdx()` and constant `WARP_SIZE` from Chapter 10.

### Fig. 11.9 — `blockScan` (p. 264)
- Purpose: block-level inclusive scan built from warp scans via scan-scan-add. Signature `__device__ inline float blockScan(float val)`. Assumes `NUM_WARPS` warps per block.
- Walkthrough:
  - line 03: `val = warpScan(val);`
  - lines 05–08: `__shared__ float warpSums_s[NUM_WARPS];` the last lane of each warp (`laneIdx() == WARP_SIZE - 1`) writes `warpSums_s[warpIdx()] = val;`
  - line 09: barrier so all warp sums are visible
  - lines 11–17: threads of warp 0 each load one warp sum, `(threadIdx.x<NUM_WARPS)?warpSums_s[threadIdx.x]:0.0f`, run `warpScan` on them, and threads with `threadIdx.x < NUM_WARPS` write the scanned sum back to the same slot
  - line 18: barrier so other warps wait for warp 0
  - lines 20–22: `if(warpIdx() > 0) val += warpSums_s[warpIdx() - 1];`
  - line 23: return.
- Care: one warp scans the warp sums, so this needs `NUM_WARPS <= WARP_SIZE` (our inference; consistent with a 1024-thread block). Lanes of warp 0 beyond `NUM_WARPS` feed the identity 0.0f. The `__shared__` array is declared inside a device function.
- APIs: `__syncthreads()`, `__shared__`, `warpIdx()`, `laneIdx()`.

### Fig. 11.10 — block-level kernel using `blockScan` (p. 265)
- Purpose: wrapper kernel. `__global__ void scan_kernel(float* input, float* output, unsigned int N)`.
- Walkthrough: line 02 global index; line 03 `float val = (i < N)?input[i]:0.0f;`; line 04 `val = blockScan(val);`; lines 05–07 guarded store.
- Care: all threads, including out-of-range ones, must call `blockScan` because it contains barriers and full-mask shuffles.

### Fig. 11.12 — scan kernel with thread coarsening (p. 268)
- Purpose: block scans `COARSE_FACTOR*BLOCK_DIM` elements with `BLOCK_DIM` threads. Same signature. Launch: block size `BLOCK_DIM`; grid sized so each block owns one segment.
- Walkthrough:
  - line 02: `unsigned int blockSegment = blockIdx.x*COARSE_FACTOR*BLOCK_DIM;`
  - line 04: `__shared__ float buffer_s[COARSE_FACTOR*BLOCK_DIM];`
  - lines 05–08: coalesced load, chunk by chunk: `buffer_s[c*BLOCK_DIM + threadIdx.x] = input[blockSegment + c*BLOCK_DIM + threadIdx.x];`
  - line 09: barrier (whole segment loaded before threads touch their own subsegments)
  - line 11: `unsigned int threadSegment = threadIdx.x*COARSE_FACTOR;`
  - lines 12–14: sequential in-place scan, `buffer_s[threadSegment + c] += buffer_s[threadSegment + c - 1];` for c = 1..COARSE_FACTOR−1
  - lines 16–17: `threadSum` = last element of the subsegment, then `threadSum = blockScan(threadSum);`
  - lines 19–21: `__shared__ float threadSums[BLOCK_DIM];` store own scanned sum; barrier
  - lines 23–28: threads other than 0 read `threadSums[threadIdx.x - 1]` and add it to every element of their subsegment
  - line 29: barrier (all subsegments final)
  - lines 31–34: coalesced store, chunk by chunk.
- Care: two different index mappings: chunk-major (`c*BLOCK_DIM + threadIdx.x`) for global ↔ shared transfers, thread-major (`threadIdx.x*COARSE_FACTOR + c`) for the scan. There is no `i < N` guard anywhere and `N` is unused, so N is implicitly a multiple of the block segment size (our observation).
- APIs: as above plus `blockScan` from Fig. 11.9.

### Fig. 11.13 — coarsened scan kernel with register tiling (p. 271)
- Purpose: Fig. 11.12 with each thread's subsegment kept in a local array. Same signature and launch.
- Walkthrough (differences from Fig. 11.12):
  - lines 12–13: `float buffer_r[COARSE_FACTOR]; buffer_r[0] = buffer_s[threadSegment];`
  - lines 14–17: `#pragma unroll`, then `buffer_r[c] = buffer_s[threadSegment + c] + buffer_r[c - 1];` (one shared read per element, running sum in registers)
  - lines 19–20: `threadSum = buffer_r[COARSE_FACTOR - 1]`, `blockScan`
  - lines 22–24: `threadSums`, barrier
  - line 26: `float prevPartialSum = (threadIdx.x>0)?threadSums[threadIdx.x - 1]:0.0f;` (ternary replaces the `if`, so thread 0 also runs the loop and writes back)
  - lines 27–30: `#pragma unroll`, `buffer_s[threadSegment + c] = buffer_r[c] + prevPartialSum;` (add and return to shared memory in one pass)
  - line 31: barrier; lines 33–36: coalesced store.
- Care: shared memory is touched once on the way in and once on the way out per element. The strided accesses at lines 13 and 29 are the bank-conflict risk the book mentions (p. 272). `N` unused, as in Fig. 11.12.
- APIs: `#pragma unroll`.

### Fig. 11.17 — `interBlockScan`, single lookback (p. 278)
- Purpose: obtain the sum of all preceding blocks and publish this block's scanned sum. Signature `__device__ inline float interBlockScan(float val, unsigned int bid, float* partialSums, unsigned int* flags)`. `val`: this thread's contribution (meaningful for the leader, which holds the block sum); `bid`: dynamically assigned block index; `partialSums`, `flags`: global arrays, one entry per block. Returns the scanned sum of the previous block.
- Walkthrough:
  - line 03: `__shared__ float prevBlockPartialSum_s;`
  - line 04: only the leader, `threadIdx.x == blockDim.x - 1`, runs lines 05–20
  - lines 05–11: if `bid > 0`, build a device-scope atomic reference to `flags[bid - 1]` and spin: `while(prevBlockFlag_ref.fetch_add(0, cuda::memory_order_acquire)==0){}`, then `prevBlockPartialSum_s = partialSums[bid - 1];`
  - lines 12–14: block 0 uses `0.0f`
  - line 16: `partialSums[bid] = prevBlockPartialSum_s + val;`
  - lines 18–20: atomic reference to `flags[bid]`; `myBlockFlag_ref.fetch_add(1, cuda::memory_order_release);`
  - line 22: `__syncthreads();` line 23: every thread returns `prevBlockPartialSum_s`.
- Care: the atomic reference type is `cuda::atomic_ref<unsigned int, cuda::thread_scope_device>`. Acquire on the read side and release on the write side are what make the plain (non-atomic) accesses to `partialSums` safe. The busy-wait loop has an empty body. `flags` must start at zero (implied by "expected to remain zero until the previous block sets it", p. 278).
- APIs: `cuda::atomic_ref`, `cuda::thread_scope_device`, `fetch_add`, `cuda::memory_order_acquire`, `cuda::memory_order_release`.

### Fig. 11.18 — single-kernel global scan (p. 281)
- Purpose: complete global inclusive scan in one kernel launch, loading the input once and storing the output once. Signature as printed: `__global__ void scan_kernel(float* input, float* output, unsigned int* blockCounter, float* partialSums, unsigned int* flags unsigned int N)` (the comma before `unsigned int N` is missing in the listing).
- Walkthrough:
  - lines 04–11: dynamic block id. `__shared__ unsigned int bid_s;` thread 0 does `bid_s = blockCounter_ref.fetch_add(1, cuda::memory_order_relaxed);` on a device-scope atomic reference to `*blockCounter`; barrier; every thread copies `bid = bid_s`.
  - line 12: `unsigned int blockSegment = COARSE_FACTOR*bid*blockDim.x;` (uses `bid`, not `blockIdx.x`)
  - lines 14–19: coalesced load into `buffer_s`, barrier
  - lines 21–27: register-tiled sequential scan of the thread subsegment (as Fig. 11.13)
  - lines 29–34: `blockScan` on thread sums, collect in `threadSums`, barrier
  - lines 36–40: `prevPartialSum`, then `buffer_r[c] += prevPartialSum;` (stays in registers this time)
  - lines 42–43: `float prevBlockPartialSum = interBlockScan(buffer_r[COARSE_FACTOR - 1], bid, partialSums, flags);`
  - lines 45–48: `buffer_s[threadSegment + c] = buffer_r[c] + prevBlockPartialSum;`
  - line 49: barrier; lines 51–54: coalesced store to `output`.
- Care: the block-counter increment uses relaxed ordering (no other memory access depends on it), unlike the flags. Each thread passes its own last scanned element to `interBlockScan`; only the last thread's value (the block total) is used. `N` is unused and there are no bounds checks. Line 12 uses `blockDim.x` while line 14 uses `BLOCK_DIM`.
- APIs: everything from Figs. 11.9, 11.13, 11.17.

## Relevance to LLM-inference kernels
The book does not connect scan to LLM sampling; Chapter 20's text was searched for top-p/top-k/sampling and has no such discussion. The mapping below is ours.
- **Top-p (nucleus) sampling**: after sorting probabilities in descending order, an inclusive scan gives the cumulative probability at each rank; the nucleus is the shortest prefix whose cumulative value reaches p. Equivalently, with an exclusive scan (mass strictly before each token), keep token i when that value is below p. The exclusive/inclusive distinction of §11.1 is exactly the off-by-one that decides whether the token that crosses p is kept.
- **Sampling from the distribution** is the sausage picture (p. 252): the inclusive scan of probabilities gives the cut points of the unit interval; a uniform random number falls into one section; finding that section is a search over the scanned array.
- **Sizes**: a vocabulary row is a "modest-sized" scan, the regime the book says Kogge-Stone-style block scans suit (p. 285). One block with coarsening covers `BLOCK_DIM*COARSE_FACTOR` elements, so a whole vocabulary row can fit in one block or a handful of blocks, and batched sampling is one independent scan per row. The inter-block machinery of §11.9 matters mostly when rows are much larger than a block segment or when one scan spans the whole batch.
- **Memory-bound**: at about 1/8 OP/B (p. 272) a cumulative sum over logits is limited by bandwidth, not arithmetic. Fusing softmax normalization, scan and thresholding into one pass over the data follows the same "load once, store once" reasoning as §11.9.
- **Operator assumptions**: the parallel algorithms need an associative operator (p. 255). Floating-point addition is only approximately associative, so a tree-ordered GPU prefix sum can differ in the last bits from a sequential CPU cumsum, which can move a top-p cutoff by one token. The chapter does not discuss this; treat it as a testing consideration, not a book claim.
- **Filter dependency**: the exclusive scan of 0/1 keep flags is what Chapter 12 uses for stable compaction of candidates.
- **GEMM / attention / quantized ops**: little direct relevance. Transferable techniques: double-buffering, register tiling with unrolled loops, using shared memory only to make global accesses coalesced, arithmetic-intensity and bytes-per-element analysis.
- **Other**: scan-based offsets are how variable-length outputs (e.g. per-sequence token counts in a batch) are packed into one contiguous buffer, the "memory allocation" use the book names on p. 253.
