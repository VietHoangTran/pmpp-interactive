# Chapter 19 — Convolutional neural networks

- **Book pages:** 453–475  **PDF pages:** 478–500 (pdf = book + 25)
- **In one paragraph:** The chapter (with contributions from Juan Gómez-Luna, p. 453) uses LeNet-5 to define the forward path of a convolutional layer, writes it as a sequential C loop nest, parallelises it directly as a CUDA kernel (one thread per output pixel, 3D grid over output map × tile × batch sample), and then shows the more important move: re-express the layer as one matrix multiplication `Y = F · B`, where `F` is the filter bank viewed as an `M × (C·K·K)` matrix and `B` is the input "unfolded" into a `(C·K·K) × (H_out·W_out)` matrix. `B` is never stored; a tiled-matmul kernel computes each `B` element's source address in `X` while loading tiles into shared memory. The chapter closes with how the cuDNN library exposes and implements the same idea. Afterwards a reader can write the direct kernel, derive and apply the `B[u,v] → X[...]` index map, adapt a tiled GEMM kernel to an implicitly materialised operand, and explain why frameworks lower convolution to GEMM. Marking convention used in these notes: anything labelled **(derived)** is our own arithmetic or reading of a listing, not a statement in the book.

## Concepts

### Chapter opening (pp. 453–454)
- Deep learning = ML with deep hierarchies of classifiers / feature extractors and very many parameters; it stayed dormant until large datasets and GPU compute arrived. The book dates the industry take-off to 2012 (p. 453).
- Readers are pointed to Appendix B for ML and neural-network background (p. 454).
- Claim that motivates the chapter: convolutional layers have a high compute-to-memory-access ratio and a lot of parallelism, which makes them good GPU targets (p. 454).
- Stated plan: a basic CUDA implementation of the forward (inference) path of a convolutional layer, "a few optimizations", then formulation as matrix multiplication (p. 454). See "Unclear in the PDF": the only optimisation actually developed is the GEMM formulation.

### §19.1 Convolutional neural networks (pp. 454–459)
Kept brief; the target reader knows this material.
- History as the book tells it (pp. 454–455): CNNs invented in the late 1980s; feed-forward networks revived around 2006 with unsupervised methods; GPUs let researchers train "ten times faster" than CPUs; 2012 University of Toronto ILSVRC entry (about 60 million parameters, 650,000 neurons, 1.2 million ImageNet images, 1000 classes, trained in one week on two GPUs with Krizhevsky's CUDA library cuda-convnet, 15.3% test error vs 26.2% for the runner-up).
- LeNet-5 is the working example (p. 455). Three layer types: convolutional, subsampling, fully connected. The book says convolutional layers account for most CNN execution time, so the chapter covers only them.
- Forward path vs backward-propagation path: the forward path runs in both inference and training, so it is the one accelerated here. A footnote leaves CUDA back-propagation to the reader (p. 455).
- Terms (p. 456): inputs and outputs of a layer are **feature maps** (or **features**); a set of weights applied to a local patch is a **filter** (the convolution mask of Chapter 7). Later pages also call one K×K filter a **filter bank** (p. 458) and the whole collection "the bank" (p. 456); the terminology drifts.
- In this chapter an output pixel = sum, over all input feature maps, of the convolution of a patch with the filter for that (output map, input map) pair. The activation function is deliberately left out; the book says it can be added as a separate kernel or at the end of the same kernel (p. 456).
- Filter count: one filter per (input map, output map) pair, so `M × C` filters. Fig. 19.2 example: 3 inputs × 2 outputs = 6. LeNet C3: 6 × 16 = 96 (p. 456).
- Worked dot product for output map 0, pixel (0,0) of Fig. 19.2(b), Eq. 19.1 (p. 457): `(1,2,1,1)·(1,1,2,2) + (0,2,0,3)·(1,1,1,1) + (1,2,0,1)·(0,1,1,0) = 14`. Footnote: integers are used for readability; real values are floating point.
- Boundary handling (p. 457): LeNet-5 uses 5×5 filters and no ghost-cell assumption; instead the last four rows and columns of the input act as the ghost cells, so each dimension shrinks by four (32×32 → 28×28). In code this is `H_out = H - K + 1`, `W_out = W - K + 1`.
- Array shapes used throughout (p. 458): input `X` is `C × H × W` (called the **input tensor**), output `Y` is `M × (H-K+1) × (W-K+1)`, filter bank `F` is `M × C × K × K`. `F[m, c, _, _]` is the filter for the contribution of input map `c` to output map `m`. Row-major layout, highest dimension first.
- LeNet-5 numbers (p. 458): C1 input 1×32×32, output 6×28×28. C3: 6 input maps of 14×14, 16 output maps of 10×10, 96 filters of 25 weights each. S4 produces 16 maps of 5×5. C5 uses 16 × 120 = 1920 filters of 5×5 to produce 120 one-pixel maps. F6: 84 outputs, `Y6 = sigmoid(W * X + b)`, equivalent to 84 perceptrons each reading all 120 C5 values. Output layer: Gaussian connections producing 10 values (p. 459). The fully connected layer implementation is "left as an exercise" (p. 458), though no numbered exercise asks for it.
- **Batched convolution layer** (p. 459): several inputs are run together; the input and output maps belonging to one input are a **sample**. Stated benefit: a larger grid with more thread blocks, hence better use of GPU execution resources; especially common in training. `X` and `Y` gain a leading `N` dimension; `F` does not, because weights are shared across the batch. The batched loop nest (Fig. 19.4) is the baseline for the CUDA kernels.

### §19.2 A CUDA convolutional layer kernel (pp. 460–463)
- Loop classification in Fig. 19.4 (p. 460):
  - "Easy" parallel loops: `n` (samples), `m` (output maps), `h` and `w` (output pixels). Their iterations write different `Y` elements.
  - The inner `c`, `p`, `q` loops are also parallelisable in principle, but all their iterations accumulate into the same `Y` element (read-modify-write), which would need heavy use of atomic operations. The book keeps them serial "unless we really need more parallelism".
- Available parallelism: `N * M * H_out * W_out` independent iterations (p. 460).
- Design decisions (p. 460):
  - One thread computes one output-map element.
  - 2D thread blocks of `TILE_WIDTH × TILE_WIDTH`; with `TILE_WIDTH = 16` that is 256 threads per block; a block computes one tile of one output map.
  - Number of blocks the easy parallelism supports: `N * M * (H_out/TILE_WIDTH) * (W_out/TILE_WIDTH)`.
- The 3D grid can be assigned in several ways; the book details one and leaves the others as an exploration for the reader (p. 460). The chosen mapping (pp. 460–461):
  1. Grid X ↔ output feature map `m` (`blockIdx.x`).
  2. Grid Y ↔ linearised tile index inside the output map (`blockIdx.y`).
  3. Grid Z ↔ sample `n` in the batch (`blockIdx.z`).
- Why Y is linearised (p. 461): two grid dimensions would be the natural fit for vertical and horizontal tile indices, but X and Z are already taken, so the 2D tile index `(tile_row, tile_col)` is packed row-major into one number: `blockIdx.y = tile_row * W_grid + tile_col`. Total `T = H_grid * W_grid` blocks in Y.
- Worked example for Fig. 19.6 (p. 461): `M = 4`, each output map is 2×2 tiles (`W_grid = 2`, `H_grid = 2`) of 16×16 = 256 pixels, tiles (0,0), (0,1), (1,0), (1,1) ↔ `blockIdx.y` 0, 1, 2, 3, so `T = 4` and the launch is `gridDim(4, 4, N)`.
- Recovering pixel coordinates in the kernel (p. 463): `blockIdx.y / W_grid` gives the vertical tile index, `blockIdx.y % W_grid` the horizontal one; multiply by `TILE_WIDTH` and add `threadIdx.y` / `threadIdx.x`.
- Each thread keeps its running sum in a local `acc` (a register) and writes `Y` once at the end, so no atomics and no repeated global writes (p. 463).
- The listing uses multi-dimensional index notation (`X[n, c, h + p, w + q]`) as pseudo-code; the reader is told to translate to linearised row-major indexing as in Chapter 3 (pp. 461, 463).
- Performance verdict (p. 463): high parallelism, but "consumes too much global memory bandwidth"; like the Chapter 7 convolution kernels its speed is limited by global memory bandwidth. Shared-memory tiling as in Chapter 7 would help and is left as an exercise for the reader. The book moves on to "a more systematic approach".
- (derived) Per output pixel the kernel does `C*K*K` multiply-adds and `2*C*K*K` global loads (one from `X`, one from `F`), with nothing shared between threads or blocks. This is the low compute-to-memory-access situation the book criticises, though the book gives no number.

### §19.3 Formulating convolutional layer as GEMM (pp. 463–472)

**Why the direct kernel cannot simply be tiled (p. 463)**
- Reuse opportunity: every input feature map is used to compute every output feature map.
- Obstacle: in Fig. 19.7 different thread blocks compute different output maps, and shared memory is private to a block, so an input tile loaded by one block cannot be reused for another output map. Getting that reuse needs a redesign.

**The idea (pp. 463–464)**
- Approach credited to Chellapilla et al. [8]: turn the convolutional layer into an equivalent matrix multiplication. Then the known tiling techniques for matmul (the book cites Chapter 15) give reuse of both the input feature maps and the filter banks, and one can "just use or slightly adapt" a GEMM (General Matrix Multiply) kernel from cuBLAS, the CUDA linear algebra library (p. 464).
- Core observation: each output element is a dot product between input elements and filter elements; a matrix product is a table of dot products between rows of the first operand and columns of the second. So arrange filters as rows and input patches as columns (p. 464).
- Footnote 3 (p. 464) points to Pete Warden's 2015 blog post "Why GEMM is at the heart of deep learning".

**Matrix F: the filter bank (pp. 464–465)**
- Row `m` of `F` = all filters for output map `m`, each linearised row-major, concatenated in increasing input-map order: `F[m,0], F[m,1], …, F[m,C-1]`.
- Shape `M × (C·K·K)`. In the example: `2 × (3·4) = 2 × 12`.
- No data movement needed: the `F` array is already stored as `m × c × p × q` in row-major order, so the 4D array reinterpreted as a 2D matrix is exactly this layout (p. 465). The book stresses this twice.
- Example rows: row 0 = `1 1 2 2 | 1 1 1 1 | 0 1 1 0`, row 1 = `1 0 0 1 | 2 1 2 1 | 1 2 2 0`.

**Matrix B: the unfolded input (pp. 465–466)**
- Column `v` of `B` = for the output pixel with row-major index `v`, the K×K patch of every input map, each linearised row-major, concatenated in increasing channel order.
- Shape `(C·K·K) × (H_out·W_out)`. In the example: `12 × 4`.
- Single-dot-product form of the worked pixel, Eq. 19.3 (p. 466): `(1,2,1,1,0,2,0,3,1,2,0,1)·(1,1,2,2,1,1,1,1,0,1,1,0) = 14`.
- Column ordering is chosen so that the product comes out in row-major pixel order: row `m` of `Y = F·B` is output map `m` linearised. So the product matrix is already `Y[n, m, _, _]` in the layout the next layer expects; no reshuffle after the multiply (p. 466).
- Samples in a batch are independent, so the picture is drawn for one sample `n`; `F` is shared by all samples (p. 464, Fig. 19.8 caption p. 465).
- Full example product (Fig. 19.8, p. 465; we re-computed and it checks): `Y` matrix rows are `14 20 15 24` and `12 24 17 26`.

**Cost of explicitly unfolding (pp. 466–467)**
- Example: `B` has 12·4 = 48 elements; the three 3×3 inputs have 27. Ratio 48/27 = 16/9 ≈ 1.78×.
- Cause: patches for neighbouring output pixels overlap, so input pixels are replicated. Per 3×3 input map with K = 2: the centre pixel is used 4 times, the 4 edge-middle pixels 2 times each, the 4 corners once: `4·1 + 2·4 + 1·4 = 16` entries from 9 pixels.
- General size: rows = `C * K * K` (inputs contributing to one output pixel), columns = `H_out * W_out` (pixels per output map). `M` does not appear, because all output maps are computed from the same `B`.
- Expansion ratio, Eq. 19.4 (p. 467): `(C·K·K·H_out·W_out) / (C·H_in·W_in) = K²·H_out·W_out / (H_in·W_in)`. It approaches `K²` when maps are much larger than filters. The book's rough claim: with maps of hundreds to thousands of pixels per side and `K ≥ 5`, expansion "can be easily 20× or more".
- Second cost: building `B` explicitly is an extra pass that itself consumes global memory bandwidth, cancelling the benefit the matmul formulation was meant to bring (p. 467).
- (derived) For LeNet C1 the ratio is 25·28·28/(32·32) ≈ 19.1; for C3 it is 25·10·10/(14·14) ≈ 12.8.

**Implicit unfolding (pp. 467–470)**
- Practical systems generate `B` piecemeal inside the tiled matmul. A tiled kernel (Fig. 5.9) already has a "load a tile of each operand into shared memory" step per phase; change the `B` load so each thread fetches its element straight from `X`. `X` stays in global memory in its original form. In the book's words, `B` is conceptual and **materialized** on demand, tile by tile (p. 468).
- Requirement: a mapping from any `B[u,v]` to a unique `X` element (p. 468).
- Tile walk-through with 2×2 tiles (Fig. 19.9, p. 468): the 2×4 `Y` matrix needs two thread blocks of 4 threads. For the block producing the left half of `Y`:
  - Phase 0 loads `B[0,0] ← X[n,0,0,0]`, `B[0,1] ← X[n,0,0,1]`, `B[1,0] ← X[n,0,0,1]`, `B[1,1] ← X[n,0,0,2]`.
  - Phase 1 loads `B[2,0] ← X[n,0,1,0]`, `B[2,1] ← X[n,0,1,1]`, `B[3,0] ← X[n,0,1,1]`, `B[3,1] ← X[n,0,1,2]`.
  - Note the same `X` element feeding two `B` elements in each phase: that is the replication, now happening only in shared memory.
- Derivation of the map (pp. 469–470):
  - `v` is the row-major index of the output pixel. Output coordinates: `(v / W_out, v % W_out)`. These are also the coordinates of the upper-left corner of the input patch.
  - `u` encodes the input channel and the position within the patch. Channel `c = u / K²`. Position inside the patch: `u % K²`, i.e. local row `(u % K²) / K`, local column `(u % K²) % K`.
  - Add the local offsets to the patch corner to get coordinates in the input map.
- Eq. 19.5 (p. 470), the mapping (`/` integer divide, `%` remainder):
  `B[u, v] ← X[n, u/(K²), (u%K²)/K + v/W_out, (u%K²)%K + v%W_out]`
- Worked example (Fig. 19.10, pp. 469–470): `B[10,2]` with K = 2, `W_out = 2`. Channel `10/4 = 2`. Local row `(10%4)/2 = 1`, local column `(10%4)%2 = 0`. Patch corner `(2/2, 2%2) = (1, 0)`. Source `X[n, 2, 1+1, 0+0] = X[n,2,2,0]`, whose value is 3.

**The adapted kernel (pp. 470–471)**
- Fig. 19.11 is Fig. 5.9 with: convolution parameters instead of `Width`; batch sample taken from `blockIdx.z`; phase count `(C*K*K)/TILE_WIDTH` (the width of `F`); `F` tile load unchanged in form; `B` tile load replaced by a load from `X` using Eq. 19.5 with the 4D `N×C×H×W` index linearised row-major and `W_out` written as `W-K+1`; final store into the 3-level-linearised `Y`.
- Bounds checking is deliberately omitted and left as an exercise for the reader (p. 470).
- (derived from the listing) Because one block now covers `TILE_WIDTH` rows of `Y` (16 output maps) and `TILE_WIDTH` columns (16 output pixels), each `B` tile loaded from `X` is shared by 16 output maps, and each `F` tile by 16 output pixels. This is precisely the cross-output-map reuse that the direct kernel of Fig. 19.7 could not get.

**When it pays off (p. 472)**
- Matmul is highly optimised on all hardware platforms. Tiled matmul on GPUs has a high ratio of floating-point operations per byte of global memory accessed.
- Reuse per loaded element is proportional to the tile dimension (recalled from Chapter 5), so small matrices that force small tiles lose efficiency, and kernel launch overhead becomes significant for small multiplications. The approach works best when it produces large matrices.
- Size argument: `F` is `M × (C*K*K)`, `B` is `(C*K*K) × (H_out*W_out)`. Apart from the height of `F`, every dimension is a product of convolution parameters. Early layers: small `C`, large `H_out`, `W_out`. Late layers: large `C`, small `H_out`, `W_out`. So `C * H_out * W_out` tends to be large in every layer, the matrices are consistently large, and GPU utilisation stays high across the network.
- (derived) LeNet shapes: C1 gives `F` 6×25 and `B` 25×784; C3 gives 16×150 and 150×100; C5 gives 120×400 and 400×1.

### §19.4 CUDNN library (pp. 472–474)
- What it is (p. 472): a library of optimised routines for deep-learning primitives, built so frameworks can use GPUs easily. C-language API. Frameworks named: PyTorch, Caffe, TensorFlow, MXNet. The book writes the name "CUDNN" in the text.
- Data must already reside in GPU device memory for inputs and outputs, the same requirement as cuBLAS (p. 472).
- Thread-safe: its routines can be called from different host threads (p. 472).
- API shape (p. 472): forward and backward convolution routines share a common descriptor holding the layer's attributes. Tensors and filters are accessed through opaque descriptors; tensor layout can be specified with arbitrary strides along each dimension.
- The key primitive is a batched convolution; the section covers its forward form (p. 472). Footnote 4: a tensor is an array with more than two dimensions; treat a T-dimensional tensor as a T-dimensional array.
- Naming differs from §19.1–19.3 (Table 19.1, p. 473). Note especially that cuDNN's `K` is the number of output maps (the chapter's `M`), and filter height/width are `R`, `S` (the chapter's single `K`).
- Inputs (pp. 472–473): `D`, an `N × C × H × W` data tensor, and `F`, a `K × C × R × S` filter tensor. Output `O` is `N × K × P × Q` with `P = f(H; R; u; pad_h)` and `Q = f(W; S; v; pad_w)`. The book gives only this functional dependence, no formula.
- Stride `u`, `v`: lets the user cut computation by computing only a subset of output pixels. Padding: number of rows/columns of zeros appended to each feature map; the reason the book gives is "improved memory alignment and/or vectorized execution" (p. 473).
- Algorithms cuDNN supports for a convolutional layer (p. 473): matrix-multiplication-based (GEMM [10] and Winograd [11]), FFT-based [12], "etc."
- cuDNN's GEMM-based algorithm matches §19.3: it avoids materialising the expanded input matrix in global memory by lazily generating and loading it into on-chip memory only, instead of gathering it in off-chip memory and then calling a matmul routine (p. 473).
- The underlying matmul routine (pp. 473–474): NVIDIA's routine achieves high utilisation of the maximal theoretical floating-point throughput; its algorithm is similar to reference [10] (Tan et al., DGEMM on Fermi). Fixed-size sub-matrices of inputs A and B are read successively into on-chip memory and used to compute a sub-matrix of output C. While computing on the current tiles, the next tiles are being fetched from off-chip memory into on-chip caches and other memories. This hides memory latency so the multiplication is limited only by arithmetic time.
- Index mapping in cuDNN (p. 474): the matmul tiling is independent of convolution parameters, so the correspondence between tile boundaries of the expanded matrix and the convolution problem is non-trivial. cuDNN computes that mapping dynamically as the computation proceeds and uses it to load the right elements. It costs extra indexing arithmetic compared with plain matmul but reuses the full matmul engine.
- After computing, cuDNN performs the required tensor transposition to store the result in the user's desired data layout (p. 474).

### §19.5 Summary (p. 474)
- Recaps: CNN basics; CUDA convolutional-layer kernel built on the Chapter 7 convolution pattern; formulation as matrix multiplication by "implicitly unrolling" the input feature maps (the summary's word; §19.3 says "unfolding"); the matmul kernel with implicit unrolling; cuDNN overview. Most deep learning frameworks use cuDNN, so framework users get these implementations without writing CUDA kernels.

## Code listings

### Fig. 19.3 — `convLayer_forward` (p. 457)
- Purpose: sequential C reference for the forward path of one convolutional layer, one sample, no activation.
- Signature: `void convLayer_forward(int M, int C, int H, int W, int K, float* X, float* F, float* Y)`.
- Walkthrough:
  - Lines 2–3: `H_out = H - K + 1`, `W_out = W - K + 1`.
  - Lines 4–6: loops over output map `m`, output row `h`, output column `w`.
  - Line 7: zero `Y[m, h, w]`.
  - Lines 8–11: loops over input channel `c` and filter offsets `p`, `q`; accumulate.
- Line that needs care: `Y[m, h, w] += X[c, h + p, w + q] * F[m, c, p, q];` No filter flip and no centring: the output pixel `(h, w)` reads the patch whose upper-left corner is `(h, w)`.
- Multi-dimensional indexing is pseudo-code; arrays are flat `float*`.

### Fig. 19.4 — `convLayer_batched` (p. 459)
- Purpose: same as Fig. 19.3 for a batch of `N` samples; baseline for the CUDA kernels.
- Signature: `void convLayer_batched(int N, int M, int C, int H, int W, int K, float* X, float* F, float* Y)`.
- Walkthrough: line 4 adds the outer `n` loop; lines 5–7 are `m`, `h`, `w`; line 8 zeroes `Y[n, m, h, w]`; lines 9–11 are `c`, `p`, `q`.
- Key line: `Y[n,m,h,w] = Y[n,m,h,w] + X[n, c, h+p, w+q] * F[m,c,p,q];`. `X` and `Y` carry the `n` index, `F` does not.
- Loop roles used by §19.2: lines 4–7 are the parallel loops; lines 9–11 stay serial.

### Fig. 19.5 — host launch code (p. 461)
- Purpose: compute the launch configuration for the direct kernel.
- Content (pseudo-code; `W_grid`, `H_grid`, `T` have no declared types):
  - `#define TILE_WIDTH 16`
  - `W_grid = W_out/TILE_WIDTH;` number of tiles horizontally per output map
  - `H_grid = H_out/TILE_WIDTH;` number of tiles vertically
  - `T = H_grid * W_grid;` tiles per output map
  - `dim3 blockDim(TILE_WIDTH, TILE_WIDTH, 1);`
  - `dim3 gridDim(M, T, N);`
  - `ConvLayerForward_Kernel<<<gridDim, blockDim>>>(...);`
- Needs care: integer division means the code as printed only covers output maps whose sides are multiples of `TILE_WIDTH`; the book does not discuss the remainder case. (derived) LeNet C1's 28×28 output would give `W_grid = 1` and leave 12 rows and columns uncomputed; a real version needs ceiling division plus bounds checks in the kernel.
- APIs: `dim3`, `<<<gridDim, blockDim>>>` launch syntax.

### Fig. 19.7 — `ConvLayerForward_Kernel` (p. 462)
- Purpose: direct parallelisation; one thread per output pixel.
- Signature: `__global__ void ConvLayerForward_Kernel(int C, int W_grid, int K, float* X, float* F, float* Y)`.
- Launch assumed: `blockDim(TILE_WIDTH, TILE_WIDTH, 1)`, `gridDim(M, T, N)` from Fig. 19.5.
- Walkthrough:
  - Line 3: `int m = blockIdx.x;`
  - Line 4: `int h = (blockIdx.y / W_grid) * TILE_WIDTH + threadIdx.y;`
  - Line 5: `int w = (blockIdx.y % W_grid) * TILE_WIDTH + threadIdx.x;`
  - Line 6: `int n = blockIdx.z;`
  - Line 7: `float acc = 0.;`
  - Lines 8–12: serial loops over `c`, `p`, `q`: `acc += X[n, c, h + p, w + q] * F[m, c, p, q];`
  - Line 13: `Y[n, m, h, w] = acc;`
- Needs care: lines 4–5 undo the row-major tile linearisation. Divide for the vertical tile index, remainder for the horizontal one; mixing them up transposes tiles. No bounds check on `h` and `w`. Index notation must be hand-linearised (e.g. (derived) `X[((n*C + c)*H + (h+p))*W + (w+q)]`, which needs `H` and `W` passed in; the printed signature does not carry them, nor `M`).
- No shared memory, no `__syncthreads()`, no atomics.
- APIs / built-ins: `__global__`, `blockIdx.{x,y,z}`, `threadIdx.{x,y}`.

### Fig. 19.11 — `ConvLayer_MM_Kernel` (p. 471)
- Purpose: tiled matrix multiplication `Y = F · B` in which `B` is never stored; each `B` element is read from `X` via Eq. 19.5 as its tile is loaded.
- Signature: `__global__ void ConvLayer_MM_Kernel(int C, int M, int H, int W, int K, float* F, float* X, float* Y)` with `#define TILE_WIDTH 16`.
- Launch assumed: the book states only that grid Z = batch size (p. 470) and that block/thread X and Y indices are used as in Fig. 5.9. (derived) That implies `blockDim(TILE_WIDTH, TILE_WIDTH)`, `gridDim.x = (H_out*W_out)/TILE_WIDTH` (columns of `Y`), `gridDim.y = M/TILE_WIDTH` (rows of `Y`), `gridDim.z = N`. The host code is not shown.
- Walkthrough:
  - Lines 5–6: `__shared__ float Fds[TILE_WIDTH][TILE_WIDTH];` and `Bds[...]` likewise.
  - Lines 8–11: `bx`, `by`, `bz` (sample index), `tx`, `ty`.
  - Lines 14–15: `Row = by * TILE_WIDTH + ty;` (row of `Y` = output map `m`), `Col = bx * TILE_WIDTH + tx;` (column of `Y` = linearised output pixel).
  - Line 18: `float Pvalue = 0;`
  - Line 19: `for (int ph = 0; ph < (C*K*K)/TILE_WIDTH; ++ph)`; `C*K*K` is the width of `F`.
  - Line 23: `Fds[ty][tx] = F[Row*(C*K*K) + (ph*TILE_WIDTH+tx)];`
  - Lines 25–26: `int u = ph*TILE_WIDTH + ty; int v = Col;` (the `B` element this thread loads).
  - Line 28 (exact, as printed): `Bds[ty][tx]=X[bz*(C*H*W)+(u/(K*K))*(H*W)+((u%(K*K))/K + v/(W-K+1))*W+((u%(K*K))%K + (v%(W-K+1)))];`
  - Line 30: `__syncthreads();` after both tile loads.
  - Lines 32–33: `for k < TILE_WIDTH: Pvalue += Fds[ty][k] * Bds[k][tx];`
  - Line 35: `__syncthreads();` before the next phase overwrites the tiles.
  - Line 37: `Y[bz*M*(H-K+1)*(W-K+1)+Row*(H-K+1)*(W-K+1)+Col]=Pvalue;`
- How line 28 decomposes: sample offset `bz*(C*H*W)`; channel offset `(u/(K*K))*(H*W)`; row `((u%(K*K))/K + v/(W-K+1))` times `W`; column `((u%(K*K))%K + v%(W-K+1))`. `W-K+1` is `W_out`. Careful: the multiplier for the row is the input width `W`, while the divisor for `v` is the output width `W-K+1`.
- Difference from Fig. 5.9 (p. 108): there `Mds[ty][tx] = M[Row*Width + ph*TILE_WIDTH + tx]` and `Nds[ty][tx] = N[(ph*TILE_WIDTH + ty)*Width + Col]`. Here `F` plays `M` with row stride `C*K*K`, and the `N` load becomes the Eq. 19.5 gather with `u = ph*TILE_WIDTH + ty`, `v = Col`.
- Needs care:
  - No bounds checks (stated, p. 470). (derived) Correct only when `M`, `H_out*W_out` and `C*K*K` are all multiples of 16; e.g. LeNet C1 has `C*K*K = 25`, so the phase loop would run once and silently drop 9 of the 25 terms.
  - Two `__syncthreads()` per phase, same roles as Fig. 5.9.
  - Integer division and remainder per loaded element: "additional indexing arithmetic" (the phrase the book uses for cuDNN, p. 474).
- APIs / qualifiers: `__global__`, `__shared__`, `__syncthreads()`, `blockIdx`, `threadIdx`.

## Relevance to LLM-inference kernels
- **Matmul / GEMM: high relevance, and the main reason to study this chapter.** §19.3 is the book's worked example of "lower an operator to GEMM, then reuse the tuned GEMM machinery". The pattern has three parts worth teaching as a reusable recipe: (1) show each output is a dot product; (2) find a view of the weights that is already a matrix without copying (here the `M×C×K×K` array read as `M×(C·K·K)`); (3) present the other operand as a virtual matrix whose elements are computed by an index function during the tile load. Elsewhere the book says attention layers of LLMs are likewise formulated as large matrix multiplications (Chapter 15, p. 350) and that GEMM matters for Chapter 20 (Chapter 3, p. 59).
- **Virtual operand in the tile-load stage.** Fig. 19.11 shows that the "load tile into shared memory" step of a tiled GEMM is a place to insert a transformation without touching the inner product loop. The book uses it for an index gather. Course-design suggestion (ours, not the book's): the same slot is where an inference kernel could dequantise packed weights, apply a layout permutation, or gather rows, so this listing is a good template for quantised matmul labs.
- **Shape reasoning (p. 472).** Reuse scales with tile dimension, and small matrices plus launch overhead make GEMM inefficient. This is directly relevant to LLM decode steps, where one operand can be very thin (batch 1, one token): the chapter's argument predicts that such shapes benefit less from tiled GEMM. The book does not discuss this case here.
- **(derived) K = 1 special case.** With `K = 1`, Eq. 19.5 reduces to `B[u,v] ← X[n, u, v/W_out, v%W_out]`, the expansion ratio of Eq. 19.4 is 1, and `B` is just `X` viewed as `C × (H·W)`. A 1×1 convolution is a linear layer applied at every position, which is what an LLM projection does per token.
- **Library layer (§19.4).** cuDNN is the convolution analogue of calling cuBLAS for linear layers: descriptors, layout flexibility, algorithm choice, device-resident data. Useful as the model of how frameworks reach kernels.
- **Attention, quantised ops, sampling (softmax, top-k/top-p, argmax):** little direct relevance. None is discussed. The activation function is explicitly out of scope (p. 456).
- **Batching (p. 459)** as a way to fill the GPU is the same motivation as batched inference, but the chapter gives no numbers.

## Portability notes

## Ideas for interactives and labs
- **Unfold explorer (Fig. 19.8).** Show X, F, B, Y with the book's numbers. Hover a `Y` matrix cell to highlight its `F` row, its `B` column, and the three patches in `X`. Animate patches sliding into `B` columns. Display a per-pixel replication count (centre 4, edge 2, corner 1) and the running expansion ratio.
- **Expansion-ratio sliders (Eq. 19.4).** Sliders for `K`, `H_in`, `W_in`, `C`; plot ratio vs map size approaching `K²`. Predict-then-reveal: LeNet C1 (≈19.1, derived) and the book's 3×3, K = 2 case (16/9).
- **Index-map trainer (Eq. 19.5, Fig. 19.10).** Given `(u, v)`, `K`, `W_out`, the learner predicts channel, local row/column, patch corner, and final `X` index. Seed with `B[10,2] → X[n,2,2,0] = 3`. Reverse mode: given an `X` pixel, list every `(u, v)` that maps to it.
- **Phase stepper (Fig. 19.9, Fig. 19.11).** Step `ph`; show `Fds`, `Bds`, the `X` addresses each thread reads, and `Pvalue` per thread. Make visible that `X[n,0,0,1]` is read by two threads in phase 0.

- **Bug hunts.** (a) Fig. 19.11 with `C*K*K = 25`: find why the result is wrong (truncated phase count), then add bounds checks, which the book leaves to the reader. (b) Fig. 19.5 with a 28×28 output map: find the uncovered pixels. (c) Line 28 with `W` and `W-K+1` swapped.
- **Lab: three ways to convolve.** Implement (1) Fig. 19.7 direct kernel, (2) Fig. 19.11 implicit-GEMM kernel with bounds checks, (3) explicit unfold into `B` followed by a library GEMM call. Validate all against Fig. 19.4 on CPU. Measure time and count global-memory loads for an "early layer" shape (small `C`, large `H`, `W`) and a "late layer" shape (large `C`, small `H`, `W`) to test the p. 472 claim that the matrices stay large across layers. Measure the memory overhead of variant 3 against Eq. 19.4.
- **Lab: tile width.** Vary `TILE_WIDTH` in variant 2 and relate throughput to the "reuse proportional to tile dimension" statement (p. 472).
- **Bridge lab to LLM kernels (ours).** Set `K = 1` and show the kernel degenerates to plain tiled GEMM; then swap the Eq. 19.5 gather in the tile-load slot for another per-element transform (e.g. dequantisation) to show the slot's generality.
