# Chapter 12 — Filter

- **Book pages:** 289–302  **PDF pages:** 315–328 (pdf = book + 26)
- **In one paragraph:** (Chapter subtitle: "And warp voting".) Filter removes the items of a list that fail a criterion and compacts the survivors so there are no holes. The chapter (new in this edition) treats two families. *Unstable* out-of-place filters let every thread grab an output slot by atomically bumping a shared counter; the work is then about reducing contention on that counter (one atomic per warp via warp voting, then one per block via privatization) and making the output writes coalesce. *Stable* filters keep the input order, so each thread must know how many earlier keys survive, which is an exclusive scan of 0/1 "keep" flags (Chapter 11); the work there is about coalescing the writes through shared memory, coarsening, and showing that the single-pass scan already orders blocks correctly for an in-place filter. Afterwards a reader can write each variant, explain when stability is needed, use `__activemask`/`__ffs`/`__popc`/shuffle or a coalesced group to rank active lanes, and recognise related one-directional data-movement patterns.

## Concepts

### Chapter opening (p. 289)
- Filter rearranges a list to use memory more efficiently after some elements are deleted. Viewing deleted and remaining elements as two sub-lists, filter is the inverse of a merge operation.
- New technique introduced: **warp voting**, used to coalesce atomic operations across the threads of a warp.
- Also covered: doing the stable filter in place, and related patterns (removing duplicates from a sorted list, adding/removing rows and columns of a matrix).

### §12.1 Background (pp. 289–290)
- **Filtering**: remove selected items according to a criterion, then compact the list to eliminate the holes (p. 289).
- Use case: garbage collection. After objects are freed, the heap has many small free chunks; compacting the live objects into consecutive locations leaves one large free region at the end, so a large allocation can succeed. For a very large list, many threads moving items in parallel reduce execution time (pp. 289–290).
- **In-place** filters compact within the original list; **out-of-place** filters compact into a new list. Out-of-place needs room for a whole new list (a whole new heap in the example). In-place has a hazard: moving an item to an earlier position can overwrite an item that is itself still waiting to be moved, so threads must synchronize (p. 290).
- Out-of-place filters are common in data search/retrieval, where irrelevant items are removed to build a relevant list. General parallel approach: many threads move the remaining items into the new list simultaneously. In-place techniques are built on the scan pattern of Chapter 11 (p. 290).
- Terminology: items in a filtered list are called **keys** (p. 290).
- **Stable** filters preserve the original order of the remaining keys; **unstable** filters do not and are used when the list does not need to be ordered (p. 290, Fig. 12.1).

### §12.2 A simple parallel unstable filter (pp. 290–291)
- Kernel (Fig. 12.2): one thread per input key; a global counter `*outputSize`, zeroed before launch, holds the output length. A thread whose key passes `cond()` atomically increments the counter and uses the returned old value as its output index (pp. 290–291).
- Why unstable: the hardware may perform the atomic operations in any order, so each thread gets an arbitrary slot regardless of its key's input position (p. 291).
- Bottleneck: contention on the atomic operations, made worse because every atomic targets the *same* counter and is serialized by the hardware (p. 291). (Contrast, our note: the histogram of Chapter 9 spreads atomics over many bins.)
- Two remedies: privatization (Chapter 9, applied in §12.4) and **coalesced atomic operations**, which exploit the fact that threads of the same warp hit the same counter (p. 291).

### §12.3 Coalescing atomic operations with warp-level primitives (pp. 291–295)
- Threads of one warp issue their atomics at the same time, so they are certain to conflict and be serialized. Since lanes of a warp can coordinate cheaply, let them compute the total increment and have one lane issue a single atomic for all: a **coalesced atomic operation**. The book draws the analogy with how the hardware coalesces loads and stores from one warp (Chapter 5) (pp. 291–292).
- Four steps (p. 292):
  1. pick a **leader** among the lanes that are active at the atomic operation;
  2. find the total amount to add (number of active lanes);
  3. leader performs the atomic and broadcasts the start of the acquired range;
  4. each lane finds its offset inside the range and stores its key.
- **`__activemask()`** (p. 292): returns a 32-bit integer with bit i set if lane i of the warp is active at that point. Example: lanes 1, 2, 4, 5 active inside the `if` gives `00000000000000000000000000110110`.
- **Leader** (p. 293): deterministic choice = active lane with the smallest index = index of the least significant set bit. **`__ffs()`** (Find First Set) finds that bit but returns index + 1, because 0 is reserved for "no bit set"; hence `__ffs(activeThreads) - 1`.
- **Total increment** (p. 293): each active lane would have added one, so the total is the number of set bits: **`__popc()`** (Population Count).
- **Broadcast** (p. 293): the leader's `fetch_add(numActive)` returns the beginning index `j`; a shuffle from the leader lane distributes `j` to the other active lanes.
- **Per-lane offset** (p. 293): a lane's offset is the number of active lanes before it, a **binary prefix sum** over the active mask (ref. [1], Harris and Garland). Lane i builds a mask with bits 0..i−1 set (2^i − 1), ANDs it with the active mask, and popcounts the result.
- Worked example (ours, continuing the book's mask): lanes 1, 2, 4, 5 active → leader = lane 1, `numActive` = 4, offsets 0, 1, 2, 3 for lanes 1, 2, 4, 5.
- **Second benefit** (p. 293): active lanes of a warp now store to adjacent output locations, so the stores to global memory are more likely to be coalesced by the hardware.
- **Cooperative groups** (pp. 293–294): the API provides a **coalesced group**, a cooperative group representing the active threads of a warp. Handle: `coalesced_group activeThreads = coalesced_threads();`. Then `activeThreads.size()` is the number of active lanes and `activeThreads.thread_rank()` is a lane's index among the active lanes. Mapping from Fig. 12.3 to Fig. 12.4: `__activemask()` → declare the group; `__ffs` leader → the thread with rank 0; `__popc` → `size()`; shuffle → `activeThreads.shfl(j, 0)`; bit tricks for offset → `thread_rank()`.
- **In practice** (p. 294): the compiler already performs this coalescing of atomic operations, so programmers need not do it by hand; and the compiler refrains when it can establish that only one thread in the warp is active (where the optimization is pointless). The section exists to teach warp voting, the bit intrinsics and coalesced groups (pp. 294–295).
- **Warp voting functions** (p. 295): `__activemask()` is one. Others the reader may meet: `__all_sync()` (do all threads in the warp evaluate a condition as true), `__any_sync()` (does some thread), `__ballot_sync` (mask of which threads evaluate the condition as true). The book names `__ffs()` and `__popc()` as intrinsic functions, separately from voting functions.

### §12.4 Privatization (pp. 295–297)
- Recalled from Chapters 6 and 9: keep private versions of the output, update those to avoid contention on the public output, merge at the end (p. 295).
- Applied to filter (Fig. 12.5, p. 295): each thread block has a private output array and private counter in shared memory. Threads atomically bump the block's private counter and store kept keys in the private array. When all inputs are processed, one thread atomically adds the block's count to the public counter, and all threads together copy the private array to the reserved range of the public array. Shared memory is used so that the atomic updates and private writes have lower latency and higher throughput.
- Scope of the atomic reference changes to `cuda::thread_scope_block` for the private counter, since only threads of the same block touch it (p. 296).
- Barriers in Fig. 12.6: after zeroing the private counter (before anyone updates it), after the filtering step (all keys in the private list before commit), and after the public reservation (start index `j` visible to all threads) (pp. 296–297).
- **Second benefit** (p. 297): consecutive threads write consecutive keys to global memory, so the stores are coalesced. The private list stays unordered, so the result is still an unstable filter (Fig. 12.5 caption and layout).

### §12.5 A simple parallel stable filter (pp. 297–298)
- Stability means a thread cannot take an arbitrary slot from a counter. It needs the exact slot: the number of preceding input keys that are kept. Stable filters are used when selected elements are deleted or extracted from a *sorted* list (p. 297).
- Scheme (Fig. 12.7): one thread per key; evaluate the condition to a "keep" flag (1 or 0); the key's output offset is the sum of the keep flags of all preceding threads, i.e. an **exclusive scan** of the flags (Chapter 11); threads with keep = 1 write their key at that offset (pp. 297–298).
- Because the scan input is binary, small segments can use the **binary prefix sum** via bit operations shown in §12.3 (ref. [1]) (p. 298).
- Fig. 12.8: the grid-wide exclusive scan is done inside the same kernel, following the single-kernel scan of Chapter 11. The last thread of the grid (`i == N - 1`) writes the output size as `offset + keep` (p. 298).

### §12.6 Improving memory coalescing with shared memory and thread coarsening (pp. 298–300)
- Inefficiency of Fig. 12.8: only threads with kept keys store to global memory. Adjacent output locations may be written by threads in different warps with many inactive threads in between, so coalescing opportunities are lost (p. 298).
- Fix (Fig. 12.9): gather each block's kept keys in shared memory, then write them to global memory as one contiguous chunk with consecutive threads writing adjacent keys. The book calls this a form of privatization (pp. 298–299).
- **Thread coarsening** (Fig. 12.10): give each block more keys than it has threads. Result: fewer, larger contiguous chunks, more coalescing. Stated as the "price of finer-grain parallelization": output lists get divided into smaller chunks, which hurts coalescing (p. 299).
- Larger benefit of coarsening: the scan is the most expensive part of the stable filter, and Chapter 11 showed scan gains a lot from coarsening (better work efficiency, less synchronization). Coarsening the filter coarsens the scan inside it (pp. 299–300).
- The full implementation (exclusive scan + privatization + coarsening) is left as an exercise (p. 300).

### §12.7 In-place stable filter (p. 300)
- Motivation: the array may be very large relative to GPU global memory capacity (the heap compaction example), leaving no room for a second array.
- Rule: never write an output key to a location before the key that used to live there has been read.
- Within a block (example from Fig. 12.10): k3 ends up where k1 was, so the read must finish before that write. Enforced by a barrier between "all threads read inputs" and "all threads write outputs".
- Across blocks (same figure): k8 ends up at location 4, where k4 was; the reader and writer are in different blocks. General requirement: no block writes before all *preceding* blocks have read.
- This ordering is already enforced by the device-wide scan: for blocks i < j, read(i) → scan(i) → scan(j) → write(j) (Fig. 12.11). So the code written for the out-of-place case also works in place.
- Adapting a single-kernel exclusive scan into a single-kernel in-place stable filter is left as an exercise.

### §12.8 Related patterns (p. 301)
- Stable filter is one example of a class of patterns where data moves in one direction; many of its optimizations carry over.
- **Removing duplicates from a sorted list**: a filter whose keep-condition is "key differs from the preceding key".
- **Removing rows and/or columns from a matrix**: keys are removed by *index*, not value, so each thread can compute its key's output position analytically with no scan. In place, earlier blocks must still read before later blocks write; use the one-directional synchronization of the single-pass scan purely for ordering, with no partial sum to pass along.
- **Adding rows and/or columns to a matrix** (often done to adjust layout for memory alignment): positions are again analytic, but keys move *outward*. Out of place this makes no difference. In place it reverses the constraint: later blocks must finish reading before earlier blocks write, so the one-directional synchronization runs from the block handling the last keys toward the block handling the first.
- More complex in-place movement (transposition of matrices and tensors) is in the literature (ref. [2]).

### §12.9 Summary (p. 302)
- Unstable out-of-place filters: atomic operations; optimizations minimize the number of atomics on the counter and coalesce output writes.
- Stable out-of-place filters: built on scan, in particular the single-pass scan kernel of Chapter 11.
- In practice Thrust and CUB provide filter implementations; understanding the variants helps pick the right library call.

## Relevance to LLM-inference kernels
The book does not mention LLM sampling in this chapter; the mapping is ours.
- **Top-k candidate compaction**: once a threshold (the k-th largest logit) is known, `cond(val)` is "logit ≥ threshold" and filter produces the compact candidate list. If each candidate carries its token id, order does not matter for sampling, so the cheap unstable filter (Figs. 12.2–12.6) is enough. The book's kernels move bare `unsigned int` keys; carrying (token id, value) pairs is an extension the reader must add.
- **Top-p candidate compaction**: probabilities are sorted, a scan gives cumulative mass (Chapter 11), the keep flag is "mass before me < p", and a *stable* filter (Fig. 12.8) keeps the sorted order. In this special case the kept set is a prefix of the sorted list, so the "filter" degenerates to finding one cut index; the general stable filter matters when combining criteria (top-k ∩ top-p ∩ min-probability ∩ banned-token masks) on an unsorted row.
- **Batched sampling**: one row of logits per thread block maps directly onto privatization (Fig. 12.6): the block's shared-memory list is that row's candidate list and its private counter is that row's candidate count. If every row has its own fixed-capacity output slot, the public counter step is unnecessary.
- **Warp voting for counts**: `__popc` of an active/ballot mask counts how many lanes in a warp pass a threshold, and the masked popcount gives each lane's rank. That is a register-only way to count and place survivors of a threshold test, useful for top-k counting passes.
- **Other compaction jobs in an inference server** (ours): dropping finished sequences from a batch, pruning beams, removing duplicate token ids from a sorted list (the §12.8 dedup pattern), packing variable-length results. In-place stable filter (§12.7) fits when the buffers are large and memory is tight.
- **GEMM, attention, quantized ops**: little direct relevance. The row/column removal and insertion patterns of §12.8 relate loosely to padding or unpadding matrices for alignment.
- **Caveat stated by the book**: hand-coalescing atomics is something the compiler already does (p. 294), so the practical gains are in privatization and write coalescing; and the book recommends Thrust/CUB for production (p. 302).

## Portability notes
The chapter is CUDA-only; it says nothing about HIP or Metal. Every HIP/Metal statement below is `[unverified]`.
- Device-scope atomic counter (`cuda::atomic_ref` with `thread_scope_device`): a port needs an atomic fetch-and-add on a global-memory integer. `[unverified]` for HIP and Metal.
- Block-scope atomic on a shared-memory counter (`thread_scope_block`): needs atomics on block-shared storage. `[unverified]`.
- `__activemask()`, `__ffs()`, `__popc()`, `__shfl_sync()`: need a way to learn which lanes of the SIMD group are active, bit-scan and popcount, and an intra-group broadcast; 32-lane width assumed. `[unverified]` for HIP (including wavefront width on a given device) and for Metal.
- `__all_sync()`, `__any_sync()`, `__ballot_sync`: `[unverified]` elsewhere.
- Cooperative groups `coalesced_group`: `[unverified]` elsewhere.
- The book's remark that the CUDA compiler coalesces atomics automatically (p. 294) is specific to that toolchain; `[unverified]` for other compilers.
- Fallback with no warp-level features: the privatized kernel of Fig. 12.6 needs only shared memory, barriers and atomics; the three-kernel stable filter of exercise 1 needs only a scan and no atomics at all.
- `gridExclusiveScan` inherits all portability concerns of the Chapter 11 single-pass scan (cross-block atomics with acquire/release, busy-waiting, dynamic block ids).
