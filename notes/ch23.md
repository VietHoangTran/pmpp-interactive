# Chapter 23 — Multi-GPU programming

- **Book pages:** 541–576  **PDF pages:** 565–600 (pdf = book + 24)
- **In one paragraph:** The chapter scales one computation, a 2D Jacobi stencil with a convergence test, from one GPU to a cluster of GPUs, and uses it to introduce three programming models: MPI (host-side, two-sided message passing), NCCL (two-sided communication primitives that run inside CUDA streams) and NVSHMEM (one-sided put/get that GPU threads call from inside a kernel). The spine of the chapter is one idea: do not alternate between "everyone computes" and "everyone communicates"; compute the boundary first and overlap its transfer with the remaining computation. Achieving that introduces CUDA streams, stream priorities, events, asynchronous memset/memcpy and pinned host memory. Afterwards a reader can read a multi-GPU halo-exchange loop, explain what each synchronisation point costs, and say why NCCL and NVSHMEM remove host-side synchronisation that MPI needs. Subtitle and byline as printed: "And an introduction to MPI, NCCL, and NVSHMEM", "With special contributions from Jiri Kraus and Isaac Gelado" (p. 541).

## Concepts

### Chapter introduction (p. 541)
- Until now the book assumed one host and one device. Many applications need the aggregate power of several hosts and devices; clusters and data centres have one or more hosts with one or more devices attached to each (p. 541).
- Three programming models are covered: the Message Passing Interface (MPI), the NVIDIA Collective Communications Library (NCCL), and the NVIDIA OpenSHMEM Library (NVSHMEM) (p. 541).
- Only the key concepts needed to scale a heterogeneous application to multiple GPUs and nodes are presented. Topics: domain partitioning, point-to-point communication, collective communication, and overlapping computation with communication, all on a CUDA stencil scaled across multiple GPU nodes (p. 541).
- The implementations illustrate core principles and "can each be further optimized"; readers are pointed to tutorials and case studies for full coverage (p. 541).

### §23.1 Stencil as a running example (pp. 542–545)
- Running example: the stencil computation from Ch. 8, specifically the **Jacobi Iterative Method**. In each iteration (time step) a point's value in a structured grid is computed as a weighted sum of its neighbours from the previous time step. The kernel is called repeatedly until values stop changing significantly (p. 542).
- Convergence test: compute the **L2 norm of the residual values**, where a residual is the difference between old and new value at a grid point (p. 542).
- Terminology footnote: in this chapter "grid" means the structured grid of data values (Section 8.1); "thread grid" means a grid of GPU threads (p. 542, footnote 1).
- The kernel in Fig. 23.1 differs from Ch. 8 in two ways (the book cites NVIDIA's "Multi GPU programming models" repository for these): it is 2D instead of 3D, to simplify figures and code; and it also computes the residual and the L2 norm (p. 542).
- Points at x = 0, x = nx − 1, y = 0 and y = ny − 1 are skipped by the kernel because they are either boundary points or halo points (p. 542).
- The new value is the average of the old values at the four neighbouring points (p. 542). The residue is new minus old. Squares of residues must be summed across all threads in the grid: a block-wide reduction (as in Ch. 10) sums within the block, then one thread per block atomically adds the block sum to the grid-wide L2 norm (p. 543).
- Possible further optimisations the chapter deliberately skips: shared-memory tiling and thread coarsening (Ch. 8) to cut global memory accesses; optimised reduction (Ch. 10) or the block-wide reduction function from the CUB library (p. 543).
- **Modelled system (Fig. 23.2):** a structured grid with constant spacing in each direction, so a 2D array can represent it, one element per grid point; a grid spacing variable represents the physical distance between adjacent elements (p. 543).
- **Layout:** row-major, with x the lowest dimension followed by y. All elements with y = 0 are consecutive in memory ordered by x, then all with y = 1, and so on (p. 543).
- **Domain partitions:** with multiple GPUs the input data is divided into partitions, one per GPU. With row-major layout the natural split is along y, giving each GPU a contiguous set of rows, so each partition is contiguous in memory (pp. 543–544).
- **Halo points:** to compute values at the edge of its partition a GPU needs old values from the edge rows of adjacent partitions. For GPU 1 these are the bottom row of GPU 0's partition and the top row of GPU 2's partition (p. 544).
- **Meaning of `ny`:** the span of input rows a GPU needs, *including* the two halo rows. The first and last rows of the span are halo rows (input only); the middle `ny − 2` rows are both input and output (p. 544).
- **Why exchange is needed (Fig. 23.3):** before computing, a GPU needs valid halo rows. After computing, its halo rows are out of date, because their new values were computed by the neighbouring GPUs. Before the next iteration, each GPU must obtain updated halo rows from its neighbours and simultaneously send its own edge rows to them. This is **halo exchange** (p. 544).
- Second benefit of the 1D y-decomposition with row-major layout: halo rows are contiguous in memory, which simplifies the copy (pp. 544–545).
- **Drawback of 1D decomposition:** depending on domain shape and GPU count, large volumes must be communicated; for a very wide domain each GPU communicates an entire row. A **2D decomposition** (each GPU takes a 2D tile) reduces the surface-to-volume ratio and thus the data communicated, but each GPU then talks to four neighbours instead of two, and some of the communicated data is not contiguous. The chapter stays with 1D for simplicity (p. 545).
- **Structure of every iteration:** a **computation phase** (compute new grid values) and a **communication phase** (exchange new halo rows between adjacent partitions). Because the L2 norm must cover all partitions, the communication phase also includes a reduction of the per-GPU norms (p. 545).

### §23.2 Multi-GPU stencil with MPI (pp. 545–553)
- **Two categories of parallel programming model (p. 545):**
  - **Shared memory models:** threads or processes access the same memory space, which simplifies sharing. CUDA kernels follow a shared memory model: different CUDA threads can access the same global memory variable through the same pointer.
  - **Distributed memory models:** threads or processes have distinct memory spaces; sharing must be explicit, for example by passing messages.
- **MPI** is described as the dominating programming interface for computing clusters: a set of API functions for communication between processes in a cluster, assuming distributed memory, with processes exchanging messages. Applications need not deal with the interconnect. Processes address each other by logical numbers, likened to phone numbers: you dial without knowing where the other person is or how the call is routed (pp. 545–546).
- In a typical MPI application data and work are partitioned among processes; each node can hold one or more processes (Fig. 23.4). Processes get data from each other by sending and receiving messages (e.g. halo exchange) and produce collective results with collective communication functions (e.g. reducing the L2 norm) (p. 546).
- **SPMD:** like CUDA, MPI programs follow the SPMD model: all MPI processes execute the same program (p. 546).
- **Launching:** the user gives the executable to `mpirun` or `mpiexec`, which creates the processes. Footnote: the MPI standard suggests `mpiexec`; implementations such as Open MPI offer both as synonyms (p. 546).
- **Setup/teardown (Figs. 23.5, 23.6):**
  - `MPI_Init()` initialises the communication system for all processes running the application (pp. 546–547).
  - `MPI_Comm_rank()` returns the calling process's **MPI rank**, a unique number from 0 to (number of processes − 1). The rank is the "phone number". The book compares it to `blockIdx.x*blockDim.x + threadIdx.x` for a CUDA thread, and notes that ranks can be organised in multiple dimensions with MPI Cartesian communicators, as CUDA threads can have up to three dimensions (p. 547).
  - **Communicator:** a variable of built-in type `MPI_Comm` specifying the group of processes in scope for a call. `MPI_COMM_WORLD` is the default and includes all MPI processes running the application. An application can create several communicators (footnote points to the MPI reference manual for intracommunicators and intercommunicators). MPI types live in `"mpi.h"` (p. 547).
  - "MPI process" and "MPI rank" are used interchangeably in the MPI literature (p. 547).
  - `MPI_Comm_size()` returns the **number of ranks** in the communicator. The value is set by the user at launch via `mpirun`/`mpiexec`; querying it avoids implicit assumptions about how the application was launched when deciding how many partitions to create (p. 548).
  - `MPI_Finalize()` frees all MPI communication resources (p. 548).
- **Per-process setup (code omitted by the book):** knowing its rank and the number of ranks, each process identifies its partition, allocates GPU memory with `cudaMalloc`, initialises it with `cudaMemset`, and launches a simple kernel to set boundary elements from the system's boundary conditions (p. 548).
- **Array layout per process:** `output` and `input` each hold `ny × nx` elements in the global memory of that host's GPU. The first row (elements 0 to `nx-1`) is the halo from the top neighbour; the last row (elements `(ny-1)*nx` to `ny*nx-1`) is the halo from the bottom neighbour (p. 548).
- **Main loop (Fig. 23.7):** iterate until the L2 norm falls below a tolerance or the iteration cap is hit; reset the norm, run the kernel, wait for it, exchange halos, bring the norm to the host, reduce it across ranks, swap buffers (double buffering) (pp. 548–549).
- **Point-to-point communication:** exchange of a message between two processes. Basic routines are `MPI_Send()` and `MPI_Recv()`: the source calls send, the destination calls receive, like dialling and answering. Because both sides must participate, this is **two-sided communication** (p. 549).
- `MPI_Send` parameters (Fig. 23.8): buffer pointer, element count, `MPI_Datatype`, destination rank, tag (classifies messages from the same process), communicator. Datatype values include `MPI_DOUBLE`, `MPI_FLOAT`, `MPI_INT`, `MPI_CHAR`; their exact sizes follow the corresponding C types on the host (pp. 549–550).
- `MPI_Recv` parameters (Fig. 23.9): buffer pointer, *maximum* element count, datatype, source rank, expected tag, communicator, status. `MPI_ANY_TAG` accepts any tag from the source (p. 550).
- **Why `MPI_Sendrecv`:** in a halo exchange every process sends its boundary to one neighbour while it must receive from the other neighbour at the same time (process 1 sends its top boundary to process 0 while process 2 sends its top boundary to process 1). `MPI_Sendrecv()` sends to a destination and receives from a source simultaneously; it is a combination of the two basic calls (pp. 550–551).
- **Non-blocking alternative:** `MPI_Isend` + `MPI_Irecv`, then `MPI_Wait`. These can express more complex concurrent patterns; `MPI_Sendrecv` is a convenient single call for this particular pattern (p. 551).
- **Periodic boundary condition technique:** neighbours are computed with wrap-around, so the topmost rank treats the bottommost rank as its top neighbour and vice versa. Used to model a large system by simulating a small portion without a disproportionate amount of edge effects (p. 551).
- **The two exchanges (Fig. 23.7 lines 13–18):** first call sends the top boundary row (starts at `output + nx`) to the top neighbour and receives the bottom halo row (starts at `output + (ny - 1)*nx`) from the bottom neighbour. Second call sends the bottom boundary row (starts at `output + (ny - 2)*nx`) to the bottom neighbour and receives the top halo row (starts at `output`) from the top neighbour. Always `nx` elements of `MPI_FLOAT` (p. 552).
- **CUDA-aware MPI:** the `output`/`input` pointers handed to `MPI_Sendrecv` point to GPU device memory. That works only with a CUDA-aware MPI. Otherwise the programmer would copy device to host and call MPI on the host array. CUDA-aware MPI removes the `cudaMemcpy` calls from the source, reducing host code bloat and added communication latency. The book states that most MPI implementations (e.g. MPICH, OpenMPI, MVAPICH2) are designed to be CUDA-aware and are built with this feature enabled (p. 552).
- **Collective communication:** involves all ranks in the communicator, unlike point-to-point. Common types: barrier, broadcast, reduce, gather, scatter. Collective functions are highly optimised by MPI runtime developers and system vendors; using them usually beats hand-built sequences of sends and receives in performance, readability and productivity (p. 552).
- **`MPI_Allreduce` (Fig. 23.11):** takes a buffer from each rank, reduces the buffers element-wise into one buffer, and gives every rank a copy. Built-in operations include sum, product, minimum, maximum, logic operations (pp. 552–553).
- **Norm reduction in the loop:** each GPU has computed the *square* of its partition's L2 norm (the sum of squared residues). The value is copied device to host, summed across ranks with `MPI_SUM` and count 1, then the square root gives the system-wide L2 norm used in the loop condition (p. 553).
- **Why copy to host before `MPI_Allreduce`** even though a CUDA-aware MPI could reduce the GPU buffer directly: the result is needed on the host for the convergence check anyway, so copying first is more efficient (p. 553).

### §23.3 Overlapping computation and communication (pp. 553–563)
- **Problem with §23.2's loop:** the system is always in one of two modes, each using only part of the hardware. While all processes compute, the network is idle. While all processes exchange halos, the GPUs are poorly used (pp. 553–554).
- **Two-stage strategy (Fig. 23.12):**
  - **Stage 1:** each process computes only its boundary rows, the rows its neighbours need as halos next iteration.
  - **Stage 2:** each process does two things in parallel: sends the new boundary values to neighbours, and computes the rest of its partition.
  - If communication takes less time than the internal computation, the communication delay is hidden. This usually requires enough internal rows per partition (p. 554).
- **Timeline comparison (Fig. 23.13):** boundary rows should get priority so the exchange starts as early as possible; internal points keep being computed during the exchanges. The L2 reduction cannot be overlapped, since it depends on all grid points (p. 555).
- **Implementation idea:** split the one Jacobi kernel call into three: top boundary row, bottom boundary row, internal rows. To run them concurrently and synchronise communication with each independently, use **CUDA streams** (p. 555).
- **Stream:** an ordered sequence of CUDA operations (kernel calls, memory copies, among others). Operations within one stream execute sequentially in insertion order. Operations in different streams may execute concurrently with no ordering constraint (pp. 555–556).
- Stream creation (p. 556):
  ```
  cudaStream_t topStream, bottomStream, internalStream;
  cudaStreamCreate(&internalStream);
  cudaStreamCreate(&topStream);
  cudaStreamCreate(&bottomStream);
  ```
- **Kernel-call configuration parameters (p. 556):** two required (grid dimension, block dimension, from Ch. 2); optional third is the dynamically allocated shared memory size (Ch. 5), default 0; optional fourth is the stream. If omitted the call goes into a **default stream**. Form: `kernelName<<<dimGrid, dimBlock, 0, myStream>>>(...)`.
- **Kernel calls are asynchronous (p. 556).** Returning from the call means only that the kernel has been *inserted* into the stream. It does not mean the kernel finished, nor even that it started. A thread grid will eventually be launched after all preceding operations in that stream complete.
- **Row arithmetic for the three calls (pp. 557–558):**
  - Top boundary row: needs the first three rows (top halo, top boundary, top internal) as input. Pass `output` and `input` unchanged and `3` as the row count; insert into `topStream`.
  - Bottom boundary row: needs the last three rows. Pass `output + (ny - 3)*nx`, `input + (ny - 3)*nx`, row count `3`; insert into `bottomStream`.
  - Internal rows: need everything except the two halo rows. Pass `output + nx`, `input + nx`, row count `ny - 2`; insert into `internalStream`.
- **Ordering hazard and stream priority (p. 558):** kernels in different streams may execute in any order. The boundary kernels will likely run first because they were called first, but that is not guaranteed. If the internal kernel runs first and occupies all GPU resources, the boundary kernels and the exchange are delayed and the overlap is lost. Fix: give `topStream` and `bottomStream` higher priority than `internalStream`.
  ```
  int low, high;
  cudaDeviceGetStreamPriorityRange(&low, &high);
  cudaStreamCreateWithPriority(&internalStream, cudaStreamDefault, low);
  cudaStreamCreateWithPriority(&topStream, cudaStreamDefault, high);
  cudaStreamCreateWithPriority(&bottomStream, cudaStreamDefault, high);
  ```
  Streams from `cudaStreamCreate` all have the same priority. Only relative priority values matter, not absolute ones; intermediate values can be used for more than two levels (p. 558).
- **`cudaStreamSynchronize(stream)`:** waits for all preceding (existing) tasks in that stream to finish. Used on the host to wait for the top kernel before the top exchange and the bottom kernel before the bottom exchange. The internal kernel's stream is not synchronised on at that point, so it keeps running while the `MPI_Sendrecv` calls proceed: that is the overlap (p. 559).
- **New difficulty: the shared L2 norm (p. 559).** All three kernels update the same norm. So all three must wait until it is zeroed, and all three must finish before it is copied to the host. But the three kernels are in three streams, while the zeroing and the copy can each be in only one stream. Operations in one stream must be able to wait on operations in another.
- **Event:** a marker for a certain point in a stream. One can wait for a stream's execution to reach that point, either from the host thread or by placing a wait operation into *another* stream. The latter is what is needed here (p. 559).
- **Asynchronous memset:** `cudaMemset` is blocking. `cudaMemsetAsync` is non-blocking and takes a stream. It goes into `internalStream`, which orders it before the internal kernel (p. 559).
- **Event creation and use (p. 560):**
  ```
  cudaEvent_t resetL2;
  cudaEventCreateWithFlags(&resetL2, cudaEventDisableTiming);
  ```
  `cudaEventDisableTiming` is a compile-time constant saying the event will not be used for timing, which lets event-based synchronisation be implemented more efficiently. `cudaEventRecord(event, stream)` places the event in a stream (here, after the memset, so `resetL2` marks the memset's completion). `cudaStreamWaitEvent(stream, event, 0)` inserts into `stream` a wait for `event`; the third argument selects options, 0 meaning default.
- **Asynchronous copy-back (p. 560):** `cudaMemcpyAsync` is non-blocking and takes a stream. Placed in `internalStream` it waits for the internal kernel. To also wait for the boundary kernels, events `computeTop` and `computeBottom` are recorded in `topStream` and `bottomStream` after their kernels, and waits for them are inserted in `internalStream` before the copy.
- **Further overlap (pp. 560–561):** because `cudaMemcpyAsync` is non-blocking, it is inserted *before* the `MPI_Sendrecv` calls, so the device-to-host copy of the norm can overlap with network communication if the internal kernel finishes before the exchange does. The copy must be complete before `MPI_Allreduce`, ensured by `cudaStreamSynchronize(internalStream)`.
- **Reading the timeline (Fig. 23.15, pp. 561–562):** a host slot marks when an operation is *inserted*; the stream slot shows when the GPU *executes* it. E.g. the top Jacobi kernel inserted by host line 10 cannot start until the `resetL2` event is reached, so it would run earlier or later depending on how long the reset takes.
- **Synchronisation overhead (p. 562):** host synchronisation can add significant latency between completion of a compute operation and the dependent data transfer. Example: `MPI_Sendrecv` is blocking, so the host cannot begin synchronising on the bottom stream, nor start the bottom exchange, until the top exchange completes, even if the bottom kernel finished long before. That shrinks the overlap with the internal kernel. Reducing this overhead is stated as an important design goal of NCCL and NVSHMEM.
- **Pinned memory (pp. 562–563):**
  - The host buffer `l2norm_h` used by `cudaMemcpyAsync` cannot come from `malloc()`. It must be **pinned** (also called **page-locked**) memory:
    ```
    float* l2norm_h;
    cudaMallocHost(&l2norm_h, sizeof(float));
    ```
  - Background: the OS gives each application a large, logically consecutive **virtual address space**, but physical memory is limited and shared. Virtual spaces are divided into virtual pages mapped to physical pages. Goals: isolation (a process only reaches physical pages mapped into its own virtual space) and handling demand above physical capacity (only the most active virtual pages are mapped; others are placed on disk). The OS may "page out" pages to mass storage at any time.
  - `cudaMemcpy()` is implemented with **Direct Memory Access (DMA)** hardware, which works on *physical* addresses on the host side. If the data were paged out mid-transfer, the physical locations could be reassigned and the DMA operation corrupted.
  - Common solution: the CUDA runtime copies in two steps. Host-to-device: copy source into a pinned buffer (marked so the pager will not page it out), then DMA from the pinned buffer to device memory. Device-to-host: DMA into a pinned buffer, then copy to the destination.
  - Two problems with that: the extra copy adds delay; and the extra complexity leads to a synchronous `cudaMemcpy()`, because the host must take part in the copy and cannot continue until it returns.
  - Therefore `cudaMemcpyAsync()` requires the host buffer to be already allocated as pinned memory, which removes the host-side staging copy.

### §23.4 Multi-GPU stencil with NCCL (pp. 563–568)
- **Remaining inefficiency in §23.3:** the host calls `cudaStreamSynchronize` before each `MPI_Sendrecv` so that boundary kernels finish before the network transfer begins. During that time the host thread is blocked and can do no other useful work (pp. 563–564).
- **Idea:** if communication operations could themselves be placed in streams, the stream mechanism would start them as soon as their dependencies complete, without the host. This is one motivation for NCCL (p. 564).
- **NCCL:** a library of inter-GPU communication primitives. Point-to-point (send, receive) and collective (reduce, broadcast, scatter, gather). They resemble MPI's, with one important difference: NCCL primitives run on the GPU, not the host CPU, and can be placed inside CUDA streams, so the host is no longer the synchronising intermediary (p. 564).
- Second benefit: the primitives are highly optimised for multi-GPU communication within and across nodes in a topology-aware manner. Interconnects named: PCIe, NVLINK, InfiniBand Verbs, sockets (p. 564).
- NCCL is not a complete replacement for MPI; it is used together with MPI (p. 564).
- **Setup (Figs. 23.16, 23.17; pp. 565–566):**
  - NCCL operations are also based on communicators. For a group of n CUDA devices, each gets a unique rank from 0 to n − 1. With a 1-to-1 mapping between MPI processes/threads and CUDA devices, the MPI ranks can be reused as NCCL ranks.
  - Exactly one rank calls `ncclGetUniqueId` to create a unique ID object (rank 0 in the example). `MPI_Bcast` sends it from rank 0 to all ranks; all receiving ranks must also execute `MPI_Bcast` to receive it. `MPI_Barrier` makes all ranks wait until everyone has the ID before creating the communicator.
  - All ranks call `ncclCommInitRank` with the same ID, which registers them as part of one communicator replicated in each rank. `ncclCommDestroy` tears it down.
- **`ncclSend` / `ncclRecv` (Fig. 23.18):** resemble `MPI_Send`/`MPI_Recv` with one major difference: they are asynchronous and take a CUDA stream in which they are to execute (p. 566).
- **Group calls (Fig. 23.19):** NCCL has no fused send-receive function. Instead, primitives placed between `ncclGroupStart` and `ncclGroupEnd` are fused. NCCL primitives run concurrently on each CUDA device, so a device can send its boundary to one neighbour while receiving its halo from the other (pp. 566–567).
- **Changes in the loop (Fig. 23.20):** each `MPI_Sendrecv` becomes `ncclSend` + `ncclRecv` inside a group. There is no `cudaStreamSynchronize` on `topStream`/`bottomStream`; instead the stream is passed as the last argument, and the CUDA runtime ensures the primitives start after the preceding kernels in those streams have computed the corresponding rows (p. 567).
- **Blocking distinction:** `MPI_Sendrecv` returns only when communication is complete. The NCCL group call is non-blocking: after `ncclGroupEnd` the only guarantee is that the send and receive have been inserted into the stream. So extra action is needed to avoid starting the next iteration before the exchange completes: record events `exchangeTop` and `exchangeBottom` after the group calls and wait on them in `internalStream` before the next iteration (p. 567).
- **Result (Fig. 23.21):** halo exchange moves from the host timeline into the top/bottom stream timelines; synchronisation moves from host stream-syncs to event waits in `internalStream`. The host is free of communication and synchronisation except the sync on the internal stream before `MPI_Allreduce` (pp. 567–568).

### §23.5 Multi-GPU stencil with NVSHMEM (pp. 568–574)
- **Two-sided communication (MPI and NCCL):** for one process to send to or receive from another, both must execute corresponding primitives (`MPI_Sendrecv` with `MPI_Sendrecv`; `ncclSend` with `ncclRecv`). The sender specifies where the data comes from, the receiver where it goes. At run time the two sides wait for each other to reach these calls, which adds latency (p. 569).
- **One-sided communication:** a process sends to or receives from another without involving it, by accessing the other's address space directly: **put** stores into it, **get** loads from it. Not waiting for the other process reduces latency. It also lets device threads initiate communication: matching send and receive calls does not scale to hundreds of thousands of device threads, but one-sided put and get do (p. 569).
- **OpenSHMEM** is a commonly used one-sided library; **NVSHMEM** is NVIDIA's implementation for GPU clusters. Puts and gets can be initiated by host threads or by individual device threads of a kernel: any thread on the CPU or GPU of one process can load or store into part of the memory of another GPU in another process (pp. 569–570).
- **Processing element (PE):** NVSHMEM's term for a process or rank (p. 570).
- **Symmetric heap (p. 570):** how the initiator names an address in the target's address space. Each process sets aside part of its address space for its local instance of the symmetric heap, and all processes allocate corresponding objects at the same offset within it. The initiator passes the address of *its own* corresponding object; the runtime infers the offset and thus the target address.
- Allocation (p. 570):
  ```
  input  = (float*) nvshmem_malloc(nx*ny*sizeof(float));
  output = (float*) nvshmem_malloc(nx*ny*sizeof(float));
  ```
  freed with `nvshmem_free(input); nvshmem_free(output);`. All PEs must participate in these calls. Each PE allocates only its own partition; the layout of partitions (offsets of top and bottom grid points) is assumed identical across partitions (pp. 570–571).
- **In-kernel halo exchange (Fig. 23.23, p. 571):** a thread computing a value in the top boundary row (`y == 1`) puts it to the top PE at the address of the symmetric element in its own *bottom halo row*, because that is where the value belongs on the top PE. A thread computing a value in the bottom boundary row (`y == ny - 2`) puts it to the bottom PE at the address of the symmetric element in its own *top halo row*.
- **Host setup (Fig. 23.24, p. 572):** NVSHMEM can be used with MPI. An `nvshmemx_init_attr_t` object carries configuration; its `mpi_comm` field points to an MPI communicator defining the scope. `nvshmemx_init_attr(NVSHMEMX_INIT_WITH_MPI_COMM, &attr)` initialises; `nvshmem_finalize` releases. NVSHMEM can also be initialised without MPI (documentation referenced).
- **Host loop (Fig. 23.25, pp. 572–573):** one kernel in one stream computes the whole partition; it takes `top` and `bottom` PE ids.
- **How each version guarantees halos have arrived before the next iteration (p. 573):**
  - MPI (Fig. 23.14): `MPI_Sendrecv` is blocking, so by the time all processes reach `MPI_Allreduce` all halo data have been received.
  - NCCL (Fig. 23.20): waits on the exchange events, inserted with `cudaStreamWaitEvent()` before the end of the iteration.
  - NVSHMEM (Fig. 23.25): stream synchronisation only guarantees the kernel finished computing and *sending*; it does not guarantee receipt. `nvshmemx_barrier_all_on_stream(stream)` makes all PEs wait at a barrier until all NVSHMEM memory-access operations initiated by preceding kernels in the stream have completed (pp. 573–574).
- **Advantage 1: automatic overlap (p. 574).** With MPI and NCCL a kernel must terminate before its communication can start, which forced splitting boundary and internal computation into separate kernels. With NVSHMEM, some threads send halo values with put as soon as they are computed while other threads continue with internal points; the communication proceeds in the background. No separate kernels, no orchestration.
- **Advantage 2: kernel fusion (p. 574).** If a computation has several steps with communication between them, MPI and NCCL need one kernel per step; NVSHMEM allows fusing them and communicating from inside. Fusion reduces kernel launch overhead for small kernels and lets data stay in shared memory and registers across the fused steps. (Less visible in the Jacobi example, which has one operation.)
- **Granularity caveat (p. 574):** the fine-grained per-thread puts in Fig. 23.23 would perform reasonably for GPUs connected over NVLINK (low latency, high bandwidth). For slower interconnects and network communication, fewer and coarser puts are more efficient. `nvshmemx_float_put_block` lets the threads of one thread block collaborate on one coarse-grained put.

### §23.6 Summary (pp. 574–575)
- Three implementations: MPI alone (compute everything, then exchange); MPI with overlap via CUDA streams (boundary first, exchange while computing internal); NCCL with MPI (communication inside streams, host freed from synchronising; library optimised for system organisation and network topology); NVSHMEM (one-sided, removes the latency of matching sends with receives; puts/gets inside kernels allow fusion and transparent overlap) (pp. 574–575).
- **Host-initiated vs device-initiated communication (p. 575):** the comparison contrasted host-initiated two-sided communication (NCCL) with device-initiated one-sided communication (NVSHMEM). Host-initiated works well when the data is coarse-grained and can be determined independently of the overlapping computation. Device-initiated is preferred when the data is fine-grained and determined as part of that computation.
- **Convergence of the APIs (p. 575):** the book notes that NCCL recently added support for symmetric memory and device-initiated communication and may add one-sided communication soon, and that NVSHMEM also supports host-initiated communication.
- The major multi-GPU concepts covered (SPMD, ranks, barriers) all have counterparts in the CUDA programming model, which the authors take as confirming that learning one model well makes others easy to pick up (p. 575).

### Fig. 23.1 — `jacobi_kernel`, 2D Jacobi stencil with L2 norm (p. 542)
- **Purpose/signature:** `__global__ void jacobi_kernel(float* out, float* in, float* l2norm, unsigned int ny, unsigned int nx)`. One thread per interior grid point of an `ny × nx` row-major array. Launch configuration not shown; a 2D thread grid is implied by the use of `blockIdx.x/.y` and `threadIdx.x/.y`.
- **Walkthrough:**
  - Lines 03–04: thread to grid mapping with a +1 offset, so thread (0,0) handles point (1,1): `int y = blockIdx.y*blockDim.y + threadIdx.y + 1;` and the same for `x`.
  - Line 06: `residue` initialised to `0.0f` so inactive threads contribute nothing to the reduction.
  - Line 07: bounds guard `if(y < ny - 1 && x < nx - 1)`. Combined with the +1 offset this skips row 0, row `ny-1`, column 0 and column `nx-1`.
  - Lines 08–11: `val = 0.25*(in[y*nx + (x + 1)] + in[y*nx + (x - 1)] + in[(y + 1)*nx + x] + in[(y - 1)*nx + x]);` the average of the four neighbours (the centre value is not part of the sum).
  - Line 12: write `out[y*nx + x] = val`. Line 13: `residue = val - in[y*nx + x]`.
  - Line 16: `float blockL2norm = blockReduce(residue*residue);` executed by every thread, including inactive ones, outside the guard.
  - Lines 17–19: only thread (0,0) of each block does `atomicAdd(l2norm, blockL2norm);`.
- **Lines needing care:** the value accumulated in `*l2norm` is the *sum of squared residues* (square of the L2 norm); the square root is taken later on the host. `blockReduce` must be called by all threads of the block (it is outside the `if`). One atomic per block rather than per thread. Separate `in` and `out` buffers are required (Jacobi reads only old values).
- **APIs/built-ins:** `__global__`, `blockIdx`, `blockDim`, `threadIdx`, `atomicAdd`; `blockReduce` (not defined in the book; text points to Ch. 10 or CUB).

### Fig. 23.7 — host loop, MPI without overlap (p. 549)
- **Purpose:** one process's main loop: compute, then exchange, then reduce. Assumes `output`, `input` (device arrays, `ny × nx`), `l2norm_d` (device), `l2norm_h` (host pointer), `l2norm`, `tol`, `iter_max`, `rank`, `numRanks` exist.
- **Walkthrough:**
  - Line 01: `for(unsigned int iter = 0; l2norm > tol && iter < iter_max; ++iter)`.
  - Line 04: `cudaMemset(l2norm_d, 0, sizeof(float));` (blocking).
  - Line 07: `launch_jacobi_kernel(output, input, l2norm_d, ny, nx);` Line 08: `cudaDeviceSynchronize();` so new values exist before the exchange.
  - Lines 11–12: neighbours with wrap-around: `const int top = rank > 0 ? rank - 1 : (numRanks - 1);` and `const int bottom = (rank + 1) % numRanks;`.
  - Lines 13–15: `MPI_Sendrecv(output + nx, nx, MPI_FLOAT, top, 0, output + (ny - 1)*nx, nx, MPI_FLOAT, bottom, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);` send top boundary row up, receive bottom halo from below.
  - Lines 16–18: `MPI_Sendrecv(output + (ny - 2)*nx, nx, MPI_FLOAT, bottom, 0, output, nx, MPI_FLOAT, top, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);` send bottom boundary row down, receive top halo from above.
  - Line 21: `cudaMemcpy(l2norm_h, l2norm_d, sizeof(float), cudaMemcpyDeviceToHost);`.
  - Lines 24–25: `MPI_Allreduce(l2norm_h, &l2norm, 1, MPI_FLOAT, MPI_SUM, MPI_COMM_WORLD); l2norm = std::sqrt(l2norm);`.
  - Line 27: `std::swap(output, input);` (double buffering).
- **Lines needing care:** the exchange operates on `output` (the freshly computed buffer) *before* the swap, so after the swap the new `input` has valid halos. Row offsets: row 1 = `output + nx` (top boundary), row `ny-2` (bottom boundary), row 0 (top halo), row `ny-1` (bottom halo). Device pointers are passed straight to MPI, which requires CUDA-aware MPI. Tag is 0 everywhere.
- **APIs:** `cudaMemset`, `cudaDeviceSynchronize`, `cudaMemcpy`, `cudaMemcpyDeviceToHost`, `MPI_Sendrecv`, `MPI_FLOAT`, `MPI_STATUS_IGNORE`, `MPI_Allreduce`, `MPI_SUM`, `std::sqrt`, `std::swap`.

### Fig. 23.14 — host loop, MPI with overlap via streams and events (p. 557)
- **Purpose:** same loop, with boundary rows computed in high-priority streams, the internal rows in a low-priority stream, and events tying the shared L2 norm together. Assumes streams `topStream`, `bottomStream`, `internalStream` and events `resetL2`, `computeTop`, `computeBottom` were created (creation code is shown inline for the streams and for `resetL2` only, pp. 556, 558, 560), and `l2norm_h` is pinned (p. 562).
- **Walkthrough:**
  - Lines 04–07 (reset): `cudaMemsetAsync(l2norm_d, 0, sizeof(float), internalStream);` then `cudaEventRecord(resetL2, internalStream);` then `cudaStreamWaitEvent(topStream, resetL2, 0);` and `cudaStreamWaitEvent(bottomStream, resetL2, 0);`. All three kernels are now ordered after the zeroing.
  - Line 10: `launch_jacobi_kernel(output, input, l2norm_d, 3, nx, topStream);` Line 11: `cudaEventRecord(computeTop, topStream);`.
  - Lines 12–13: `launch_jacobi_kernel(output + (ny - 3)*nx, input + (ny - 3)*nx, l2norm_d, 3, nx, bottomStream);` Line 14: `cudaEventRecord(computeBottom, bottomStream);`.
  - Lines 15–16: `launch_jacobi_kernel(output + nx, input + nx, l2norm_d, ny - 2, nx, internalStream);`.
  - Lines 19–22 (copy norm): wait in `internalStream` for `computeTop` and `computeBottom`, then `cudaMemcpyAsync(l2norm_h, l2norm_d, sizeof(float), cudaMemcpyDeviceToHost, internalStream);`.
  - Lines 25–34 (halo exchange): compute `top`, `bottom`; `cudaStreamSynchronize(topStream);` (line 27) then the top `MPI_Sendrecv` (lines 28–30); `cudaStreamSynchronize(bottomStream);` (line 31) then the bottom `MPI_Sendrecv` (lines 32–34). Same buffer arguments as Fig. 23.7.
  - Lines 37–39: `cudaStreamSynchronize(internalStream);` then `MPI_Allreduce` and `std::sqrt`.
  - Line 41: `std::swap(output, input);`.
- **Lines needing care:**
  - The 3-row trick: each sub-launch reuses the same kernel with a smaller `ny`. With `ny = 3` the guard `y < ny - 1` admits only local row 1, i.e. global row 1 for the top call and global row `ny-2` for the bottom call. The internal call with `ny - 2` rows starting at global row 1 computes global rows 2 to `ny-3`. Together the three calls cover rows 1 to `ny-2` exactly once (derived by us from Fig. 23.1's guard; the book states only which rows each call needs).
  - Events are the only way an operation in one stream waits on another stream without the host.
  - The memcpy is queued before the exchanges so it can overlap them, but line 37 must precede the reduction.
  - Both `MPI_Sendrecv` calls are blocking, so line 31 cannot even be reached until the top exchange completes: the synchronisation overhead discussed on p. 562.
  - As printed, line 19 has an unbalanced extra `)`: `cudaStreamWaitEvent(internalStream, computeTop, 0));` (see Unclear).

### Fig. 23.23 — `jacobi_kernel` with NVSHMEM puts (p. 571)
- **Purpose/signature:** `__global__ void jacobi_kernel(float* out, float* in, float* l2norm, unsigned int ny, unsigned int nx, int top, int bottom)`, preceded by `#include <nvshmem.h>`. `out` and `in` must be symmetric-heap allocations.
- **Walkthrough:** lines 04–14 are Fig. 23.1's body. New lines 15–20, inside the bounds guard:
  ```
  if (y == 1) {
      nvshmem_float_p(out + (ny - 1)*nx + x, val, top);
  }
  if (y == ny - 2) {
      nvshmem_float_p(out + x, val, bottom);
  }
  ```
  Lines 22–26: block reduction and atomic add as before.
- **Lines needing care:** the destination address is a *local* address used as a symmetric name. A top-boundary value (`y == 1`) is written to row `ny-1` (bottom halo) *of the top PE*; a bottom-boundary value (`y == ny - 2`) to row 0 (top halo) *of the bottom PE*. This works only because every PE's partition has the same layout. One put per boundary grid point (fine-grained). The remote write lands in the neighbour's `out` halo rows, which the neighbour's own kernel never writes (our observation).
- **APIs:** `nvshmem_float_p` (a `__device__` function per Fig. 23.22).

## Relevance to LLM-inference kernels

Candid assessment for a reader writing single-GPU inference kernels: most of this chapter can be condensed heavily. About a third of it (the §23.3 material on streams, asynchrony, events and pinned memory) is directly useful on one GPU; the rest is cluster plumbing.

**Transfers to single-GPU inference:**
- **Kernel launches are asynchronous (p. 556).** Returning from a launch means "queued", not "done" and not even "started". Essential for correct timing of matmul/attention kernels and for understanding where a host loop actually blocks.
- **Streams as ordered queues that run concurrently with each other (pp. 555–556),** plus the optional fourth launch parameter. Useful for overlapping independent work on one GPU, which is also what Ch. 22 (p. 538) proposes for small tasks.
- **Stream priorities (p. 558).** The stated hazard, a large kernel occupying the GPU so that a small latency-critical one is delayed, is the same shape as a long batched GEMM delaying a small sampling kernel. That analogy is ours.
- **Events and cross-stream waits (pp. 559–560)** as a way to express a dependency graph on the device without blocking the host.
- **The per-iteration "small result to host" pattern.** The Jacobi loop copies one float to the host every iteration to decide whether to continue (pp. 553, 560–561). An autoregressive decode loop has the same structure: each step produces a small result (a sampled token id, an end-of-sequence check) that the host needs before deciding to continue. The lessons carry over: use `cudaMemcpyAsync` into pinned memory, queue the copy early, and synchronise only at the point where the host truly needs the value. The mapping to decoding is ours.
- **Pinned (page-locked) host memory and why async copies need it (pp. 562–563).** Directly relevant to moving token ids, logits or weights between host and device. Appendix C §C.2 (p. 624) refers back to this chapter for pinned memory when describing zero-copy access.
- **Overlapping computation with communication (pp. 553–555).** As a principle (do the part others are waiting on first, then overlap the transfer with the remaining work) it applies to any host-device or device-device transfer.
- **Fusing a reduction into a compute kernel (Fig. 23.1):** per-block reduction plus one `atomicAdd` per block. The same structure serves for computing a max, a sum for softmax normalisation, or an argmax alongside another pass. Our mapping; the book presents it only for the L2 norm.
- **Kernel fusion argument (p. 574):** fewer launches for small kernels and data kept in registers/shared memory across fused steps. Relevant to fusing small per-token operations.
- **Double buffering with pointer swap (Fig. 23.7 line 27).**

**Specific to NVIDIA clusters, little use for single-GPU kernels:**
- MPI itself (ranks, communicators, `MPI_Sendrecv`, `MPI_Allreduce`, CUDA-aware MPI).
- NCCL (communicator setup, `ncclSend`/`ncclRecv`, group calls) and NVSHMEM (symmetric heap, in-kernel put/get, barriers). These are NVIDIA libraries; the chapter gives no non-NVIDIA equivalents. Ch. 24 (p. 579) notes NCCL is used extensively for *training* LLMs in hyperscaler data centres, which is a different problem from single-GPU inference.
- NVLINK-dependent advice about fine- vs coarse-grained puts (p. 574).
- Halo exchange and domain decomposition as such. As a *pattern* (each worker owns a slab, keeps a read-only copy of its neighbours' edges, refreshes it each step) it is worth one diagram; it would matter if a model were split across GPUs, which the book does not discuss.

**By operation:** matmul/GEMM: nothing new. Attention: nothing new. Quantised ops: nothing. Sampling: only the "small result to host each step" analogy above.

## Portability notes

The book states nothing about HIP or Metal in this chapter (or anywhere in Chapters 22–24). Everything below about ports is therefore `[unverified]`.

- **CUDA streams** (`cudaStream_t`, `cudaStreamCreate`, `cudaStreamCreateWithPriority`, `cudaStreamSynchronize`, fourth `<<<>>>` parameter): a HIP port would need the HIP stream equivalents `[unverified]`; a Metal port would need to map streams onto command queues / command buffers `[unverified]`. Whether either offers stream priorities is `[unverified]`.
- **CUDA events** (`cudaEventCreateWithFlags`, `cudaEventRecord`, `cudaStreamWaitEvent`): cross-queue dependencies without host blocking would need an equivalent mechanism on HIP and Metal `[unverified]`.
- **Async memset/memcpy** (`cudaMemsetAsync`, `cudaMemcpyAsync`) and **pinned memory** (`cudaMallocHost`): HIP counterparts `[unverified]`. On Metal, the notion of host-device copies and pinning may differ on unified-memory hardware `[unverified]`; the book's DMA/paging explanation is given only for CUDA.
- **CUDA-aware MPI:** passing device pointers to MPI is a property of specific MPI builds for CUDA (p. 552). Equivalent GPU-aware MPI support for other vendors' devices is `[unverified]`.
- **NCCL and NVSHMEM:** NVIDIA libraries. The book names no counterparts for other platforms; assume none without checking `[unverified]`. OpenSHMEM itself is described as a general one-sided library (p. 569).
- **`atomicAdd` and block-wide reduction** in the kernel: both are CUDA device-side facilities; ports need the corresponding atomics and a reduction implementation `[unverified]`.
- **Portable ideas regardless of API:** two-stage boundary-first ordering, overlap of transfer with compute, two-sided vs one-sided communication, host-initiated vs device-initiated communication, symmetric addressing.

## Ideas for interactives and labs

- **Timeline simulator (Figs. 23.13, 23.15, 23.21):** one canvas with Host / Top / Bottom / Internal rows. Learner picks the model (MPI no overlap, MPI overlap, NCCL, NVSHMEM) and drags durations for memset, boundary kernel, internal kernel and each exchange. The simulator applies the dependency rules from the listings and shows total iteration time and idle gaps. Target insight: in the MPI version the bottom exchange waits for the blocking top exchange (p. 562); in NCCL it does not.
- **"Queued, not done" predict-then-reveal (p. 556):** show a host snippet with a launch followed by a host-side timer read; ask what was measured.
- **Dependency-graph puzzle (Fig. 23.14):** give the operations as nodes; learner draws required orderings (memset before all three kernels; all three kernels before memcpy; top kernel before top exchange; memcpy before Allreduce), then chooses which mechanism enforces each edge: same stream, event + wait, or host synchronise.
- **Bug hunts:**
  - Remove the `resetL2` waits (lines 06–07 of Fig. 23.14): boundary kernels may add to the norm before it is zeroed.
  - Replace `cudaMallocHost` with `malloc` for `l2norm_h` (p. 562).
  - Drop `nvshmemx_barrier_all_on_stream` from Fig. 23.25: next iteration may read stale halos.
  - Create all three streams with `cudaStreamCreate` (equal priority): correct results, lost overlap (p. 558).
  - Drop the waits at lines 43–44 of Fig. 23.20.
- **Halo pointer arithmetic drill (Figs. 23.7, 23.14, 23.23):** for given `nx`, `ny`, map each expression (`output`, `output + nx`, `output + (ny - 2)*nx`, `output + (ny - 1)*nx`, `output + (ny - 3)*nx`) to a row on a drawn grid and say whether it is halo, boundary or internal.
- **Three-row launch check:** learner verifies that the three sub-launches cover rows 1 to `ny-2` exactly once.
- **Single-GPU lab (transferable part):** split a workload into a small urgent kernel and a large background kernel on two streams; measure the urgent kernel's completion latency with equal vs different stream priorities; copy a scalar back each iteration with `cudaMemcpy` from pageable memory vs `cudaMemcpyAsync` into pinned memory and measure loop time. Measurable outcome: host-side blocking time per iteration.
- **1D vs 2D decomposition calculator (p. 545):** domain size and GPU count in; halo elements exchanged per iteration and neighbour count out.
- **Symmetric heap animation (p. 570, Fig. 23.23):** two PEs with identical heap layouts; clicking a local halo cell shows the remote cell a put will hit.
