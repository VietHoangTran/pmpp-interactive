# Chapter 17 — Sparse matrix computation

- **Book pages:** 401–424 (p. 424 is blank)  **PDF pages:** 427–450 (pdf = book + 26)
- **In one paragraph:** The chapter uses one computation, sparse matrix–vector multiply-and-accumulate (SpMV, `y = A·x + y`), to show how the choice of storage format decides how a kernel behaves on a GPU. It walks through COO, CSR, ELL, hybrid ELL+COO, JDS and CSC, and scores each against the same five criteria: space efficiency, flexibility, accessibility, memory access efficiency (coalescing) and load balance (control divergence). The recurring tension is *compaction* (drop the zeros) versus *regularization* (keep the data shape predictable so that threads in a warp do the same thing on adjacent memory). After it, a reader can write a one-thread-per-nonzero or one-thread-per-row SpMV kernel for each format, say which threads diverge and which loads coalesce, and reason about when padding, hybrid splitting or sorting is worth the preprocessing.

Conventions in these notes: "read" = taken from the page; "derived" = worked out by us from what is on the page; "figure-read" = read off an unlabeled picture (colours/positions), so slightly less certain.

## Concepts

### Chapter opening (p. 401)
- A sparse matrix is one where most elements are zero. Storing and processing zeros wastes memory capacity, memory bandwidth, time and energy (p. 401).
- Every sparse format uses some *compaction* to avoid storing/processing zeros, and pays for it with *irregularity* in the data representation (p. 401).
- Irregularity has three named costs in parallel code: under-used memory bandwidth, control flow divergence, and load imbalance (p. 401).
- The goal is a balance between *compaction* and *regularization*. Some formats compact hard and are very irregular; others compact less and stay more regular (p. 401).
- Which format is fastest is known to depend heavily on how the non-zeros are distributed (p. 401).

### §17.1 Background (pp. 402–404)
- Motivating source of sparse matrices: coefficient matrices of linear systems in science, engineering and financial modelling, where each equation (row) involves only a few variables (columns) — "sparsely coupled" (p. 402).
- Running example (Fig. 17.1): 4×4 matrix. Row 0 has non-zeros in columns 0 and 1 (so equation 0 involves x0, x1); row 1 in columns 0, 2, 3; row 2 in columns 1, 2; row 3 in column 3 (p. 402).
- Linear system form used by the book: `A × X + Y = 0`, with `A` an M×N matrix, `X` a vector of N unknowns, `Y` a vector of M constants (p. 402).
- Direct approach: `X = A⁻¹ × (−Y)`, e.g. via Gaussian elimination. Workable for moderate sizes, impractical for large sparse matrices: the size overwhelms it, and inversion creates many new non-zeros called **fill-ins**, so the inverse is often much larger than the original (p. 402).
- Iterative approach: when `A` is positive-definite (`xᵀAx > 0` for all non-zero x), Conjugate Gradient methods converge to a solution with a guarantee [ref 1]. Each iteration guesses `X`, evaluates `A × X + Y`, checks closeness to the zero vector, and refines the guess with a gradient formula (p. 402). The book relates these to the iterative PDE solvers of Chapter 8 (p. 403).
- The expensive step of each iteration is evaluating `A × X + Y`: a sparse matrix–vector multiplication **and accumulation**. `A` is sparse; `X` and `Y` are typically dense (p. 403).
- **SpMV** is the name of the standardized library interface for this: "Sparse Matrix Vector multiplication and accumulation" (p. 403). Note the book's SpMV includes the `+ Y`.
- Why remove zeros: saves storage; avoids fetching zeros and doing useless multiply/adds (saves memory bandwidth and compute); and may let the whole matrix fit in one node's memory, avoiding out-of-core or distributed methods with their I/O or network latency (p. 403).
- The five **design considerations** used for every format (pp. 403–404):
  1. **Space efficiency (compaction):** memory needed to represent the matrix.
  2. **Flexibility:** how easily non-zeros can be added or removed.
  3. **Accessibility:** which kinds of data the format makes easy to reach (e.g. "all non-zeros of row r", or "row and column of non-zero i").
  4. **Memory access efficiency:** whether the format allows an efficient access pattern for the computation — one facet of regularization.
  5. **Load balance:** whether work is balanced across threads — the other facet of regularization.

### §17.2 A simple SpMV kernel with the COO format (pp. 404–407)
- **COO (Coordinate) format:** three parallel arrays of length nnz: `rowIdx`, `colIdx`, `value`. Entry `i` is one non-zero with its row and column (p. 404). For the example: `A[0,0] = 1` is stored as `value[0]=1`, `colIdx[0]=0`, `rowIdx[0]=0` (p. 404).
- Storage overhead: two index arrays. On the tiny example the overhead exceeds the savings. Worked number: with only 1% non-zeros, COO total is about 3% of the dense size (three entries per non-zero) (p. 404).
- The figure sorts entries by row then column, and real COO data tends to be sorted, but sorting is not required; the kernel works unsorted (p. 404).
- **Parallelization:** one thread per non-zero (p. 404; Figs. 17.4, 17.5). Each thread reads its `row`, `col`, `value`, multiplies `x[col]*value`, and adds into `y[row]` with an **atomic** add, because several threads (all non-zeros of one row) target the same `y[row]` — e.g. the first two threads both hit row 0 (p. 405).
- Naming convention: kernels are named "SpMV/<format>", e.g. SpMV/COO (p. 405).
- Evaluation against the five considerations:
  - *Space efficiency:* discussion deferred until other formats exist (p. 405); later: worse than CSR (p. 409).
  - *Flexibility:* entries may be permuted freely as long as the three arrays are permuted together (Fig. 17.6). Order of processing does not change the result (pp. 405–406). Two practical reasons this matters: (1) input files may deliver non-zeros in arbitrary order, so COO is a popular format while a matrix is first being built; (2) adding a non-zero is just an append to each array, so COO is popular when the matrix changes during the computation (p. 406). A third benefit appears in §17.5 (p. 406).
  - *Accessibility:* given a non-zero, its row and column are immediate — this is what enables per-non-zero parallelism. Given a row or a column, finding all its non-zeros is not easy, so COO is poor for row-wise or column-wise traversals (p. 406).
  - *Memory access efficiency:* consecutive threads read consecutive elements of each of the three arrays, so matrix accesses are coalesced (p. 406).
  - *Load balance:* every thread does exactly one non-zero, so no control divergence except at the boundary check (p. 406).
- **Main drawback: atomics** (pp. 406–407). Two stated problems: (1) atomics have high latency and low throughput; (2) the order in which atomic adds land on one output element is non-deterministic, and with floating point that can cause numerical stability issues (book points to Appendix A).
- The fix is to give all non-zeros of a row to one thread, which needs row accessibility that COO lacks → motivates CSR (p. 407).

### §17.3 Grouping row non-zeros with the CSR format (pp. 407–410)
- **CSR (Compressed Sparse Row):** `value` and `colIdx` (length nnz) hold the non-zeros grouped by row; `rowPtrs` (length numRows+1) holds the starting offset of each row in those arrays (pp. 407–408).
- Example: values grouped as row 0 (1, 7), row 1 (5, 3, 9), row 2 (2, 8), row 3 (6). `rowPtrs[0]=0`, `rowPtrs[1]=2`, …; the extra `rowPtrs[4]` is the start of a non-existent row 4 and serves as the end marker of row 3 (pp. 407–408).
- Within a row the figure sorts by column index. Sorting gives favourable memory access patterns but is not required for correctness. When sorted, `value`/`colIdx` are the row-major layout of the matrix with zeros deleted (pp. 407–408).
- Key difference from COO: `rowIdx` (nnz entries) is replaced by `rowPtrs` (rows+1 entries) (p. 408).
- **Parallelization:** one thread per row; the thread loops `i` from `rowPtrs[row]` to `rowPtrs[row+1]`, accumulates into a local `sum`, then writes to `y[row]`. No atomics: each row is owned by one thread, so each thread writes a distinct output element (pp. 408–409).
- Evaluation:
  - *Space efficiency:* better than COO — two nnz-length arrays plus one (rows+1)-length array, versus three nnz-length arrays (p. 409).
  - *Flexibility:* worse than COO. Adding a non-zero means inserting into a specific row, shifting all later rows' entries and incrementing all later `rowPtrs`. COO just appends (given over-allocated memory) (p. 409).
  - *Accessibility:* given a row, its non-zeros are easy to reach. The book's rule of thumb for real matrices: thousands to millions of rows, each with tens to hundreds of non-zeros — so per-row threads are many and each has real work. Caveats: if a matrix has too few rows to fill the GPU, COO extracts more parallelism (more non-zeros than rows); and CSR gives no easy column access — keep a second, column-oriented copy (CSC, §17.7) if needed (p. 409).
  - *Memory access efficiency:* **not coalesced.** In iteration 0 of the dot-product loop, threads 0–3 read `value[0]`, `value[2]`, `value[5]`, `value[7]`; in iteration 1 they read `value[1]`, `value[3]`, `value[6]`, and nothing (thread 3 is done). Adjacent threads read far-apart addresses (pp. 409–410).
  - *Load balance:* loop trip count = row length, and adjacent rows can have very different lengths, so control divergence can be widespread in most or all warps (p. 410).
- Summary: CSR beats COO on space and removes atomics; loses on flexibility, coalescing and divergence. The next formats give back some space to fix coalescing and divergence (p. 410).
- Aside: converting COO→CSR on the GPU is suggested as an exercise using histogram and prefix sum (p. 410; Exercise 3).

### §17.4 Improving memory coalescing with the ELL format (pp. 410–414)
- **ELL** comes from ELLPACK, a package for elliptic boundary value problems [ref 2]. Two ideas: **padding** and **transposition** (p. 410).
- Construction (Fig. 17.10), starting from the row-grouped data: find the longest row; pad every other row at its end up to that length so the data is rectangular; pad `colIdx` identically; then store the rectangle in **column-major** order (all rows' 0th elements, then all rows' 1st elements, …) — equivalent to transposing the rectangle relative to C's row-major layout (pp. 410–411).
- Example: row 1 is longest (3). Rows 0 and 2 get one pad each, row 3 gets two. After column-major storage `value[0..3] = 1, 5, 2, 6` (pp. 410–411).
- `rowPtrs` is no longer needed: row `r` starts at index `r`, and the next element of the same row is `numRows` further on. Example: row 2's 0th element is `value[2]`, its next is `value[2+4] = value[6]` (p. 411).
- **Kernel** (Fig. 17.12): one thread per row; loop `t` over that row's non-zeros; index `i = t*numRows + row`. The kernel assumes an `nnzPerRow` vector so each thread stops at its own row length. Without that vector, a thread may simply loop over the full padded width: padding values are zero and do not change the result (p. 411).
- Coalescing argument: `i` is a function of `row`, which is a function of `threadIdx.x`, so in each iteration consecutive threads touch consecutive array elements (p. 412).
- Evaluation:
  - *Space efficiency:* worse than CSR because of padding, and the overhead depends strongly on the non-zero distribution. One or a few very long rows cause excessive padding. On the 4×4 example the 4×3 padded data plus indices is more than the dense matrix (p. 412). Worked example (pp. 412–413): 1000×1000 matrix, 1% non-zero → 10 non-zeros per row on average → CSR ≈ 2% of dense size. If one row has 200 non-zeros and the rest fewer than 10, ELL pads everything to 200 → ≈ 40% of dense size, 20× the CSR size.
  - *Flexibility:* better than CSR. A non-zero can replace a padding slot if its row is not at maximum length. With over-allocated arrays one can even extend the longest row by adding one more column (one more pad for every other row) without shifting anything — in that case as flexible as COO (p. 413).
  - *Accessibility:* both CSR-style and COO-style. Row → its non-zeros (as in the kernel). Non-zero index `i` → column via `colIdx[i]`, row via `row = i % numRows` (inverse of `i = t*numRows + row` since `row < numRows`). So ELL can be parallelized over rows or over non-zeros, but per-non-zero threads would be wasted on padding slots (p. 413).
  - *Memory access efficiency:* coalesced thanks to column-major layout (p. 413). Alignment note: some architectures, especially older generations, have stricter address-alignment rules for coalescing; one can force every iteration to start aligned to an architecture-specified unit "such as 64-bytes" by appending a few rows to the matrix before transposition `[device: unspecified older GPU generations]` (p. 413).
  - *Load balance:* unchanged from CSR — each thread still loops over its own row length, so divergence remains (pp. 413–414).
- Summary: ELL improves on CSR in flexibility, accessibility and (most importantly) coalescing; it is worse in space and no better in divergence (p. 414).

### §17.5 Regulating padding with the hybrid ELL-COO format (pp. 414–415)
- ELL's space and divergence problems are worst when a few rows are far longer than the rest. Fix: before building ELL, remove some elements from those long rows and put them in a separate COO structure. Run SpMV/ELL on the remainder, then SpMV/COO on the leftovers. Using two formats together for one computation is called a **hybrid** method (p. 414).
- Example (Fig. 17.13): pure ELL is 5 wide; after moving 3 non-zeros of one long row and 2 of another into COO, ELL is 2 wide. Padding drops from 22 slots to 3, and every thread needs only 2 iterations (p. 414).
- Is the preprocessing worth it? "It depends." For a single SpMV it can be significant overhead. In an iterative solver the same matrix is reused every iteration (only `x` and `y` change), so the cost is amortized (pp. 414–415).
- Evaluation (p. 415):
  - *Space:* better than ELL alone (less padding).
  - *Flexibility:* better than ELL alone — if a row has no padding left, append to the COO part instead of adding an ELL column.
  - *Accessibility:* worse than ELL alone. Row → all its non-zeros only works for rows that fit entirely in the ELL part; for rows that overflowed, one must search the COO part, which is expensive.
  - *Memory access efficiency:* both parts are coalesced, so the combination is too.
  - *Load balance:* less divergence in the ELL kernel; the COO part has none.
- Summary: versus ELL, hybrid gains space, keeps flexibility and coalescing, reduces divergence; price is harder row access for overflowed rows (p. 415).

### §17.6 Reducing control divergence with the JDS format (pp. 416–418)
- Goal: coalesced access and low divergence *without any padding*. Idea: sort the rows by length. The sorted matrix looks roughly triangular, hence **Jagged Diagonal Storage (JDS)** (p. 416).
- Construction (Fig. 17.14): group non-zeros by row (as CSR/ELL); sort rows by non-zero count (the figure sorts longest first — see "Unclear"); keep a `row` array recording each sorted row's original index (swap its entries whenever rows are swapped); store `value` and `colIdx` in column-major order; add an `iterPtr` array giving where each iteration's (each "column" of the jagged shape) elements begin (p. 416).
- Parallelization (Fig. 17.15): one thread per (sorted) row; in iteration `t` the threads use `iterPtr[t]` to find where that iteration's elements start. Accesses are coalesced. The book does **not** give the kernel code; it is Exercise 5 (pp. 416–417).
- **Sectioned variant:** after sorting, partition the rows into sections; rows in a section have similar lengths; build an ELL representation per section, padding only to that section's longest row. Much less padding than whole-matrix ELL. Needs a section-offset array instead of `iterPtr` (p. 417).
- Correctness of sorting: reordering rows = reordering equations, which does not change the solution, provided `y` is reordered along with the rows; the final result is put back in original order using the `row` array (p. 417).
- Cost of sorting: same amortization argument as the hybrid format — acceptable inside an iterative solver (p. 417).
- Evaluation (pp. 417–418):
  - *Space:* better than ELL (no padding). The sectioned variant has some padding, still less than ELL.
  - *Flexibility:* poor; worse than CSR, because adding a non-zero changes a row's length and may force re-sorting.
  - *Accessibility:* like CSR (row → its non-zeros). Unlike COO and ELL, it does not make it easy to go from a non-zero to its row and column.
  - *Memory access efficiency:* column-major like ELL, so coalesced. But with no padding, each iteration's start address varies arbitrarily, so there is no cheap way to force every iteration to start on an architecture-specified alignment boundary; this can make JDS accesses less efficient than ELL's.
  - *Load balance:* the defining feature — threads in the same warp get rows of similar length, so divergence is effectively reduced.

### §17.7 Column-wise accessibility with the CSC format (pp. 418–421)
- Recap of accessibility so far: COO and ELL give non-zero → (row, col); CSR, ELL and JDS give row → non-zeros. For column → non-zeros, use **CSC (Compressed Sparse Column)** (p. 418).
- CSC is CSR with rows and columns swapped: `value` grouped by column, `rowIdx` giving each value's row, and `colPtrs` (numCols+1 entries) giving each column's start. Example grouping: column 0 (1, 5), column 1 (7, 2), column 2 (3, 8), column 3 (9, 6). `colPtrs[4]` marks the end of column 3. Sorting by row within a column is shown but not required (pp. 418–419).
- The book says CSC is not intended for SpMV; the SpMV/CSC kernel is shown for completeness and for comparison (p. 419).
- **SpMV/CSC** (Figs. 17.17, 17.18): one thread per column. The thread loads `x[col]` once, loops over the column's non-zeros, and atomically adds `inValue*value` into `y[row]`. Atomics are required because threads on different columns may update the same `y` element (e.g. the first and second threads) (pp. 419–420).
- Evaluation (p. 420):
  - *Space:* same as CSR if rows ≈ columns (two nnz arrays plus numCols+1).
  - *Flexibility:* as inflexible as CSR (shift later columns, bump later `colPtrs`).
  - *Accessibility:* column → non-zeros; not useful for SpMV itself.
  - *Memory access efficiency:* not coalesced — threads 0–3 read `value[0]`, `[2]`, `[4]`, `[6]` then `[1]`, `[3]`, `[5]`, `[7]`. Plus atomics on the output.
  - *Load balance:* trip count = column length, so potentially divergent in most warps. (In the example every column happens to have 2 non-zeros, which is a coincidence.)
- Verdict: for SpMV, CSC combines the worst of COO (atomics) and CSR (uncoalesced + divergent). ELL/JDS-like tricks could partly fix the last two, but the atomics remain (pp. 420–421).
- One good property: the input vector is read in a coalesced way (adjacent threads read adjacent `x` elements), and each `x` value is loaded once and reused for the whole column. All the other formats' kernels read `x` at effectively random positions. Not enough to save CSC for SpMV (p. 421).
- Where CSC fits (p. 421): (1) **vector–matrix multiplication** (vector is the first operand): each output element is the dot product of the vector with a column. (2) **SpMSpV** (sparse-matrix–sparse-vector multiplication): when the input vector is sparse, whole columns whose `x` entry is zero can be skipped, which is easy because a column's non-zeros are grouped together.

### §17.8 Summary (pp. 421–422)
- Sparse computation is the book's simple example of **data-dependent performance**: both execution efficiency and memory-bandwidth efficiency of the SpMV kernels depend on the input matrix's non-zero distribution, unlike most earlier kernels in the book (pp. 421–422).
- **Regularization** techniques introduced: hybrid methods and sorting/partitioning. Some regularization re-introduces zeros (padding) into the compacted form; hybrids limit the pathological cases (p. 421).
- Further reading suggested: Bell & Garland [ref 3]; readers are encouraged to try different sparse data sets (p. 421).
- Sparse vs dense: dense matrices have implicit indices and are easy to tile for the memory hierarchy; sparse formats store explicit indices that must be read, and are harder to tile. Sparse only pays off when sparsity is very high (p. 422).
- FLOPS achieved on sparse matrix computation is much lower than on dense, on both CPUs and GPUs (p. 422).
- The cuSPARSE library [ref 4] provides GPU routines for basic linear algebra on several sparse formats (p. 422).

## Code listings

All four kernels share: signature `(…Matrix m, float* x, float* y)`, a 1-D grid, and `blockIdx.x*blockDim.x + threadIdx.x` as the work-item index followed by a bounds check. The book shows no host/launch code and no struct definitions for `COOMatrix`, `CSRMatrix`, `ELLMatrix`, `CSCMatrix`; the field names below are the ones used in the listings.

### Fig. 17.5 — `spmv_coo_kernel` (p. 405)
- Purpose: SpMV with one thread per non-zero. Signature: `__global__ void spmv_coo_kernel(COOMatrix cooMatrix, float* x, float* y)`. Assumes at least `numNonzeros` threads in a 1-D grid.
- Walkthrough: line 02 computes non-zero index `i`; line 03 bounds check against `cooMatrix.numNonzeros`; lines 04–06 load `row`, `col`, `value` from `rowIdx[i]`, `colIdx[i]`, `value[i]`; lines 07–08 atomically add the product into `y[row]`.
- Lines that need care (exact text):
  ```
  cuda::atomic_ref<float, cuda::thread_scope_device> y_ref(y[row]);
  y_ref.fetch_add(x[col]*value, cuda::memory_order_relaxed);
  ```
  The atomic is on a `float`; scope is device-wide; ordering is relaxed. Order of adds into one `y[row]` is non-deterministic (pp. 405, 407).
- APIs: `__global__`, `blockIdx`, `blockDim`, `threadIdx`, `cuda::atomic_ref`, `cuda::thread_scope_device`, `fetch_add`, `cuda::memory_order_relaxed`.

### Fig. 17.9 — `spmv_csr_kernel` (p. 408)
- Purpose: SpMV with one thread per row. Signature: `__global__ void spmv_csr_kernel(CSRMatrix csrMatrix, float* x, float* y)`. Assumes at least `numRows` threads.
- Walkthrough: line 02 row index; line 03 bounds check against `csrMatrix.numRows`; line 04 `float sum = 0.0f`; lines 05–06 loop `i` from `rowPtrs[row]` while `i < rowPtrs[row+1]`; lines 07–09 load `col`, `value`, do `sum += x[col]*value`; line 11 writes the result.
- Lines that need care: the loop bounds `csrMatrix.rowPtrs[row]` … `csrMatrix.rowPtrs[row+1]` (relies on the extra end marker); line 11 is `y[row] += sum;` — a plain (non-atomic) accumulate, safe because one thread owns each row.
- Data-dependent trip count → divergence; `value[i]`/`colIdx[i]` loads are not coalesced across threads (p. 410).
- APIs: `__global__`, built-in index variables only.

### Fig. 17.12 — `spmv_ell_kernel` (p. 412)
- Purpose: SpMV with one thread per row over column-major padded storage. Signature: `__global__ void spmv_ell_kernel(ELLMatrix ellMatrix, float* x, float* y)`.
- Walkthrough: line 02 row; line 03 bounds check against `ellMatrix.numRows`; line 04 `sum = 0.0f`; line 05 loop `t` from 0 while `t < ellMatrix.nnzPerRow[row]`; line 06 `i = t*ellMatrix.numRows + row`; lines 07–09 load `colIdx[i]`, `value[i]`, accumulate; line 11 writes the result.
- Lines that need care:
  - `unsigned int i = t*ellMatrix.numRows + row;` — column-major index; consecutive `row` → consecutive `i` → coalesced.
  - Line 11 is `y[row] = sum;` (assignment), unlike `+=` in Fig. 17.9. See "Unclear".
  - The loop bound uses `nnzPerRow[row]`; the text says the kernel would still be correct looping over the full padded width because pads are zero (p. 411). The listing does not show what `colIdx` holds in pad slots.
- APIs: `__global__`, built-in index variables only.

### Fig. 17.18 — `spmv_csc_kernel` (p. 419)
- Purpose: SpMV with one thread per column (shown for completeness). Signature: `__global__ void spmv_csc_kernel(CSCMatrix cscMatrix, float* x, float* y)`.
- Walkthrough: line 02 column index; line 03 bounds check against `cscMatrix.numCols`; line 04 `float inValue = x[col];` (one coalesced load of `x`, reused); lines 05–06 loop `i` from `colPtrs[col]` while `i < colPtrs[col + 1]`; line 07 `row = cscMatrix.rowIdxs[i]`; line 08 `value = cscMatrix.values[i]`; lines 09–10 atomic add of `inValue*value` into `y[row]`.
- Lines that need care:
  ```
  cuda::atomic_ref<float, cuda::thread_scope_device> y_ref(y[row]);
  y_ref.fetch_add(inValue*value, cuda::memory_order_relaxed);
  ```
  Field names here are plural (`rowIdxs`, `values`) while the text and Fig. 17.16 use `rowIdx` and `value`.
- APIs: as Fig. 17.5.

### No listing: SpMV/JDS (p. 417)
- The book deliberately omits it (Exercise 5). Any course code for JDS is ours, not the book's.

## Relevance to LLM-inference kernels

Candid summary: **the domain content (linear solvers, the catalogue of six formats) has little direct use for dense LLM inference; the reasoning method transfers well.** Good candidate for condensing to one lesson built around the comparison table.

Transferable techniques (keep):
- **Thread-to-work mapping decides whether you need atomics.** Per-non-zero threads (COO) collide on the output; per-row threads (CSR) own their output. Same choice arises in any scatter/accumulate kernel (e.g. histogramming logits, scatter-add into a vocabulary-sized buffer). The two costs of atomics — latency/throughput and non-deterministic floating-point summation order — are stated on p. 407.
- **Data-dependent trip counts cause control divergence and load imbalance** (CSR, p. 410). Any LLM kernel with per-row variable work has this shape: variable-length sequences in a batch, per-row top-k/top-p cut-offs, ragged KV-cache lengths. (The mapping to these LLM cases is our inference, not the book's.)
- **Padding to a rectangle + column-major (transposed) layout** makes per-iteration accesses coalesced (ELL, pp. 410–413). This is the same idea as padding a ragged batch and choosing which axis is contiguous across threads.
- **Padding has a price that depends on the longest row** (the 2% → 40% worked example, pp. 412–413): directly analogous to padding a batch to its longest sequence.
- **Hybrid "regular bulk + irregular tail"** (pp. 414–415): handle the common case with a regular kernel and the outliers with a slower general path.
- **Sort/bucket by length to cut divergence** (JDS and its sectioned variant, pp. 416–417): the same trick as length-bucketing sequences. Also the caveat that sorting needs an index array to restore order.
- **Amortizing preprocessing** over repeated use of the same structure (pp. 414–415, 417): relevant to one-time weight repacking/quantization layout before many forward passes.
- **Explicit indices vs implicit indices; tiling is harder on sparse data** (p. 422): the honest reason sparse/pruned weights rarely beat dense GEMM unless sparsity is very high.
- **Coalesced read of the input vector, loaded once and reused** (CSC, p. 421): a small reminder to hoist shared operands.

Domain material that can be skipped or reduced to a sentence:
- Conjugate Gradient, positive-definiteness, fill-ins, `A·X + Y = 0` framing (p. 402).
- ELLPACK history, JDS naming, alignment tricks for older GPUs (pp. 410, 413, 416).
- SpMV/CSC kernel and the SpMSpV / vector–matrix discussion (pp. 419–421), unless the course covers sparse attention masks or pruned weights.
- cuSPARSE pointer (p. 422) — one line.

Direct relevance by kernel family:
- matmul/GEMM: little direct relevance (dense). Useful only as contrast: why dense is easy to tile and sparse is not (p. 422).
- attention: little direct relevance; padding/bucketing ideas apply to ragged sequence lengths (our inference).
- quantized ops: little direct relevance.
- sampling (softmax, top-k/top-p, argmax): indirect — variable per-row work and scatter-with-atomics patterns.
