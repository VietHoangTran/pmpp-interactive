# Chapter 9 — Histogram (An introduction to atomic operations and privatization)

- **Book pages:** 201–220  **PDF pages:** 228–247 (pdf = book + 27)
- **In one paragraph:** Every pattern before this chapter let each output element be owned by exactly one thread ("owner-computes"). A histogram breaks that: which bin a thread writes depends on the data it reads, so any thread may update any output element. The chapter uses an 8-bit grayscale image histogram to introduce read-modify-write race conditions and atomic operations (through the CUDA C++ atomics API, `cuda::atomic_ref` + `fetch_add`), then shows why atomics on a contended location are slow (their throughput is bounded by roughly 1 / (2 x memory latency)), and develops four remedies in sequence: let atomics hit the last-level cache, privatize the output per thread block (first in global memory, then in shared memory), coarsen threads so fewer private copies need initialising and committing (contiguous vs interleaved partitioning), and privatize a single bin per thread to merge runs of identical values. After the chapter a reader can write a correct data-dependent-output kernel, estimate atomic throughput from latency numbers, and choose between these optimisations based on bin count, input distribution and hardware.

Legend used in these notes: **[book]** = stated in the PDF; **[inferred]** = our deduction, not printed in the book.

## Concepts

### Chapter opening (p. 201)
- **Owner-computes rule**: in all earlier patterns each output element is assigned to one thread, so threads write their own outputs with no risk of interfering (p. 201).
- **Parallel histogram pattern**: each output element can be updated by any thread. Threads must coordinate so the result is not corrupted. The book calls the conflict **output interference** (pp. 201, 204).
- Plan: a simple but slow baseline that serialises updates with atomic operations, then optimisations, "most notably privatization". The book stresses that the cost/benefit depends on the hardware and on the input data, so the developer has to reason about applicability (p. 201).

### §9.1 Background (pp. 202–203)
- A histogram shows how often data values occur; usually value intervals on the horizontal axis and a bar per interval whose height is the count (p. 202).
- Running example: an 8x8 grayscale image of a tree. Grayscale intensity is 0–255, 0 = black, 255 = white. The example histogram uses **four intervals of 64 values each**: [0-63] = 6 black trunk pixels, [64-127] = 12 dark-gray leaf pixels, [128-191] = 14 light-gray grass pixels, [192-255] = 32 white sky pixels (p. 202).
- The shape of a histogram is sometimes called a **feature** of the data set; e.g. it reveals low or high light exposure. Other uses named: credit-card fraud detection (histogram shape of purchase categories/locations deviating from the norm), computer vision (faces vs cars have different histogram shapes; histograms of image sub-areas for feature extraction), speech recognition, website purchase recommendations, scientific data analysis such as correlating movements of heavenly objects (pp. 202–203).
- Sequential algorithm (Fig. 9.2): one pass, load pixel, increment its bin. The image is treated as a 1D array of `width*height` because 2D position is irrelevant. The code assumes **one bin per pixel value**; for interval bins as in Fig. 9.1 you would divide the pixel value by the interval width before indexing (p. 203).
- Cost analysis of the sequential code: O(N); image is read sequentially so cache lines are used well; `bins` is small enough to sit in the CPU's L1 data cache; so on most modern CPUs the loop is **memory bound**, limited by how fast data moves from DRAM into the cache (p. 203).

### §9.2 Atomic operations and a basic histogram kernel (pp. 203–209)
- Simplest parallelisation: launch as many threads as input elements; each thread reads its pixel and increments that pixel's bin (pp. 203–204, Fig. 9.3). Several threads can hold pixels of the same value and so target the same bin.
- An increment is an **update**, i.e. a **read-modify-write** operation: read the location, add one, write it back (p. 204).
- Two everyday analogies for a lost update (pp. 204–205):
  - Airline seat map: two customers view the same seat map, both pick seat 9C, both mark it unavailable, both believe they hold 9C.
  - Store kiosks: customers take a ticket number from kiosks and are served in number order; if two customers sign in at two kiosks simultaneously they may both receive the same number.
- **Read-modify-write race condition**: the outcome of two or more simultaneous updates depends on their relative timing; some outcomes are right, some wrong (p. 205).
- Worked interleavings on `bins[x]` initially 0, two threads each doing Old <- bins[x]; New <- Old + 1; bins[x] <- New (Figs. 9.4, 9.5, pp. 205–206):
  - Non-overlapping sequences (either thread first) end with 2. Correct.
  - Overlapping sequences: the later reader reads 0 before the earlier writer stores 1, both write 1, final value 1. One update is lost.
- **Atomic operation** on a memory location: a read-modify-write sequence that no other read-modify-write sequence on the same location can overlap; the three parts form an indivisible unit. In practice implemented with hardware support that locks other operations out of that location until the current one completes (p. 206).
- Key caveat: atomics **do not enforce any order** between threads. Either thread may go first; the only guarantee is that the trailing thread's atomic cannot start until the leading thread's atomic has finished. This "effectively serializes" atomics on a given location (p. 206).
- CUDA API used in this edition (pp. 206–209):
  - Atomics are done through C++ **atomic objects** or **atomic reference objects**. CUDA "extends the C++ atomic library"; include with `#include <cuda/atomic>` (p. 206).
  - Footnote 1 (p. 206) is a short primer on C++ classes/templates for readers new to them, pointing to cppreference [ref 1].
  - First step is to create an atomic reference to an existing object with class `cuda::atomic_ref`. The book prints its declaration as `template <typename T, cuda::thread_scope> class cuda::atomic_ref;` (p. 207). `T` is the object type (examples: `int`, `unsigned int`, `float`). The second parameter, a `cuda::thread_scope`, says which set of threads can synchronise through the class's methods; the book lists three example scopes: within the same thread block, within the same GPU device, and across all GPU devices in a multi-GPU system (p. 207). Only two scope constants are named in the chapter: `cuda::thread_scope_device` (p. 208) and `cuda::thread_scope_block` (p. 212).
  - Footnote 2 (p. 207): alternatively declare the object itself atomic from creation with class `cuda::atomic`, which makes every access atomic. The book uses references instead because it wants to access the bins non-atomically elsewhere in the code.
  - Constructing the reference (line 06 of Fig. 9.6) looks heavy but mostly tells the compiler how to generate code for the following call; it "adds little execution cost at run time" (p. 208).
  - The atomic reference class offers methods for "addition, minimum, maximum, and, or, xor, etc." (p. 208). Only `fetch_add` is named.
  - `fetch_add`, printed as `T fetch_add(T arg, cuda::std::memory_order order)` (p. 208). `arg` is the amount to add and must have type `T` (the literal 1 is treated as an unsigned constant here). Return value: the **old** value of the object before the add. It is unused in this chapter; Chapters 12 and 18 use it (p. 209).
  - `order` is a compile-time constant "defined in the C++ standard library" restricting how the atomic may be reordered relative to **other memory accesses by the same invoking thread** (compiler or hardware may reorder memory accesses for performance). In the histogram kernel the only other access is the load of `image[i]` into `b`, and `b` selects which bin is updated, so a data dependency already forces the load first. Hence `cuda::memory_order_relaxed`: no restriction beyond what the instruction-level dependencies already impose. Chapter 11 has a case needing a stricter order (pp. 208–209).
- Basic kernel (Fig. 9.6): same as the sequential loop except (1) the loop is replaced by a global thread index + bounds check, and (2) `++bins[b]` becomes an atomic reference with device scope plus `fetch_add(1, ...)` (p. 207). Device scope is needed because incrementing threads may be in different blocks (p. 208).

### §9.3 Latency and throughput of atomic operations (pp. 209–210)
- Serialising any part of a massively parallel program can drastically raise execution time, so serialised operations should be as small a share as possible (p. 209).
- Recap of earlier chapters the argument relies on: DRAM access latency can be hundreds of clock cycles (Ch. 5); GPUs tolerate it with zero-cycle context switching (Ch. 4); with many threads whose latencies overlap, speed is limited by memory-system *throughput*, so GPUs exploit DRAM bursts, banks and channels (Ch. 6) (p. 209).
- That strategy needs many accesses in flight at once. It fails for atomics on the same location: only one can be in progress, and each lasts about **load latency + store latency** (Fig. 9.7). That duration, usually hundreds of cycles, sets the maximum rate of atomics on that location (p. 209).
- Worked example `[device: hypothetical memory system, not a named product]` (pp. 209–210):
  - 64-bit (8-byte) Double Data Rate DRAM interface per channel, 8 channels, 1 GHz clock, typical access latency 200 cycles.
  - Peak throughput = 8 bytes/transfer x 2 transfers/clock/channel x 1 G clocks/s x 8 channels = **128 GB/s**. At 4 bytes per element: **32 G elements/s**.
  - Atomics on one location: one per 400 cycles (200 read + 200 write) = 1/400 x 1 G = **2.5 M atomics/s**.
  - 256 bins with perfectly uniform pixels would give 256 x 2.5 M = **640 M atomics/s**. Real images are biased (Fig. 9.1 is heavily bright), so the real boost is "much lower than the number of intervals" (p. 210).
- Remedy 1, reduce latency: "modern GPUs allow atomic operations with device scope to be performed in the last-level cache, which is shared among all SMs". Found in cache: updated there. Not found: cache miss, brought in, then updated. Heavily updated variables tend to stay cached. Last-level cache access is "tens of cycles rather than hundreds", so atomic throughput improves "by at least an order of magnitude" (p. 210). `[device: "most modern GPUs", no model named]`

### §9.4 Privatization (pp. 211–213)
- Remedy 2, reduce contention: **privatization** = replicate a heavily contended output structure into private copies, each updated by a subset of threads, then merge the copies into the final output. Benefit: far less contention and often much lower latency. Cost: the merge. Because contention must be balanced against merge cost, on massively parallel systems privatization is typically done per **subset of threads**, not per thread (p. 211).
- Ways to choose subsets: two copies (even-index vs odd-index blocks); four copies (block `i` uses copy `i mod 4`); most commonly **one copy per thread block**, which has further advantages (p. 211).
- Merging is just adding the private histograms into the public one; it works in any order because addition is commutative and associative (p. 211).
- Fig. 9.8 toy: blocks of 8 threads ("in practice, thread blocks are much larger"). Contention now exists only among threads of one block, and across blocks only during the final merge (pp. 211–212).
- Version 1, private copies in global memory (Fig. 9.9, pp. 212–213):
  - Up to 1024 threads ("the maximum allowed per block on current hardware") share one private copy (p. 212). `[device: current CUDA hardware, unnamed]`
  - Host allocates `bins_pool` with `gridDim.x*NUM_BINS` integers; a block finds its copy at offset `blockIdx.x*NUM_BINS`. These copies "will likely be cached" (p. 212).
  - Contention drops by roughly the **number of active blocks across all SMs** (p. 212).
  - The per-pixel atomic now uses `cuda::thread_scope_block`: only threads of the same block need to synchronise. "Depending on the hardware implementation of atomic operations, such narrower scope may be able to achieve shorter latencies and thus higher throughput" (pp. 212–213).
  - Commit phase: `__syncthreads()` so the whole block has finished updating, then each thread walks bins `threadIdx.x, threadIdx.x + blockDim.x, ...` (a loop, so `NUM_BINS` may exceed the block size), and for each **non-zero** private bin atomically adds it to the public bin with device scope. Atomic is still required because several blocks may commit to the same public bin at once, but only one thread per block touches a given public bin, so contention is "modest" (p. 213).
- Why per-block copies are convenient (p. 213): (1) `__syncthreads()` gives the needed "everyone is done" barrier before committing; (2) if the bin count is small enough the private copy can live in the block's **shared memory**. The book states shared memory "is private to each SM and has very short access latency (a few cycles)", and since atomic throughput on a location is set by latency, this is a dramatic improvement.
- Per-cluster variant (p. 213): on GPUs with **thread block clusters** and **distributed shared memory**, a private copy per cluster is possible; blocks in the cluster use cluster-level barrier synchronisation before committing and can keep the copy in distributed shared memory, "which allows them to support a larger number of bins". No code is given.
- Version 2, private copies in shared memory (Fig. 9.10, p. 213–214): `__shared__ unsigned int bins_s[NUM_BINS]`, zeroed in parallel by the block, `__syncthreads()` so zeroing completes before any update, then the same update/commit structure as Fig. 9.9.

### §9.5 Thread coarsening (pp. 214–217)
- Privatization overhead = initialising each private copy + committing it. Both happen **once per thread block**, so more blocks means more overhead. Worth it when the blocks really run in parallel. If more blocks are launched than the hardware can run simultaneously, the scheduler serialises them and the overhead is paid "unnecessarily" (p. 214).
- **Thread coarsening**: fewer blocks, each thread processes several input elements (a factor `COARSE_FACTOR`). Two ways to assign elements to threads (p. 214):
  - **Contiguous partitioning** (Fig. 9.11, Fig. 9.12): each block gets a contiguous block segment of `COARSE_FACTOR*blockDim.x` elements; inside it each thread gets its own contiguous run of `COARSE_FACTOR` elements (p. 215).
    - On a CPU this is usually best: few threads, each walking sequentially, good cache-line use, little interference between threads sharing a cache (p. 216).
    - On a GPU it is sub-optimal: so many threads are active in an SM that data cannot be expected to stay cached across one thread's sequential accesses; what matters is that threads **in a warp access consecutive locations** in the same step so the accesses coalesce (p. 216, refers to Ch. 6).
  - **Interleaved partitioning** (Fig. 9.13, Fig. 9.14): in iteration `c` all threads of the block together cover the next `blockDim.x` consecutive elements; each thread's elements are `blockDim.x` apart, so the per-thread partitions interleave. Accesses coalesce and need the fewest memory transactions (pp. 216–217).
- The only code difference between the two is the index expression on line 12 (see listings).
- Extra hint: "each thread should process four pixels (a 32-bit word) in each iteration to fully utilize the interconnect bandwidth between the caches and the SMs" (p. 216). No code for this.

### §9.6 Thread-level privatization (pp. 217–219)
- Once each thread handles several elements, it can keep counts privately and update them **without atomics**, committing to the block-level private histogram with atomics at the end (p. 217).
- Limit: number of bins. With very few bins a full per-thread histogram is feasible, even in shared memory or the thread's registers. With many bins it is "prohibitively expensive" (p. 217).
- Workaround: privatise only frequently hit bins. Motivation: real data often has runs of identical values (large patches of identical sky pixels). Such runs cause the worst contention but are also the best opportunity: merge consecutive updates to the same bin into one (p. 218).
- Fig. 9.15 privatises exactly **one bin per thread: the most recently accessed one**. A register `b` holds the current pixel value and `bin_r` its run length. Same value again: `++bin_r`. Different value: flush `bin_r` into the block-level bin with one atomic, then restart the run. Because the flush always lags by one element, one final flush is needed after the loop (pp. 218–219).
- Trade-offs the book states (p. 219):
  - More statements and variables; with low similarity between consecutive pixels the kernel "may execute at slower speed than the previous kernel"; with highly repetitive data it may be significantly faster.
  - The added `if` can cause control divergence, but with either no similarity or heavy similarity the threads mostly take the same branch. Where divergence does occur it is "likely compensated by the reduced contention".

### §9.7 Summary (pp. 219–220)
- Histograms are the vehicle for data-dependent output locations, read-modify-write races and atomics.
- Atomics are slow compared with plain reads/writes: throughput is "approximately the inverse of two times the memory latency" (p. 219).
- Privatization systematically reduces contention and enables shared memory. The book adds that "supporting fast atomic operations among threads in a block is an important use case of the shared memory" (p. 219).
- Coarsening reduces the number of private copies to merge; contiguous vs interleaved were compared; thread-level privatization helps most for data with high similarity between elements (p. 220).

### Fig. 9.9 — privatized kernel, private bins in global memory (p. 212)
- Purpose: one private histogram per block inside a host-allocated pool; block-scope atomics for updates; device-scope atomics for the merge. Signature adds `unsigned int* bins_pool` after `bins`.
- Assumes `bins_pool` holds `gridDim.x*NUM_BINS` unsigned ints (p. 212). It must start zeroed [inferred; not stated]. `NUM_BINS` is a constant defined outside the listing.
- Walkthrough:
  - Line 04: `unsigned int* bins_priv = &bins_pool[blockIdx.x*NUM_BINS];` locates this block's copy.
  - Lines 06–12: index, bounds check, load `b`, block-scope atomic reference to `bins_priv[b]`, `fetch_add(1, ...)`.
  - Line 13: `__syncthreads();` so every thread in the block has finished its update.
  - Lines 15–21: commit loop `for(unsigned int b = threadIdx.x; b < NUM_BINS; b += blockDim.x)`; if `bins_priv[b] > 0`, device-scope atomic reference to `bins[b]` and `fetch_add(bins_priv[b], ...)`.
- Care: the stride-`blockDim.x` loop lets the number of bins exceed the number of threads; the zero test skips needless global atomics; the read of `bins_priv[b]` in the commit is a plain (non-atomic) read, safe because of the barrier.
- APIs: `cuda::thread_scope_block`, `cuda::thread_scope_device`, `__syncthreads()`, `gridDim` (in the text).

### Fig. 9.14 — coarsened kernel, interleaved partitioning (p. 217)
- Identical to Fig. 9.12 except line 12: `unsigned int i = segment + c*blockDim.x + threadIdx.x;`
- Meaning: iteration 0 covers `segment + 0 .. segment + blockDim.x - 1`, iteration 1 the next `blockDim.x` elements, and so on. In iteration `c` each thread adds `c*blockDim.x` to its first element `segment + threadIdx.x` (pp. 216–217). Adjacent threads read adjacent bytes: coalesced.

### Fig. 9.15 — kernel with thread-level privatization (p. 218)
- Purpose: on top of Fig. 9.14, collapse runs of equal pixel values seen by one thread into a single atomic add.
- Walkthrough:
  - Lines 04–08: shared bins, zero, barrier (as before). Line 10: `segment` as before.
  - Line 11: `if(segment + threadIdx.x < width*height) {` bounds check on the thread's first pixel.
  - Line 12: `unsigned int b = image[segment + threadIdx.x];` first pixel value. Line 13: `unsigned int bin_r = 1;` run length.
  - Line 14: `for(unsigned int c = 1; c < COARSE_FACTOR; ++c)` (starts at 1 because the first pixel is already loaded). Line 15: `i = segment + c*blockDim.x + threadIdx.x`. Line 16: bounds check.
  - Line 17: `unsigned char bNext = image[i];` Lines 18–19: `if(bNext == b) { ++bin_r; }`.
  - Lines 20–26 (else): block-scope atomic `bins_s_ref(bins_s[b])`, `fetch_add(bin_r, ...)`, then `b = bNext; bin_r = 1;`.
  - Lines 29–31: after the loop, one more block-scope atomic `fetch_add(bin_r, ...)` on `bins_s[b]` to flush the last run. Line 32 closes the `if` of line 11.
  - Line 33 barrier; lines 35–41 commit to global `bins` as before.
- Care: the flush is always one element behind, hence the unconditional final flush. A thread whose first pixel is out of range skips everything through line 32 but still joins the barrier and the commit. `b` is declared `unsigned int` on line 12 while `bNext` is `unsigned char` on line 17 (as printed).
- APIs: as Fig. 9.10.

## Relevance to LLM-inference kernels

The book makes no LLM connection in this chapter; everything below is our mapping [inferred].
- **Direct uses are few.** GEMM, attention and most quantized ops are owner-computes patterns and need no atomics.
- **Where data-dependent output does appear in inference:**
  - Token-count histograms over the context for repetition / frequency / presence penalties in sampling: bins = vocabulary (tens of thousands or more), inputs = token ids. The "number of bins" limit from §9.4 and §9.6 applies directly: a vocabulary-sized private copy will not fit in a block's shared memory, so only the global-memory or "hot bin" variants are options.
  - Bucketed selection for top-k / top-p (histogram the logits or probabilities into buckets, find the bucket holding the threshold, then refine) is a histogram plus a scan (Ch. 11).
  - Calibration histograms of activations when choosing quantization ranges (usually offline).
  - Any scatter-add (e.g. accumulating into an output indexed by data) is the same race and takes the same cure.
- **Transferable techniques that matter much more than the histogram itself:**
  - Atomic throughput reasoning (1 / (2 x latency)) explains why "one global accumulator updated by every thread" is a performance trap; the multi-block reduction of Ch. 10 (softmax denominator, max logit) uses exactly the privatize-then-commit shape, with one atomic per block.
  - Privatize into shared memory, barrier, then commit: the template for per-block partial results.
  - Thread coarsening with **interleaved** indexing (`segment + c*blockDim.x + threadIdx.x`) is the coalescing-friendly way to let one thread handle many elements, e.g. a block reducing a long logits row.
  - Run-length merging (Fig. 9.15) is a reminder to exploit input redundancy and that it adds data-dependent branches.

## Ideas for interactives and labs

- **Race-schedule builder (Figs. 9.4, 9.5).** Two threads, three micro-ops each; the learner arranges them on a 6-slot timeline. The page computes the final `bins[x]`, marks lost updates, and counts how many of the possible interleavings are wrong. Toggle "atomic" to glue each thread's three ops together and show that both orders remain legal (atomics give mutual exclusion, not ordering).
- **Predict-then-reveal:** N threads all increment the same bin with plain `++`. Ask for the range of possible final values, then simulate random schedules.
- **Atomic throughput calculator (Fig. 9.7, pp. 209–210).** Sliders: latency in cycles, clock rate, bins, skew of the distribution (uniform to single-bin). Outputs: atomics/s, ratio to peak memory throughput (32 G elements/s in the book's example), and the effect of moving the bins to a last-level cache ("tens of cycles") or shared memory ("a few cycles").
- **Contention visualiser (Figs. 9.3 vs 9.8).** Same image, slider for block size and number of private copies; show per-location contender count in the update phase and in the commit phase; plot merge cost against contention.
- **Bug hunt on Fig. 9.10.** Variants with one defect each: missing zeroing loop; missing first `__syncthreads()`; missing second `__syncthreads()`; block scope used for the global commit; commit loop `for(b = threadIdx.x; b < blockDim.x; ...)` that drops bins when `NUM_BINS > blockDim.x`. Learner identifies the symptom.
- **Index-pattern explorer (Figs. 9.11–9.14).** Pick block size, `COARSE_FACTOR`, block, thread, `c`; show `i` for both line-12 formulas and colour the cells a warp reads in one iteration. Count memory transactions for each.
- **Run-length lab (Fig. 9.15).** Feed images with different run statistics (noise, gradients, sky). Count atomics issued per pixel and per-warp divergence for each; find the similarity level at which thread-level privatization wins.
- **Measured lab (CUDA).** Implement Figs. 9.6, 9.9, 9.10, 9.12, 9.14, 9.15 and time them on (1) uniform random bytes, (2) a constant image, (3) a natural photo. Sweep `COARSE_FACTOR` and block size. Expected qualitative outcomes from the book: the basic kernel is worst under skew; shared-memory privatization helps most; interleaved beats contiguous; Fig. 9.15 wins only with long runs.
- **LLM-flavoured variant [inferred]:** histogram of token ids over a long context with a vocabulary-sized bin array, to feel the "too many bins for shared memory" limit and motivate hot-bin privatization.
- **Exercise drill:** exercises 1–5 as numeric-entry cards with the arithmetic revealed stepwise.
