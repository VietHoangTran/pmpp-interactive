# Chapter 18 — Graph traversal

- **Book pages:** 425–451  **PDF pages:** 451–477 (pdf = book + 26)
- **In one paragraph:** The chapter (with contributions credited to John Owens and Juan Gómez-Luna, p. 425) uses breadth-first search (BFS) to show how to parallelize work whose amount and location change at run time. It first maps graphs onto the sparse formats of Chapter 17 (CSR = outgoing edges, CSC = incoming edges, COO = edge list), then builds BFS five ways: vertex-centric push, vertex-centric pull, edge-centric, frontier-based push, and frontier-based push with per-block private frontiers. It ends by folding all BFS levels into one cooperative-groups kernel with grid-wide barriers to avoid per-level launch overhead. After it, a reader can choose a thread-to-work mapping from the data's degree distribution, build an output work list with atomic counters and compare-and-swap, cut contention with shared-memory privatization, and launch a kernel that synchronizes the whole grid safely.

Conventions in these notes: "read" = taken from the page; "derived" = worked out by us; "figure-read" = read off a drawing.

## Concepts

### Chapter opening (p. 425)
- A graph represents relations between entities: entities are **vertices**, relations are **edges**. Examples: social networks, driving-direction map services (p. 425).
- Two families of parallel strategies: process vertices in parallel, or process edges in parallel (p. 425).
- Graph adjacency matrices tend to be very sparse, so graph computation can be phrased as sparse-matrix operations on square matrices; but exploiting properties of the specific graph computation often does better (p. 425).

### §18.1 Background (pp. 425–429)
- Relations can be bidirectional (friendships) or directional (one-way streets). The chapter uses **directional** edges; a bidirectional relation is two directional edges (p. 426).
- Each vertex has a unique number, the **vertex id**. An edge goes from a **source** vertex to a **destination** vertex (p. 426).
- Running example (Fig. 18.1): 9 vertices (0–8), 15 directed edges (p. 426). Edge list (figure-read, confirmed by Figs. 18.2 and 18.3): 0→1, 0→2, 1→3, 1→4, 2→5, 2→6, 2→7, 3→4, 3→8, 4→5, 4→8, 5→6, 6→8, 7→0, 7→6.
- **Adjacency matrix** `A`: `A[i][j] = 1` if there is an edge from source `i` to destination `j`, else 0. Rows = sources, columns = destinations. Zeros are left blank in the figure (pp. 426–427).
- Fully connected graph with N vertices: N−1 outgoing edges per vertex, N·(N−1) edges in total (no self-edges). For N = 9: 8 per vertex, 72 total. The example has at most 3 outgoing edges per vertex → **sparsely connected** (average out-degree much smaller than N−1) (p. 427).
- Sparse formats applied to graphs (Fig. 18.3). Naming used for the rest of the chapter (p. 427):
  - row indices → `src`, row offsets → `srcPtrs`
  - column indices → `dst`, column offsets → `dstPtrs`
  - CSR graph = `srcPtrs` + `dst` (+ `data`); CSC graph = `dstPtrs` + `src` (+ `data`); COO graph = `src` + `dst` (+ `data`).
- Worked reading of CSR: `srcPtrs[3]=7` and `srcPtrs[4]=9`, so vertex 3's outgoing edges are entries 7 and 8; `dst[7]=4`, `dst[8]=8` → edges 3→4 and 3→8 (p. 427).
- The `data` array is all ones here and can be dropped (existence of an index implies an edge). It is needed when edges carry information such as distance or the date a connection was made (p. 427).
- Storage: with `data` dropped, CSR for the example needs 25 locations (10 + 15) versus 9² = 81 for the dense matrix (p. 428).
- **Vertex degree** = number of edges at a vertex; the degree *distribution* characterizes a graph. Road networks: low average degree, fairly uniform. Social "follower" graphs: broad distribution with very high-degree vertices (popular users). Graph structure may influence the choice of algorithm (p. 428).
- Accessibility by format — the key link to the algorithms (pp. 428–429):
  - CSR → outgoing edges of a given vertex.
  - CSC → incoming edges of a given vertex.
  - COO → source and destination of a given edge.
  - So choice of representation goes hand in hand with choice of traversal algorithm.

### §18.2 Breadth-first search (pp. 429–431)
- BFS is used to find the smallest number of edges needed to get from one vertex to any other. One way to report the result: given a **root** vertex, label every vertex with its **level** (number of hops / "depth" from the root) (p. 429).
- Example paths from 0 to 5: 0→1→3→4→5, 0→1→4→5, 0→2→5; the last is shortest (p. 429).
- Fig. 18.4(a), root 0: level 1 = {1, 2}; level 2 = {3, 4 (via 1), 5, 6, 7 (via 2)}; level 3 = {8} (via 3, 4 or 6) (pp. 429–430).
- Fig. 18.4(b), root 2: level 1 = {5, 6, 7}; level 2 = {8 (via 6), 0 (via 7)}; level 3 = {1}; level 4 = {3, 4} (via 1). Moving the root by one edge changes the labelling a lot (p. 430).
- **BFS tree:** rooted at the search root; contains all labelled vertices and only those traversed edges that go from one level to the next (p. 430).
- **Path recovery:** start at the destination and repeatedly step to a predecessor whose level is one less; if several qualify, any is fine (multiple equally good solutions). Example (root 2 → vertex 1): 1 ← 0 ← 7 ← 2, i.e. path 2→7→0→1. This needs each vertex's list of incoming-edge sources (p. 430).
- **Application: maze routing in integrated-circuit CAD** (pp. 430–431, Fig. 18.5). The chip is a grid of wiring blocks; connectors of components are **net terminals**; a wire extends horizontally or vertically; used blocks and component-occupied blocks are **blockages** that later wires must route around. As a graph: blocks are vertices, an edge i→j means a wire can extend from block i to block j; occupied blocks are marked as blockage vertices or removed.
- BFS from the root terminal marks its four non-blocked neighbours level 1, their unvisited non-blocked neighbours level 2, and so on. In Fig. 18.5(a): 4 level-1, 8 level-2, 12 level-3 vertices. BFS forms a **wavefront** per level, small at first but growing very quickly (p. 431).
- After BFS, back-trace from the target to form a shortest wire; when several predecessors tie, heuristics can pick the one that least constrains wires still to be routed (p. 431).

### §18.3 Vertex-centric parallelization of BFS (pp. 431–436)
- **Vertex-centric:** threads are assigned to vertices; each thread works on its vertex, usually iterating over neighbours (via outgoing edges, incoming edges, or both). **Edge-centric:** threads are assigned to edges; each looks up its edge's source and destination (pp. 431–432).
- Level strategy shared by §18.3–§18.6 (p. 432): label the root level 0; then call a kernel once per level — the kernel for level L labels the unvisited neighbours of level L−1 vertices as level L; stop when no new vertex is labelled.
- Why one kernel launch per level: all vertices of the previous level must be labelled before the next level starts, otherwise a vertex may be labelled incorrectly. (§18.7 replaces this with one kernel and grid-wide barriers.) (p. 432)

**Push / top-down (Fig. 18.6, CSR)** (pp. 432–434)
- One thread per vertex. If the vertex is in the previous level (`level[vertex] == currLevel - 1`), loop over its outgoing edges and label every unvisited neighbour with `currLevel`.
- Name (footnote 1, p. 432): in the BFS tree, threads sit on parents and look for children — *top-down*; *push* = an active vertex pushes its depth along outgoing edges.
- Needs outgoing edges of a vertex (a row of the adjacency matrix) → CSR.
- "Unvisited" is a sentinel: every level starts as `UNVISITED`, e.g. the largest unsigned integer (p. 433).
- A thread that labels a vertex sets `*newVertexVisited = 1`; the host uses that flag to decide whether to launch another level (p. 433).
- In Fig. 18.7 (level 1 → 2) only the threads on vertices 1 and 2 pass the level check (p. 432).
- **Benign race** (pp. 433–434): several threads may write the same `level[neighbor]` and the same flag. These are technically data races (unordered access, at least one write). Per Chapter 14 they are benign in practice because the writes are idempotent. But the code violates the C++ memory model and is not guaranteed to work; a conservative programmer should use atomics for both.

**Pull / bottom-up (Fig. 18.8, CSC)** (pp. 434–435)
- One thread per vertex. If the vertex is still `UNVISITED`, loop over its incoming edges; on finding a neighbour in the previous level, label *itself* `currLevel`, set the flag, and `break`.
- Name (footnote 2, p. 434): threads sit on potential children looking for a parent — *bottom-up*; *pull* = a vertex reaches back to predecessors and pulls active status.
- Needs incoming edges of a vertex (a column) → CSC.
- Why `break` is valid: one previous-level neighbour is sufficient. Only threads with no previous-level neighbour scan their whole list. In Fig. 18.9 (level 1 → 2) threads on vertices 3–8 pass the unvisited check; only vertex 8's thread scans its entire list without labelling (pp. 434–435).

**Push vs pull** (pp. 435–436)
1. *Early exit:* push always scans the whole neighbour list; pull may break early. Unimportant for low-degree, low-variance graphs (road networks, CAD circuit models); a substantial gain for high-degree, high-variance graphs (social networks), where long and uneven lists cause load imbalance and control divergence.
2. *Which threads loop:* push loops only for previous-level vertices; pull loops for every unvisited vertex. Early levels have few frontier vertices and many unvisited ones → push is typically better early. Later levels have more frontier vertices, fewer unvisited ones, and a higher chance of an early exit → pull is typically better late.
- **Direction-optimized BFS:** push for early levels, switch to pull for later ones. The switch point depends on the graph type: low-degree/low-variance graphs have many levels and switch late; high-degree/high-variance graphs have few levels that grow fast and switch much earlier. Graphs where any vertex is a few levels from any other are **small world graphs** (p. 436).
- Direction-optimized needs both CSR and CSC. For undirected graphs (symmetric adjacency matrix — the book cites social networks and maze routing) CSR and CSC are equivalent, so one copy serves both (p. 436).

### §18.4 Edge-centric parallelization of BFS (pp. 436–438)
- One thread per edge (Fig. 18.10, COO): if the edge's source is in the previous level and its destination is unvisited, label the destination `currLevel` and set the flag (pp. 436–437).
- Advantages over vertex-centric (pp. 437–438):
  1. *More parallelism:* graphs usually have many more edges than vertices, so more threads can be launched; better for small graphs that would not fill the device with one thread per vertex.
  2. *Less load imbalance and control divergence:* every thread handles exactly one edge. The book calls this an instance of re-mapping threads to work/data to reduce divergence (Chapter 6). Better for high-average-degree, high-variance graphs.
- Disadvantages (p. 438):
  1. Every edge is checked every level. A vertex-centric kernel can skip a whole edge list after one check of the vertex. Example: an irrelevant vertex `v` with `n` edges costs `n` threads each inspecting `v` in edge-centric, versus one thread inspecting `v` once in vertex-centric.
  2. COO takes more storage than CSR/CSC.
- **Link to linear algebra** (p. 438): these kernels resemble the SpMV kernels of Chapter 17. A BFS level can be written entirely as SpMV plus a few vector operations, with SpMV dominant. This is the **linear algebraic formulation** of graph problems, the focus of the **GraphBLAS** API specification [refs 1, 2]. Pro: reuse mature sparse linear algebra libraries. Con: may miss optimizations specific to the graph algorithm.

### §18.5 Improving work efficiency with frontiers (pp. 438–442)
- Problem with §18.3–18.4: every vertex or edge is checked every level. Good: highly parallel, no synchronization. Bad: many launched threads do nothing — not **work efficient** (p. 438).
- Work complexity for a graph with `n` vertices, `m` edges and diameter `d` (= number of BFS levels excluding level 0) (pp. 438–439):

  | Approach | Work |
  |---|---|
  | Ideal (each vertex and edge once) | O(n + m) |
  | Vertex-centric push | O(d·n + m) — every vertex checked each level; each edge traversed once |
  | Vertex-centric pull | O(d·n + d·m) — every vertex each level; an edge may be re-checked every level until its destination is visited |
  | Edge-centric | O(d·m) |
  | Push with frontiers | O(n + m) |

- **Frontier:** the threads processing level L−1 collaboratively build the list of vertices they newly visit; the next launch has one thread per frontier element only [ref 3] (p. 439).
- Kernel changes (Fig. 18.12; pp. 439–440): extra parameters `prevFrontier`, `currFrontier` (arrays of vertex ids), `numPrevFrontier` (by value), `numCurrFrontier` (pointer to a counter). The visited flag is gone; the host stops when the current frontier size is 0.
- Appending to the frontier: atomically `fetch_add(1)` on the shared counter to claim a slot, then write the vertex id into that slot (p. 440).
- **Why visiting must now be atomic** (pp. 440–441): without frontiers, duplicate labelling was harmless (idempotent). With frontiers, if two threads both see a neighbour as unvisited, both append it, and it is processed twice in the next level — redundant work. So "check unvisited, then label" must be one atomic step: **compare-and-swap**, via C++ `compare_exchange_strong` (Fig. 18.14).
- `compare_exchange_strong` arguments as used (pp. 441–442): (1) the expected value — must be an lvalue, so a local `unvisited` initialized to `UNVISITED` is passed, not the constant; (2) the desired value `currLevel`; (3) and (4) memory orderings for the success and failure cases, both `cuda::memory_order_relaxed` because no ordering with other independent accesses is required. The return value says whether the swap happened.
- Cost of the frontier approach: long-latency atomics, worse under contention. Contention on the CAS is expected to be *moderate* (only some threads target the same neighbour). Contention on the frontier counter is expected to be *high* (every appending thread hits the same counter) (p. 442).

### §18.6 Reducing contention with privatization (pp. 442–444)
- Inserting into a frontier is the **unstable filter** pattern of Chapter 12. Two optimizations from there apply: coalesced atomic operations and privatization. The book says (per Chapter 12) the coalescing of atomics can be assumed to be done by the compiler; this section does privatization (p. 442).
- **Privatization** (recalled from Chapter 6): apply partial updates to a private copy, then update the public copy once (p. 442).
- Here: each **thread block** keeps a private frontier and counter in **shared memory**. Benefits (p. 442): threads contend only with others in their block; shared-memory atomics and stores have lower latency; and the final copy from the private frontier to the public one in global memory can be coalesced.
- Kernel structure (Fig. 18.15; pp. 443–444):
  1. *Initialize:* declare `currFrontier_s[PRIVATE_FRONTIER_CAPACITY]` and `numCurrFrontier_s` in shared memory; thread 0 zeroes the counter; `__syncthreads()`.
  2. *BFS step:* as before, but on a successful visit the thread atomically increments the **private** counter (block-scope atomic). If the returned index is below capacity it stores into the private frontier. Otherwise (overflow) it sets the private counter back to capacity and appends directly to the public frontier with a device-scope atomic.
  3. `__syncthreads()` so no more private insertions can happen.
  4. *Allocate:* thread 0 does one `fetch_add(numCurrFrontier_s)` on the public counter and stores the returned start index in a shared variable; `__syncthreads()`.
  5. *Commit:* threads copy private entries to `currFrontier[start + idx]`, each thread taking indices `threadIdx.x, threadIdx.x + blockDim.x, …`. Consecutive threads write consecutive global addresses → coalesced.
- Fig. 18.16 shows the effect: blocks reserve contiguous ranges in the public frontier in whatever order they finish, so the public frontier is grouped by block but not ordered by block.

### §18.7 Reducing launch overhead with cooperative groups (pp. 445–448)
- All kernels so far are launched once per BFS level from the host. With large frontiers (high-average-degree graphs such as social networks) launch overhead is negligible. With small frontiers (low-average-degree graphs such as road networks) launch overhead may dominate (p. 445).
- Goal: one grid launch for the whole BFS. Requirement: a **grid-wide barrier synchronization** between levels. CUDA provides it through the **cooperative groups** API (p. 445).
- **Constraint and why** (p. 445): a normal grid may have more blocks than can run at once; the hardware runs as many as fit and brings in more as older ones finish (Chapter 4). A grid-wide barrier would then **deadlock**: running blocks wait at the barrier for blocks that have not been scheduled, while unscheduled blocks wait for running blocks to finish. So all participating blocks must be resident on the SMs simultaneously → launch no more blocks than can execute at once.
- Computing that number (pp. 445–446):
  ```
  int numBlocksPerSM;
  cudaOccupancyMaxActiveBlocksPerMultiprocessor(&numBlocksPerSM,
                                     bfs_kernel, numThreadsPerBlock, 0);
  cudaDeviceProp deviceProp;
  cudaGetDeviceProperties(&deviceProp, 0);
  int numSMs = deviceProp.multiProcessorCount;
  unsigned int numBlocks = numSMs*numBlocksPerSM;
  ```
  Arguments of the occupancy call: output pointer, kernel, threads per block, dynamic shared memory per block (0 here).
- Launching (p. 446): the usual kernel-call syntax of Chapter 2 cannot be used. Arguments go into a `void*` array and the kernel is launched through `cudaLaunchCooperativeKernel`:
  ```
  void *kernelArgs[] = { (void*)&csrGraph_d, (void*)&level_d,
            (void*)&prevFrontier_d, (void*)&currFrontier_d,
          (void*)&numPrevFrontier, (void*)&numCurrFrontier_d };
  cudaLaunchCooperativeKernel((void*)bfs_kernel, numBlocks,
                              numThreadsPerBlock, kernelArgs);
  ```
- Kernel (Fig. 18.17; pp. 446–448):
  - Includes `<cooperative_groups.h>`, `using namespace cooperative_groups;`, obtains `grid_group grid = this_grid();`.
  - Outer loop over levels: `for(currLevel = 1; numPrevFrontier > 0; ++currLevel)`.
  - Loop body ≈ Fig. 18.15, with one change: because the thread count is now capped, a thread may own several frontier elements, so it strides through the frontier: start at `grid.thread_rank()`, step by `grid.num_threads()`.
  - End of each level — swap frontiers with **three** grid-wide barriers: `grid.sync()` (everyone finished appending) → every thread reads `*numCurrFrontier` into its local `numPrevFrontier` → `grid.sync()` (everyone has read it) → grid thread 0 resets `*numCurrFrontier = 0` → `grid.sync()` (reset is visible before anyone appends) → each thread swaps its local `prevFrontier`/`currFrontier` pointers.
- Two of the three barriers can be removed by using a separate counter per level, all zeroed before the kernel starts — described as a more general form of double buffering; left as Exercise 3 (p. 448).
- Other benefits of single-kernel execution (p. 448): the CPU is free for other work; and (not seen in this example) data can stay in shared memory or registers across grid-wide barriers instead of being written to and re-read from global memory. This is similar to the kernel fusion of Chapter 11's grid-wide prefix sum, except that Chapter 11 used grid-wide *unidirectional* synchronization rather than a grid-wide *barrier*.

### §18.8 Other optimizations (pp. 448–449)
- In vertex-centric kernels the work per thread depends on vertex degree. In social graphs a few vertices ("celebrities") have degrees orders of magnitude higher; one or a few threads then run very long and hold up the whole grid (p. 448).
- Remedy 1: edge-centric (already seen). Remedy 2: **degree bucketing** — sort frontier vertices into buckets by degree and process each bucket in a separate kernel with an appropriately sized group of processors. One notable implementation [ref 4] uses three buckets: small-degree vertices get one **thread** each, medium get one **warp** each, large get an entire **thread block** each. Especially useful with high degree variance (p. 449).
- BFS is simple but shows the challenges of harder graph applications: problem decomposition for parallelism, privatization, fine-grained load balancing, proper synchronization (p. 449).
- Graph computation application areas named: recommendations, community detection, pattern finding, anomaly detection (p. 449).
- Open challenges/opportunities named: graphs larger than GPU memory; preprocessing into other formats or reordering vertices to expose parallelism or locality or ease load balancing (p. 449).

### §18.9 Summary (p. 449)
- Recap of the chapter's arc; efficient implementations of many graph algorithms are available in **RAPIDS cuGraph** [ref 5].

## Code listings

Common to all kernels: 1-D grids; `level` is an `unsigned int*` array indexed by vertex id; `UNVISITED` is a sentinel constant; graph structs (`CSRGraph`, `CSCGraph`, `COOGraph`) are passed by value and never defined in the chapter. The host loop that calls the per-level kernels is never shown.

### Fig. 18.6 — `bfs_kernel`, vertex-centric push (p. 433)
- Signature: `__global__ void bfs_kernel(CSRGraph csrGraph, unsigned int* level, unsigned int* newVertexVisited, unsigned int currLevel)`. One thread per vertex; launched once per level.
- Walkthrough: line 03 vertex index from block/thread indices; line 04 bounds check against `csrGraph.numVertices`; line 05 `if(level[vertex] == currLevel - 1)`; lines 06–07 loop `edge` from `srcPtrs[vertex]` while `edge < srcPtrs[vertex + 1]`; line 08 `neighbor = csrGraph.dst[edge]`; line 09 `if(level[neighbor] == UNVISITED)`; line 10 `level[neighbor] = currLevel;`; line 11 `*newVertexVisited = 1;`.
- Care: lines 09–11 are unsynchronized check-then-write on shared data (benign, idempotent, but formally a data race — pp. 433–434). `currLevel - 1` assumes `currLevel ≥ 1`.
- APIs: `__global__`, `blockIdx`, `blockDim`, `threadIdx`.

### Fig. 18.8 — `bfs_kernel`, vertex-centric pull (p. 434)
- Signature: `__global__ void bfs_kernel(CSCGraph cscGraph, unsigned int* level, unsigned int* newVertexVisited, unsigned int currLevel)`.
- Walkthrough: line 03 vertex; line 04 bounds check `cscGraph.numVertices`; line 05 `if(level[vertex] == UNVISITED)`; lines 06–07 loop `edge` from `dstPtrs[vertex]` while `edge < dstPtrs[vertex + 1]`; line 08 `neighbor = cscGraph.src[edge]`; line 09 `if(level[neighbor] == currLevel - 1)`; line 10 `level[vertex] = currLevel;`; line 11 flag; line 12 `break;`.
- Care: each thread writes only its own `level[vertex]`, so the only shared write is the flag. The `break` is what makes pull cheap late in the search.
- APIs: as above.

### Fig. 18.10 — `bfs_kernel`, edge-centric (p. 437)
- Signature: `__global__ void bfs_kernel(COOGraph cooGraph, unsigned int* level, unsigned int* newVertexVisited, unsigned int currLevel)`. One thread per edge.
- Walkthrough: line 03 edge index; line 04 bounds check `cooGraph.numEdges`; line 05 `vertex = cooGraph.src[edge]`; line 06 `if(level[vertex] == currLevel - 1)`; line 07 `neighbor = cooGraph.dst[edge]`; line 08 `if(level[neighbor] == UNVISITED)`; lines 09–10 label and set flag.
- Care: no loop → no trip-count divergence; same benign races as push.
- APIs: as above.

### Fig. 18.12 — `bfs_kernel`, push with frontiers (p. 439)
- Signature: `__global__ void bfs_kernel(CSRGraph csrGraph, unsigned int* level, unsigned int* prevFrontier, unsigned int* currFrontier, unsigned int numPrevFrontier, unsigned int* numCurrFrontier, unsigned int currLevel)`. One thread per element of the previous frontier.
- Walkthrough: line 05 index `i`; line 06 `if(i < numPrevFrontier)`; line 07 `vertex = prevFrontier[i]`; lines 08–09 loop over `srcPtrs[vertex]`…`srcPtrs[vertex + 1]`; line 10 `neighbor = csrGraph.dst[edge]`; line 11 `if(visitVertexAtomically(neighbor, level, currLevel))`; lines 12–15 atomic increment of the public counter; line 16 store.
- Lines that need care (exact text):
  ```
  cuda::atomic_ref<unsigned int, cuda::thread_scope_device>
      numCurrFrontier_ref(*numCurrFrontier);
  unsigned int currFrontierIdx =
      numCurrFrontier_ref.fetch_add(1, cuda::memory_order_relaxed);
  currFrontier[currFrontierIdx] = neighbor;
  ```
  `fetch_add` returns the old value, which is the claimed slot. No capacity check on `currFrontier` is shown.
- APIs: `cuda::atomic_ref`, `cuda::thread_scope_device`, `fetch_add`, `cuda::memory_order_relaxed`.

### Fig. 18.14 — `visitVertexAtomically` (p. 441)
- Signature: `__device__ inline unsigned int visitVertexAtomically(unsigned int vertex, unsigned int*level, unsigned int currLevel)`.
- Whole body (short, exactness matters):
  ```
  cuda::atomic_ref<unsigned int, cuda::thread_scope_device>
      level_ref(level[vertex]);
  unsigned int unvisited = UNVISITED;
  unsigned int visitSuccess = level_ref.compare_exchange_strong(unvisited,
      currLevel, cuda::memory_order_relaxed, cuda::memory_order_relaxed);
  return visitSuccess;
  ```
- Care: the expected value is passed through a local variable because the function needs a reference to an object, not a constant (p. 441). Exactly one of several racing threads gets a true return.
- APIs: `__device__`, `cuda::atomic_ref`, `compare_exchange_strong`.

### Fig. 18.15 — `bfs_kernel`, push with privatized frontiers (p. 443)
- Signature: same as Fig. 18.12. Uses `PRIVATE_FRONTIER_CAPACITY` (constant, value not given).
- Walkthrough by line range:
  - 07–08: `__shared__ unsigned int currFrontier_s[PRIVATE_FRONTIER_CAPACITY];` and `__shared__ unsigned int numCurrFrontier_s;`
  - 09–12: thread 0 sets `numCurrFrontier_s = 0`; `__syncthreads()`.
  - 15–21: same traversal as Fig. 18.12 up to the `visitVertexAtomically` test.
  - 22–25: block-scope atomic increment of the private counter:
    ```
    cuda::atomic_ref<unsigned int, cuda::thread_scope_block>
        numCurrFrontier_s_ref(numCurrFrontier_s);
    unsigned int currFrontierIdx_s =
        numCurrFrontier_s_ref.fetch_add(1, cuda::memory_order_relaxed);
    ```
  - 26–27: if `currFrontierIdx_s < PRIVATE_FRONTIER_CAPACITY`, store into `currFrontier_s`.
  - 28–35: else (overflow) `numCurrFrontier_s = PRIVATE_FRONTIER_CAPACITY;` then device-scope `fetch_add(1)` on `*numCurrFrontier` and store directly into `currFrontier`.
  - 39: `__syncthreads()`.
  - 42–49: `__shared__ unsigned int currFrontierStartIdx;` thread 0 does `currFrontierStartIdx = numCurrFrontier_ref.fetch_add(numCurrFrontier_s, cuda::memory_order_relaxed);` then `__syncthreads()`.
  - 52–56: commit loop
    ```
    for(unsigned int currFrontierIdx_s = threadIdx.x;
         currFrontierIdx_s < numCurrFrontier_s; currFrontierIdx_s += blockDim.x) {
        unsigned int currFrontierIdx = currFrontierStartIdx + currFrontierIdx_s;
        currFrontier[currFrontierIdx] = currFrontier_s[currFrontierIdx_s];
    }
    ```
- Lines that need care:
  - Line 29 is a **plain (non-atomic) store** to a counter that other threads update with atomics; the book describes it as "restores the value of the private frontier counter" (p. 444). It is what keeps `numCurrFrontier_s ≤ capacity` for the allocate/commit phases.
  - Three block barriers: after init (12), after traversal (39), after allocation (49). All are outside conditionals.
  - Atomic scope differs by target: `thread_scope_block` for the shared-memory counter, `thread_scope_device` for the global one.
  - Commit stores are coalesced because the index is `start + threadIdx.x + k*blockDim.x` (p. 444).
- APIs: `__shared__`, `__syncthreads()`, `cuda::atomic_ref`, `cuda::thread_scope_block`, `cuda::thread_scope_device`.

### Fig. 18.17 — `bfs_kernel`, multi-level with cooperative groups (p. 447)
- Header lines: `#include <cooperative_groups.h>` and `using namespace cooperative_groups;`.
- Signature: `__global__ void bfs_kernel(CSRGraph csrGraph, unsigned int* level, unsigned int* prevFrontier, unsigned int* currFrontier, unsigned int numPrevFrontier, unsigned int* numCurrFrontier)` — no `currLevel` parameter. Must be launched with `cudaLaunchCooperativeKernel` and at most `numSMs*numBlocksPerSM` blocks (p. 446).
- Walkthrough by line range:
  - 08: `grid_group grid = this_grid();`
  - 10: `for(unsigned int currLevel = 1; numPrevFrontier > 0; ++currLevel) {`
  - 12–18: private frontier declared and reset each level (thread 0 zeroes, `__syncthreads()`).
  - 21–22: frontier stride loop `for(unsigned int i = grid.thread_rank(); i < numPrevFrontier; i += grid.num_threads())`.
  - 23–44: same logic as Fig. 18.15 lines 17–38 (load vertex, walk out-edges, CAS visit, private append with overflow path); only the enclosing construct differs (stride loop here, bounds `if` there).
  - 45–62: block barrier, allocate, block barrier, commit — as Fig. 18.15.
  - 65–74: swap frontiers:
    ```
    grid.sync();
    numPrevFrontier = *numCurrFrontier;
    grid.sync();
    if(grid.thread_rank() == 0) {
        *numCurrFrontier = 0;
    }
    grid.sync();
    unsigned int* tmp = prevFrontier;
    prevFrontier = currFrontier;
    currFrontier = tmp;
    ```
- Lines that need care:
  - `numPrevFrontier`, `prevFrontier`, `currFrontier` are by-value parameters, i.e. per-thread copies; every thread performs the same update so they stay consistent.
  - Each `grid.sync()` has a distinct job (p. 448): finish appends → finish reads of the size → make the reset visible.
  - The loop exit condition is evaluated per thread from its local `numPrevFrontier`; all threads read the same value between barriers, so they exit together.
  - `__shared__` declarations appear inside the level loop.
- APIs: `cooperative_groups::grid_group`, `this_grid()`, `grid.sync()`, `grid.thread_rank()`, `grid.num_threads()`, plus everything from Fig. 18.15.

## Relevance to LLM-inference kernels

Candid summary: **BFS itself is not needed for LLM inference. The second half of the chapter (§18.5–18.7) is the most reusable systems material in these two chapters**: building a dynamic output list with atomics, privatizing it in shared memory, and running a multi-step algorithm inside one launch. Good candidate for condensing §18.1–18.4 into a short lead-in and keeping §18.5–18.7 nearly whole.

Transferable techniques (keep):
- **Launch overhead vs work per launch** (p. 445). LLM decoding issues many small kernels per token; when each does little work, launch overhead matters in the same way as small BFS frontiers. (The LLM mapping is our inference.) The single-kernel + grid-barrier pattern, and its residency constraint and deadlock argument, are the general tool.
- **Occupancy query to size a grid that must be fully resident** (pp. 445–446).
- **Keeping state in shared memory/registers across steps by fusing kernels** (p. 448).
- **Compaction / work-list building**: atomic counter to claim a slot, then store (Fig. 18.12). This is the same shape as collecting survivors of a top-k/top-p threshold or a non-zero mask into a dense list (the book ties it to the "unstable filter" of Chapter 12, p. 442).
- **Compare-and-swap for exactly-once claims** (Fig. 18.14) — the general primitive for "first writer wins".
- **Privatization with overflow fallback and allocate-then-commit** (Fig. 18.15, Fig. 18.16): per-block buffer in shared memory, one global atomic per block instead of one per element, coalesced bulk copy.
- **Benign race vs correct code** (pp. 433–434): idempotent writes work in practice but violate the C++ memory model — a useful discipline point for flag-setting kernels.
- **Thread-to-work mapping to control divergence** (edge- vs vertex-centric, pp. 437–438) and **workload bucketing by size onto thread / warp / block** (p. 449): directly reusable for variable-length rows (e.g. per-sequence work that varies with length).
- **Work efficiency accounting** (pp. 438–439): counting wasted thread launches, not just parallelism.
- **Push vs pull as "who does the scanning" and early exit** (pp. 435–436): a general lens for scatter vs gather formulations; gather (pull) writes only its own output and needs no atomics.

Domain material that can be skipped or reduced:
- Graph terminology, adjacency matrices, CSR/CSC/COO for graphs (pp. 425–429) — one paragraph plus Fig. 18.3.
- Maze routing application (pp. 430–431).
- Direction-optimized switching heuristics and small-world graphs (p. 436).
- GraphBLAS / linear-algebraic formulation (p. 438) and cuGraph (p. 449) — one line each.

Direct relevance by kernel family:
- matmul/GEMM: little direct relevance.
- attention: little direct relevance; scatter-vs-gather and variable-length bucketing ideas apply (our inference).
- quantized ops: little direct relevance.
- sampling (softmax, top-k/top-p, argmax): indirect but real — filter/compaction with atomic counters, privatized buffers, CAS for first-wins; and launch-overhead thinking for tiny per-token kernels.
