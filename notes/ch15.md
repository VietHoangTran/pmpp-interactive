- **Book pages:** 349–372  **PDF pages:** 375–398 (pdf = book + 26). Chapter text ends on p. 370; p. 371 is blank and p. 372 is the "Part 3: Advanced patterns and applications" divider page (outline of Chapters 16–24).
- **In one paragraph:** The chapter takes the 32×32 shared-memory-tiled matmul of Chapter 5 and turns it into the skeleton of a library-grade GEMM kernel. It first redoes the data-reuse (arithmetic intensity) analysis for non-square tiles and shows that only the *output* tile size matters, then enlarges the output tile to 128×128 per block by giving each of 256 threads an 8×8 patch held in registers (thread coarsening). After it, a reader can write each kernel variant, compute the tile/register/shared-memory budgets, and explain which bottleneck each transformation removes. The chapter gives **no measured speedups**; every benefit is argued analytically or qualitatively.

## Concepts

### Chapter opening (p. 349)
- Matmul matters across science, engineering and graphics; its high computational complexity is exactly why it has a high degree of data reuse and therefore large optimization headroom (p. 349).
- The book's earlier uses of matmul: Chapter 3 used it to show mapping of multidimensional grids to data; Chapter 5 used it to introduce shared-memory tiling for reducing global memory accesses. This chapter goes deeper into GPU-specific optimizations (p. 349).

### §15.1 Background (pp. 349–350)
- Start from vector-matrix multiplication u = v × B, where the first operand has a single row. It linearly transforms v into u: each element of u is a linear combination of all elements of v, and **column j of B holds the coefficients that produce element j of u** (pp. 349–350). Note the row-vector-on-the-left convention.
- Graphics example: rotate a point by multiplying its 3D coordinate vector with a 3×3 matrix; add a vector for a shift and/or multiply by a scale factor to express the point from a new vantage point, orientation and scale (p. 350).
- To apply the same transform to many vectors, stack them as the **rows** of A and compute D = A × B; each row of D is one transformed vector (p. 350).
- Adding scale and shift gives the general form **D = αA × B + βC**, called **General Matrix Multiply (GEMM)** in the linear algebra / HPC communities. C's rows are the vectors to add to the corresponding transformed rows (p. 350).
- The A × B product is the compute-intensive part of GEMM, so the chapter covers only that step (p. 350).
- Storage order: each matrix may be row-major or column-major depending on context, e.g. because one operates on a matrix or on its transpose (pointer to Chapter 6). **The chapter assumes both input matrices are row-major.** The techniques carry over to the other combinations, and GEMM libraries usually support all of them (p. 350).
- Whether an optimization applies and pays off depends on matrix dimensions. Before deep learning, application matmuls mostly involved matrices of modest size, because they transformed vectors with modest element counts (p. 350).
- Forward pointer: Chapters 19 and 20 formulate the training of CNN convolutional layers and of LLM attention layers as multiplications of large matrices. These large multiplications motivate optimizations that were not worthwhile at small scale; many optimizations in this chapter target the large-scale case (p. 350).

### §15.2 Data reuse analysis (pp. 350–352)
- Setting (Fig. 15.1): one thread block computes an m × n output tile of C. Its threads together walk over input tile pairs, each pair being an m × k tile of A and the matching k × n tile of B, loaded from global memory into shared memory. For each pair the threads add that pair's partial contribution to every output element. The output tile lives collectively in the threads' registers and is written to global memory once at the end (pp. 350–351).
- Chapter 5's reuse analysis assumed square tiles; here it is redone for non-square tiles (p. 351).
- Per pair of input tiles (p. 351):
  - operations: k multiplies + k adds for each of the m·n output elements → **2·m·n·k floating-point operations**
  - bytes loaded: an m×k tile and a k×n tile at 4 B per element → **4·k·(m + n) bytes**
  - ratio: **arithmetic intensity = 0.5 · m · n / (m + n) operations per byte**
- Higher arithmetic intensity lets the computation get past the memory-bandwidth bottleneck (as argued in Chapter 5). The expression grows with m and n, i.e. with **larger output tiles** (p. 351).
- Worked numbers `[device: NVIDIA H100]` (p. 351):
  - m = n = 32 → 0.5·1024/64 = **8 FLOP/B**; the kernel stays **memory-bound** on an H100.
  - m = n = 128 → 0.5·16384/256 = **32 FLOP/B**; the kernel becomes **compute-bound** on an H100.
  - The chapter does not restate the threshold; it says "see Chapter 5". Chapter 5 gives the H100 threshold as 66.9 TFLOPS / 3.35 TB/s = 20.0 FLOP/B (Ch. 5, pp. 94 and 111; read from the Chapter 5 text extraction, not from Chapter 15).
- Intuition (pp. 351–352): a larger output tile lets the same input data serve more output values. If n grows from 32 to 128, the output tile is 4× wider, so one block now computes what used to be four output tiles. Those four tiles all need the same A input tile. Before, four separate blocks each loaded that A tile redundantly; now one block loads it once. Growing the height m does the same for redundant loads of B tiles. Removing redundant loads across blocks is what raises reuse and hence intensity.
- `[inferred]` The analysis counts only input loads; the 4·m·n bytes written once per block for the output are not included in the ratio.
- Section 15.3 shows how to actually get the larger tiles (p. 352).

### §15.3 Using larger tiles with thread coarsening (pp. 352–357)
- **Why this is thread coarsening** (p. 352): a larger tile than the block has threads means each thread must compute several output elements per output tile and load several input elements per input tile. The "price of fine-grained parallelism" being removed here is that different thread blocks load the same input value repeatedly. The book compares it to Chapter 8's stencil, where coarsening also enlarged the output tile for reuse and intensity.
- **Terms** (p. 352):
  - **block-level output tile**: the bM × bN output tile computed by one thread block.
  - **thread-level output tile**: the tM × tN part of it owned by one thread.
  - Example: bM × bN = 128 × 128 with a block of 16 × 16 threads → each thread owns tM × tN = 8 × 8.
- **Tile hierarchy** (p. 352): input and output matrices can be divided into a hierarchy of tiles, each level assigned to a unit of the thread hierarchy (block-level tile ↔ thread block, thread-level tile ↔ thread). Other useful levels: warp-level tiles (used in §15.5), GPU-level tiles, and compute-cluster node-level tiles. §15.3's code uses only block and thread levels.
- **Kernel outline** (Fig. 15.3; pp. 352–354). Details in "Code listings".
  1. Find the block's output-tile origin (`bRow`, `bCol`) from the block indices times the block tile dimensions.
  2. Find the thread's output-tile origin inside the block tile (`tRow`, `tCol`) from the thread index times the thread tile dimensions.
  3. Declare a tM × tN local array `C_r` and zero it with `clear()`.
  4. Loop over input tile pairs: load A and B tiles into shared memory with `loadTile()`, barrier, accumulate with `mm()`, barrier.
  5. After the loop, `writeTile()` stores the thread's tile from registers to global memory.
- **Keeping `C_r` in registers** (p. 353): the book recalls from Chapters 5 and 6 that a local array is placed in (global) memory by default, and that the compiler can move it to registers when every access uses a constant index. So every loop that touches `C_r` is fully unrolled (inside the helper functions) to make the indices constant. Result: each thread's output tile sits in that thread's registers.
- **Panels and tile pairs** (p. 353): computing one block's output tile needs a horizontal bM × K panel of A and a vertical K × bN panel of B. The panels split into K/bK input tile pairs (the code uses the ceiling, `(K + bK - 1)/bK`).
- **Barriers** (pp. 353–354): the first `__syncthreads()` (after loading) guarantees no thread computes before all data is in shared memory. The second (after `mm()`) guarantees all threads are done computing before the next iteration overwrites the tiles.
- **All helper functions are inlined into the kernel** (`__forceinline__`), which is what lets constant propagation and unrolling make the array indices constant (p. 354).
- **`clear()`** (Fig. 15.4; p. 354): two nested, fully unrolled loops set every element to 0.0f. The `#pragma unroll` annotations are the important part.
- **`loadTile()`** (Fig. 15.5; pp. 355–356):
  - **Leading dimension** (footnote 1, p. 355): in row-major layout, the number of elements in memory between successive elements of the same column. For a tile, it is the width of the larger matrix that contains the tile.
  - When the block has fewer threads than the tile has elements, each thread loads several. Example: a 128×8 tile has 1024 elements, the block has 256 threads, so each thread loads four. The tile is logically cut into four sub-tiles and loaded one sub-tile at a time (p. 355).
  - Out-of-range elements are written as zero into shared memory, so `mm()` needs no boundary checks (p. 356).
  - Suggested optimization, left as an exercise: vector loads so that each thread loads four elements with one instruction (Chapter 6) (p. 356).
- **`mm()` and thread-level input tiles** (Fig. 15.6; pp. 356–357):
  - A thread-level output tile (e.g. Thread 17's in Fig. 15.2) only needs a **tM × bK sub-tile of the block's A tile** and a **bK × tN sub-tile of the block's B tile**. These are the thread's **thread-level input tiles** (p. 356).
  - **Inner dimension** of the block-level multiplication: the dimension shared by the A tile and the B tile, i.e. A tile's horizontal size and B tile's vertical size. Because a thread-level sub-tile is made of whole rows of the A tile and whole columns of the B tile, the thread-level multiplication has the same inner dimension bK (p. 356).
  - The output tile is passed by address, but after inlining it is still register-allocated because its indices are constants (p. 356).
  - Although indices are written relative to the thread-level tiles, the data is read from the block-level arrays in shared memory. `a` and `b` point at the thread tile's first element inside `A_s` / `B_s` (`&A_s[tRow*bK]`, `&B_s[tCol]`), and multiplying the row index (`row` for a, `i` for b) by the leading dimension (`lda`, `ldb` = block tile widths) skips to the right row (p. 357).
- **`writeTile()`** (Fig. 15.7; p. 357): unrolled double loop with a boundary check; in-range elements go to global memory. The destination address is computed by the kernel (line 36 of Fig. 15.3). Suggested optimization, left as an exercise: vector stores, four elements per instruction (Chapter 6).
- Claimed benefit of the section (p. 357): larger block-level and thread-level tiles improve arithmetic intensity and overall performance (no number given beyond §15.2's 8 → 32 FLOP/B). More optimizations follow.

### §15.4 Register tiling of the input tiles (pp. 357–360)
- **Problem** (pp. 357–358): shared-memory tiling cured the global-memory bandwidth bottleneck by loading reused data once and reading it many times from shared memory. An input element is loaded once from global to shared memory by one thread, then loaded from shared memory into registers by many threads. Shared memory is much faster than global memory but still slower than a register, so after shared-memory tiling, **shared-memory access latency is the new bottleneck**.
- **Observation** (p. 358): a thread uses the same input value for several of its output elements. In the §15.3 `mm()` the same thread reloads the same value from shared memory once per output element it contributes to. The "thread-level input tile" was only a logical view; every use still read the block-level array in shared memory.
- **Fix: register tiling of the input** (p. 358): a thread loads each needed input element from shared memory once into a register and reuses it from there for all the output values it feeds.
- **How** (Fig. 15.8, Fig. 15.9; pp. 358–359):
  - The thread walks its sections of the shared-memory tiles **one pair of strips at a time**: load the pair into registers, add their contribution to all of its output elements, then go to the next pair.
  - In code this is a **loop interchange**: the loop over the inner dimension (`i < k`) moves from innermost (Fig. 15.6) to outermost (Fig. 15.9).
  - For a given i the strips are: `a_r` = tM values (column i of the thread's tM × bK part of A) and `b_r` = tN values (row i of the thread's bK × tN part of B). The update is `c[row][col] += a_r[row]*b_r[col]`, i.e. a rank-1 (outer-product) update of the tM × tN tile.
  - The book now calls these strips the (refined) thread-level input tiles. Restricting them to strips keeps them small enough to fit in registers (p. 359).
  - All loops (strip loads and the compute nest) are fully unrolled so that `a_r`, `b_r` and the output tile all have constant indices and are promoted to registers (p. 359).
- **Claimed benefit** (p. 359): fewer loads of input values from shared memory to registers, which mitigates the shared-memory access latency and the instruction-execution bottleneck.
- `[inferred]` Count per thread per tile pair with tM = tN = bK = 8: Fig. 15.6 issues tM·tN·bK = 512 reads of A and 512 reads of B from shared memory (1024 total); Fig. 15.9 issues bK·(tM + tN) = 128. That is an 8× reduction: each A value is reused tN = 8 times and each B value tM = 8 times from registers. The book states the idea but not these counts.
- **Generalization** (pp. 359–360): shared-memory tiling and register tiling are two instances of one idea. Tiling can be applied at any level of the memory hierarchy where two memory structures differ in access latency and throughput. The book calls the combination in Fig. 15.8 the **hierarchical technique**: block-level tiles in shared memory, thread-level tiles in registers. For very large matrices the hierarchy can extend to tiles across multiple GPUs or across nodes of a cluster.

### §15.5 Coalesced storing of the output tile (pp. 360–361)
- **Problem** (p. 360): large thread-level output tiles (8×8) are good for reuse under shared-memory and register tiling, but bad at store time. When each thread walks its 8×8 tile to store it, threads of the same warp that own adjacent tiles write locations that are **eight elements apart**. The access pattern is not coalesced.
- **Vector stores alone are a partial fix** (p. 360): a vector store writes four consecutive elements at once, but that is only half the width of an 8×8 tile. Adjacent threads' vector stores are then four elements apart, still not fully coalesced.
- **Goal** (p. 360): threads of the same warp should own **adjacent 4×4 output tiles**. Then each thread's four-element vector store is directly next to its neighbor's, giving a fully coalesced store transaction. So each thread's 8×8 tile is replaced by **four separate 4×4 tiles**.
- **Rearrangement** (Fig. 15.10; pp. 360–361):
  1. Block level: partition the block-level output tile among the block's warps. Each part is a **warp-level output tile**. Example: 128×128 block tile, 256 threads = 8 warps arranged 2×4; each warp gets a **64×32** sub-tile (64 rows, 32 columns).
  2. Warp level: split the warp-level tile into **four quadrants**; with a 64×32 warp tile each quadrant is **32×16**. Arrange the warp's 32 threads as **8×4**. Each thread then takes one **4×4** sub-tile from **each** quadrant.
  3. Thread level: the four 4×4 sub-tiles (one per quadrant) together are the thread's **logical 8×8** thread-level output tile; the 4×4 pieces are the **physical** output sub-tiles.
- **Effect** (p. 361): a thread can store a whole row of a 4×4 sub-tile with one vector store, and stores from same-warp threads with adjacent sub-tiles are coalesced.
- **Required code changes** (p. 361): `mm()` and `writeTile()` must iterate over the 4×4 sub-tiles and load the correspondingly small input strips at each step. The book gives no code; it is Exercise 3.
- `[inferred]` Within one store instruction, the four threads of one thread-row write 16 contiguous floats (64 B); the eight thread-rows of the warp write to eight different matrix rows (4 rows apart). The book calls the result "fully coalesced"; it does not discuss the per-row split.
- `[inferred]` Register count is unchanged by the rearrangement: 4 × 16 = 64 output values, and per inner step two 4-element A strips and two 4-element B strips (Fig. 15.10 right panel) = 16 input values.

### §15.6 Eliminating bank conflicts (pp. 361–363)
- **Problem** (p. 361): threads that own large output tiles read shared memory with a stride, and strided shared-memory access can cause bank conflicts (Chapter 6).
- Analysis uses the §15.5 layout (Fig. 15.10): a warp is 8×4 threads, so the first four threads (one thread-row) read **identical** locations of the block's A tile (p. 361).
- **Without padding** (Fig. 15.11(a); pp. 361–362), warp 0 loading the first input strip of A, with each thread on a 4×4 output tile and the shared A tile 8 elements wide `[device: 32 shared-memory banks, bank = linear index mod 32]`:
  - threads 0–3: first element of row 0 → linear index 0 → bank 0 (assumed).
  - threads 4–7: first element of row 4 → 4 × 8 + 0 = 32 → bank 0 (32 mod 32).
  - threads 8–11: first element of row 8 → 8 × 8 + 0 = 64 → bank 0 (64 mod 32).
  - Full list in the figure: elements 0, 32, 64, 96, 128, 160, 192, 224, all bank 0.
  - The second elements loaded by the eight four-thread groups all land in bank 1. In general, corresponding elements loaded by the 8 four-thread groups always share a bank → **8-way bank conflict on every access**.
- **With one padding column** (Fig. 15.11(b); p. 362): the tile's logical width stays 8 but its **leading dimension becomes 9**:
  - row 0 → index 0 → bank 0; row 4 → 4 × 9 + 0 = 36 → bank 4; row 8 → 8 × 9 + 0 = 72 → bank 8.
  - Full list in the figure: elements 0, 36, 72, 108, 144, 180, 216, 252 → banks 0, 4, 8, 12, 16, 20, 24, 28.
  - Second elements fall in banks 1, 5, 9, …, 29. The 8-way conflicts are gone. The book invites the reader to verify this for all accesses with 32 banks.
- `[inferred]` General check: the group g (g = 0..7) reads row 4g + r, column i. Unpadded index = (4g + r)·8 + i ≡ 8r + i (mod 32), the same for all g. Padded index = (4g + r)·9 + i ≡ 4g + 9r + i (mod 32), eight distinct banks for g = 0..7. The four threads inside a group read the same address, which is not a conflict.
- **Code change** (pp. 362–363): declare `__shared__ float A_s[bM*(bK + 1)];` and pass bK + 1 instead of bK as the leading dimension of `A_s` to `loadTile()` and `mm()`.
- **B needs nothing** (p. 363): the strip of `B_s` that the threads of one warp load is 32 consecutive elements in shared memory, so it falls in 32 different banks.
- Cost of padding is not discussed here (Chapter 6 covers it). `[inferred]` `A_s` grows from 1024 to 128 × 9 = 1152 floats (4608 B).

### §15.7 Occupancy considerations (pp. 363–364)
- Large tiles raise arithmetic intensity but press on two SM resources: **shared memory** (block-level input tiles) and the **register file** (thread-level input strips and output tiles). Both affect occupancy (p. 363).
- **Shared memory pressure is easy to relieve** (p. 363): the intensity 0.5·m·n/(m + n) does not depend on k, so choose a small k. With m = n = 128 and k = 8, `A_s` is 128 × 8 and `B_s` is 8 × 128 elements, **4 KB each**, which does not limit occupancy "on a modern GPU" `[device: unspecified modern GPU]`.
- **Register pressure stays high** (p. 363):
  - 8×8 thread-level output tile → 64 registers.
  - register-tiled input strips → 8 more for each strip → **80 registers** total.
  - plus locals and temporaries; aggressive loop unrolling raises the number of live temporaries further.
- **Registers are the limiting factor** (p. 363) `[device: "modern GPU"; "typical SM"]`:
  - such kernels use the maximum allowed, **255 registers per thread**.
  - a typical SM register file holds **64k registers** → at most **256 threads per SM**.
  - this is why the block size was chosen as 256 threads in §15.3.
  - each SM runs **one** block of 256 threads = **12.5%** of the maximum occupancy of **2048 threads**.
- The trade is judged worthwhile: the book says the benefit of register tiling for arithmetic intensity outweighs the low occupancy (p. 364).
- **Two drawbacks of low occupancy and their fixes** (p. 364):
  1. Fewer threads issue fewer memory-access instructions, so memory bandwidth is under-used. Fix: each thread issues **larger accesses via vector loads and stores**.
  2. Fewer threads are available to cover for long-latency instructions. Fix: **aggressive loop unrolling**, which removes long-latency branch instructions and exposes independent instructions the compiler can schedule between a long-latency instruction and its users (Chapter 6). With good unrolling and scheduling, most of the compiled kernel is a run of independent **fused-multiply-add** instructions that keeps the SM's cores busy with little stalling.
- **What remains: memory accesses and barrier synchronizations** (p. 364). Normally a compute-bound, high-intensity kernel can ignore memory latency, because while one block waits for its tiles, another block on the same SM computes. With only one block per SM that overlap is gone, and the block alternates between two phases:
  - a **memory-bound phase** (input tiles loading, compute cores idle), and
  - a **compute-bound phase** (computing, memory-access hardware idle).
- With no second block to hide the latency, software must overlap the phases; one way is software pipelining (§15.8) (p. 364).

### §15.8 Software pipelining (pp. 364–368)
- Goal (p. 364): in each phase one kind of resource is under-used, so execution speed is below potential. Overlap the phases so the long latency of memory instructions hides behind compute instructions.
- **Baseline interleaving** (Fig. 15.12(a), Fig. 15.13(a); pp. 365–366): load A0 and B0; `__syncthreads()` so all threads have loaded before anyone computes; compute their contribution C0; `__syncthreads()` so everyone has finished with A0/B0 before they are overwritten; repeat with A1/B1. While tiles load, no floating-point work happens (ALUs idle); while computing, nothing is loaded from global memory (memory hardware idle).
- Ideal (p. 366): interleave global-load instructions with floating-point instructions, placing independent fused-multiply-adds after long-latency loads, so both the memory hardware and the floating-point ALUs stay busy. The compiler cannot do this across a barrier synchronization that separates the load stage from the compute stage.
- **True vs false dependence** (p. 366):
  - barrier between loading a pair and computing with it → **true dependence** (data must arrive before use).
  - barrier between computing with a pair and loading the next pair → **false dependence**: the two activities are independent, and only collide because the next pair is written to the same memory that holds the pair still in use.
- **Step 1: double-buffering** (p. 366; Fig. 15.12(b)): load the next pair into a different buffer from the one being computed on (Chapter 6 technique). The false dependence disappears and so does that barrier. Buffers are reused, so **two buffers suffice**: one for even iterations, one for odd.
- **Step 2: software pipelining** (p. 366; Fig. 15.12(c), Fig. 15.13(b)): even with the barrier gone, the instructions to interleave sit in different loop iterations, which stops the compiler from interleaving them. Rearrange the loop so that **iteration i computes with pair i while loading pair i + 1**. The compiler can then interleave memory and floating-point instructions, which lengthens runs of independent instructions and reduces how often the warp must stall.
- **Code** (Fig. 15.14; p. 367): prefetch pair 0 and barrier; loop `tile < numTiles - 1`: `mm` on the current buffers, `loadTile` of pair tile + 1 into the next buffers, barrier, swap buffer pointers; after the loop, one final `mm`. No barrier is needed between the `mm` and the `loadTile` calls inside the loop because they use different buffers; that is what lets the compiler interleave the two inlined functions (p. 367).
- **Limitation** (pp. 367–368): the result depends on the compiler estimating instruction latencies well when scheduling, and the compiler knows little about run-time conditions.
- **Alternatives that delegate interleaving to hardware** (p. 368):
  - **warp specialization**: program some warps to do the memory accesses and other warps to do the computation; the hardware interleaves them naturally as it schedules warps.
  - specialized hardware that moves data between global and shared memory in the background (§15.9).
- `[inferred]` Shared-memory cost of double-buffering: two A buffers and two B buffers, about 4 × 4 KB = 16 KB (slightly more with the padding column). The book does not give this figure.

### §15.9 Specialized software and hardware support (pp. 368–369)
- Vendors ship libraries with highly optimized matmul that embody this chapter's optimizations. NVIDIA examples (p. 368):
  - **cuBLAS** [1]: GPU implementation of the standard BLAS API for basic linear algebra, including matmul.
  - **cuDNN** [2]: routines for deep neural networks on GPUs, which perform matmul underneath.
  - **CUTLASS** [3]: open-source library for implementing matmul at different levels and scales; makes it easier to use matmul as a building block inside a larger kernel.
  - **cuTile**: a more recent programming interface in which developers write array-based code and the compiler performs advanced optimizations using the special properties of tensors.
- Consequence: GPU programmers typically do not write matmul from scratch, but the techniques are worth learning because they apply elsewhere (p. 368).
- **Tensor cores** `[device: NVIDIA, Volta architecture onward, "some" GPUs]` (p. 368): special-purpose cores that each perform a small matrix multiplication in a single instruction. Usable by the compiler, through a special API, or (most commonly) through cuBLAS/cuDNN/CUTLASS. Benefits stated:
  - fewer instructions per matmul removes bottlenecks from limited instruction decode and processing throughput;
  - very high throughput from warp-level hardware features for exchanging register contents and from lower-precision floating-point arithmetic units.
- **WMMA** `[device: pre-Hopper]` (p. 369): Warp Matrix Multiply and Accumulate instructions; how tensor cores were programmed before Hopper; limited to individual warps.
- **WGMMA** `[device: Hopper]` (p. 369): Warp Group Matrix Multiply Accumulate; a group of warps cooperates on a larger tensor-core multiplication. It can take input operands **directly from shared memory** (less register pressure) and can **execute asynchronously** with other instructions (less reliance on compiler scheduling to overlap long-latency instructions).
- **TMEM** `[device: Blackwell]` (p. 369): tensor memory, an on-chip memory for the inputs and outputs of tensor-core operations; reduces register pressure further. Readers are referred to the literature for details of WGMMA and TMEM.
- Once tensor cores raise compute throughput, matmul throughput can become limited by the rate of moving data to and from shared and global memory. Beyond raw bandwidths, instruction-processing overhead for data movement and the effect of register use on occupancy matter (p. 369).
  - Vector stores (§15.5) are one hardware feature for higher data throughput: with a suitable output-tile configuration each thread stores more data per instruction, with less instruction overhead and better coalescing.
  - But global↔shared transfer via vector load + vector store is still two steps through registers, costing registers and instructions.
- **LDGSTS** `[device: "recent NVIDIA GPUs"]` (p. 369): instructions that load vector data directly from global memory to shared memory without passing through registers. One instruction instead of two; the hardware performs the access asynchronously in the background, so overlap with compute no longer depends on the compiler interleaving instructions.
  - The "NVCC" compiler (as printed) can recognize a vector load from global memory into registers followed by a vector store to shared memory and emit a single LDGSTS.
  - Programmers can call `cuda::memcpy_async` from the "libcu++" library (as printed) in kernel code to use LDGSTS. Code examples and details such as data alignment are deferred to the literature.
- **TMA** `[device: Hopper onward]` (p. 369): Tensor Memory Accelerator; asynchronous transfer of entire tensors between global and shared memory without intermediate registers. Described as a generalization of LDGSTS from 1D vectors to multidimensional tensors. Usable via the `cuda::memcpy_async` API and via cuBLAS/cuDNN/CUTLASS routines that use it.

### §15.10 Summary (p. 370)
- The chapter applied many Chapter 6 optimizations to matmul. Mapping given by the summary:
  - large output tiles (via thread coarsening) → higher arithmetic intensity → compute-bound kernel;
  - register tiling of input tiles → overcomes shared-memory access latency (after global bandwidth is no longer the bottleneck);
  - re-mapping threads to data → coalesced stores of the output tile;
  - padding one shared-memory input tile → no bank conflicts.
- Heavy register use → very low occupancy; mitigations:
  - vector loads and stores → enough memory accesses to use the memory bandwidth;
  - aggressive loop unrolling → enough independent compute instructions to use the floating-point ALU throughput;
  - software pipelining or warp specialization → memory and compute instructions interleaved so memory latency overlaps compute.
- These optimizations are available in cuBLAS, cuDNN and CUTLASS, which also use tensor cores, tensor memory, asynchronous memory copies and the tensor memory accelerator. Programmers normally use the libraries; matmul remains a good showcase for the book's optimizations.

### Fig. 15.3 — `mm_tiled_kernel` (p. 354)
- **Purpose:** tiled matmul with a large block-level output tile and a per-thread register tile.
- **Signature:** `__global__ void mm_tiled_kernel(float* A, float* B, float* C, unsigned int M, unsigned int N, unsigned int K)` (lines 01–02).
- **Walkthrough:**
  - Lines 05–06, block tile origin in C: `bRow = blockIdx.y*bM;` `bCol = blockIdx.x*bN;`
  - Lines 09–13, thread tile origin inside the block tile:
    `tilesPerBlockX = bN/tN;` `ty = threadIdx.x/tilesPerBlockX;` `tx = threadIdx.x%tilesPerBlockX;` `tRow = ty*tM;` `tCol = tx*tN;`
    With bN/tN = 16, thread t owns patch (t / 16, t % 16), matching Fig. 15.2's numbering.
  - Lines 16–17: `float C_r[tM][tN];` then `clear(C_r, tM, tN);`
  - Line 20, loop over input tile pairs: `for(unsigned int tile = 0; tile < (K + bK - 1)/bK; ++tile)` (ceiling of K/bK).
  - Lines 23–24, declared inside the loop body: `__shared__ float A_s[bM*bK];` `__shared__ float B_s[bK*bN];`
  - Lines 25–26, loads:
    `loadTile(&A[bRow*K + tile*bK], K, M - bRow, K - tile*bK, &A_s[0], bK, bM, bK);`
    `loadTile(&B[tile*bK*N + bCol], N, K - tile*bK, N - bCol, &B_s[0], bN, bK, bN);`
    Argument order is (source tile start, source leading dimension, rows remaining in the source matrix, columns remaining, shared destination, shared leading dimension, tile height, tile width).
  - Line 27: `__syncthreads();`
  - Line 30: `mm(tM, tN, bK, &A_s[tRow*bK], bK, &B_s[tCol], bN, C_r);`
  - Line 31: `__syncthreads();`
  - Lines 36–39, after the loop:
    `float* c = &C[(bRow + tRow)*N + bCol + tCol];`
    `maxRow = (bRow + tRow < M)?(M - (bRow + tRow)):0;`
    `maxCol = (bCol + tCol < N)?(N - (bCol + tCol)):0;`
    `writeTile(c, N, maxRow, maxCol, C_r, tM, tN);`
- **Lines that need care:**
  - A is M×K so its row stride is K; B is K×N so its row stride is N; C's is N.
  - `maxRow`/`maxCol` are unsigned "elements remaining"; the ternaries on lines 37–38 clamp to 0 so a thread whose patch starts outside the matrix writes nothing. The load calls pass `M - bRow` and `N - bCol` unguarded, which is safe only if every launched block starts inside the matrix `[inferred]`.
  - With the §15.6 padding, `A_s` becomes `bM*(bK + 1)` and the leading dimension arguments become `bK + 1` (p. 363). `[inferred]` The offset in `&A_s[tRow*bK]` must then also use `bK + 1`; the book does not spell this out.
- **APIs / qualifiers / built-ins:** `__global__`, `__shared__`, `__syncthreads()`, `blockIdx.x/.y`, `threadIdx.x`.

### Fig. 15.4 — `clear` (p. 355)
- **Purpose:** zero the thread's register tile.
- **Signature:** `__device__ __forceinline__ void clear(float C_r[][tN], unsigned int m, unsigned int n)`.
- **Walkthrough:** `#pragma unroll` (line 03) on the row loop `row < m` (line 04); `#pragma unroll` (line 05) on the column loop `col < n` (line 06); body `C_r[row][col] = 0.0f;` (line 07).
- **Care:** both pragmas are required so indices become constants and `C_r` is register-allocated (p. 354). The parameter type hard-codes the second dimension as `tN`.
- **APIs:** `__device__`, `__forceinline__`, `#pragma unroll` (no factor = full unroll).

### Fig. 15.5 — `loadTile` (p. 355)
- **Purpose:** block-cooperative copy of one input tile from global memory to shared memory, with zero fill outside the matrix.
- **Signature:** `__device__ __forceinline__ void loadTile(float* T, unsigned int lda, unsigned int maxRow, unsigned int maxCol, float* T_s, unsigned int ldas, unsigned int height, unsigned int width)` (lines 01–03).
  - `T`: start of the tile in the source matrix; `lda`: source leading dimension; `maxRow`, `maxCol`: tile boundaries within the source matrix; `T_s`: start of the shared tile; `ldas`: its leading dimension; `height`, `width`: tile size (p. 355).
- **Walkthrough:**
  - Lines 04–05: `rowsPerSubTile = NUM_THREADS_PER_BLOCK/width;` `numSubtiles = height/rowsPerSubTile;`
  - Lines 06–07: `#pragma unroll` on `for(subTile = 0; subTile < numSubtiles; ++subTile)`.
  - Lines 08–09: `row = subTile*rowsPerSubTile + threadIdx.x/width;` `col = threadIdx.x%width;`
  - Lines 10–14: `if(row < maxRow && col < maxCol) T_s[row*ldas + col] = T[row*lda + col]; else T_s[row*ldas + col] = 0.0f;`
- **Worked instances** `[inferred from the code with the chapter's constants]`:
  - A tile (height 128, width 8): rowsPerSubTile = 256/8 = 32, numSubtiles = 4. Thread t loads (s·32 + t/8, t%8) for s = 0..3: four scalar loads per thread, matching the book's "four elements" (p. 355). A warp covers 4 rows × 8 columns, so its global loads are four 8-element runs separated by the row stride K.
  - B tile (height 8, width 128): rowsPerSubTile = 256/128 = 2, numSubtiles = 4. Thread t loads (s·2 + t/128, t%128). A warp covers 32 consecutive elements of one row.
- **Care:** `[inferred]` the arithmetic assumes `width` divides `NUM_THREADS_PER_BLOCK` and `rowsPerSubTile` divides `height`. Full unrolling needs `height` and `width` to be constants after inlining. The zero fill is what lets `mm` skip bounds checks.
- **APIs:** `__device__`, `__forceinline__`, `#pragma unroll`, `threadIdx.x`.

### Fig. 15.6 — `mm`, version 1 (p. 356)
- **Purpose:** add the current tile pair's contribution to the thread's register tile, reading shared memory in the innermost loop.
- **Signature:** `__device__ __forceinline__ void mm(unsigned int m, unsigned int n, unsigned int k, float* a, unsigned int lda, float* b, unsigned int ldb, float c[][tN])` (lines 01–02; the comma after `k` is cut off at the figure's right edge in the PDF, see "Unclear").
  - `m`, `n`: thread-level output tile size; `k`: inner dimension; `a`, `b`: starts of the thread-level input tiles; `lda`, `ldb`: their leading dimensions; `c`: thread-level output tile (p. 356).
- **Walkthrough:** three nested loops, each preceded by `#pragma unroll` (lines 03, 05, 07): `row < m` (04), `col < n` (06), `i < k` (08). Body (line 09):
  `c[row][col] += a[row*lda + i]*b[i*ldb + col];`
- **Care:** `a[row*lda + i]` is row `row`, column `i` of the thread's A rows; `b[i*ldb + col]` is row `i`, column `col` of the thread's B columns. With the Fig. 15.3 call, `lda = bK` and `ldb = bN`.
- **APIs:** `__device__`, `__forceinline__`, `#pragma unroll`.

### Fig. 15.7 — `writeTile` (p. 357)
- **Purpose:** store the thread's register tile to global memory with a boundary check.
- **Signature:** `__device__ __forceinline__ void writeTile(float*c, unsigned int ldc, unsigned int maxRow, unsigned int maxCol, float C_r[][tN], unsigned int m, unsigned int n)` (lines 01–02; the parameter list wraps and the opening brace is not visible in the PDF, see "Unclear").
- **Walkthrough:** `#pragma unroll` row loop `row < m` (03–04), `#pragma unroll` column loop `col < n` (05–06), then
  `if(row < maxRow && col < maxCol) { c[row*ldc + col] = C_r[row][col]; }` (07–09).
- **Care:** called with `ldc = N`. For a fixed (row, col), threads t and t+1 of a warp write addresses tN = 8 elements apart; this is the non-coalesced pattern §15.5 fixes.
- **APIs:** `__device__`, `__forceinline__`, `#pragma unroll`.

### Fig. 15.9 — `mm`, version 2: register tiling of input tiles (p. 359)
- **Purpose:** same contract and signature as Fig. 15.6 (here the signature is fully visible, with `unsigned int k,`), but each shared-memory value is read once per thread.
- **Walkthrough:**
  - Lines 04–05: `#pragma unroll` on the now-outermost loop `for(unsigned int i = 0; i < k; ++i)`.
  - Lines 07–12, "Load A strip to registers": `float a_r[tM];` then an unrolled loop `row < m` with `a_r[row] = a[row*lda + i];`
  - Lines 14–19, "Load B strip to registers": `float b_r[tN];` then an unrolled loop `col < n` with `b_r[col] = b[i*ldb + col];`
  - Lines 21–28, "Compute with strips": unrolled `row < m`, unrolled `col < n`, body `c[row][col] += a_r[row]*b_r[col];`

## Dated or device-specific content

- **NVIDIA H100** as the reference device for memory-bound vs compute-bound: 8 FLOP/B (32×32 tiles) is memory-bound, 32 FLOP/B (128×128) is compute-bound (p. 351). The threshold itself (20.0 FLOP/B = 66.9 TFLOPS / 3.35 TB/s) is stated in Chapter 5 (pp. 94, 111), not here.
- **4 B per element** (single-precision float) assumed in the intensity formula (p. 351).
- **32 shared-memory banks**, bank = linear element index mod 32 (p. 362). **32 threads per warp** is implied by "256 threads or eight warps" and "32 threads in the warp" (p. 360).
- **255 registers per thread** is the maximum a kernel may use "on a modern GPU" (p. 363).
- **64k registers** in "a typical SM's register file" (p. 363).
- **2048 threads** maximum occupancy per SM (p. 363).
- **4 KB** per shared tile "does not limit occupancy on a modern GPU" (p. 363).
- **Tensor cores**: "beginning with the Volta architecture, some NVIDIA GPUs" (p. 368).
- **WMMA** (Warp Matrix Multiply and Accumulate): the pre-Hopper way to program tensor cores, per-warp (p. 369).
- **WGMMA** (Warp Group Matrix Multiply Accumulate): introduced with **Hopper**; operands from shared memory; asynchronous (p. 369).
- **TMEM** (tensor memory): introduced with **Blackwell** (p. 369).
- **LDGSTS** instructions: "recent NVIDIA GPUs" (no architecture named) (p. 369).
- **"NVCC compiler"** automatically fusing vector load + vector store into LDGSTS (p. 369; spelling as printed).
- **`cuda::memcpy_async`** in the **"libcu++"** library (p. 369; name as printed), used for LDGSTS and for TMA.
- **TMA** (Tensor Memory Accelerator): "beginning with the Hopper architecture" (p. 369).
- **Libraries / interfaces:** cuBLAS [1] (http://docs.nvidia.com/cuda/cublas, cited as 2025), cuDNN [2] (Chetlur et al., arXiv:1410.0759, 2014), CUTLASS [3] (https://docs.nvidia.com/cutlass, cited as 2025), cuTile ("more recently", no citation) (pp. 368, 370).
- **`#pragma unroll`**, `__forceinline__`: compiler-specific directives relied on for register promotion (pp. 354–359). No CUDA toolkit version is named anywhere in the chapter.
- Copyright line reads 2027 Elsevier (p. 349).

## Relevance to LLM-inference kernels

- **GEMM is the core op.** The book itself ties this chapter to LLMs: attention layers are formulated as large matrix multiplications (p. 350, pointing to Ch. 20), and Chapter 20 refers back here for "hierarchical tiling, tensor cores" (Ch. 20, pp. 482, 501). Linear projections (Q/K/V/output), feed-forward layers, and Q·Kᵀ / scores·V in attention are all instances of the C = A×B kernel built here.
- **The intensity formula tells you when a custom kernel can win.** 0.5·m·n/(m+n) FLOP/B (p. 351) depends only on the output tile. `[our derivation, not in the book]` For batch-1 decode a linear layer is effectively matrix×vector: with m = 1 the formula caps at 0.5 FLOP/B, so the kernel is hopelessly memory-bound and bandwidth, not FLOPs, sets tokens/s. Batched decode and prompt processing (prefill) have large m and benefit from everything in this chapter.
- **Quantized ops.** `[our derivation]` The "4 B per element" in the formula becomes 1 B for int8 or 0.5 B for 4-bit weights, so the bytes term shrinks and intensity rises proportionally; that is the bandwidth argument for weight quantization. The book's only related statement is that tensor cores use lower-precision arithmetic units (p. 368). Register tiling still applies; dequantization would happen when filling the register strips.
- **Structure to copy for hand-written kernels:** output accumulators in registers; inner dimension streamed through small shared-memory tiles (k is free, p. 363); rank-1 updates from register strips (Fig. 15.9); explicit full unrolling; store path designed for coalescing (§15.5); padding for strided shared reads (§15.6); double-buffered, pipelined loads (Fig. 15.14). The same skeleton fits attention score computation (QKᵀ tiles) and fused "matmul + epilogue" kernels.
- **Budgeting skills transfer directly:** register budget (64 + 16 → 255 limit → 256 threads/SM, p. 363) and shared-memory budget (4 KB per tile, p. 363) are the calculations needed when sizing any attention or GEMM kernel.
- **When not to hand-roll:** the book is explicit that programmers normally call cuBLAS/cuDNN/CUTLASS, which also use tensor cores, TMEM, async copies and TMA (pp. 368–370). For the course: write these kernels to learn and for non-standard ops (custom quantization formats, fused ops), and benchmark against the library.
- **Sampling (softmax, top-k/top-p, argmax):** little direct relevance. Indirectly useful: vector loads/stores at low occupancy, full unrolling for register promotion, and software pipelining for any load-then-compute loop.

## Ideas for interactives and labs

1. **Arithmetic-intensity explorer (Fig. 15.1, p. 351).** Sliders for m, n, k and bytes per element. Show FLOPs, bytes, FLOP/B and a marker against a device threshold. Checkpoints: reproduce 8 and 32 FLOP/B; show that k has no effect; set m = 1 to see the matrix-vector case.
2. **"Who owns what" tile map (Fig. 15.2, Fig. 15.3 lines 05–13).** Enter blockIdx and threadIdx.x; the page computes bRow, bCol, ty, tx, tRow, tCol and highlights the C patch plus the A rows and B columns read. Predict-then-reveal for thread 17 and thread 255.
3. **loadTile stepper (Fig. 15.5).** For the 128×8 and 8×128 tiles, step sub-tile by sub-tile and show which element each of the 256 threads loads; color by warp to show the coalescing difference between the A and B tiles.
4. **Loop-interchange counter (Figs. 15.6 vs 15.9, Fig. 15.8).** Animate both versions for one thread and count shared-memory reads (1024 vs 128 for 8×8×8, our count). Ask the reader to predict the ratio before running.
5. **Register budget calculator (§15.7).** Inputs: tM, tN, strip sizes, overhead registers, registers per SM, max registers per thread. Output: threads per SM and occupancy. Reproduce 80 registers minimum, 255 limit → 256 threads → 12.5%.
6. **Store-pattern visualizer (§15.5, Fig. 15.10).** For one store instruction of one warp, draw the byte ranges written under (a) 8×8 tiles with scalar stores, (b) 8×8 with float4 stores, (c) four 4×4 tiles with float4 stores. Reader classifies each as coalesced or not.
7. **Bank-conflict lab (Fig. 15.11).** Interactive 32-bank histogram for a warp's A-strip load; sliders for leading dimension (8, 9, 10, …) and row stride between thread groups. Task: find all leading dimensions without conflicts and explain why 9 works (odd stride × 4 rows).
8. **Dependence quiz + pipelining Gantt (Figs. 15.12, 15.13).** Classify each barrier as true/false dependence, then drag load and compute boxes into a legal overlapped schedule. Sliders for load latency vs compute time show total time for the two schemes.
9. **Bug hunts.** (a) Remove one `#pragma unroll` and ask what happens to `C_r` (falls back to memory). (b) Apply padding to the declaration but leave `&A_s[tRow*bK]` and `lda = bK` unchanged; find the wrong-result bug. (c) In Fig. 15.14, move the barrier before the `loadTile` calls, or drop the final `mm`; predict the failure. (d) Launch with a 2D 16×16 block and explain why `threadIdx.x`-only indexing breaks.
10. **Measured lab series (GPU required).** Implement in order: Ch. 5 32×32 tiled kernel → Fig. 15.3 with Fig. 15.6 → swap in Fig. 15.9 → add float4 load/store (Exercises 1–2) → §15.5 rearrangement (Exercise 3) → padding → Fig. 15.14 pipelining. After each step record GFLOPS, registers per thread and occupancy from the compiler/profiler, and compare with the vendor BLAS. The book supplies no timings, so the lab produces the missing numbers.
11. **Design exercise for the LLM reader.** Given a target (e.g. 4096×4096 weight matrix, batch 1 vs batch 64, fp16 vs int8), choose bM, bN, bK, tM, tN and justify with the intensity, shared-memory and register budgets from this chapter.
