# Chapter 5 — Memory architecture and data locality

- **Book pages:** 93–122 (p. 122 blank)  **PDF pages:** 121–150 (pdf = book + 28)
- **Read by:** main session, every page as an image (2026-11-20).
- **In one paragraph:** The kernels from chapters 2–3 run far below what the hardware
  can do because nearly every operation waits on global memory. The chapter gives a
  way to quantify that (FLOP per byte of global-memory traffic, the roofline model,
  speed-of-light analysis), surveys the memories a CUDA kernel can use (registers,
  local, shared, global, constant) with their scope and lifetime, and then uses shared
  memory to *tile* matrix multiplication so each global element is fetched once per
  block instead of once per thread. It finishes with boundary checks for arbitrary
  sizes and with how shared-memory use trades against occupancy. Afterwards the reader
  can classify a kernel as memory- or compute-bound, write a correct tiled matmul with
  the two barriers it needs, and budget shared memory per thread.

## Concepts

### Chapter intro (p. 93)
- Global memory is "typically implemented with off-chip DRAM": long latency (the book
  says hundreds of clock cycles) and finite bandwidth.
- Many threads can hide latency (ch. 4), but if the global-memory paths congest, only a
  few threads make progress and SM cores sit idle.
- GPUs therefore provide on-chip memories that remove most redundant global traffic.

### §5.1 Memory bandwidth as a performance limiter (pp. 93–97)
- Two hardware limits: **peak computational throughput** (operations per unit time) and
  **peak memory bandwidth** (bytes per unit time from a given memory structure).
  Limits differ by datatype and by memory structure; the chapter fixes single-precision
  floating point and global memory. (p. 94)
- `[device: Hopper H100]` peak computational throughput **66.9 TFLOPS**; peak global
  memory bandwidth **3.35 TB/s**. (p. 94)
- **Compute-bound**: limited by computational throughput; cores busy with a steady
  supply of instructions. **Memory-bound**: limited by memory bandwidth; memory channels
  busy, cores often idle waiting for data. (p. 94)
- **Compute-to-global-memory-access ratio** = floating-point operations performed per
  byte accessed from global memory, in FLOP/B. The book notes the literature also calls
  it *arithmetic intensity* or *computational intensity*. (p. 94)
- **Threshold** between the regimes = peak throughput / peak bandwidth.
  `[device: H100]` 66.9 TFLOPS / 3.35 TB/s = **20.0 FLOP/B**. Above: likely
  compute-bound; below: likely memory-bound. (p. 94)
- The peaks are **limits, not guarantees**: only well-optimised kernels approach them.
  Comparing a kernel to the limit tells you how well optimised it is. (p. 94)
- **Roofline model** (sidebar, pp. 95–96): x = computational intensity (FLOP/B),
  y = computational throughput (GFLOPS). Two hardware lines: a horizontal line at peak
  throughput and a line through the origin with slope = peak bandwidth (labelled
  "Peak bandwidth (GB/s) × FLOP/B"). They meet at the threshold intensity. Left of it
  an application is memory-bound, and raising its intensity raises its ceiling; right of
  it, compute-bound. A point is an application (its intensity, its achieved throughput);
  points must lie under both lines. Distance below the lines = inefficiency.
  Example points: A1 and A2 are memory-bound, A3 compute-bound; A1 sits near the
  bandwidth line (efficient: the only way up is to raise intensity), A2 is well below
  it (room to use bandwidth better).
- **Vector addition** (Fig. 2.10 kernel, `C[i] = A[i] + B[i]`): 1 FLOP per 12 B
  (load 4 B, load 4 B, store 4 B) = **0.083 FLOP/B**, far under 20.0, so deeply
  memory-bound on the H100. (p. 96)
- **Speed-of-light analysis** (p. 96): compare the achieved access rate to the hardware
  peak. Worked numbers: two vectors of one billion elements → 12 GB touched; if it
  finishes in 4 ms the rate is 12 GB / 4 ms = 3 TB/s = 3/3.35 = **90%** of peak, so
  only 10% headroom. Fastest possible: 12 GB / 3.35 TB/s = **3.6 ms**. `[device: H100]`
- **Matrix multiplication in the abstract** (p. 96): N×N output, each element a dot
  product of N multiplies and N adds → **2N³ FLOP**. Memory if every element were
  touched exactly once: load 2N² elements, store N², at 4 B each → **12N² B**. Ideal
  ratio = 2N³ / 12N² = **0.167·N FLOP/B**. For N = 1024 that is **167 FLOP/B**, well
  over the threshold: matmul *can* be strongly compute-bound. (pp. 96–97)
- **The naive kernel (Fig. 3.11) in practice** (p. 97): each inner-loop iteration does
  two global loads (one M, one N; 8 B) for one multiply and one add → 2 FLOP / 8 B =
  **0.25 FLOP/B** (slightly less, counting the final store of `Pvalue`). Lower than
  ideal because each input element is fetched many times. Under the threshold →
  memory-bound.
- Consequence `[device: H100]`: 3.35 TB/s × 0.25 FLOP/B = **0.84 TFLOPS**, about **1%**
  of 66.9 TFLOPS. Against the tensor-core peak of **989 TFLOPS** it is **0.08%**. (p. 97)
- Caveat the book states: the real ratio is somewhat higher than 0.25 because some
  global accesses are served by on-chip caches rather than DRAM. (p. 97)
- To raise the ratio, reduce the number of global accesses. Matmul speed "can vary by
  orders of magnitude" with how well that is done. (p. 97)

### §5.2 CUDA memory types (pp. 98–104)
- Declaring a variable into a memory type sets its **visibility and access speed**. (p. 98)
- **Global** and **constant** memory: host can read and write both. Device can read and
  write global; constant is **read-only** for the device with short latency and high
  bandwidth (details deferred to ch. 7). (p. 98)
- **Local memory**: *actually placed in global memory* with similar latency, but private
  per thread. Holds what cannot go in registers: statically allocated arrays, spilled
  registers, other call-stack contents. Small constant-size arrays accessed only with
  constant indices may be promoted to registers (ch. 6). (p. 98)
- **Registers**: on-chip, very fast, highly parallel, private per thread. (p. 98)
- Sidebar *CPU vs. GPU register architecture* (p. 99): CPUs save/restore registers on
  context switch. GPUs keep the registers of **all threads scheduled on the processing
  block** in its register file, so switching warps is instantaneous (zero-overhead
  scheduling), which is why GPU register files are much larger. They also support
  dynamic partitioning: fewer registers per thread and more threads, or the reverse.
- **Shared memory**: on-chip; fast relative to global but slower than registers;
  allocated **per thread block**; all threads of a block can access it. The mechanism
  for threads of a block to cooperate on inputs and intermediate results. (p. 99)
- Von Neumann framing (Fig. 5.2, pp. 99–100): global memory = the Memory box, off-chip
  DRAM. Registers = the Register File inside the processor. Aggregate register-file
  bandwidth across SMs is "at least two orders of magnitude" higher than global memory.
  A value kept in a register consumes no global bandwidth, raising the FLOP/B ratio.
- Fewer instructions too (p. 100): arithmetic instructions take register operands
  directly (`fadd r1, r2, r3`); an operand in memory needs a load first
  (`load r2, r4, offset` then `fadd r1, r2, r3`).
- Energy (pp. 100–101): reading a register costs at least an order of magnitude less
  energy than reading global memory.
- But registers per thread are limited; exceeding the full-occupancy budget lowers
  occupancy (ch. 4). (p. 101)
- Shared memory vs registers (Fig. 5.3, p. 101): both on-chip. Shared memory is part of
  the memory space on the chip, so using it still needs a **load** instruction: lower
  latency and much higher throughput than global, longer latency and lower bandwidth
  than registers. Architecturally a **scratchpad memory**. An SM has multiple processing
  units; a block's threads spread across them, and the hardware lets those units access
  shared memory simultaneously.
- **Distributed shared memory** (p. 102): from the Hopper architecture, threads in the
  same *thread block cluster* can access the shared memory of any block in the cluster.
  `[device: Hopper and later]`
- **Scope** = which threads can access a variable (one thread, all threads of a block,
  all threads of all grids). Thread scope means one private copy per thread: a kernel
  launched with a million threads creates a million copies. **Lifetime** = within a
  grid's execution (declared in the kernel body, not preserved between launches, must be
  re-initialised each launch) or the whole application (declared outside any function,
  preserved, visible to all kernels). (p. 102)
- Declaration table (Fig. 5.4, p. 102):

  | Declaration | Memory | Scope | Lifetime |
  |---|---|---|---|
  | automatic variables other than arrays | register | thread | grid |
  | automatic array variables | local | thread | grid |
  | `__device__ __shared__ int SharedVar;` | shared | block | grid |
  | `__device__ int GlobalVar;` | global | grid | application |
  | `__device__ __constant__ int ConstVar;` | constant | grid | application |

- Automatic scalars (example: `blurRow`, `blurCol`, `curRow`, `curCol`, `pixels`,
  `pixVal` in Fig. 3.8) live in registers. Fast, but too many hurts occupancy. (pp. 102–103)
- Automatic arrays go to local memory by default and may see long delays; the compiler
  *may* use registers if every access uses constant indices. (p. 103)
- `__shared__` (optionally preceded by `__device__`), typically inside a kernel or
  device function. Block scope: one copy per block. Lifetime: the kernel's execution.
  Typical use: hold the part of global data that is heavily reused in one execution
  phase; algorithms may need restructuring to *create* such phases. (p. 103)
- `__constant__` (optionally with `__device__`): must be declared **outside** any
  function; scope all grids; lifetime the application; cannot be changed by kernel code;
  stored in global memory but cached. **Total size limited to 65,536 bytes**
  ("currently"). (p. 103) `[dated]`
- `__device__` alone: a global variable in global memory, slow, visible to all threads
  of all kernels, persists. Used to pass data between kernel invocations without a
  parameter; considered bad style. (pp. 103–104)

### §5.3 Tiling for reduced memory traffic (pp. 104–107)
- The trade-off: global memory is large but slow, shared memory small but fast. **Tile**
  = a subset of the data that fits in shared memory (the wall/tiles analogy). The
  computation on tiles must be independently doable; not every data structure and kernel
  can be tiled. (p. 104)
- Running example (Fig. 5.5): 4×4 matrices, four 2×2 blocks. Block (0,0)'s four threads
  compute P0,0, P0,1, P1,0, P1,1.
- **The overlap** (Fig. 5.6, p. 105): thread(0,0) and thread(0,1) both read all of row 0
  of M; thread(0,1) and thread(1,1) both read all of column 1 of N. In block (0,0) every
  M and N element used is read **exactly twice**. If the threads cooperated, global
  traffic would halve.
- General claim: the potential reduction is proportional to the output tile dimension.
  With `TILE_WIDTH × TILE_WIDTH` tiles it is a factor of `TILE_WIDTH` (32×32 → 1/32). (p. 105)
- **Tiled algorithm**: split M and N into input tiles sized to fit shared memory; in the
  simplest form input tile = output tile = block dimensions (Fig. 5.7). (pp. 105–106)
- **Phases** (Fig. 5.8): the dot product is cut into phases. In each phase every thread
  of the block loads **one M element and one N element** into shared arrays `Mds` and
  `Nds`, then all threads use those arrays for a partial dot product. Each shared value
  is used twice in the 2×2 example (e.g. M1,1 loaded by thread(1,1) is used by
  thread(1,0) and thread(1,1)).
- Number of phases = `Width / TILE_WIDTH`. (p. 107)
- `Mds`/`Nds` are **reused across phases**, so a small shared memory serves most of the
  accesses.
- **Locality**: each phase focuses on a small subset of the input. Locality is what lets
  small fast memories serve most accesses; it matters equally for multicore CPUs. (p. 107)

### §5.4 A tiled matrix multiplication kernel (pp. 108–112)
- Kernel is Fig. 5.9 (see Code listings).
- `Mds`, `Nds` are shared: one copy per block, visible to all its threads, which is
  exactly what cooperation needs. `tx, ty, bx, by` are automatic scalars → registers. (p. 108)
- Output element owned by a thread: `Row = by*TILE_WIDTH + ty`, `Col = bx*TILE_WIDTH + tx`.
  Reasoning: `bx` blocks before this one cover `bx*TILE_WIDTH` columns, and `tx` threads
  before this one in the block cover `tx` more. Worked example: thread(0,1) of block(1,0)
  → Col = 0·2+1 = 1, Row = 1·2+0 = 2 → P2,1. (p. 109)
- At the start of phase `ph`, `ph*TILE_WIDTH` pairs of elements have been processed. (p. 109)
- Loading (p. 110): the M tile for this phase starts at column `ph*TILE_WIDTH` of the
  thread's row; each thread takes the element `tx` positions along:
  `M[Row*Width + ph*TILE_WIDTH + tx]`. The N tile starts at row `ph*TILE_WIDTH` of the
  thread's column; each thread takes the element `ty` positions down:
  `N[(ph*TILE_WIDTH + ty)*Width + Col]`. Every (tx, ty) is unique, so the block loads
  `TILE_WIDTH²` distinct M elements and `TILE_WIDTH²` distinct N elements per phase.
- **First barrier** (line 21): all loads must finish before anyone reads, because the
  elements a thread needs were loaded by *other* threads. **Second barrier** (line 26):
  everyone must finish reading before anyone starts the next phase's loads, or a fast
  thread overwrites values others still need. (p. 110)
- **Dependence vocabulary** (pp. 110–111): the first is a **read-after-write** dependence
  = **true dependence** (the reader really needs the writer's data). The second is a
  **write-after-read** dependence = **false dependence** (the writer needs nothing from
  the reader; it exists only because the same location is reused and would vanish with
  separate locations). Revisited in ch. 6.
- **Strip-mining** (p. 111): break a long loop into phases: an outer loop over phases,
  an inner loop over a few consecutive iterations, original order preserved. With
  barriers around the inner loop it forces all threads of a block to focus on the same
  section of input in each phase. Footnote: strip-mining is old CPU practice; followed
  by loop interchange it enables tiling in sequential code, and it is how vectorising
  compilers produce SIMD.
- **Payoff** (p. 111): global accesses drop by a factor of `TILE_WIDTH`. With 32×32
  tiles the ratio rises from 0.25 to **8 FLOP/B**. `[device: H100]` 3.35 TB/s × 8 =
  **26.8 TFLOPS** vs 0.84 before; still memory-bound (8 < 20), and only **40%** of the
  66.9 TFLOPS peak. Caches may help further in practice.
- To go beyond: more optimisations in ch. 15. Libraries named: **cuBLAS** and
  **CUTLASS**. (p. 111) `[dated]`
- **Register tiling** (p. 112): tiling means putting frequently accessed data in a
  memory faster than where it lives, not only shared memory. `Pvalue` is the P element
  held in a register and updated repeatedly by one thread; that is register tiling
  (trivial here; non-trivial in chs. 8, 11, 15).
- **CPU vs GPU tiling** (p. 112): CPUs rely on the cache *implicitly* keeping reused data
  on-chip; a core runs one or two threads, so the cache is dependable. A GPU SM runs
  many threads at once to hide latency, they compete for cache slots, so the cache is
  less reliable and important reused data is placed in shared memory *explicitly*.
- Simplifying assumptions in Fig. 5.9: width is a multiple of the block width; matrices
  are square. (p. 112)

### §5.5 Boundary checks (pp. 112–115)
- Example: 3×3 matrices with 2×2 tiles (Figs. 5.11, 5.12).
- Block (0,0), second phase (Fig. 5.11): thread(0,1) and thread(1,1) try to load M0,3 and
  M1,3 (past the end of a row); thread(1,0) and thread(1,1) try to load N3,0 and N3,1
  (past the end of a column).
- **Past the end of a row** is silent: in the linearised layout the element after M0,2 is
  M1,0, so the thread reads a *valid but wrong* element and corrupts the result. (p. 113)
- **Past the end of a column** reads outside the allocation: may return garbage from
  other data, or abort, depending on the system. (p. 113)
- It is **not** just the last phase: Fig. 5.12 shows block (1,1) in phase 0, where
  thread(1,0) and thread(1,1) reach for M3,0 and M3,1, and thread(0,1) and thread(1,1)
  for N0,3 and N1,3. (p. 113)
- You **cannot** fix it by excluding threads that own no valid P element: (as printed; the
  thread index looks swapped, see "Unclear in the PDF") thread(1,0) of
  block (1,1) owns no valid P element but must still load M2,1 for its peers. Conversely
  a thread that *does* own a valid P element (thread(0,1) of block (0,0), owner of P0,1)
  tries to load the non-existent M0,3. (pp. 113–114)
- So three **different** tests are needed (rule of thumb: every memory access gets its
  own bounds check on the indices it uses) (p. 114):
  - load M: `Row < Width && (ph*TILE_WIDTH + tx) < Width`
  - load N: `(ph*TILE_WIDTH + ty) < Width && Col < Width`
  - store P: `Row < Width && Col < Width`
- When a load is out of range, store **0.0f** in the shared slot: harmless in a sum of
  products. (p. 114)
- The phase count becomes `ceil(Width / (float)TILE_WIDTH)` (Fig. 5.13 line 16).
- **Rectangular matrices** (pp. 114–115): M is j×k, N is k×l, P is j×l. Replace `Width`
  by `j` where it means height of M / height of P, by `k` where it means width of M /
  height of N, by `l` where it means width of N / width of P. Left as an exercise.

### §5.6 Impact of memory usage on occupancy (pp. 115–118)
- On-chip memory capacity is limited per SM; the more each thread needs, the fewer
  threads fit. The programmer balances arithmetic intensity (use more on-chip memory)
  against occupancy (latency tolerance). (p. 115)
- `[device: H100]` up to **228 KB** shared memory per SM (configurable), max **2048**
  threads per SM → full occupancy needs ≤ 228 KB / 2048 = **114 B/thread**. (p. 116)
- Tiled matmul uses `TILE_WIDTH²·4 B` for each of `Mds` and `Nds` over `TILE_WIDTH²`
  threads = **8 B/thread**, independent of tile size → not shared-memory-limited. (p. 116)
- Counter-example: blocks using 38 KB with 256 threads → 152 B/thread → at most
  228 KB / 152 B = 1536 threads per SM → **75%** occupancy. (p. 116) `[device: H100]`
- CUDA lets an SM be reconfigured to give more of its on-chip memory to shared memory
  **at the expense of cache**, so both predictable and unpredictable access patterns can
  benefit. (p. 116)
- Shared memory per SM varies across devices. Query it:
  `cudaGetDeviceProperties(…, &devProp)` then `devProp.sharedMemPerBlock`, which the
  book describes as "the amount of shared memory available in each SM". (p. 116)
  *(See "Unclear in the PDF": the field name says per block.)*
- **Dynamically sized shared memory** (pp. 116–118): fixed `__shared__ float
  Mds[TILE_WIDTH][TILE_WIDTH]` bakes the size in at compile time. Instead declare one
  unsized array with `extern __shared__`, pass the byte count as the **third**
  execution-configuration parameter (`kernel<<<dimGrid, dimBlock, size>>>(…)`), and
  carve the single 1-D array into the `Mds` and `Nds` sections by hand, indexing with
  linearised indices (`Mds[ty*TILE_WIDTH + tx]` instead of `Mds[ty][tx]`). For 32×32
  tiles, `size = 2·32·32·4 = 8192` bytes.

### §5.7 Summary (pp. 118–119)
- Speed depends on the compute-to-global-memory-access ratio. Registers, shared and
  constant memory are small but fast and consume no global bandwidth; using them well
  requires redesigning the algorithm. Tiling uses barrier synchronisation to make
  threads jointly focus on a subset of data per phase.
- Capacities are implementation-dependent; exceeding them cuts the number of threads
  per SM, hurting throughput and latency tolerance.
- Tiling is general: on multicore CPUs locality lets on-chip caches do the same job.

## Code listings

### Fig. 3.11 — `MatrixMulKernel`, one thread per P element (p. 61; the baseline)
- `__global__ void MatrixMulKernel(float* M, float* N, float* P, int Width)`.
- `row = blockIdx.y*blockDim.y + threadIdx.y`, `col = blockIdx.x*blockDim.x + threadIdx.x`.
- Guard `if ((row < Width) && (col < Width))`; `float Pvalue = 0;` loop `k` from 0 to
  `Width`, `Pvalue += M[row*Width+k]*N[k*Width+col];` then `P[row*Width+col] = Pvalue;`.
- M is walked along a row (consecutive addresses), N down a column (stride `Width`).

### Fig. 5.9 — tiled `matrixMulKernel` using shared memory (p. 108)
- `#define TILE_WIDTH 16`; same signature as Fig. 3.11. Assumes blocks are
  `TILE_WIDTH × TILE_WIDTH` threads, and `Width` a multiple of `TILE_WIDTH`.
- Lines 04–05: `__shared__ float Mds[TILE_WIDTH][TILE_WIDTH];` and the same for `Nds`.
- Lines 07–08: copy `blockIdx.x/.y` into `bx, by` and `threadIdx.x/.y` into `tx, ty`.
- Lines 11–12: `Row = by*TILE_WIDTH + ty; Col = bx*TILE_WIDTH + tx;`
- Line 15: `float Pvalue = 0;`
- Line 16: `for (int ph = 0; ph < Width/TILE_WIDTH; ++ph)`
- Lines 19–20 (the lines that need care):
  `Mds[ty][tx] = M[Row*Width + ph*TILE_WIDTH + tx];`
  `Nds[ty][tx] = N[(ph*TILE_WIDTH + ty)*Width + Col];`
- Line 21: `__syncthreads();` (read-after-write, true dependence)
- Lines 23–25: `for (int k = 0; k < TILE_WIDTH; ++k) Pvalue += Mds[ty][k] * Nds[k][tx];`
- Line 26: `__syncthreads();` (write-after-read, false dependence)
- Line 29: `P[Row*Width + Col] = Pvalue;`
- Built-ins/qualifiers: `__global__`, `__shared__`, `blockIdx`, `threadIdx`, `__syncthreads()`.

### Fig. 5.13 — boundary-checked loop (p. 115)
- Line 16 becomes `for (int ph = 0; ph < ceil(Width/(float)TILE_WIDTH); ++ph)`.
- M load guarded by `if ((Row < Width) && (ph*TILE_WIDTH+tx) < Width)` else `Mds[ty][tx] = 0.0f;`
- N load guarded by `if ((ph*TILE_WIDTH+ty) < Width && Col < Width)` else `Nds[ty][tx] = 0.0f;`
- Store guarded by `if (Row < Width) && (Col < Width)`.
- Inner loop and both barriers unchanged.

### Fig. 5.14 — dynamically sized shared memory (p. 117)
- `#define TILE_WIDTH 32`; kernel gains two `unsigned` parameters for the section sizes.
- One unsized `extern __shared__` array `Mds_Nds[]`; then
  `float *Mds = (float *) Mds_Nds;` and `float *Nds = (float *) Mds_Nds + Mds_sz;`
- Launch (p. 117): `matrixMulKernel<<<dimGrid, dimBlock, size>>>(Md, Nd, Pd, Width, size/2, size/2);`
- As printed this listing is inconsistent in several places; see "Unclear in the PDF".

## Relevance to LLM-inference kernels
- Direct and central. Every linear layer, the QKV projections, the MLP and the
  unembedding are GEMMs; this chapter is the first time the reader sees *why* a naive
  GEMM is ~1% of the hardware and the first real fix.
- FLOP/B and roofline reasoning are the tools for every later decision: why batch-1
  token generation (matrix × vector) is memory-bound however well it is written (ideal
  ratio ≈ 2·rows·cols FLOP over 4·rows·cols B of weights = 0.5 FLOP/B), and therefore why
  quantisation speeds up inference (fewer bytes per weight raises FLOP/B directly).
- Rectangular matmul with boundary checks (§5.5 exercise) is the real shape of the
  problem: hidden × vocab, batch × hidden.
- Shared-memory budgeting per thread and occupancy carry over to attention kernels
  that stage K/V tiles.

## Unclear in the PDF
- **p. 97:** "the H100 GPU's threshold of 25.1 FLOP/B or 20.0 FLOP/B". Every other
  mention is 20.0, and 66.9/3.35 = 19.97. The 25.1 looks like a leftover from another
  device or draft. Use 20.0 and flag it.
- **Fig. 5.8 vs text (p. 107):** the figure heads the phases "Phase 0" and "Phase 1";
  the text calls them "Phase 1 and Phase 2". The kernel's `ph` starts at 0. Use 0-based.
- **p. 106–107:** "the reduction is by a factor of N if the tiles are N × N": here N is
  the tile dimension, not the matrix name used a line earlier.
- **Fig. 5.14 (p. 117), several problems:**
  1. Line 04 reads `extern __shared__ char float Mds_Nds[];` (two types). The prose
     shows `extern __shared__ Mds_Nds[];` with no type at all.
  2. The parameter is spelled `Mdz_sz` in the signature and `Mds_sz` in line 07.
  3. The text says the two extra arguments are sizes **in bytes**, but line 07 adds
     `Mds_sz` to a `float*`, which advances by `Mds_sz` *elements*. With bytes passed,
     `Nds` would start 4× too far along.
  4. The text says `size/2` "is 1024 bytes"; with `size = 8192` bytes it is 4096 bytes
     (1024 *elements*).
  5. The text refers to "the kernel code in Figs. 5.9 and 5.11"; 5.11 is a diagram, 5.13
     is the kernel meant.
  The course should present a corrected, compiled version and say it differs.
- **p. 113:** the text says "thread(1,0) in block(1,1) does not calculate any valid P
  element. However, it needs to load M2,1 during phase 0". By the (row, column)
  convention the book uses for threads everywhere else on these pages (Figs. 5.11 and
  5.12), thread (1,0) has Row 3 and would load M3,0, which does not exist. The thread
  that owns no valid P element (it would own P2,3) and loads M2,1 is thread (0,1), i.e.
  ty = 0, tx = 1. Almost certainly an index swap in the text. The point being made is
  unaffected. Found by the section 5.5 builder and confirmed with the simulator.
- **p. 116:** `devProp.sharedMemPerBlock` is described as shared memory "available in
  each SM". The field name says per block. Check current CUDA docs before stating
  either.
- **Exercise 10 (pp. 119–120):** text says `BLOCK_WIDTH`, code uses `BLOCK_SIZE` in
  lines 08–09 and the questions.
- **Exercise 11 (p. 120):** line 18 contains a typesetting artefact (`\texttts{N}`), and
  `foo` takes `int*` while the kernel takes `float*`.
- **Exercise 12 (p. 121):** "4 KB of shared memory/SM" and "8 KB of shared
  memory/SM" for a per-kernel characteristic; per block is probably intended.
