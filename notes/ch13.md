# Chapter 13 — Merge

- **Book pages:** 303–328  **PDF pages:** 329–354 (pdf = book + 26)
- **In one paragraph:** The chapter parallelizes the ordered merge of two sorted arrays. Unlike every earlier pattern, a thread cannot compute which input elements it needs from its index alone: the input range depends on the data values. The fix is the *co-rank function*, a binary search that converts an output position into the pair of input positions that feed it. With it, each thread takes a slice of the output, finds its two input slices, and runs an ordinary sequential merge. The chapter then spends most of its length on memory efficiency: a basic kernel (uncoalesced, binary search in global memory), a tiled kernel that stages input in shared memory (coalesced, but throws away half of what it loads), and a circular-buffer kernel that keeps the unused half (efficient, noticeably more complex). After the chapter a reader can write and trace a co-rank function, explain why merge tiling must over-load its inputs, and reason about hiding a circular buffer behind a "virtual index" interface. Conventions used below: anything marked `[inferred]` is our reasoning, not a statement in the book.

## Concepts

### Chapter opening (p. 303)
- Chapter subtitle: "And dynamic input data identification". Credited "with special contributions from Li-Wen Chang and Jie Lv" (p. 303).
- Ordered merge takes two sorted lists and produces one combined sorted list (p. 303).
- Uses named by the book: building block of sorting algorithms (Ch. 14) and the basis of modern map-reduce frameworks (p. 303).
- What makes it a new pattern: the input data each thread uses is "dynamically determined", which makes locality and tiling hard. The same principle is said to matter for set intersection and set union (p. 303).
- The chapter promises "increasingly sophisticated buffer management schemes" (p. 303): that is the basic → tiled → circular-buffer progression.

### §13.1 Background (pp. 303–305)
- Setup: sorted lists A and B are stored in arrays; each element has a key; an order relation written ≤ is defined on keys. In the simplest case elements are just keys (pp. 303–304).
- Sorted means: if element e1 appears before e2 then k1 ≤ k2 (p. 304).
- A merge function based on ordering relation R takes sorted A (m elements) and sorted B (n elements); m and n need not be equal. It produces sorted C with m + n elements containing all input elements (p. 304).
- Running example used in the whole chapter (Fig. 13.1, p. 304): A = [1, 7, 8, 9, 10] (m = 5), B = [7, 10, 10, 12] (n = 4), C = [1, 7, 7, 8, 9, 10, 10, 10, 12] (9 elements).
- **Stability** (p. 304): an ordering operation is stable if elements with equal keys keep their input order in the output. Two flavours shown by the example:
  - within one input list: the two 10s from B appear in C in their original order;
  - across input lists: the 7 from A is placed before the 7 from B.
- Why stability matters (p. 304): it preserves orderings that the current key does not capture, for example when the lists were previously sorted by a different key. It lets a merge keep the work of earlier steps.
- Merge is the core of merge sort: split the input into sections, give them to threads, sort sections, then cooperatively merge. The book calls this a "divide-and-concur" approach (pp. 304–305).
- Map-reduce frameworks such as Hadoop distribute work to many compute nodes; the reduce step assembles sorted results with merges arranged as a reduction tree, so efficient merge matters to them (p. 305).

### §13.2 A sequential merge algorithm (pp. 305–306)
- `merge_sequential` (Fig. 13.2) has two parts (p. 305):
  1. a while-loop that runs while both inputs have elements left. Each iteration fills exactly one position of C with either A[i] or B[j], using indices i (into A), j (into B), k (into C), all starting at 0.
  2. a tail copy: whichever input is not exhausted is copied to the rest of C.
- The comparison is `A[i] <= B[j]`, so on a tie the A element goes first. This is what gives across-list stability (p. 305, code line 06; the stability link is made explicit on p. 311).
- The `if (i == m) … else …` around the two tail loops is not needed for correctness; two bare while-loops would do because only one can execute. It is kept for readability (p. 306).
- Trace on the running example (p. 306): iterations 0–2 write A[0], A[1], B[0] to C[0], C[1], C[2]. After iteration 5, A is exhausted; six C positions were filled from A[0]–A[4] and B[0]. The tail loop copies B[1]–B[3].
- Cost: every input element is visited once and every C position written once, so complexity is O(m + n), linear in the total size (p. 306).

### §13.3 A parallelization approach (pp. 306–308)
- Approach credited to Siebert et al. [1] (p. 306): each thread first decides the range of *output* positions it will produce, then uses that output range as input to a *co-rank function* to find the input ranges that merge into it. After that, threads touch disjoint sub-arrays (two input, one output) and can each run the sequential merge independently.
- **Observation 1** (p. 306): for any k with 0 ≤ k < m + n, either (case 1) there is an i with 0 ≤ i < m such that C[k] comes from A[i], or (case 2) there is a j with 0 ≤ j < n such that C[k] comes from B[j].
- Case 1 worked example (p. 307, Fig. 13.3(a)): C[4] (value 9) comes from A[3]; k = 4, i = 3. The 4-element prefix C[0..3] is the merge of the 3-element prefix A[0..2] and the 1-element prefix B[0] (4 − 3 = 1). General form: C[0..k−1] is the merge of A[0..i−1] (i elements) and B[0..k−i−1] (k − i elements).
- Case 2 worked example (p. 307, Fig. 13.3(b)): C[6] comes from B[1]; k = 6, j = 1. The 6-element prefix C[0..5] is the merge of A[0..4] (5 elements) and B[0] (1 element). General form: C[0..k−1] is the merge of A[0..k−j−1] (k − j elements) and B[0..j−1] (j elements).
- In case 1 we find i and derive j = k − i; in case 2 we find j and derive i = k − j. The symmetry gives:
- **Observation 2** (p. 307): for any k with 0 ≤ k ≤ m + n, there exist i and j with k = i + j, 0 ≤ i ≤ m, 0 ≤ j ≤ n, such that C[0..k−1] is the merge of A[0..i−1] and B[0..j−1]. Note the ranges are now inclusive of m + n, m and n, so "one past the end" is a legal query.
- Siebert et al. also proved i and j are unique (p. 308).
- **Terminology** (p. 308): for element C[k], k is its *rank*; the unique i and j are its *co-ranks*. Examples: C[4] has rank 4 and co-ranks 3 and 1; C[6] has rank 6 and co-ranks 5 and 1.
- Parallel plan (p. 308): split the output array into sub-arrays, one per thread. The rank of each thread's first output is then known; the co-rank function gives the two input sub-arrays.
- The key contrast with all earlier patterns (p. 308): the input range of a thread cannot be found by a simple index calculation; it depends on the actual input values.

### §13.4 Co-rank function implementation (pp. 308–313)
- Signature (p. 308): `int co_rank(int k, int * A, int m, int * B, int n)`. k is the rank, A/m and B/n are the inputs and their sizes; the return value is i, the co-rank of k in A. The caller derives j = k − i.
- How a thread uses it (pp. 308–309, Fig. 13.4), two-thread example: thread 0 produces C[0..3], thread 1 produces C[4..8].
  - Start of thread 1's inputs: `co_rank(4, A, 5, B, 4)` should yield i1 = 3, j1 = 1: thread 0 takes A[0..2] and B[0]; thread 1 starts at A[3] (value 9) and B[1] (value 10).
  - Why other choices fail (p. 309): i1 = 2 forces j1 = 2, which puts B[1] = 10 into thread 0's share while A[2] = 8 goes to thread 1, so C would not be sorted. i1 = 4 forces j1 = 0, which puts A[3] = 9 into thread 0's share while B[0] = 7 goes to thread 1, again wrong. This "too low / too high" feedback is what suggests a search.
  - End of thread 1's inputs: `co_rank(9, A, 5, B, 4)` yields i2 = 5, j2 = 4 (both inputs exhausted, because rank 9 is one past the end of C).
  - General rule: thread t's input sub-arrays are delimited by the co-ranks of thread t and thread t+1 (p. 309; see "Unclear in the PDF" for the garbled index expression).
- The co-rank function is a search. Because both inputs are sorted, a binary search "or even a higher radix search" gives O(log N) (p. 309).
- Variables (p. 309): i and j are the current candidate co-ranks; `i_low` and `j_low` are the smallest values the co-ranks could still take.
- Initialization (pp. 309–310, Fig. 13.5 lines 02–05):
  - i starts at its largest possible value, min(k, m): it cannot exceed m (size of A) nor k.
  - j = k − i. **Invariant:** i + j == k at all times.
  - `i_low = max(0, k−n)`: at most n of the k prefix elements can come from B, so at least k − n must come from A. Likewise `j_low = max(0, k−m)`. Setting both to 0 would still be correct; the tighter bounds only shrink the search (p. 310).
- Goal condition (p. 311): find i and j such that `A[i-1] <= B[j]` and `B[j-1] < A[i]`. Intuition: nothing in the "previous" A sub-array may be greater than anything in the "current" B sub-array, and vice versa. The first relation allows equality because, for stability, A elements go first on ties; the second is strict for the same reason.
- Loop body (p. 311, Fig. 13.5 lines 09–21):
  - If i is too high (`i > 0 && j < n && A[i-1] > B[j]`): reduce i by `delta = ceil((i − i_low)/2)`, set `j_low = j`, and raise j by the same delta so the invariant holds.
  - Else if j is too high (`j > 0 && i < m && B[j-1] >= A[i]`): symmetric, reduce j by `ceil((j − j_low)/2)`, set `i_low = i`, raise i by delta.
  - Else: both relations hold; stop and return i.
- **Full trace** (pp. 310–312, Figs. 13.6–13.8): three threads, three outputs each; thread 1 produces C[3..5] and calls `co_rank(3, A, 5, B, 4)`.

  | Iteration | i | j | i_low | j_low | Test and result |
  |---|---|---|---|---|---|
  | 0 (Fig. 13.6) | 3 | 0 | 0 | 0 | A[2] = 8 > B[0] = 7, so i too high. delta = (3 − 0 + 1) >> 1 = 2. Next: i = 1, j = 2, j_low = 0 (old j), i_low unchanged. |
  | 1 (Fig. 13.7) | 1 | 2 | 0 | 0 | A[0] = 1 ≤ B[2] = 10, first test fails. B[1] = 10 ≥ A[1] = 7, so j too high. delta = (2 − 0 + 1) >> 1 = 1. Next: j = 1, i_low = 1, i = 2. |
  | 2 (Fig. 13.8) | 2 | 1 | 1 | 0 | A[1] = 7 ≤ B[1] = 10 and B[0] = 7 < A[2] = 8: done. Return i = 2; caller computes j = 3 − 2 = 1. |

- Complexity (p. 313): for long inputs delta halves each step, so the algorithm is log2 N where N is the larger of the two input sizes.
- The same process for thread 2 is left as an exercise (p. 313; it is Exercise 2).

### §13.5 A basic parallel merge kernel (pp. 313–314)
- Assumption for the rest of the chapter: A, B and C all live in global memory and one kernel launch performs the merge (p. 313).
- `merge_basic_kernel` (Fig. 13.9): each thread computes its first output index `k_curr` and the next thread's first output index `k_next`, calls `co_rank` twice, derives `j_curr`, `j_next`, and calls `merge_sequential` on `&A[i_curr]`, length `i_next − i_curr`, `&B[j_curr]`, length `j_next − j_curr`, output `&C[k_curr]` (p. 313).
- The total output count need not be a multiple of the thread count, hence the `min(…, m+n)` clamp on `k_next` (p. 313).
- Worked example (p. 314): three threads on the running example have `k_curr` = 0, 3, 6. Thread 1: `i_curr` = 2, `j_curr` = 1, `k_next` = 6, `i_next` = 5, `j_next` = 1; it calls merge with (&A[2], 3, &B[1], 0, &C[3]). The n = 0 means all three of its outputs come from A (A[2]–A[4] → C[3]–C[5]).
- Two memory-efficiency problems (p. 314):
  1. Inside `merge_sequential`, adjacent threads of a warp do not touch adjacent addresses. In the example the first loop iteration reads A[0], A[2], B[0] and writes C[0], C[3], C[6] (the book's list). Reads and writes are not coalesced, so memory bandwidth is used poorly.
  2. `co_rank` itself reads A and B from global memory in a binary-search pattern that is irregular and unlikely to coalesce.

### §13.6 A tiled merge kernel to improve coalescing (pp. 314–320)
- Recap of Chapter 6's three coalescing strategies (p. 314): (1) rearrange the thread-to-data mapping, (2) rearrange the data, (3) move data between global and shared memory in a coalesced way and do the irregular accesses in shared memory. Merge uses strategy 3. Shared memory also captures the small amount of data reuse between the co-rank calls and the merge phase.
- Key observation (p. 314): the input sub-arrays of adjacent threads are adjacent in memory. So a whole block collectively uses one contiguous block-level sub-array of A and one of B to produce one block-level sub-array of C. One co-rank per block boundary finds them; then all threads in the block can load them cooperatively in a coalesced pattern.
- Block-level partitions can differ a lot in size between A and B depending on the data; their sizes always sum to the block's output size (p. 315).
- Why iterate (p. 315): shared memory is limited, so `A_S` and `B_S` may not hold a block's whole input. Let each hold x elements and let the block's output sub-array be y elements; the block works in y/x iterations. Each iteration loads x elements of A and x of B.
- **Why loading 2x inputs guarantees only x outputs** (pp. 315–316): in the worst case every output of the iteration comes from the same input. Loading x from each side is the only way to be safe without knowing the split. "This uncertainty of input usage" is what makes merge tiling harder than earlier patterns.
- Alternative mentioned (p. 316): call co-rank for the current and next output sections first, then load exactly what will be used, at the cost of an extra binary search. Left as an exercise (Exercise 3).
- Part 1 (Fig. 13.11, p. 316): the block-level analogue of the basic kernel's setup. Only thread 0 of the block calls `co_rank` (twice) on global memory and parks the two results in `A_S[0]` and `A_S[1]`; a barrier makes them visible before others read. Fewer threads doing binary search in global memory means fewer irregular global accesses.
- `tile_size` (pp. 316–317): number of A elements and of B elements held in shared memory. With `tile_size` = 1024, the block uses (1024 + 1024) · 4 = 8,192 bytes of shared memory.
- **Running example** (p. 317): m = 33,000, n = 31,000, 64,000 outputs; 16 blocks (`gridDim.x` = 16), 128 threads per block (`blockDim.x` = 128); each block produces 64,000 / 16 = 4,000 outputs. With `tile_size` = 1024 the while-loop needs four iterations per block. In each iteration the block loads 1024 A and 1024 B elements; 128 threads load 128 elements per for-loop pass, so each load loop runs 8 passes. Consecutive threads load consecutive elements (indexed by `threadIdx.x`), so the loads are coalesced.
- Part 3 (Fig. 13.13, p. 318): per iteration the block emits `tile_size` outputs (except possibly the last). Each of the 128 threads owns 1024 / 128 = 8 outputs, runs `co_rank` twice on the shared-memory tiles to find its A/B split, then calls `merge_sequential` from shared memory to global C. Example splits: one thread may use 3 A + 5 B, another 6 A + 2 B. Block totals might be 476 A + 548 B (= 1024), or even 1024 A + 0 B.
- Since 2048 elements were loaded and 1024 are consumed, exactly half of the loaded data is used each iteration (p. 318).
- Tracking progress (pp. 319–320):
  - `A_consumed` = total A elements consumed in earlier iterations (starts at 0). The tile for an iteration starts at `A[A_curr + A_consumed]`; likewise `B[B_curr + B_consumed]` (Fig. 13.14).
  - `C_completed` grows by `tile_size` per iteration; `A_consumed` grows by `co_rank(tile_size, A_S, tile_size, B_S, tile_size)` (how many of the first `tile_size` merged outputs came from the A tile); `B_consumed = C_completed − A_consumed`.
  - Tail guards (p. 320): near the end there may be fewer than `tile_size` elements left in A or B (block 2 in Fig. 13.14). The `if` in each load loop compares the tile offset with `A_length − A_consumed` (resp. B) so threads never load outside the block's sub-array.
  - Pitfall the book flags (p. 320): after the *last* iteration `A_consumed`, `B_consumed`, `C_completed` may be wrong (there may not have been a full tile). They are not used again so it is harmless, but if you need totals after the loop, use `A_length`, `B_length`, `C_length`.
- Result (p. 320): global accesses by co-rank are greatly reduced and global accesses are coalesced. Deficiency: only half of what is loaded is used, the unused half is reloaded next iteration, which "wastes half of the memory bandwidth".

### §13.7 A circular-buffer merge kernel (pp. 321–327)
- `merge_circular_buffer_kernel` has the same structure as the tiled kernel; only the management of A and B elements in shared memory changes so that every loaded element is eventually used (p. 321).
- The tiled kernel always starts tiles at `A_S[0]` and `B_S[0]` and overwrites leftovers; that is the waste (p. 321).
- New state (pp. 321–322):
  - `A_S_start`, `B_S_start`: where the current tile begins inside each buffer (0 before the loop).
  - `A_S_consumed`, `B_S_consumed`: how many elements of each tile were used in the current iteration, which is also how many must be refilled at the start of the next.
- Start advance with wrap (p. 322): `A_S_start = (A_S_start + A_S_consumed)%tile_size;` and the same for B. The book describes this as "if the new start exceeds `tile_size`, subtract `tile_size`".
- Walkthrough of Fig. 13.15 (pp. 321–322): (a) iteration 0 fills both buffers from index 0; (b) after iteration 0 the consumed prefixes are free and the start markers move to just after them; (c) at the start of iteration 1 only `A_S_consumed` / `B_S_consumed` new elements are loaded, into the freed space, so the tile now wraps around the end of the buffer; (d) after iteration 1 the consumed section itself can wrap and the start marker wraps via `%`.
- Refill loops (Fig. 13.16, pp. 322–323): loop bound is `A_S_consumed` instead of `tile_size`. Destination index for a thread is `A_S_start + (tile_size − A_S_consumed) + i + threadIdx.x`, taken modulo `tile_size`: the tile starts at `A_S_start` and `tile_size − A_S_consumed` leftover elements are already in place ahead of the new ones. The B loop is "left as an exercise" in the text.
- Design lesson, **simplified model** (pp. 323–324, Fig. 13.17): giving threads real buffer indices would leak the wrap everywhere (for example a "next" index smaller than a "current" index, requiring `next − curr + tile_size` in some cases). Instead co-rank values are kept as *offsets from the tile start*: each tile looks like one continuous run of up to `tile_size` elements, so `a_next ≥ a_curr` and `b_next ≥ b_curr` always. Only `co_rank_circular` and `merge_sequential_circular` translate offsets into wrapped indices.
- Both circular functions take the original parameters plus `A_S_start`, `B_S_start`, `tile_size` (p. 324). The thread-level code (Fig. 13.18) changes only by calling these instead of the originals: "a well-designed library interface can reduce the impact on the user code" (p. 324).
- `co_rank_circular` (Fig. 13.19, pp. 324–325): i, j, `i_low`, `j_low` are handled exactly as in Fig. 13.5. The values i, i−1, j, j−1 are no longer indices but offsets added to the start and wrapped, giving `i_cir`, `i_m_1_cir`, `j_cir`, `j_m_1_cir`. You cannot write `i_cir − 1` for the i−1 access: the full index must be formed and then wrapped.
- `merge_sequential_circular` (Fig. 13.20, p. 325): same logic as Fig. 13.2; in the four places that read A or B, the index is formed as `(start + i) % tile_size`. It is only ever called on `A_S` / `B_S`.
- Cost discussion (pp. 325, 327): the full kernel is not listed in one piece. Tiling plus circular buffers uses more registers per thread (start points, remaining counts), which can reduce occupancy, i.e. the number of thread blocks that fit on each streaming multiprocessor. Because merge is memory-bandwidth bound, compute and register resources are probably under-used, so spending registers and address arithmetic to save bandwidth is "a reasonable tradeoff".

### §13.8 Thread coarsening for merge (p. 327)
- The overhead of parallelizing merge is mainly the per-thread binary searches for co-ranks.
- Fewer threads, each producing more outputs, means fewer binary searches. Every kernel in the chapter already processes multiple elements per thread.
- A fully uncoarsened kernel (one output per thread) would need a binary search per element, which is expensive. Coarsening amortizes one search over many elements.

### §13.9 Summary (p. 327)
- Ordered merge needs each thread to identify its input ranges dynamically; a fast search (co-rank) does that.
- Data-dependent ranges make tiling for bandwidth and coalescing harder; circular buffers let all loaded data be used.
- A richer data structure raises code complexity; the simplified access model keeps index-manipulating code nearly unchanged, exposing the wrap only at the point of element access.

## Code listings

### Fig. 13.2 — `merge_sequential` (p. 305)
- Purpose: sequential stable merge. Signature: `void merge_sequential(int *A, int m, int *B, int n, int *C)`. Plain C function; later called from kernels as the per-thread worker (the book does not show a device-function qualifier on it).
- Lines 02–04: i, j, k = 0 (indices into A, B, C).
- Lines 05–11: while both inputs have elements: `if (A[i] <= B[j]) C[k++] = A[i++]; else C[k++] = B[j++];`.
- Lines 12–20: `if (i == m)` copy the rest of B, else copy the rest of A.
- Care: the `<=` is the stability rule (A wins ties). m or n may be 0, in which case the first loop is skipped and the tail copies everything (this happens for thread 1 in the basic-kernel example).

### Fig. 13.5 — `co_rank` (p. 310)
- Purpose: given rank k, return i such that the first k merged outputs are the merge of A[0..i−1] and B[0..k−i−1]. Signature: `int co_rank(int k, int* A, int m, int* B, int n)`.
- Lines 02–05: `i = k < m ? k : m`; `j = k - i`; `i_low = 0 > (k-n) ? 0 : k-n`; `j_low = 0 > (k-m) ? 0 : k-m`.
- Lines 06–07: `delta`, and a `bool active = true` loop flag.
- Lines 08–22, the search loop. Exact conditions matter:
  - line 09: `if (i > 0 && j < n && A[i-1] > B[j])` then line 10 `delta = ((i - i_low +1) >> 1)`, line 11 `j_low = j`, line 12 `j = j + delta`, line 13 `i = i - delta`;
  - line 14: `else if (j > 0 && i < m && B[j-1] >= A[i])` then line 15 `delta = ((j - j_low +1) >> 1)`, line 16 `i_low = i`, line 17 `i = i + delta`, line 18 `j = j - delta`;
  - lines 19–21: else `active = false`.
- Line 23: `return i`.
- Care:
  - The bounds tests (`i > 0`, `j < n`, `j > 0`, `i < m`) come first and rely on short-circuit evaluation to avoid reading A[−1], B[n], B[−1], A[m].
  - `>` in the first test and `>=` in the second encode the tie rule; swapping them breaks stability.
  - `(x + 1) >> 1` is the ceiling of x/2, so delta is at least 1 whenever the branch is taken.
  - The comment on line 05 says `i_low` but the statement sets `j_low` (comment typo).

### Fig. 13.9 — `merge_basic_kernel` (p. 313)
- Purpose: one launch merges A and B into C, all in global memory. Signature: `__global__ void merge_basic_kernel(int* A, int m, int* B, int n, int* C)`. Assumes a 1D grid; total threads = `blockDim.x*gridDim.x`. Host code and launch are not shown.
- Line 02: `tid = blockIdx.x*blockDim.x + threadIdx.x`.
- Line 03: `int elementsPerThread = ceil((m+n)/(blockDim.x*gridDim.x));`.
- Lines 04–05: `k_curr = tid*elementsPerThread`; `k_next = min((tid+1)*elementsPerThread, m+n)`.
- Lines 06–09: `i_curr = co_rank(k_curr, …)`, `i_next = co_rank(k_next, …)`, `j_curr = k_curr - i_curr`, `j_next = k_next - i_next`.
- Line 10: `merge_sequential(&A[i_curr], i_next-i_curr, &B[j_curr], j_next-j_curr, &C[k_curr]);`.
- Care:
  - Line 03 divides integers before `ceil`, so the ceiling has no effect as written `[inferred from C semantics]`; see "Unclear in the PDF".
  - `k_curr` is not clamped, only `k_next`; correctness for threads past the end relies on the launch configuration `[inferred]`.
  - Each thread performs two binary searches on global memory; neighbouring threads recompute the same boundary (thread t's `k_next` is thread t+1's `k_curr`).
- APIs: `__global__`, `blockIdx`, `blockDim`, `gridDim`, `threadIdx`, `ceil`, `min`.

### Figs. 13.11–13.13 — `merge_tiled_kernel` (pp. 316–318)
- Purpose: same merge, with inputs staged through shared memory. Signature: `__global__ void merge_tiled_kernel(int* A,int m, int* B, int n, int* C, int tile_size)`. Assumes a 1D grid where each block owns a contiguous slice of C; shared memory of 2 × `tile_size` ints declared as `extern __shared__ int shareAB[];` (unsized, so the size must be supplied from outside the kernel; the chapter does not show how). `tile_size` is used as a multiple of `blockDim.x` (`tile_size/blockDim.x` outputs per thread) `[inferred]`.
- **Part 1, Fig. 13.11 (lines 01–16)**
  - Lines 02–04: `A_S = &shareAB[0]`, `B_S = &shareAB[tile_size]` (the comments call them shareA / shareB: first and second half).
  - Lines 05–06: `C_curr = blockIdx.x * ceil((m+n)/gridDim.x)`; `C_next = min((blockIdx.x+1) * ceil((m+n)/gridDim.x), (m+n))`.
  - Lines 07–10: only `threadIdx.x == 0` computes `A_S[0] = co_rank(C_curr, A, m, B, n)` and `A_S[1] = co_rank(C_next, A, m, B, n)`.
  - Line 11: `__syncthreads()` so everyone sees the two values.
  - Lines 12–15: each thread copies them to private `A_curr`, `A_next` and derives `B_curr = C_curr - A_curr`, `B_next = C_next - A_next`.
  - Line 16: second `__syncthreads()`. The book does not explain it; it guarantees every thread has read `A_S[0]`/`A_S[1]` before the tile loads overwrite those slots `[inferred]`.
- **Part 2, Fig. 13.12 (lines 17–36)**
  - Lines 17–24: `counter = 0`; `C_length`, `A_length`, `B_length` as next − curr; `total_iteration = ceil((C_length)/tile_size)`; `C_completed`, `A_consumed`, `B_consumed` = 0. All are per-thread private variables that every thread updates identically.
  - Line 25: `while(counter < total_iteration){`.
  - Lines 26–30 load A: `for(int i=0; i<tile_size; i+=blockDim.x)`; guard `if( i + threadIdx.x < A_length - A_consumed)`; body `A_S[i + threadIdx.x] = A[A_curr + A_consumed + i + threadIdx.x ];`.
  - Lines 31–35: the same for B with `B_length`, `B_consumed`, `B_curr`.
  - Line 36: `__syncthreads()` (tiles complete before anyone searches them).
- **Part 3, Fig. 13.13 (lines 37–52)**
  - Lines 37–38: `c_curr = threadIdx.x * (tile_size/blockDim.x)`, `c_next = (threadIdx.x+1) * (tile_size/blockDim.x)`: the thread's output range *within this iteration's tile* (lower-case c is thread level, upper-case C is block level).
  - Lines 39–40: clamp both to `C_length - C_completed` (last iteration).
  - Lines 41–44: `a_curr = co_rank(c_curr, A_S, min(tile_size, A_length-A_consumed), B_S, min(tile_size, B_length-B_consumed))`, `b_curr = c_curr - a_curr`; the same with `c_next` for `a_next`, `b_next`. The `min` terms are the number of valid elements in each tile.

  - Lines 46–49: `counter ++; C_completed += tile_size; A_consumed += co_rank(tile_size, A_S, tile_size, B_S, tile_size); B_consumed = C_completed - A_consumed;`.

- Care:
  - Three barriers per iteration boundary matter: after publishing co-ranks (11), after loading (36), after merging (50).
  - The destination pointer in line 45 sums four offsets: array base, block start, outputs done in earlier iterations, thread offset in this tile.
  - Line 48's co-rank assumes full tiles; wrong on the last iteration but unused afterwards (book's own caveat, p. 320).
  - The integer `ceil` on lines 05, 06 and 21 has the same issue as in Fig. 13.9; for the book's running example line 21 would give 3, not the 4 iterations the text describes `[inferred]`.
  - Every thread executes line 48 (a third shared-memory binary search per iteration).
- APIs: `__global__`, `extern __shared__`, `__syncthreads()`, `blockIdx`, `blockDim`, `gridDim`, `threadIdx`, `ceil`, `min`.

### Fig. 13.20 — `merge_sequential_circular` (p. 326)
- Signature: `void merge_sequential_circular(int *A, int m, int *B, int n, int *C, int A_S_start, int B_S_start, int tile_size)`.

## Relevance to LLM-inference kernels
Candidly: **little direct relevance.** Nothing in matmul/GEMM, attention, or quantized arithmetic performs an ordered merge, and the book does not connect this chapter to LLM inference. Everything below is our own mapping `[inferred]`.
- **Sampling (top-k / top-p):** merge is the combining step of merge sort (Ch. 14) and of "sort chunks then merge" schemes, so it sits underneath any comparison-based sort of logits. Merging per-block or per-chunk top-k candidate lists into a global top-k is a small ordered merge. In practice a library sort or a partial selection is used instead of a hand-written merge kernel.
- **Top-p cutoff:** after sorting probabilities and taking a prefix sum (Ch. 11), the nucleus boundary is a binary search over a monotone array. The co-rank function is a good worked example of a branchy, data-dependent binary search on the GPU, including its short-circuit bounds tests and its uncoalesced access pattern.
- **Transferable engineering ideas (the real value for this reader):**
  - output-centric decomposition when input ranges are data dependent (each thread owns a fixed slice of the *output*);
  - load irregularly accessed data into shared memory with coalesced reads, then do the irregular work there (the same move used for tiled matmul, here applied to a search);
  - why over-provisioned tiles waste bandwidth, and the "memory-bandwidth bound, so spend registers and index arithmetic" trade-off, which is the normal regime for inference kernels;
  - hiding a ring buffer behind virtual indices: a pattern that reappears in any streaming or sliding-window buffer.
- Matmul, attention, quantized ops, softmax, argmax: no direct use.

## Portability notes

Items 1–13 are read directly from the PDF. Items 14–18 are our inferences from reading or emulating the code.
1. **p. 306:** the text says the second part of the function "is on the right Fig. 13.2", but the figure is a single-column listing. Looks like leftover wording.

9. **p. 321:** says the tiled kernel's structure is shown in "Figs. 13.12 through 13.14"; the listings are Figs. 13.11–13.13. The same page says tiles start at positions "inside A_S[0] and B_S[0]" (meaning inside the arrays A_S and B_S). p. 322 calls the kernel `merge_tile_kernel` once, and introduces the two modulo statements as "the if-statement below".

12. **Fig. 13.17(b) and pp. 323–324:** the panel labels the B arrow "B_Start"; the prose compares `a_next` with "A_curr" and `b_next` with "B_curr" where the thread-level `a_curr` / `b_curr` are evidently meant.

14. **Integer `ceil` `[inferred]`:** `ceil((m+n)/(blockDim.x*gridDim.x))` (Fig. 13.9), `ceil((m+n)/gridDim.x)` (Fig. 13.11) and `ceil((C_length)/tile_size)` (Fig. 13.12) divide integers first, so the result is already truncated. 15. **Missing barrier `[inferred]`:** the circular-buffer listing goes from the load loops (Fig. 13.16, ends at line 39) straight into the co-rank calls (Fig. 13.18, starts at line 40) with no `__syncthreads()`, whereas the tiled version has one (Fig. 13.12 line 36). One is needed for the same reason.
16. **Refill source index `[inferred, from our own emulation]`:** in Fig. 13.16 the source is `A[A_curr + A_consumed + i + threadIdx.x]`, and p. 322–323 states the refill "starts at global memory location A[A_curr+A_consumed+i]". But `A_consumed` counts consumed elements, and `tile_size − A_S_consumed` unconsumed elements beyond that point are still in the buffer, so this reloads elements already present. Fig. 13.15(c) draws the refill section starting right after the previously loaded tile, which matches a source offset of `A_consumed + (tile_size − A_S_consumed)`. A sequential Python emulation of the listing as printed gave wrong merges on most random inputs; with the extra offset (and matching guard) it was correct on all 300 random trials. The book does not acknowledge this; verify before teaching the listing as-is.
17. **Line 16 of Fig. 13.11 `[inferred]`:** the purpose of the second `__syncthreads()` is not explained in the text; our reading is given in the code-listing notes.
18. **Line 48 of Fig. 13.13 before the last iteration `[inferred, from our own emulation; added 2026-11-20 after re-reading pp. 318 and 320 as images]`:** `A_consumed += co_rank(tile_size, A_S, tile_size, B_S, tile_size);` treats every slot of both tiles as loaded. The book says the count may be wrong only after the last iteration, where it is unused (p. 320), and p. 320 itself says partial tiles happen "during the last iterations" (plural); Fig. 13.14 draws one in iteration 1 (block 2's A_S). On any iteration that is not the last, a partly loaded tile leaves slots holding the previous tile, and the search can read them. Hand-checkable case: one block, `tile_size` 8, A = 0..9, B = 10..39. Iteration 0 uses A[0..7] correctly. Iteration 1 loads only A[8], A[9] into A_S[0..1] (A_S[2..7] still hold 2..7); its merges are right (lines 41–43 use the `min` counts), but line 48 starts at i = 8, j = 0, finds A_S[7] = 7 ≤ B_S[0] = 10 and j = 0, and returns 8, so `A_consumed` becomes 16 (true 10) and `B_consumed` 0 (true 6); iteration 2 then reloads B[0..7] and passes a negative A length to `co_rank`. A sequential emulation of Figs. 13.11–13.13 (ceil corrected, Fig. 13.5's `co_rank`) gave wrong merges on 143 to 181 of 300 random small inputs depending on what the never-loaded slots held; computing the count as the circular kernel's line 50 does, `co_rank(min(tile_size, C_length − C_completed), A_S, min(tile_size, A_length − A_consumed), B_S, min(tile_size, B_length − B_consumed))` with the values from before lines 47–48, was correct on all 300. The book's own example sizes with uniformly random keys passed (3 of 3), because the search rarely reaches the stale end of a large tile. `app/src/sim/mergetile.ts` counts the slots at risk per iteration (`staleSlots`; preset `shortTileEarly` is the case above).
