# Chapter 7 — Convolution

- **Book pages:** 159–181  **PDF pages:** 187–209 (pdf = book + 28)
- **In one paragraph:** (Chapter subtitle: "And constant memory".) First of the "parallel patterns" chapters. It defines 1D/2D convolution as a per-output weighted sum over a neighbourhood, with boundary ("ghost") cells defaulting to 0, then builds four CUDA kernels of increasing sophistication: a basic one-thread-per-output kernel, a version with the filter in constant memory, a shared-memory tiled version that loads the whole input tile including halo cells, and a tiled version that keeps only the tile interior in shared memory and leaves halo accesses to the L2 cache. Each step is judged by its arithmetic intensity (FLOP per byte of global memory traffic), reusing the Chapter 5 method. Afterwards a reader can write a bounds-checked 2D convolution kernel, declare and fill constant memory, reason about input-tile vs output-tile sizes, and compute how close a tiled kernel gets to the ideal `m²/4` FLOP/B.

## Concepts

### Chapter opening (p. 159)
- Chapters from here on cover "important patterns of parallel computation"; convolution is first (p. 159).
- Application areas named: signal processing, digital recording, image processing, video processing, computer vision. Convolution usually acts as a filter. The earlier image blur kernel is cited as an example of a smoothing filter (p. 159).
- The book says Gaussian filters "can be used to sharpen boundaries and edges of objects in images" (p. 159). See "Unclear in the PDF".
- Why it is a good parallel case study: each output element needs many arithmetic operations; outputs are mutually independent (good); but neighbouring outputs share much input data and boundaries are awkward (hard). Hence "sophisticated tiling methods and input data staging methods" are the chapter focus (p. 159).

### §7.1 Background (pp. 159–164)
- **Definition:** each output element is a weighted sum of the corresponding input element and the input elements centred around it. The weights come from a filter array. The literature calls this the "convolution kernel"; the book calls it the **convolution filter** to avoid a clash with CUDA "kernel" functions (pp. 159–160).
- Dimensionality examples: 1D audio, 2D photo, 3D video (p. 160).
- **1D formula** (p. 160): input `[x0..x(n-1)]`, filter `[f0..f(2r)]` of `2r+1` elements, output `y_i = sum over j = -r..r of f[j+r] * x[i+j]`.
- Filter size is odd (`2r+1`) so the sum is symmetric around the element; `r` elements on each side; `r` is the **radius** (p. 160).
- Note for the course (our observation, not stated by the book): the formula does not flip the filter, i.e. it is what ML frameworks call cross-correlation. The book's examples use symmetric filters, so the distinction does not show up in the worked numbers.
- **Worked 1D example** (pp. 160–161, Figs. 7.1–7.2): `x = [8, 2, 5, 4, 1, 7, 3]`, `f = [1, 3, 5, 3, 1]`, `r = 2`.
  - `y[2] = 1*8 + 3*2 + 5*5 + 3*4 + 1*1 = 52` (products 8, 6, 25, 12, 1).
  - `y[3] = 1*2 + 3*5 + 5*4 + 3*1 + 1*7 = 47` (products 2, 15, 20, 3, 7).
  - `y[i]` is an inner product of `f` with the sub-array of `x` starting at `x[i-2]` (p. 161).
  - Footnote 1 (p. 161): because each output is an inner product, convolution can be formulated as matrix multiplication; deferred to Chapter 19 (Convolutional Neural Networks).
- **Boundary conditions / ghost cells** (pp. 161–162, Fig. 7.3): near the array ends there are not enough neighbours. Usual fix: give missing elements a default value, most often 0 (audio: volume is 0 before recording starts and after it ends). `y[1] = 1*0 + 3*8 + 5*2 + 3*5 + 1*4 = 53`. `y[0]` needs two missing elements and is left as an exercise.
- The missing elements are called **"ghost cells"**. The book adds that tiling creates "other types of ghost cells" too and that these affect tiling efficiency (p. 162). Later sections call the tiling-induced ones **halo cells**.
- Other boundary policies mentioned (p. 162): replicate the nearest valid edge value; or treat the array as circular (wrap-around).
- **2D formula** (p. 162): filter `(2rx+1)` by `(2ry+1)`; `P[y][x] = sum over j = -ry..ry, k = -rx..rx of f[j+ry][k+rx] * N[y+j][x+k]`. The filter need not be square but usually is.
- **Worked 2D example** (pp. 162–164, Fig. 7.4): 7×7 input `N`, 5×5 filter, output `P[2][2] = 321`. Take the 5×5 sub-array centred on the output position, multiply element-wise with the filter, sum. Row sums of the product array: 27 + 56 + 95 + 84 + 59 = 321 (row sums are ours; the book lists every term).
- The book writes `N[y][x]` as `N_{y,x}` and says real code will use linearised indices because `N` and `P` are dynamically allocated (p. 163).
- **2D boundaries** (p. 164, Fig. 7.5): an output can cross a horizontal boundary, a vertical one, or both. `P[1][0]` is missing two columns and one row of its patch; with 0 defaults the result is 112.

### §7.2 Parallel convolution – a basic kernel (pp. 164–166)
- All outputs can be computed in parallel, so convolution is "an ideal use case for data parallel computing" (p. 164). Code is 2D; 1D and 3D are exercises; filters assumed square (pp. 164–165).
- Kernel parameters: input `N`, filter `F`, output `P`, radius `r`, `width`, `height` (p. 165). The text says "five arguments" but lists six (see Unclear).
- **Thread mapping** (p. 165, Fig. 7.6): 2D grid of threads, one thread per output element. A block has up to 1024 threads, "typically organized as a 32×32 square". Toy example: 16×16 image, 4×4 threads per block, 4×4 blocks. Same arrangement as `ColorToGrayScaleConversion` in Chapter 3.
- Example mapping: thread (1,1) of block (1,1) computes `P[1*4+1][1*4+1] = P[5][5]` (p. 166).
- Input patch for an output: columns `outCol - r .. outCol + r`, rows `outRow - r .. outRow + r`. For `P[5][5]` with `r = 2`: indices 3..7 in both dimensions. `(outRow - r, outCol - r)` is the patch's upper-left corner (p. 166).
- `Pvalue` is a register accumulator "to save DRAM bandwidth"; written to `P` once after the loops (p. 166).
- Ghost cells: an `if` in the inner loop skips taps whose input index is out of range; skipping is equivalent to multiplying by a 0 ghost value (p. 166).
- **Observation 1, control divergence** (p. 166): threads near the four edges skip a different number of taps (the `P[0][0]` thread skips most, `P[0][1]` fewer, etc.). Cost depends on image size and filter radius. For large images and small filters only a small fraction of outputs is affected, so the effect is expected to be "from modest to insignificant".
- **Observation 2** (p. 166): memory bandwidth is the more important issue (next section).

### §7.3 Memory bandwidth considerations (pp. 167–168)
- Setup: `n × n` input, `m × m` filter with `m = 2r + 1`, 4 B single-precision elements (p. 167).
- Operations: per output, `m²` taps × (1 multiply + 1 add) → total `2·n²·m²` FLOP (p. 167).
- Bytes that must be touched at minimum: load input (`n²`), load filter (`m²`), store output (`n²`) → `8·n² + 4·m²` B; with `m << n` approximate as `8·n²` B (p. 167).
- **Ideal arithmetic intensity** = `2·n²·m² / (8·n²)` = **`m²/4` FLOP/B**. This is what a perfect implementation that touches each input and output element once would achieve (p. 167).
- AI depends on filter size:
  - 3×3 → `9/4 = 2.25` FLOP/B → memory bound on an H100 `[device: NVIDIA H100]`; cannot reach peak compute throughput (p. 167).
  - 11×11 → `121/4 = 30.25` FLOP/B → compute bound on an H100 `[device: NVIDIA H100]`; can approach peak throughput "provided that the right optimizations are applied" (p. 167).
  - The threshold itself is not restated here; Chapter 5 gives it as (66.9 TFLOPS)/(3.35 TB/s) = 20.0 FLOP/B for the H100 (Ch. 5, p. 94) `[device: NVIDIA H100]`.
- **Basic kernel's AI** (p. 167): in the inner statement each iteration loads two elements (one `F`, one `N` = 8 B) from global memory and does 2 FLOP → `2/8 = 0.25` FLOP/B, regardless of filter size. The single store per thread is ignored because it is outside the loop nest.
- In practice the measured AI is higher because filter and input elements are reused by many threads and tend to be in L1/L2 (p. 168). To get high AI reliably, use on-chip structures explicitly: constant cache (§7.4) and shared memory (§7.5).

### §7.4 Constant memory and caching (pp. 168–172)
- Three properties of `F` that make it a constant-memory candidate (p. 168):
  1. It is small. Book: "the radius of most convolution filters is 7 or smaller"; a 3D filter "typically contains only less than or equal to 7³ = 343 elements" (see Unclear for the radius/dimension mismatch).
  2. Its contents never change during kernel execution.
  3. Every thread reads it, and in the same order (from `F[0][0]` onwards through the nested loop).
- **Constant memory facts** (p. 168): declared by the programmer (Chapter 5, Fig. 5.4); visible to all thread blocks like global memory; cannot be modified by threads during kernel execution; size "currently" 64 KB.
- **Declaring** (p. 169): a global-scope variable outside any function, e.g.
  ```
  #define FILTER_RADIUS 2
  __constant__ float F[2*FILTER_RADIUS+1][2*FILTER_RADIUS+1];
  ```
  `__constant__` has two underscores on each side. The radius is now a compile-time constant.
- **Filling from host** (p. 169): with the filter already in a host array `F_h` of `(2*FILTER_RADIUS+1)²` elements,
  ```
  cudaMemcpyToSymbol(F, F_h, (2*FILTER_RADIUS + 1)*(2*FILTER_RADIUS + 1)*sizeof(float));
  ```
  General form `cudaMemcpyToSymbol(dest, src, size)`: `dest` is the constant-memory destination, `src` host source, `size` bytes. The book describes it as a special copy that tells the CUDA runtime the data will not change during kernel execution. Footnote 2: two more optional arguments, offset and kind, "seldom used and often omitted"; see the CUDA C++ Programming Guide.
- Kernels access constant variables as ordinary globals, so no pointer argument is needed. Normal C++ scoping applies: if host and kernel code live in different files, the kernel file needs the external declaration (p. 169).
- **Where constant memory physically is** (p. 169): also in DRAM, like global memory. The difference is that the runtime knows it is read-only during the kernel, so it directs the hardware to cache it aggressively.
- **Cache background** (pp. 170–171, Fig. 7.10):
  - DRAM latency and bandwidth are the bottleneck in "virtually all modern processors"; caches reduce how many variables must be fetched from main memory.
  - Caches are "transparent": the program just accesses the original variable and hardware keeps recently/frequently used data, remembering its original address. Shared memory (a scratchpad) is not transparent: you declare `__shared__` variables and copy explicitly.
  - Size vs speed tradeoff → multiple levels. L1 is attached to a core, runs near processor speed in latency and bandwidth, "typically up to 128 KB". L2 is larger, "a few hundred KBs to a few tens of MBs", but "can take tens to hundreds of cycles to access", and is typically shared among multiple CPU cores, or among SMs in a CUDA device, so its bandwidth is shared. Some high-end processors have L3 caches of "hundreds of MBs" (p. 171).
- **Constant cache** (p. 171): since constant variables are never written during a kernel, the cache for them does not need write support. Supporting high-throughput writes in a general cache costs chip area and power; a read-only cache can be built much more cheaply. Constant memory is small (64 KB), so a small specialised cache captures the heavily used constants of each kernel. This is the **constant cache**.
- When all threads of a warp read the same constant element (true for `F`, whose indices do not depend on thread indices), the constant cache supplies "a tremendous amount of bandwidth". Working assumption: all `F` accesses hit the constant cache, so no DRAM bandwidth is spent on `F` (p. 171).
- **AI of the constant-memory kernel** (p. 171): per iteration one 4 B load of `N`, 2 FLOP → `2/4 = 0.5` FLOP/B, double the basic kernel. In practice higher still because `N` elements are reused across threads and sometimes found in L1/L2.
- **Two other ways to exploit a constant filter** (p. 172):
  1. Pass the weights as kernel parameters. The CUDA compiler places kernel parameters in constant memory too. Concisely: put the weights in a C++ struct and pass it by value. Benefit: the kernel can be called repeatedly with different weights without explicit `cudaMemcpyToSymbol`; the runtime still copies them at launch, transparently.
  2. Hard-code the values if they are known at compile time. Drawback: kernel not reusable for other weights.

### §7.5 Tiled convolution with halo cells (pp. 172–177)
- Goal: fix the memory-bandwidth bottleneck with shared-memory tiling (Chapter 5): threads cooperatively load input into on-chip memory and then reuse it (p. 172).
- **Output tile:** the set of output elements processed by one block. Toy example of Fig. 7.6 has 16 output tiles of 4×4 (p. 172). The book notes that real blocks should have at least 32 threads (one warp) and typically more, for occupancy and data reuse.
- **Input tile:** the set of input elements needed to compute one output tile. It extends the output tile's footprint by the filter radius in every direction to include **halo** input elements (p. 172, Fig. 7.11).
- Size ratio (pp. 172–173): toy case 4² = 16 outputs vs (4+2+2)² = 64 inputs → 4× larger. With a 16×16 output tile and the same 5×5 filter: (16+2+2)² = 400 vs 256 → ratio about 1.6. Still significant.
- Difference from tiled matmul in Chapter 5: there, input and output tiles have equal dimensions; here input tiles are bigger, which complicates the design (p. 173).
- **Two thread organisations** (p. 173):
  1. Block size = input tile size. Loading is trivial (one element per thread) but some threads must be disabled during the compute phase. This is the one implemented (Fig. 7.12).
  2. Block size = output tile size. Loading needs each thread to iterate so all input-tile elements get loaded; compute phase needs no disabling. Left as an exercise (Exercise 11).
- **Kernel logic** (pp. 174–175, Fig. 7.12, Fig. 7.13): see Code listings. Key points: the thread's `(row, col)` is offset by `-FILTER_RADIUS`; ghost cells are stored as 0 in shared memory; `__syncthreads()` separates load and compute; the outer `FILTER_RADIUS` layers of threads are deactivated for compute; active thread `(tx, ty)` computes output-tile element `(tx - R, ty - R)` from the input-tile patch whose upper-left corner is `(tx - R, ty - R)`.
- **AI derivation** (p. 176). Consider only internal blocks (ghost-cell effects ignored as insignificant for large arrays and small filters). Let `t = OUT_TILE_DIM`, `m = 2*FILTER_RADIUS + 1`:
  - FLOP per block: `t² · m² · 2`.
  - Loads per block: input tile dimension is `t + m - 1`, so `(t + m - 1)² · 4` B.
  - Stores per block: `t² · 4` B. Stores must be counted now because loads are no longer inside the loop nest and no longer dwarf them.
  - AI = `t²·m²·2 / (((t+m-1)² + t²)·4)` = `(m²/4) · 1 / ( ½·(1 + (m-1)/t)² + ½ )`.
  - So it equals the ideal `m²/4` times an attenuation factor that approaches 1.0 as `t` grows: bigger output tiles reuse each loaded element more.
  - `t` is capped by the thread-block size limit and shared-memory capacity; the book says techniques to overcome this are in Chapter 8 (p. 176).
- **Table of values** (p. 177, Fig. 7.14): see Figures. Memory bound for small filters/tiles, compute bound for large filters/tiles. Running example: 5×5 filter, 28×28 output tile (32×32 input tile) → 5.42 FLOP/B vs ideal 6.25 FLOP/B; could be higher in practice due to caches.
- **Three inefficiencies of the Fig. 7.12 design** (p. 177), all stemming from block/input tile being larger than the output tile:
  1. Some threads only load data and do no compute. Possibly helpful when memory bound (more parallel memory access), a waste when compute bound.
  2. Output tile dimensions are not powers of two (max block and input tile 32×32 → 28×28 output for 5×5), so stores to global memory may be misaligned.
  3. A bigger filter forces a smaller output tile because the input tile cannot grow; that lowers AI and worsens 1 and 2.
- Remedies (p. 177): organisation 2 (block = output tile, threads loop to load), or do not load halos into shared memory at all and rely on caches (§7.6).

### §7.6 Tiled convolution using caches for halo cells (pp. 178–179)
- Halo cells of one block's input tile are interior elements of neighbouring tiles. There is "a significant probability" they are already in the L2 cache because neighbouring blocks accessed them, so reading them straight from global `N` may cause no extra DRAM traffic (p. 178).
- Consequence: shared-memory tile and output tile can have the same dimension (`TILE_DIM`); only tile interiors go to shared memory (pp. 178–179).
- Loading gets simpler: each thread loads the input element with its own output row/column; the load condition only needs the upper-bound check for tiles that overhang the array (p. 179).
- Compute gets more complex: each tap first tests whether it falls inside the tile (→ shared memory); otherwise tests whether it is a ghost cell (→ skip, value 0); otherwise reads global memory (p. 179).
- "Subtle advantage" (p. 179): block size, input tile size and output tile size are equal and can be a power of two. The Fig. 7.12 kernel, with unequal sizes, "likely" has more memory divergence and control divergence.

### §7.7 Summary (pp. 179–180)
- Convolution is a general pattern; stencil algorithms in PDE solvers can be viewed as a special case (Chapter 8). The summary says the material will be applied to convolutional neural networks "in Chapter 20" (see Unclear; footnote 1 and the TOC put CNNs in Chapter 19).
- Progression recap: basic kernel limited by DRAM bandwidth for both input and filter → constant memory removes practically all DRAM accesses for the filter → shared-memory tiling reduces DRAM traffic for the input at the cost of more control divergence and complexity → cache-based halo handling using L1/L2.
- AI analysis is the reusable skill; small filters and small tiles limit the benefit.
- Techniques carry over to 3D with more index arithmetic and deeper loop nests (p. 180).

## Code listings

### Fig. 7.7 — `convolution_2D_basic_kernel` (p. 166)
- **Purpose:** one thread computes one output pixel of a 2D convolution, treating out-of-range inputs as 0.
- **Signature (as printed):** `__global__ void convolution_2D_basic_kernel(float *N, float *F, float *P, int r, int width, int height)`.
- **Launch configuration assumed:** 2D grid of 2D blocks covering `width × height` (toy: 4×4 blocks of 4×4 threads; typical block 32×32). Host launch code is not shown.
- **Walkthrough:**
  - Lines 02–03: `outCol = blockIdx.x*blockDim.x + threadIdx.x`, `outRow = blockIdx.y*blockDim.y + threadIdx.y`.
  - Line 04: `float Pvalue = 0.0f;` register accumulator.
  - Lines 05–13: loops `fRow`, `fCol` from 0 to `2*r` inclusive; lines 07–08 compute `inRow = outRow - r + fRow; inCol = outCol - r + fCol;`; line 09 bounds check; line 10 accumulate.
  - Line 14: write result.
- **Lines that need care:**
  - Line 09: `if (inRow >= 0 && inRow < height && inCol >= 0 && inCol < width)`; this is the ghost-cell skip and the source of control divergence.
  - Line 10 as printed: `Pvalue += F[fRow][fCol]*N[inRow*width + inCol];` and line 14 as printed: `P[outRow][outCol] = Pvalue;`. With `F` and `P` declared `float *`, the 2D subscripts are not valid C++; a compilable version needs `F[fRow*(2*r+1) + fCol]` and `P[outRow*width + outCol]` (Fig. 7.9 does use the linearised form for `P`). See Unclear.
  - `inRow` and `inCol` are assigned without a type declaration in the printed listing.
  - There is no guard that `outRow < height && outCol < width`; the printed kernel assumes the grid exactly covers the image (our observation).
- **APIs / qualifiers / built-ins:** `__global__`, `blockIdx`, `blockDim`, `threadIdx`.
- **AI:** 0.25 FLOP/B (p. 167).

### Fig. 7.9 — `convolution_2D_const_mem_kernel` (p. 170)
- **Purpose:** same computation with `F` read from constant memory.
- **Signature:** `__global__ void convolution_2D_const_mem_kernel(float *N, float *P, int r, int width, int height)`. `F` is no longer a parameter.
- **Assumes (shown in text, p. 169):** file-scope `__constant__ float F[2*FILTER_RADIUS+1][2*FILTER_RADIUS+1];` and a host call to `cudaMemcpyToSymbol(F, F_h, ...)` before launch.
- **Walkthrough:** identical line-for-line to Fig. 7.7 except line 01 (no `F` parameter) and line 14, which is `P[outRow*width+outCol] = Pvalue;`. `F[fRow][fCol]` on line 10 is now legitimate 2D indexing of a global array.
- **Lines that need care:** `r` is still a run-time parameter while `F`'s size is fixed by the compile-time `FILTER_RADIUS`; the two must agree (our observation). `inRow`/`inCol` again have no declared type in print.
- **APIs / qualifiers:** `__constant__`, `cudaMemcpyToSymbol` (host side), plus the Fig. 7.7 set.
- **AI:** 0.5 FLOP/B (p. 171).

### Fig. 7.12 — `convolution_tiled_2D_const_mem_kernel` (p. 174)
- **Purpose:** shared-memory tiling where each block loads its whole input tile (interior + halo) and then a subset of its threads compute the output tile.
- **Preamble:** `#define IN_TILE_DIM 32`, `#define OUT_TILE_DIM ((IN_TILE_DIM) - 2*(FILTER_RADIUS))`, `__constant__ float F_c[2*FILTER_RADIUS+1][2*FILTER_RADIUS+1];`.
- **Signature:** `__global__ void convolution_tiled_2D_const_mem_kernel(float *N, float *P, int width, int height)`.
- **Launch configuration assumed:** block = `IN_TILE_DIM × IN_TILE_DIM` threads (32×32 = 1024). Number of blocks per dimension = image dimension / `OUT_TILE_DIM`, rounded up (inferred from the indexing; the host code is not shown).
- **Walkthrough:**
  - Lines 06–07: `col = blockIdx.x*OUT_TILE_DIM + threadIdx.x - FILTER_RADIUS;` and the same for `row` with `.y`. This is the global index of the input element this thread loads; for active threads it is also the output index.
  - Line 09: shared tile `N_s[IN_TILE_DIM][IN_TILE_DIM]`.
  - Lines 10–14: if `(row, col)` is inside the image, `N_s[threadIdx.y][threadIdx.x] = N[row*width + col];` else store `0.0` (ghost cell).
  - Line 15: `__syncthreads();` so the whole tile is present before anyone reads it.
  - Lines 17–18: `tileCol = threadIdx.x - FILTER_RADIUS; tileRow = threadIdx.y - FILTER_RADIUS;`.
  - Line 20: only threads whose `(row, col)` is a valid output proceed.
  - Lines 21–22: only threads with `0 <= tileCol, tileRow < OUT_TILE_DIM` proceed. This deactivates the outer `FILTER_RADIUS` layers of the block.
  - Lines 23–28: accumulate `Pvalue += F[fRow][fCol]*N_s[tileRow+fRow][tileCol+fCol];` over the filter.
  - Line 29: `P[row*width+col] = Pvalue;`.
- **Lines that need care:**
  - The `- FILTER_RADIUS` in lines 06–07 does double duty (load index for all threads, output index for active threads).
  - `(tileRow, tileCol)` is the upper-left corner of the thread's patch in `N_s`; no bounds check is needed in the inner loop because ghost cells were materialised as zeros.
  - Printed line 09 is `__shared__ N_s[IN_TILE_DIM][IN_TILE_DIM];` with no element type; the constant array is declared `F_c` (line 03) but used as `F` (line 26). See Unclear.
  - `threadIdx`/`blockIdx` components are unsigned in CUDA; the subtraction relies on conversion to `int` to yield negative values (our observation, not discussed by the book).
- **APIs / qualifiers:** `__shared__`, `__syncthreads()`, `__constant__`, `__global__`, `blockIdx`, `threadIdx`.
- **AI:** `(m²/4) / (½(1+(m-1)/t)² + ½)`; 5.42 FLOP/B for m=5, t=28 (pp. 176–177).

### Fig. 7.15 — `convolution_cached_tiled_2D_const_mem_kernel` (p. 178)
- **Purpose:** tiling with equal input/output tile sizes; halo taps come from global memory (expected L2 hits).
- **Preamble:** `#define TILE_DIM 32`, `__constant__ float F_c[2*FILTER_RADIUS+1][2*FILTER_RADIUS+1];`.
- **Signature:** `__global__ void convolution_cached_tiled_2D_const_mem_kernel(float *N, float *P, int width, int height)`.
- **Launch configuration assumed:** block = `TILE_DIM × TILE_DIM`; blocks per dimension = image dimension / `TILE_DIM`, rounded up (inferred).
- **Walkthrough (line numbers as the text cites them):**
  - Lines 04–05: `col = blockIdx.x*TILE_DIM + threadIdx.x; row = blockIdx.y*TILE_DIM + threadIdx.y;` (no radius offset).
  - Line 06: `N_s[TILE_DIM][TILE_DIM]` in shared memory.
  - Lines 07–11: load own element if `row<height && col<width`, else store `0.0`.
  - Line 12: `__syncthreads();`.
  - Line 13: `if (col < width && row < height)` guards tiles that overhang the image.
  - Lines 15–16: filter loops.
  - Lines 17–20: is the tap inside this tile? Tests `threadIdx.x-FILTER_RADIUS+fCol` and `threadIdx.y-FILTER_RADIUS+fRow` against `[0, TILE_DIM)`.
  - Line 21: if so, `Pvalue += F[fRow][fCol]*N_s[threadIdx.y+fRow][threadIdx.x+fCol];` (as printed).
  - `else` branch, conditions "lines 24–27": is the tap inside the image (`row-FILTER_RADIUS+fRow` in `[0,height)`, `col-FILTER_RADIUS+fCol` in `[0,width)`)? If so read `N[(row-FILTER_RADIUS+fRow)*width+col-FILTER_RADIUS+fCol]` from global memory; otherwise it is a ghost cell and nothing is added.
  - Line 29: `P[row*width+col] = Pvalue;`.
- **Lines that need care:**
  - Printed line 21 indexes `N_s[threadIdx.y+fRow][threadIdx.x+fCol]`, which omits the `-FILTER_RADIUS` that the guarding condition on lines 17–20 uses. As printed it reads the wrong element and can run past the tile. The consistent form would be `N_s[threadIdx.y-FILTER_RADIUS+fRow][threadIdx.x-FILTER_RADIUS+fCol]`. Recorded as suspected erratum.
  - Line numbers in the printed listing are corrupted: some lines are unnumbered and the sequence runs ..., 23, 24, 25, 26, 27, 24, 25, 26, 27, 28, ... . The prose refers to the first "24–27" for the ghost check.
  - Same `__shared__` without type and `F_c` vs `F` mismatch as Fig. 7.12.
  - The comment "turning off the threads at the edges of the block" is carried over although no threads are deactivated for halo reasons here.
- **APIs / qualifiers:** same as Fig. 7.12.
- **AI:** the book gives no formula or number for this kernel.

## Relevance to LLM-inference kernels

- **Arithmetic-intensity bookkeeping is the transferable skill.** The count "FLOP inside the loop / bytes of global memory touched" used on pp. 167, 171, 176 is exactly what to do for a GEMV in single-token decode (each weight loaded once, one multiply-add: very low FLOP/B, memory bound) versus batched GEMM or attention over long contexts (reuse grows with tile size). The specific LLM numbers are ours to derive in the course; the book does the derivation only for convolution here.
- **Tile-size vs reuse formula.** The attenuation factor `1 / (½(1+(m-1)/t)² + ½)` (p. 176) is a concrete example of "bigger tiles amortise loads"; the same reasoning sizes GEMM tiles (the book's own forward pointer for matmul is Chapter 15).
- **Constant memory for small read-only tables.** Candidates in an inference engine: quantisation scales/zero-points or small codebooks, lookup tables for dequantisation, sampling hyper-parameters. The 64 KB limit rules out weights. The chapter's point that the best case is all threads of a warp reading the same element (p. 171) should guide what to put there.
- **Kernel parameters by value** (p. 172) is the practical way to pass per-call scalars and tiny structs (temperature, top-k/top-p, shapes, strides) without global buffers.
- **Register accumulator** (`Pvalue`, p. 166): same idiom as accumulating a dot product, a running max/sum for softmax, or an argmax candidate before one global write.
- **Boundary handling and divergence** (p. 166): analogous to padding and mask handling at sequence edges; the argument "edge threads are a small fraction for large inputs" is a reusable way to decide whether masking branches matter.
- **Halo/ghost machinery itself** has limited direct use in transformer inference. It matters for 1D/2D convolutional front-ends (audio or vision encoders) and any sliding-window operation. The book's direct ML link is the footnote that convolution can be cast as matrix multiplication (Chapter 19).
- **Quantised ops:** the chapter fixes 4 B floats; redoing the AI formulas with 2 B (fp16) or 1 B (int8) elements is a natural course extension (ours, not the book's).

## Portability notes

All HIP/Metal statements below are `[unverified]`; the chapter itself says nothing about HIP or Metal.

- `__constant__` global arrays and `cudaMemcpyToSymbol`: CUDA-specific. A HIP port needs the equivalent constant-symbol mechanism and copy call `[unverified]`. A Metal port needs some read-only buffer/argument mechanism in place of a constant symbol `[unverified]`. Whether either platform has a dedicated constant cache with the behaviour described on p. 171 is `[unverified]`.
- 64 KB constant-memory limit: CUDA-specific number; limits elsewhere `[unverified]`.
- Kernel parameters being placed in constant memory (p. 172): stated for the CUDA compiler only; behaviour on HIP/Metal `[unverified]`.
- `__shared__` arrays and `__syncthreads()`: CUDA spellings for per-block scratchpad memory and the block-wide barrier. Ports need the platform's per-group shared storage and barrier primitive `[unverified]`.
- `blockIdx`, `blockDim`, `threadIdx`, `__global__`: CUDA built-ins/qualifiers; ports need the platform's equivalents for group ID, group size and local ID `[unverified]`.
- Hard limits baked into the listings: 1024 threads per block (`IN_TILE_DIM 32`, `TILE_DIM 32`), 32-thread warps. Corresponding limits on other platforms `[unverified]`.
- §7.6 relies on a hardware L2 cache shared across SMs serving halo reads. Whether a given AMD or Apple GPU caches global reads this way is `[unverified]`; the Fig. 7.15 design should be re-measured rather than assumed.
- The H100-based memory/compute-bound thresholds are device numbers and must be recomputed per target device.
